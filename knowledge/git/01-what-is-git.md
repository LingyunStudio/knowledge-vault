Git 是分布式版本控制系统：给项目拍快照、记录每一次改动，让你随时回到过去、并行开发、与他人协作。学命令之前先把心智模型建对——模型错了，命令背得再多也只是照着敲。

## 快照，不是差异

很多人以为 Git 记录的是"文件改了哪几行"（diff），那是 SVN 时代的模型。Git 相反：**每次提交都是整个项目的完整快照**，没有变化的文件只是引用上一个快照里的同一份数据，并不重复存储。

```text
C0 ──── C1 ──── C2 ──── C3      ← 每个提交指向一棵完整的目录树快照
```

这个设计带来两个直接后果：

- 回到任意历史状态只是"换个指针"，开销几乎为零
- diff 是**用的时候现算的**，不是存出来的

> [!NOTE]
> 想比较 C1 和 C3 的差异，Git 把两棵快照树拿出来现场对比。存储的是状态，差异是派生品——方向别搞反。

顺带纠正另一个常见误解：Git 不是 GitHub。Git 是本地工具，GitHub/GitLab 是托管 Git 仓库、提供协作功能的平台——没有它们，Git 照样能跑。

## 三个工作区

本地仓库内部有三个区域，日常命令本质上都是在它们之间搬数据：

| 区域              | 所在位置           | 职责          |
| --------------- | -------------- | ----------- |
| 工作区             | 你正在编辑的目录       | 直接修改文件的地方   |
| 暂存区（index）      | `.git/index`   | 下次提交的"购物清单" |
| 版本库（repository） | `.git/objects` | 永久快照，提交后不可变 |

数据流向一张图：

```text
          git add           git commit
工作区 ──────────▶ 暂存区 ──────────▶ 版本库
   ▲                ▲
   │                └── git restore --staged（取消暂存，改动保留在工作区）
   └── git restore（丢弃工作区改动，恢复到最近暂存/提交的版本）
```

先跑 `git status` 看清文件在哪个区，再决定用什么命令——这一条能避免八成的新手事故。

> [!TIP]
> 暂存区是 Git 最被低估的设计。它让你把"一口气改了 10 处"拆成 3 次逻辑独立的提交——提交粒度由你决定，而不是由保存文件的时刻决定。

## .git 目录：仓库的本体

```bash
ls .git                    # 初始化后多出来的隐藏目录，仓库的全部本体
# HEAD        → 指向当前所在分支
# config      → 仓库级配置
# objects/    → 所有对象：提交、快照树、文件内容
# refs/       → 分支和标签的指针
# index       → 暂存区
```

`init` 之后项目文件一个字节都没动，Git 的全部数据都住在这个目录里。

> [!WARNING]
> `.git` 目录就是仓库本身：删掉它历史全部消失，拷贝它等于拷贝整个仓库。平时不要手动编辑里面的文件——需要操作一律走 git 命令。

## 分布式与集中式

SVN 这类集中式系统只有一台中央服务器持有完整历史，本地只有当前版本——断网就不能提交，也看不了历史。

Git 里每一次 clone 都是**完整仓库**：全部历史、全部分支都在本地。

```bash
git log                    # 断网也能看完整历史
git commit                 # 提交是纯本地操作，不碰网络
git push                   # 只有"同步"这一步才需要远程
```

| 维度     | 集中式（SVN）      | 分布式（Git）          |
| ------ | ------------- | ----------------- |
| 完整历史在哪 | 只在中央服务器       | 每个克隆都有一份          |
| 提交     | 需要联网，立即对所有人可见 | 本地瞬时完成，只有自己可见     |
| 断网     | 无法提交、无法看历史    | 除 push/pull 外一切照常 |
| 备份     | 依赖中央服务器       | 任意克隆都是完整备份        |
| 协作模型   | 中央权威          | 仓库之间 push/pull 同步 |

核心区别一句话：**提交是本地操作**。你可以高频提交、随意整理，想好了再推给别人——这直接改变了开发节奏。

## 提交是一条哈希链

每个提交对象包含：指向快照树的指针、作者与时间、提交说明，以及**父提交的哈希**。提交串成一条链，改动任何一环，后面所有提交的哈希都会跟着变。

```text
C0 ◀── C1 ◀── C2 ◀── C3      每个提交记住自己的父提交
```

```bash
git cat-file -p HEAD       # 直接查看当前提交对象的原始内容
# tree 4b825dc...          ← 指向本次快照
# parent a1b2c3...         ← 指向上一个提交
# author Zhang San <zs@example.com> 1726000000 +0800
#
#     fix: 修复登录超时
```

> [!NOTE]
> 所有对象（提交、树、文件内容）都用内容算出 SHA-1 哈希、以哈希为名字存储——内容寻址存储。内容变则哈希必变，损坏必被发现。历史一旦提交，就难以被悄悄篡改。

`git log` 里那串 40 位十六进制就是提交对象的名字，实际使用写前几位即可唯一定位。分支、标签也都只是指向提交的指针（后面专篇展开）——整个模型异常简洁。

## 文件在 Git 眼里的状态

```bash
# 一个文件的生命周期：
#   Untracked  → Git 还没在管它（新建文件的默认状态）
#   Unmodified → 与最近一次快照一致
#   Modified   → 改了，还没暂存
#   Staged     → 已暂存，等着进下一次提交
git status                 # 随时查看每个文件处于哪个状态
```

推论：**Untracked 的文件不受 Git 保护**。忘了 add，它不会进提交，也不会被任何回退操作记录——新手"丢代码"最常见的原因就是新文件没进暂存区。
