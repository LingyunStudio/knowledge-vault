网络排障的能力 = **方法论**（按层定位）× **工具熟练**（每层的诊断器）× **模式库**（见过足够多的故障形态）。[第 1 篇](01-layered-model.md)建立了分层框架，本篇把它变成可执行的诊断流程与工具链。

## 1. 分层诊断：每层的问题与工具

```text
「连不上/很慢」的分层定位（自下而上）：

① 链路/物理：接口 up 吗？
   ip link show          # 状态 DOWN? → 网线/WiFi/驱动
② 网络：IP 配置与可达性
   ip addr               # 有地址吗？（DHCP 失败）
   ping 网关             # 局域网内通吗？
   ping 8.8.8.8          # 公网 IP 通吗？（通=网络层 OK，问题在 DNS/应用）
③ 传输：端口可达吗？
   ss -tlnp | grep :443  # 服务在听吗？
   nc -zv host 443       # 端口通吗？（refused=没听 / timeout=被防火墙挡）
④ DNS：域名能解析吗？
   dig +short host       # 与 dig @8.8.8.8 对比（本地缓存问题？）
⑤ 应用：服务有响应吗？
   curl -v https://host  # 状态码/响应体/TLS 报错
```

诊断的产出形式：**「第几层通、第几层断」的结论**——「ping 通但 curl 失败」= 网络层通、问题在 DNS/端口/应用（每层的工具结论构成排除链）。

## 2. 抓包：终极诊断器

```bash
# tcpdump 基础：过滤器语法（BPF）
tcpdump -i eth0 port 443                    # 只看 443
tcpdump -i eth0 host 10.0.0.5               # 只看某主机
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'   # 只看 SYN（握手/扫描）
tcpdump -i eth0 -w capture.pcap             # 存文件给 Wireshark 深度分析

# 关键观察：谁能看到谁？
tcpdump host 10.0.0.5 and not port 22       # 排除自己 SSH 的噪音
```

抓包回答「**线上到底发生了什么**」——日志说「超时」、抓包看到「SYN 发出无响应」（对端/中间丢弃）vs「RST 回来」（对端拒绝）——**两种失败的协议级区分**是任何日志都给不了的。Wireshark 的价值：完整解码（握手流/重传标记/RTT 分析/协议解析）。

## 3. 典型故障模式库

| 模式                    | 症状                                  | 定位                                       | 修复方向                          |
| ----------------------- | ------------------------------------- | ------------------------------------------ | --------------------------------- |
| **连接被拒**             | `Connection refused`（立即失败）        | 端口没监听（服务没起/监听地址不对）          | 起服务/改监听 0.0.0.0              |
| **超时**                | 长时间等待后 `timeout`                 | 防火墙 DROP/路由黑洞/对端过载                | 逐层 ping/nc、查防火墙规则          |
| **DNS 失败**            | `Name or service not known`            | [DNS 管线](06-dns.md)某层断                  | dig 分层查（本地/解析器/权威）       |
| **TLS 错误**            | `certificate verify failed`            | 证书过期/链不全/系统时间错/SNI 不匹配        | openssl 解剖（[第 7 篇](07-tls-security.md)）|
| **间歇性失败**          | 时好时坏                               | 多实例中某实例坏（[负载均衡](02-ip-routing.md)）/漂移/资源竞争 | 逐实例隔离 + mtr/监控分布           |
| **MTU 黑洞**            | 小包通、大包挂（握手通、传数据挂）       | PMTU 发现失效（VPN/隧道）                    | 降 MSS/修 MTU（[第 1 篇](01-layered-model.md)）|
| **慢（而非断）**        | 能通但慢                               | 带宽饱和/丢包重传/RTT 大/服务器慢             | mtr 定位段 + [TCP 参数](03-tcp.md)   |
| **偶发连接重置**        | `Connection reset by peer`             | 对方崩溃/中间设备杀连接/超长连接超时          | keepalive/心跳/中间设备超时对齐     |

「refused vs timeout」的区分是第一课：**refused = 明确拒绝（服务没听——应用层问题）**、**timeout = 石沉大海（包没到或没回——网络/防火墙问题）**——两种「连不上」的修法完全不同。

## 4. 生产排障的三条纪律

```text
① 对照法：好的实例与坏的实例差在哪？
   同一服务的两个实例（一个 200 一个 500）→ 逐项 diff（版本/配置/网络位置/负载）
② 变更回顾：故障时间点前后改了什么？
   部署记录/配置变更/上游升级（[git 的变更追溯](../git/05-history.md)）—— 90% 的故障跟着变更走
③ 最小化：把问题缩到最小可复现
   同一 curl 从不同网络发（区分本机/网络/服务端）→ 单变量逐步加回
```

排障的元纪律：**一次只改一个变量**、**每个假设都要有验证实验**、**修复后复述根因**（「碰巧好了」的故障必然复发）。

## 5. 陷阱清单

- 只在服务器端排障：客户端/中间路径的视角缺失（对称抓包——两端各抓一份对照）。
- 生产环境乱抓包（抓全量）：性能与隐私风险；过滤器先行、限时。
- 「重启解决」不做根因分析：问题必然复发；根因归档（[git 复盘](../git/11-pitfalls.md)）。
- 忽略时间维度（只在故障后看）：监控基线 + 事件时间线的对齐（[部署记录](../linux/11-ops-pitfalls.md)）。
- 排障路径不记录：结论丢失、团队重复踩坑；诊断日志的沉淀。
- 测试环境与生产的网络拓扑差异忽略（NAT/防火墙/MTU 的环境差异）——「测试通生产不通」的排查从拓扑 diff 开始。

## 6. 小结

- 分层诊断是方法论：五层五工具（link/addr+ping/ss+nc/dig/curl）按层定位「第一失败层」——产出「哪层通哪层断」的结论。
- 抓包是终极诊断器：区分「拒绝 vs 超时」的协议级证据；过滤器先行、两端对照。
- 八大故障模式（拒/超时/DNS/TLS/间歇/MTU/慢/重置）各有序列——模式库的积累速度决定排障水平。
- 生产排障三纪律：对照法、变更回顾、最小化——一次一变量、假设必验证、根因必归档。
- 排障的能力模型：**方法论（分层）× 工具（tcpdump/ss/curl）× 模式库（见过多少）**——三者乘积而非相加。

## 7. 练习

**1.** 五层排障演练：在虚拟机环境依次破坏五层（关接口/错路由/未监听/坏 DNS/应用崩溃），每层用「正确工具」定位并修复——把「层-工具-特征」对照表写满。

> [!TIP]
> 思路演练的要点：**先制造故障再排障**——你才知道「正确的答案」，验证自己的诊断流程能否到达。与 [C 篇内存实验](../c/07-dynamic-memory.md)的「故意造 bug」方法论一致。

**2.** refused vs timeout 对照实验：同一目标分别制造「端口未监听」与「防火墙 DROP」两种故障，用 nc/timeout 观察两种失败的时间特征（立即 vs 等待）——把「失败的速度」变成诊断信号。

> [!TIP]
> 思路refused 是 RST（毫秒级）、DROP 是超时（秒级到分钟级）——失败速度是最便宜的第一判据。再抓包看 RST vs 无响应的包级证据。

**3.** 抓包技能实战：抓一次 TLS 握手（[第 7 篇](07-tls-security.md)）与一次 DNS 查询（[第 6 篇](06-dns.md)），分别标注协议的关键字段——tcpdump/Wireshark 的过滤器与解码能力实测。

> [!TIP]
> 思路过滤器速记：`port 443`、`port 53`、`tcp[tcpflags]`、host 组合。Wireshark 的「Follow TCP Stream」把一次会话的往返拼成完整对话——排障的「叙事视图」。

**4.** 间歇性故障攻坚：构造「4 个实例中 1 个坏」的负载均衡后端（某实例返回 500），用「循环请求 + 记录响应指纹」定位坏实例——间歇性故障的统计定位法。

> [!TIP]
> 思路间歇性故障的定位靠「把概率变成确定性」：循环请求记录（实例→结果）的矩阵——坏实例的行永远坏。对照 [ML 间歇性](../ai/11-pitfalls.md)的统计定位思想。

**5.** 两端对照抓包：客户端与服务器同时抓包（时间对齐），对一次「成功」与一次「失败」的请求各做一轮——找出「包在哪一跳消失/被改」——两端视角的排障威力。

> [!TIP]
> 思路两端抓包的对齐方法：时间同步（NTP）+ 请求序号（每个请求带唯一 ID）。中间设备的修改（NAT 改端口/防火墙丢包）在「两端差异」中原形毕露。

**6.** 讨论：为什么「网络排障」被认为是运维中最难的能力之一？从「故障的分布性（多台机器/多个路径共同作用）」「状态的不可见性（中间设备无日志）」「时序的敏感性（竞态与缓存）」三个角度分析，并评估「可观测性投资」（全链路追踪/结构化日志/持续合成监控——[第 9 篇](../ai/09-deployment.md)）在「事前排障」中的杠杆作用。

> [!TIP]
> 思路网络排障的难：**证据分布在多个系统、且会随时间消失**——传统排障靠「抓包 + 猜测」，可观测性投资（trace id 贯穿全链路/合成监控提前发现/变更与告警关联）把「事后考古」变成「事前可见」。排障的最高境界：多数问题在用户报告前已被监控发现。
