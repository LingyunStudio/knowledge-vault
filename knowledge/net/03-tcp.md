TCP 的契约：**可靠、有序、面向连接的字节流**——在「尽力而为、会丢包乱序」的 IP（[第 1 篇](01-layered-model.md)）之上，用四组机制把不可靠网络变成可靠管道。理解 TCP = 理解「不可靠底层之上如何构建可靠抽象」——这是分布式系统的元问题（[分布式一致性](../database/09-nosql.md)的传输层原型）。

## 1. 三次握手与四次挥手

```text
建立（三次握手）：
A → B: SYN (seq=x)          「我想建立连接，初始序号 x」
B → A: SYN+ACK (seq=y, ack=x+1)  「可以，我的初始序号 y，你的 x 收到」
A → B: ACK (ack=y+1)        「你的 y 收到了」
→ 双向的「收发能力与初始序号」都确认完毕

关闭（四次挥手）：
A → B: FIN      A → B: ACK       ← B 可能还有数据要发（半关闭）
B → A: FIN      A → B: ACK
→ A 进入 TIME_WAIT：等待 2×MSL（约 1~4 分钟）后才彻底关闭
```

为什么三次（不是两次）？**双向都要确认「对方的收发能力」**——两次无法让 B 确认「A 能收到我的包」。为什么 TIME_WAIT？**迟到的旧包需要自然死亡**——立刻关闭后同四元组的新连接可能收到旧连接的迟到包（序列号撞车）。

TIME_WAIT 的工程现象：**高并发短连接客户端的 TIME_WAIT 堆积**（数万个等待的 socket 耗尽端口）——对策：连接复用（长连接/连接池，[第 10 篇](../database/10-orm-access.md)）、`SO_REUSEADDR`。**「服务器 TIME_WAIT 多」是客户端短连接频繁的症状**。

## 2. 可靠性：序列号、确认与重传

```text
TCP 的核心机制：每个字节都有序号；接收方 ACK 确认「连续收到的最大位置」
  发送方：数据发出 → 未确认的留在「发送窗口」 → 超时未确认就重传

重传的触发：
① 超时重传（RTO）：等 ACK 超时（RTO 由 RTT 动态估计）
② 快速重传：收到 3 个重复 ACK（不等超时立刻重发丢失段）
③ SACK（选择性确认）：告诉发送方「我收到了哪些不连续的块」——精准重传
```

RTT 与 RTO 的动态估计是 TCP 的自适应核心：**网络延迟变化 → RTO 自动调整**——「过小会误重传、过大恢复慢」的权衡持续运行。快速重传+SACK 让丢包恢复从「等 1 秒」变成「毫秒级」。

## 3. 滑动窗口：流控与吞吐

```text
流量控制（不压垮接收方）：
  接收方通告「我的接收缓冲区还能装多少」（rwnd）
  发送方的未确认数据 ≤ rwnd —— 接收方控制发送速度

窗口机制 = 「未确认但已发送」+「可立即发送」的字节范围
  ACK 滑动窗口右移 → 管道持续流动（不是发一个等一个！）
```

「窗口大小 × 1/RTT = 吞吐上限」——**带宽时延积（BDP）**：高延迟高带宽链路（跨洋）需要大窗口才能跑满带宽——「跨洋传输慢」的第一嫌疑是窗口/缓冲不足（[linux 的缓冲区调优](../linux/07-processes.md)）。

## 4. 拥塞控制：不压垮网络

```text
拥塞窗口（cwnd）：发送方的「自觉」——估计网络的承载能力
慢启动：cwnd 从小开始指数增长（每 RTT 翻倍）
拥塞避免：接近阈值后线性增长（+1/RTT）
丢包响应：丢包 = 拥塞信号 → cwnd 骤降（乘法减少）
```

```text
「慢启动」对短连接的影响：新连接的前几个 RTT 传输很慢（cwnd 从 10 起步）
  → 大文件传输/长连接复用的性能依据（[CDN 与连接复用](05-http.md)）
```

拥塞控制的哲学：**丢包被当作「网络拥塞的信号」**（60 年代的假设）——现代数据中心/无线网络中丢包原因多元（无线误码/缓冲膨胀），BBR 等新算法改用「带宽与 RTT 测量」替代丢包信号——「TCP 拥塞控制的演化史」是「信号与假设」的演化史。

## 5. 应用层视角：与 TCP 共处的参数

```bash
ss -tin              # 看连接的 cwnd/rtt/重传——TCP 内部状态的观察窗口
```

| 机制                | 作用                        | 应用场景                       |
| ------------------- | --------------------------- | ------------------------------ |
| `TCP_NODELAY`       | 禁用 Nagle（小包合并延迟）   | 低延迟交互（游戏/SSH/实时）    |
| `SO_KEEPALIVE`      | 空闲连接保活探测             | 检测死连接（NAT 超时问题）      |
| 发送/接收缓冲区     | 吞吐调优                    | 大传输调大（BDP 匹配）         |
| 应用层心跳          | 应用级的「活着」确认         | 检测「假连接」（中间设备超时）  |

**TCP 的「连接」是逻辑的**：中间设备（NAT/防火墙）有自己的超时表——「连接还在但中间状态已丢」的假连接问题——应用层心跳（业务级 ping）与 TCP keepalive 双保险（[第 13 篇](../cpp/13-concurrency.md)的健康检查思想）。

## 6. 陷阱清单

- TIME_WAIT 堆积误判为故障：它是客户端短连接的正常痕迹；长连接/连接池是解。
- 高延迟链路吞吐慢不查窗口：BDP 不匹配；缓冲区与窗口调优。
- Nagle 与延迟 ACK 的组合延迟（40ms 卡顿）：交互式协议禁 Nagle。
- 以为 TCP 保证「实时」：重传保证可靠但牺牲实时——实时场景用 UDP/RTP（[第 4 篇](04-udp-quic.md)）。
- 大量短连接的握手+慢启动开销：连接复用（HTTP keep-alive/池）。
- 「丢包就是网络烂」：拥塞控制把丢包当信号——丢包率与吞吐的关系要按算法理解。
- 忽略拥塞对多点传输的影响：一机限速/丢包影响同路径的其他连接。

## 7. 小结

- TCP 的契约由四组机制兑现：握手（双向确认+序号同步）、序列号+确认+重传（可靠）、滑动窗口（流控）、拥塞窗口（面拥）——「不可靠网络上的可靠抽象」。
- TIME_WAIT 是「旧包死亡等待」：高并发短连接的堆积是客户端模式问题——连接复用是解。
- BDP 决定吞吐上限：窗口/缓冲要匹配带宽×RTT；跨洋慢先查窗口。
- 拥塞控制 = 「丢包当拥塞信号」的经典假设——BBR 类新算法改写假设；慢启动让短连接先天慢。
- 应用层的 TCP 参数（Nagle/keepalive/缓冲）是延迟与吞吐的精细旋钮——「知道这些参数存在」比记住默认值重要。

## 8. 练习

**1.** 握手观察：tcpdump 抓一次 TCP 连接建立（`tcpdump -i any port 8080`），识别 SYN → SYN+ACK → ACK 三包的 seq/ack 数字关系——「序号同步」的字段级验证。

> [!TIP]
> 思路SYN 的 seq 是随机初始值（ISN）、SYN+ACK 的 ack = ISN+1——「确认号 = 期望的下一个字节」。三次包的数字关系是 TCP 可靠性的地基。

**2.** TIME_WAIT 观察：写一个循环建 1000 个短连接的客户端（每次 curl 本地服务），`ss -tan | grep TIME-WAIT | wc -l` 观察堆积——然后改用连接复用（一个进程循环用连接）对比。

> [!TIP]
> 思路TIME_WAIT 只在「主动关闭方」堆积——服务端大量 TIME_WAIT 说明「服务端在主动关闭」或客户端短连接。堆积本身无害（内存小），端口耗尽才是问题。

**3.** 丢包对吞吐的影响实验：用 tc netem 注入 1% 丢包，对比「单 TCP 流吞吐」的前后——再对比 BBR 与 cubic 拥塞算法的表现——「丢包信号假设」的实测差异。

> [!TIP]
> 思路cubic 在随机丢包下吞吐骤降（把丢包当拥塞）、BBR 稳定——「算法假设匹配网络现实」的案例。`sysctl net.ipv4.tcp_congestion_control` 切换。

**4.** 延迟带宽积实验：对同数据中心（RTT<1ms）与跨区域（RTT 40ms）的机器各测一次单流 TCP 吞吐（iperf3）——验证「RTT 大 → 需要更大窗口才跑满」的 BDP 公式。

> [!TIP]
> 思路BDP = 带宽 × RTT（如 1Gbps×40ms=5MB）——窗口小于 BDP 则跑不满。「跨区复制慢」的调优：窗口/缓冲 + 并行流 + 专用传输协议。

**5.** Nagle 延迟复现：小消息高频发送的客户端，分别开/关 TCP_NODELAY，测量消息间延迟分布——验证「Nagle+延迟 ACK 的 40ms 卡顿」。

> [!TIP]
> 思路Nagle 等「攒满一个 MSS 或收到 ACK」才发——与对端的延迟 ACK（等 40ms 才确认）互锁成 40ms 卡顿。交互协议（SSH/游戏）的标准配置是禁用 Nagle。

**6.** 讨论：QUIC 在 UDP 上「重新发明 TCP」（[第 4 篇](04-udp-quic.md)）为什么是理性选择而不是重复造轮子？从「TCP 在内核（演进必须等 OS 更新）vs QUIC 在用户态（应用随版本走）」「队头阻塞的消除」「握手与加密的合并」三个角度分析——「在旧的灵活底座上重建」与「原地演进」的工程权衡。

> [!TIP]
> 思路TCP 的可靠性被内核冻结（改协议 = 等全球 OS 升级，十年尺度）；UDP 是「留给创新的口子」——QUIC 在用户态自由演进。代价：应用层重新实现可靠性（复杂度上移）。这是「[端到端原则](01-layered-model.md)」的最新胜利——智能放在端点，核心保持简单。
