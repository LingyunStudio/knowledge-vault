HTTP 是 Web 的语言：**请求-响应**模型，客户端发起、服务器回答，无状态、文本语义、简单到任何人都能手写一个。它的演进史就是一部"在 TCP 的约束上榨取性能"的历史。

## 语义基石：方法、状态码、无状态

- **方法**：GET（读）、POST（处理/创建）、PUT（整体替换）、DELETE（删）、PATCH（局部改）——幂等性是核心区分：GET/PUT/DELETE 幂等，POST 不幂等。幂等性决定能不能安全重试（网络超时后，GET/PUT 可重发，POST 要幂等键）
- **状态码**：2xx 成功、3xx 重定向（301 永久/302 临时——对 SEO 与缓存含义不同）、4xx 客户端错（401 未认证/403 无权限/404 不存在/429 限流）、5xx 服务端错。**4 和 5 的分界线是排障时首先看的**
- **无状态**：服务器不记"你是谁"，每请求自带全部凭据（Cookie/Token）——水平扩展因此免费，会话管理因此是应用的责任

## 缓存：性能的最大杠杆

HTTP 缓存是让请求根本不发生的机制，优先级从强到弱：

```text
强缓存：Cache-Control: max-age=3600        → 有效期内不发请求
协商缓存：ETag / Last-Modified              → 发 If-None-Match 问一句
         未变 → 304 Not Modified（无正文，省带宽）
```

工程铁律：**带指纹的静态资源（app.a8f3.js）用长 max-age，入口 HTML 用 no-cache**——发布即生效与极速加载兼得。缓存不可缓存的东西（个性化响应）时，确认没把 Cache-Control 头带错到 CDN。

## 版本演进：一场对队头阻塞的战争

HTTP 跑在 TCP 上（第 03 篇），每一步演进都在跟底层约束搏斗：

| 版本       | 关键变化                                  | 解决什么            |
| -------- | ------------------------------------- | --------------- |
| HTTP/1.0 | 每请求一个 TCP 连接                          | ——              |
| HTTP/1.1 | 长连接 keep-alive、管道化（失败）、分块传输           | 避免反复握手          |
| HTTP/2   | **二进制分帧 + 多路复用**、头部压缩 HPACK、服务器推送     | 同一连接上并发多请求，互不阻塞 |
| HTTP/3   | 跑在 **QUIC** 上（第 04 篇），0-RTT、连接迁移、流级独立 | TCP 队头阻塞、移动网络切换 |

关键剧情：HTTP/1.1 的"队头阻塞"——一个响应没发完，同连接上的其他请求都得等（浏览器靠开 6\~8 条连接绕行，于是有域名分片这种黑历史）。HTTP/2 用二进制帧把多个请求**交错切分**在同一条 TCP 流上，应用层阻塞解决了——**但 TCP 层的阻塞还在**：丢一个包，所有流的字节都停摆等重传。这就是 HTTP/3 存在的理由：把传输层换成 QUIC，流与流独立重传，队头阻塞才真正终结。

> [!NOTE]
> 演进主线一句话：**1.1 优化应用层，2.0 解决应用层阻塞，3.0 终结传输层阻塞**。迁移建议：公网服务上 HTTP/2 是标配（TLS 之后顺带 HTTP/2 协商），HTTP/3 按用户网络画像（移动端占比高则收益大）灰度开启。

## HTTPS 不是独立协议

HTTPS = HTTP over TLS（第 07 篇）：先 TCP/QUIC 握手，再 TLS 握手（证书验证 + 密钥协商），之后 HTTP 明文跑在加密通道里。对应用层唯一的"破坏"是中间设备看不懂内容了——代理、CDN 因此只能看到 SNI（域名）与 IP。**现代 Web 默认全站 HTTPS**：既是安全要求，也是 HTTP/2、HTTP/3 的事实门槛。

## 一张排障速查

```bash
curl -v https://example.com        # 看完整握手与头部
curl -I https://example.com        # 只看响应头（状态码、缓存头）
# 502 → 后端挂了/网关连不上；504 → 后端超时；429 → 被限流
# 304 而不是 200 → 命中协商缓存（更新资源时注意指纹是否变了）
```
