DNS 把人记得住的域名翻译成机器用的 IP，看似简单，实际是互联网上**最成功的分布式系统**：全球部署、无单点、以缓存为生命。理解 DNS 的分层与缓存，就理解了"为什么域名解析有时快如闪电有时诡异失败"。

## 分层的域名树

域名从右往左层级递减：`www.example.com.` → 根（`.`）→ `.com` → `example.com` → `www`。每一层的权威答案由对应的**权威服务器**持有，客户端看到的入口则是**递归解析器**（运营商的或 8.8.8.8 / 1.1.1.1 这类公共 DNS）。

## 一次解析的完整旅程

```text
浏览器缓存 → 系统缓存 → 路由器缓存 → 递归解析器缓存
  ↓ （都未命中）递归解析器替你跑完全程：
根服务器："去问 .com 的权威"      （返回 .com NS 列表）
.com 权威："example.com 的 NS 在这"（返回其 NS）
example.com 权威："www 的 A 记录是 93.184.216.34"  ← 唯一真正回答的地方
```

- 客户端只发一次查询，递归解析器代为迭代
- **缓存逐层生效**，TTL（记录里声明的秒数）决定缓存多久——解析快全靠缓存，改记录生效慢也是因为全世界的缓存还没过期
- UDP 53 端口、一问一答（第 04 篇 UDP 场景）；响应过大或 DNSSEC 时走 TCP 53 兜底；现代协议 DoH/DoT（走 HTTPS/TLS）解决明文监听

## 记录类型速查

| 记录       | 含义               | 典型用途                           |
| -------- | ---------------- | ------------------------------ |
| A / AAAA | 域名 → IPv4 / IPv6 | 最基本                            |
| CNAME    | 域名 → 另一个域名       | 指向 CDN 入口（**不能与 MX 等共存于同一名下**） |
| MX       | 邮件交换             | 收件路由                           |
| TXT      | 任意文本             | 域名所有权验证、SPF 防伪造                |
| NS       | 该区域的权威服务器        | 委托与迁移                          |
| SRV      | 服务发现             | 内网服务定位                         |

## DNS 是负载均衡与容灾的第一道机关

因为解析先于连接，**改 DNS 就能改流量走向**：

- **CDN**：GeoDNS 按解析者的位置返回就近节点 IP——用户在"DNS 这一步"就被调度到边缘（与 HTTP 层的调度互补）
- **故障转移**：主站挂了把 A 记录切到备用 IP；配合低 TTL（如 60s）快速生效
- **灰度/分流**：按权重返回不同 IP

> [!WARNING]
> DNS 切流的两个坑：**缓存 TTL 内旧 IP 依然被访问**（改记录 ≠ 立刻全量生效，长 TTL 的记录可能滞留数小时）；**客户端会缓存**（浏览器/操作系统/递归解析器各自一层）。需要"分钟级切换"的服务，DNS 只能是外层粗粒度开关，精细流量切换靠应用层网关/服务发现。

## 常见故障与诊断

```bash
dig example.com +trace      # 完整迭代链路，看每层权威如何回答
dig @8.8.8.8 example.com    # 指定解析器对比——"别人能解析我不能"的定位法
nslookup -type=MX example.com
```

典型症状对照：**全部域名都失败** → 递归解析器/本地网络问题（换 1.1.1.1 试）；**单个域名失败** → 该域名权威/记录问题（+trace 看）；**时好时坏** → 缓存不一致或某节点故障。

> [!NOTE]
> DNS 的安全面：劫持（明文 UDP 可被篡改 → DoH/DoT + DNSSEC 应对）、DDoS 反射放大（伪造源地址向开放解析器查询大响应 → 服务端限源/响应限速）、子域名信息泄露（zone transfer 应关闭）。它太关键，以至于"打瘫 DNS"是打瘫一个服务的最短路径——所以大厂自建解析监控 + 多家递归服务商做健康探测。
