DNS 解决的问题：**人类记得住名字（example.com），网络需要地址（93.184.216.34）**——一个全球分布式的「名字 → 地址」查询系统。它的设计奇迹在于**层级 + 缓存**：全球每天数万亿次查询，只有极少数真正到达权威服务器——其余全被各级缓存吸收（[缓存的分层](../frontend/10-http-storage.md)思想的 DNS 版）。

## 1. 层级设计：从根到权威

```text
查询 example.com 的层级路径：
① 根服务器（.）：「.com 由谁管？」→ 给出 .com TLD 服务器
② TLD 服务器（.com）：「example.com 由谁管？」→ 给出权威服务器
③ 权威服务器（example.com 的 NS）：「example.com 的 A 记录是什么」→ 给出 IP

域名的层级写在名字里：www.example.com.
  ← www 是 example.com 的子域、example.com 是 .com 的子域、.com 在 . 下
```

「层级 + 委托」让 DNS 可扩展：**每个层级只知道自己下一层的门牌**（根不用知道 4 亿域名的每个细节）；更新也是局部的（改 example.com 的记录不需要通知根）。**谁控制了权威服务器，谁就控制了域名的解析**——域名的所有权本质上是「权威 NS 记录的控制权」。

## 2. 解析流程：递归与缓存

```text
完整递归解析（通常由 ISP/公共 DNS 的解析器代劳）：
客户端 → 本地解析器（缓存命中则直接回）
  未命中 → 问根 → 问 .com → 问权威 → 拿到答案 → 缓存（按 TTL）→ 回客户端

客户端的两级缓存：
  系统/浏览器缓存 → 本地解析器缓存 → （未命中才走递归）
```

缓存的保鲜机制是 **TTL（生存时间）**：每条记录带 TTL，缓存到点就过期——**改 DNS 记录的生效时间 = 各级缓存的 TTL 剩余**（TTL=3600 的记录，改后最多 1 小时才全网生效）。DNS 变更的运维纪律：**降低 TTL → 等旧 TTL 过期 → 改记录 → 稳定后再恢复 TTL**（迁移流量的标准舞步）。

## 3. 记录类型族

| 类型   | 含义                      | 例                                     |
| ------ | ------------------------- | -------------------------------------- |
| `A`    | 域名 → IPv4               | example.com → 93.184.216.34            |
| `AAAA` | 域名 → IPv6               | [IPv6](02-ip-routing.md)               |
| `CNAME`| 域名 → 另一个域名（别名）  | www.example.com → example.com          |
| `MX`   | 邮件交换（收这个域的信到哪）| example.com MX 10 mail.example.com     |
| `NS`   | 权威服务器                 | example.com NS ns1.provider.com        |
| `TXT`  | 任意文本                  | SPF/域名验证（「证明你拥有此域」）      |
| `SOA`  | 区域的起始授权信息         | 序列号/刷新时间                         |

CNAME 的规则与坑：**CNAME 不能与其他记录共存**（域名要么是别名要么有真实记录）——「裸域（example.com）不能 CNAME」的传统问题（现代服务商有 CNAME 扁平化）；**解析链要多查一次**（CDN 场景的延迟）。TXT 的现代角色：域名所有权验证（给各云平台证明「这个域是你的」）与邮件反垃圾（SPF/DKIM）。

## 4. dig 实战：解析的诊断器

```bash
dig example.com                    # 完整解析（问系统配置的解析器）
dig +short example.com             # 只要答案
dig @1.1.1.1 example.com           # 直接问指定服务器（绕过本地缓存——排障利器）
dig +trace example.com             # 模拟完整递归路径（根→TLD→权威）
dig example.com MX                 # 查指定类型

;; ANSWER SECTION:
example.com.   3600  IN  A  93.184.216.34
               ↑TTL        ↑类型
```

dig 输出的三段：QUESTION（问了什么）、ANSWER（答案 + TTL）、权威/附加段。**「TTL 字段在答案里」**——每次查询的 TTL 是「该缓存的剩余寿命」。DNS 故障的分层诊断：

```text
「域名解析失败」的诊断：
① dig @1.1.1.1 domain → 权威层有答案吗？（有 → 是本地缓存/解析器问题）
② dig +trace → 层级委托断了？（NS 配置错误/区域传送失败）
③ 配置对了但不生效 → TTL 未过期（等）或缓存投毒（换解析器验证）
```

## 5. DNS 的进阶形态

| 形态            | 作用                                        |
| --------------- | ------------------------------------------- |
| 负载均衡        | 同名多条 A 记录轮询 / GeoDNS 按地理位置回源   |
| CDN 的入口      | 域名 CNAME 到 CDN —— 解析时返回最近的边缘节点 |
| 故障切换        | 健康检查失败后 DNS 自动切换到备用 IP          |
| DoT/DoH         | DNS 查询加密（防窃听/篡改——隐私与安全）       |

「DNS 即流量调度器」的定位：**全球流量的第一层分发**（GeoDNS 按用户位置返回最近节点）——但 DNS 缓存让「切换」不即时（TTL）——紧急切换的 TTL 设计要提前规划（平时大 TTL 省查询、切换前降 TTL）。

## 6. 陷阱清单

- TTL 与生效时间的误解：改记录后旧缓存仍服务到 TTL 过期；迁移流程先降 TTL。
- CNAME 链过长/裸域 CNAME 问题：解析延迟与平台限制；CDN 的 CNAME 扁平化。
- 靠「ping 域名」验证 DNS：ping 可能被禁；用 dig +short 直查。
- 权威服务器的单点（只有一个 NS）：NS 至少两个、不同网络。
- 忽略负缓存（不存在的域名也被缓存）：刚创建的域名「立即解析不到」（负 TTL）。
- DNS 未加密的隐私/劫持面：DoH/DoT 与 DNSSEC 的部署评估。
- 配置了 DNS 却没检查解析链（@2 个 NS 都指向同一失效服务器）。

## 7. 小结

- DNS 的架构奇迹：层级委托（每层只知下一层）+ 全网缓存（TTL 控制）——数万亿查询被缓存吸收。
- 记录族按用途记：A/AAAA（地址）、CNAME（别名）、MX（邮件）、NS（权威）、TXT（验证与策略）。
- TTL 是「变更生效时间」的控制器：迁移的降 TTL 舞步；dig 是解析的诊断器（@绕缓存/+trace 看路径）。
- DNS 即流量调度：GeoDNS/CDN 入口/故障切换——「名字层」是流量的第一分发点。
- 缓存的代价是「变更延迟」与「错误缓存」——TTL 设计与验证流程（换解析器验证）是 DNS 运维的核心。

## 8. 练习

**1.** dig 全景练习：对同一域名分别 `dig +short`、`dig`（完整）、`dig +trace`、`dig @8.8.8.8`——对比四种输出，画出「这次查询实际走了哪些服务器」。

> [!TIP]
> 思路+trace 展示完整委托链（根→TLD→权威的每一跳 ANSWER）；@8.8.8.8 绕过本地缓存。四次对比 = DNS 架构的实验课。

**2.** TTL 生效实验：自建一个测试域名（或本地 dnsmasq），TTL=60 的记录改 IP 后，分别用「命中缓存的解析器」与「直问权威」观察新旧值的过渡窗口——「缓存的不同步」的现场。

> [!TIP]
> 思路不同解析器的缓存独立——「有些用户看到新值、有些看到旧值」的分裂窗口。切换场景的「双值并行期」设计（新旧都工作）来自这个现实。

**3.** CNAME 链观察：dig 一个使用 CDN 的域名，追踪 CNAME 链（可能 3~4 跳到边缘节点 IP）——理解「CDN 的 DNS 调度」如何决定你访问哪个边缘。

> [!TIP]
> 思路CNAME 链的每一跳都是「调度的机会」：GeoDNS 看你的解析器位置 → 返回最近的边缘 IP。「第一次解析」决定整个会话的服务节点。

**4.** 故障诊断演练：构造三种 DNS 故障（域名不存在/权威 NS 失效/本地解析器故障），用 dig 家族工具按第 4 节的诊断树定位——每种故障的「指纹」记录成表。

> [!TIP]
> 思路指纹：NXDOMAIN（域名不存在）、SERVFAIL/超时（权威挂）、本地全失败但 @8.8.8.8 正常（本地解析器）——三种指纹对应三种修法。

**5.** 邮件路由验证：用 dig 查一个域的 MX 记录与 TXT（SPF），解释「一封发往该域的邮件」的路由与反垃圾校验链路——MX/SPF/DKIM 的协同。

> [!TIP]
> 思路MX 决定「送到哪台服务器」、SPF 声明「哪些服务器有权代发」、DKIM 给信签名——邮件域名的三件套。TXT 记录的「策略承载」角色。

**6.** 讨论：DNS 的「缓存层级」设计（浏览器→系统→解析器→权威）与 [HTTP 缓存](../frontend/10-http-storage.md)、[CDN](../docker/08-registry.md) 的缓存层级相比，「缓存的一致性代价」如何被 TTL 的分层设计管理？从「全局一致性不可能、只能控制不一致窗口」的角度，总结分布式缓存系统的 TTL 设计原则——「不一致窗口的显式化」。

> [!TIP]
> 思路DNS 的智慧：不追求一致（不可能），而是「让不一致的窗口可控且显式」（TTL 写在每条记录上）。TTL 设计原则：变更频率决定 TTL、紧急切换需要提前降 TTL、负缓存也有 TTL——「每条数据的时效契约」显式化是分布式缓存的设计核心。
