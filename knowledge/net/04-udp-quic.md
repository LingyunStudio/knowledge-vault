如果说 TCP 是"把一切保证做齐"，UDP 就是"**把一切保证都省掉**"：8 字节头部、无连接、不保证送达、不保证顺序。听起来像残缺，实际是无为而治——**把选择权交给应用**。

## UDP：8 个字节的全权委托

UDP 头只有：源端口、目的端口、长度、校验和。得到的服务是"IP 之上加个端口"——**多路复用**是它唯一的服务。换来的是：

- **零握手**：首包即数据，延迟最低（DNS、游戏、音视频的刚需）
- **无队头阻塞**：丢一个包不影响后续包的处理（TCP 字节流必须按序，一丢全停）
- **应用可控**：要重传自己挑着传，要 FEC 冗余自己加

经典使用姿势各有心思：

| 场景 | 用 UDP 的理由 |
| --- | --- |
| DNS 查询 | 一问一答，TCP 握手成本是查询本身的数倍；超时重发即可 |
| 音视频通话 | 旧数据重传已无意义，宁可丢帧不可延迟 |
| 游戏/实时控制 | 状态持续覆盖，最新状态比完整历史重要 |
| 自研可靠传输 | 应用层在 UDP 上定制序号/重传/拥塞（KCP、WebRTC 的 SCTP） |

> [!WARNING]
> UDP 无拥塞控制——**野蛮应用会挤压 TCP 流量，把网络推向拥塞崩溃**。公网大规模传输必须自带拥塞控制（QUIC 做了，WebRTC 做了），"UDP 快所以随便发"是初学者最危险的想法。

## QUIC：在 UDP 上重建传输层

TCP 的机制沉淀于内核，四十多年积重难返：握手固定 RTT、协议僵化（中间设备盯着 TCP 头做手脚，改协议寸步难行）。**QUIC 的路线：把传输层搬进用户态、跑在 UDP 上**——HTTP/3 的底座，也是现代移动网络的事实标准方向。

它在 TCP 的痛点上各个击破：

1. **0-RTT/1-RTT 建连**：把传输握手与 TLS 握手（第 07 篇）合并，复用连接时 0-RTT 发数据——移动端首屏延迟直接砍一个 RTT
2. **流级队头阻塞消除**：多条流独立重传，一条流丢包不再卡死其他流（TCP 只有一条字节流，丢一个全停）
3. **连接迁移**：连接由 **Connection ID** 标识而非四元组——Wi-Fi 切 5G 不掉线（TCP 换 IP 即断）
4. **内建 TLS 1.3**：加密不可协商，协议僵化也失去土壤（中间设备看不到明文头）

## TCP 还是 UDP：按"谁为可靠性付费"选

```text
要完整、有序、且不想自己写代码          → TCP（绝大多数应用）
能容忍丢失、追求最低延迟               → UDP 裸用（音视频、心跳）
要 TCP 的可靠 + UDP 的灵活/低延迟      → QUIC（HTTP/3、新式传输）
两个服务端节点内网互传海量数据          → 也考虑 QUIC/自研（绕内核栈开销）
```

> [!TIP]
> 判断题的正确问法不是"TCP 好还是 UDP 好"，而是：**丢一个包的代价是什么？** 代价无穷大（转账指令）→ TCP；代价为零（下一帧视频马上覆盖）→ UDP；代价按流区分（网页多资源）→ QUIC。代价结构决定协议选择。
