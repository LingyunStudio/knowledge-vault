UDP 的契约只有一句话：**把数据包尽力送到目的地，不保证到达、不保证顺序、不建连接**。它与 TCP 是[传输层](01-layered-model.md)的两个极端——TCP 用复杂机制换可靠，UDP 用极简换速度与灵活。**「可靠性不够的部分由应用自己补」**是 UDP 的哲学。

## 1. UDP 的形态：一个薄薄的信封

```text
UDP 头：源端口 + 目的端口 + 长度 + 校验和 —— 仅 8 字节（TCP 头 20+ 字节）
无连接：不用握手，拿到地址就发
无状态：不追踪序号/确认/窗口 —— 中间设备也无需维护连接

给了应用什么：一个「原样送达或丢失」的数据报服务
留下给应用什么：重传、排序、拥塞控制、分包——全看应用要不要自己实现
```

UDP 的速度优势来源：**没有握手**（一个包就开始）、**没有重传等待**（丢了就丢，不阻塞后续）、**没有拥塞退让**（应用自己决定节奏）、**支持一对多**（广播/组播——TCP 做不到）。

## 2. 四类典型场景

| 场景           | 为什么 UDP                          | 应用                      |
| -------------- | ----------------------------------- | ------------------------- |
| 简单查询       | 一问一答，丢了就重问（应用层重试）    | DNS（[第 6 篇](06-dns.md)）、DHCP |
| 实时音视频     | 丢一帧无所谓，**等重传更糟**（实时性>完整性）| RTP/WebRTC 通话      |
| 游戏           | 状态要最新，旧状态重传无意义          | 游戏状态同步               |
| 海量无连接服务 | 无连接状态的轻量（每连接成本≈0）      | 大规模服务的前端（现代多为 QUIC）|

「实时性 > 完整性」的取舍逻辑：**视频会议里重传 3 秒前的帧毫无意义**（对话已经过去）——宁可丢帧也要继续播。TCP 的重传与队头阻塞（一个包丢失阻塞后续交付）在实时场景是致命缺陷——**这就是 UDP 存在的核心理由**。

## 3. QUIC：在 UDP 上重建传输层

```text
QUIC（HTTP/3 的传输层）= 在 UDP 上实现的「现代化 TCP + TLS」：
  ① TLS 1.3 内建：握手与加密合并（1-RTT 甚至 0-RTT 建连）
  ② 多路流：一个连接多条独立流 —— 一条流丢包不阻塞其他流（消除队头阻塞！）
  ③ 连接迁移：用连接 ID 而非四元组标识 —— WiFi 切 4G 不断连
  ④ 可演进的传输协议：在用户态实现（随应用更新，不等内核）
```

QUIC 的每个特性都对着 TCP 的一个痛点：TCP+TLS 的多次往返握手 → QUIC 合并；TCP 的队头阻塞（一条流丢包阻塞所有流）→ QUIC 流独立；TCP 连接绑定四元组（换网络断连）→ QUIC 连接 ID 迁移；TCP 在内核（[演进等十年](03-tcp.md)）→ QUIC 在用户态（随浏览器/应用走）。

「为什么可行」：UDP 是**留给创新的口子**——[端到端原则](01-layered-model.md)让核心简单，智能在端点实现（这次端点实现了完整的传输协议+加密）。

## 4. TCP vs UDP vs QUIC：选型表

| 需求                        | 选择      | 理由                                   |
| --------------------------- | --------- | -------------------------------------- |
| 文件传输/网页/数据库          | TCP       | 完整性优先、连接复用成熟                |
| 请求-响应式查询（小且可重试）| UDP/QUIC  | 快、无连接状态                          |
| 实时音视频                   | UDP/RTP   | 实时性优先、容忍丢失                    |
| 游戏/实时交互                | UDP       | 最新状态、低延迟                        |
| Web（现代）                  | QUIC      | 低握手、无队头阻塞、连接迁移            |
| 简单可靠的内部通信           | TCP       | 成熟稳定、调试工具齐全                  |

选型的判据一句话：**「丢一个包的代价」与「等一个包的代价」哪个高**——等更贵（实时）→ UDP 系；丢更贵（文件/事务）→ TCP。

## 5. 陷阱清单

- 以为 UDP「更快」所以默认选它：无拥塞控制的 UDP 洪发会自己造成丢包与被运营商限流；大流量 UDP 要自己实现拥塞避免。
- UDP 大包不管分片：超过 MTU 的 UDP 包被 IP 分片——一片丢全包丢（比 TCP 更脆）；应用层分包（[PMTU](02-ip-routing.md)）。
- DNS 只知道 UDP 53：大响应/区域传输走 TCP 53；DoT/DoH 加密 DNS 的新形态。
- 实时应用的「重传执念」：丢了就丢、跳帧继续——实时性优先。
- QUIC 部署忽视 UDP 被 middlebox 干扰（企业防火墙限速 UDP）：回退 TCP 的降级路径。
- 无状态 UDP 服务的放大攻击面（DNS 反射放大）：响应远大于请求被滥用为攻击载体——限速与源验证。

## 6. 小结

- UDP = 极简信封：无连接无保证，换来低延迟、低开销、广播能力与应用层的自由。
- 四类场景的判据「丢包代价 vs 等待代价」：实时音视频/游戏选 UDP、查询选 UDP+重试、完整性场景选 TCP。
- QUIC 在 UDP 上重建现代传输层：握手合并、多流无队头阻塞、连接迁移、用户态可演进——HTTP/3 的底座与「UDP 留口子」哲学的胜利。
- 交付的完整性由应用定义：UDP 的「不可靠」是「把可靠性决策权交给最了解需求的应用」。

## 7. 练习

**1.** DNS 的 UDP/TCP 双形态观察：普通查询抓包（UDP 53），故意构造大响应（AXFR/长 TXT）观察 TCP 回退——验证「UDP 优先、必要时 TCP」的 DNS 行为。

> [!TIP]
> 思路DNS 响应超过 UDP 载荷限制时置 TC（truncated）标志、客户端转 TCP——「协议的优雅降级」设计。DoH（HTTPS 上的 DNS）是现代的加密形态。

**2.** 丢包对比实验：用 tc netem 注入 2% 丢包，对比 TCP 文件传输与 UDP 视频流的体验——TCP 吞吐下降但内容完整、UDP 内容跳帧但流畅——「两类需求两种传输」的体感实验。

> [!TIP]
> 思路同一网络条件下两种传输的表现分化——「丢包的代价」取决于应用（[第 2 节判据]的实证）。WebRTC 的内部（NACK/FEC/jitter buffer）是 UDP 上自建可靠性的样板。

**3.** QUIC 体验对比：用支持 HTTP/3 的浏览器访问启用了 QUIC 的站点（响应头 alt-svc/h3），Network 面板看协议列（h3 vs h2）——再断开 WiFi 切换网络观察「连接迁移」是否保持会话。

> [!TIP]
> 思路连接迁移的体验：IP 变了会话不断（连接 ID 标识）——TCP 时代切 WiFi 必断连。HTTP/3 的部署现状（CDN 已广泛支持）与回退逻辑（h3 失败回 h2）。

**4.** 队头阻塞对比：HTTP/2（TCP 上的多路流）在「一条流丢包」时所有流阻塞（TCP 层队头阻塞）；HTTP/3（QUIC 流独立）不受影响——用弱网模拟工具对比两协议的页面加载表现。

> [!TIP]
> 思路H2 的多路复用解决了 HTTP 层队头阻塞、但 TCP 层的仍在（[第 3 篇](03-tcp.md)的字节流语义）——QUIC 的流独立才彻底解决。「分层修复」的层级定位练习。

**5.** UDP 应用层可靠性练习：用 UDP 实现「可靠消息传输」的最小版（序号 + ACK + 超时重传），丢包注入下测试——体会「在 UDP 上重建 TCP 有多难」（为什么 QUIC 值得尊敬）。

> [!TIP]
> 思路实现中发现的问题清单：拥塞控制怎么办、乱序重排窗口多大、ACK 风暴如何避免——每一个都是 TCP 花四十年打磨的细节。「轮子的深度」在造的过程中显现。

**6.** 讨论：为什么「传输层协议的创新」发生在用户态（QUIC）而内核 TCP 的改进（BBR 算了例外）难以普及？从「部署路径（浏览器/应用自带 vs 全网 OS 升级）」「中间盒的僵化（对 TCP 的深度干预阻碍新选项）」「创新周期与 OS 发布周期的错配」三个角度分析——「可演进的边界」如何决定一个协议栈的长期竞争力？

> [!TIP]
> 思路部署路径决定进化速度：QUIC 随浏览器更新（周级）vs TCP 改进随内核（年级）——「用户态创新」的敏捷碾压。教训延伸到架构设计：**把「需要快速演化的部分」放在你能快速部署的层**（[端到端原则](01-layered-model.md)的工程版）。
