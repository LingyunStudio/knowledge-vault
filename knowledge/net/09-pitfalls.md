网络的陷阱集中在**边界的隐式行为**：NAT 改写地址、防火墙静默丢弃、DNS 缓存延迟、MTU 截断、中间设备超时——**看不见的层在替你做决定**。本篇先画概念地图，再给四类审查清单与故障速查。

## 1. 概念地图：网络知识的关系网

```text
分层模型（[第 1 篇]）              排障与演化的框架
  ↓ 网络层的寻址与路由
IP/CIDR/NAT（[第 2 篇]）           全球地址与路径
  ↓ 传输层的两种契约
TCP（[第 3 篇]）                   可靠：握手/重传/窗口/拥塞
UDP/QUIC（[第 4 篇]）              轻快：自管可靠性
  ↓ 应用层的主力协议
HTTP（[第 5 篇]）                  语义：方法/状态码/缓存
DNS（[第 6 篇]）                   名字系统：层级/缓存/调度
  ↓ 安全层
TLS（[第 7 篇]）                   加密/认证/完整性
  ↓ 横切的实践
排障方法论（[第 8 篇]）            分层诊断/抓包/模式库
```

关键连接点：**NAT ↔ 端到端的破坏 ↔ docker 端口映射**（[第 2 篇](02-ip-routing.md)、[docker](../docker/06-networks.md)）；**队头阻塞 ↔ TCP 字节流 ↔ HTTP/3**（[第 3 篇](03-tcp.md)→[第 4 篇](04-udp-quic.md)）；**TTL ↔ 缓存生效 ↔ 变更纪律**（[第 6 篇](06-dns.md)、[第 10 篇](../frontend/10-http-storage.md)）；**丢包信号 ↔ 拥塞控制 ↔ 排障**（[第 3 篇](03-tcp.md)、[第 8 篇](08-troubleshooting.md)）。

## 2. 四类审查清单

### 2.1 设计

- [ ] 服务间通信的协议选型有据（TCP/UDP/QUIC 按需求，[第 4 篇](04-udp-quic.md)）
- [ ] API 的幂等性设计（[重试的前提](05-http.md)）
- [ ] 超时与重试策略全链路统一（[第 7 篇](../frontend/07-async.md)）
- [ ] 降级路径存在（依赖不可用时的形态）
- [ ] DNS/TTL 策略规划（变更与故障切换，[第 6 篇](06-dns.md)）

### 2.2 部署

- [ ] 端口暴露最小化（只开放必要端口；内部服务绑内网）
- [ ] 防火墙三层核对（本机/主机防火墙/云安全组——[docker 的绕过](../docker/06-networks.md)）
- [ ] TLS 配置体检（[第 7 篇](07-tls-security.md)：链完整/协议版本/HSTS）
- [ ] 超时与 keepalive 的中间设备对齐（NAT/LB 的空闲超时）
- [ ] 健康检查与就绪探针存在（[compose](../docker/07-compose.md)/[K8s 的基础]）

### 2.3 运维

- [ ] 网络监控覆盖（延迟/丢包/重传/连接数——[第 8 篇](08-troubleshooting.md)）
- [ ] DNS 变更流程（TTL 舞步 + 双解析器验证）
- [ ] 证书续期自动化 + 到期告警
- [ ] 容量与带宽的基线与告警（[BDP](03-tcp.md)/水位）
- [ ] 变更与告警的时间线关联能力

### 2.4 安全

- [ ] 全站 HTTPS + HSTS（[第 7 篇](07-tls-security.md)）
- [ ] 内部流量的加密与身份（不只信任网络位置）
- [ ] 出站流量的白名单与审计（防数据外泄）
- [ ] 限流与防放大（[UDP 反射](04-udp-quic.md)、API 限流）
- [ ] 依赖的传输安全（第三方 API 的证书钉住/校验）

## 3. 高频故障速查表

| 故障形态                              | 第一判据                        | 高概率根因与去处                     |
| ------------------------------------- | ------------------------------- | ------------------------------------ |
| 连接被拒（refused）                    | 立即失败（RST）                 | 服务未启动/监听地址错（[第 8 篇](08-troubleshooting.md)）|
| 连接超时（timeout）                    | 长等待                          | 防火墙 DROP/路由黑洞/对端过载          |
| 能 ping 通但端口不通                   | 网络层通、传输层断              | 服务未监听/本机防火墙（[第 1 篇](01-layered-model.md)）|
| 端口通但业务失败                       | 传输层通、应用层断              | 应用错误/配置错/依赖断                 |
| DNS 解析失败                           | dig 分层查                      | 本地缓存/解析器/权威（[第 6 篇](06-dns.md)）|
| 时好时坏                               | 同一请求不同结果                | 多实例部分坏/负载不均/间歇丢包         |
| 大包丢小包通                           | ping -s 边界                    | MTU/PMTU 黑洞（[第 1 篇](01-layered-model.md)）|
| 偶发重置                               | reset by peer                   | 中间设备超时/对端崩溃/Keepalive 缺失    |
| 上线后部分用户异常                     | 地域/运营商/客户端分布          | DNS 生效分裂/CDN 节点/运营商问题       |
| 证书告警                               | 浏览器/curl 报错                | 过期/链不全/时间错（[第 7 篇](07-tls-security.md)）|

## 4. 成长路径自测

```text
□ 能对任意「连不上」问题执行五层诊断并给出「断在哪层」的结论
□ 能读懂 tcpdump/Wireshark 的握手、重传、RST 抓包
□ 能手算 CIDR 并读懂路由表的决策
□ 能解释一个 TCP 连接从建立到关闭的全部包序
□ 能描述一次 HTTPS 请求的完整生命周期（DNS→TCP→TLS→HTTP）
□ 能设计「故障时的降级路径」而不是只设计「正常路径」
□ 排障时自然地「先固化现场、再单变量、后归档根因」
```

## 5. 小结

- 网络的陷阱核心是「边界的隐式行为」：NAT/防火墙/缓存/MTU/中间超时——看不见的层在替你做决定，审查清单让它们显式。
- 概念地图的主线：分层框架 → 寻址路由 → 两种传输契约 → 应用协议 → 安全 → 排障方法论——每层「职责 + 工具 + 失效形态」。
- 四类清单（设计/部署/运维/安全）中，**部署类（端口/防火墙三层/超时对齐）是事故最密集区**——多层的语义不统一是根源。
- 故障速查表的判据第一：失败的速度（refused vs timeout）、分布（间歇性）、边界（大小包）——症状本身就是证据。
- 成长的终点不是「记住所有协议」，而是**「排障的肌肉记忆」与「设计的预防意识」**——网络知识最终都以这两型能力落地。

## 6. 练习

**1.** 概念地图复述：画出「分层→IP→TCP/UDP→HTTP/DNS/TLS→排障」的关系图，每个节点标注「职责 + 一个工具 + 一个典型故障」——断点回篇目。

> [!TIP]
> 思路「工具与故障」是网络知识的落地形式——纯理论节点（如分层的哲学）也至少配一个「观察它的窗口」（如抓包）。

**2.** 综合排障大考：在一个多层环境（应用+DB+缓存+DNS+防火墙）中，由他人（或随机脚本）注入一个故障，限时 30 分钟用完整方法论定位修复——写复盘（用了哪些工具、绕了哪些弯路）。

> [!TIP]
> 思路限时的意义：真实事故里「分钟级定位」与「小时级定位」的业务代价差异巨大——排障速度是训练出来的（[第 8 篇](08-troubleshooting.md)的肌肉记忆）。

**3.** 检查单落地：从四类清单中提炼你团队的「服务上线网络检查单」10 条（每条附验证命令），对一次真实部署走查——记录「发现的遗漏」。

> [!TIP]
> 思路网络检查单的高价值条目：端口暴露面核对、防火墙三层、超时链路一致性、健康检查存在、DNS TTL 策略——上线前的 30 分钟省掉上线后的一夜。

**4.** 全链路追踪实验：对一个跨三服务的请求做「trace id 贯穿」的实验（每层日志带同一 ID），人为制造一处延迟——体验「分布式排障」与传统网络排障的结合（[MLOps 监控](../ai/09-deployment.md)的思想同源）。

> [!TIP]
> 思路trace id 是「跨系统排障」的钥匙——单层工具（ping/tcpdump）回答「到没到」，trace 回答「在哪层慢了为什么」。可观测性是网络排障的现代延伸。

**5.** 协议设计思考题：如果让你为「物联网设备的心跳上报」设计传输方案（设备资源受限、网络不稳、服务端要实时感知掉线）——用本系列的权衡框架（TCP/UDP/QUIC、可靠性/实时性、状态/无状态）给出方案与理由。

> [!TIP]
> 思路方案的权衡点：设备的内存（能否跑 TLS）、网络的不稳（重连成本）、实时性要求（掉线检测延迟）、包大小（MQTT 的 2 字节头 vs HTTP 的几百字节）。每个约束都指向不同的取舍——设计题的答案是「权衡的论证」而非「标准答案」。

**6.** 讨论：网络知识的特点是「不可见、分布式、持续演化」——与 [C 的内存](../c/14-pitfalls.md)、[数据库](../database/11-ops-pitfalls.md)的「不可见陷阱」相比，网络排障的独特挑战是什么？从「证据的瞬时性（包飞过去了）」「多方责任（运营商/CDN/云/应用）」「环境的持续漂移（路由/策略在变）」三个角度分析「可观测性基础设施」为什么是现代网络工程的胜负手。

> [!TIP]
> 思路三系统的共同点：证据不可见 → 靠「预埋的可观测性」而非「事后推理」；差异点：网络的证据最瞬时（包飞过即消失，只能靠抓包或埋点）且责任域最多方。结论：网络工程的投资重心从「会修」前移到「可见」——监控/追踪/合成探测的覆盖度决定排障速度的上限。
