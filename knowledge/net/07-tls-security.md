TLS（HTTPS 的 T）解决明文通信的三种攻击：**窃听**（内容被看）、**篡改**（内容被改）、**冒充**（对方是假的）。它的三重防御：**加密**（看不懂）、**完整性**（改不了）、**认证**（冒不了）——用一次握手建立这三重保证，之后全程对称加密通信。

## 1. 密码学基础：四件工具

| 工具           | 特性                                | 在 TLS 中的角色               |
| -------------- | ----------------------------------- | ----------------------------- |
| 对称加密       | 同一把钥匙加密解密；**快**            | 会话数据加密（AES/ChaCha20）   |
| 非对称加密     | 公钥加密私钥解；**慢**               | 密钥交换/签名（RSA/ECDSA）     |
| 哈希           | 不可逆、内容变则摘要剧变             | 完整性校验、证书指纹           |
| 数字签名       | 私钥签、公钥验（不可伪造、不可否认）  | 证书验证、握手参数签名         |

「混合加密」的设计：**非对称做身份与密钥交换（慢但解决钥匙分发）、对称做数据加密（快）**——每个连接生成临时对称密钥（前向保密：私钥泄露也解不开历史流量）。

## 2. TLS 握手：三重防御的建立过程

```text
TLS 1.3 握手（1-RTT）：
① ClientHello：客户端支持的密码套件 + 随机数 + SNI（域名）
② ServerHello + 证书 + 密钥交换参数 + 签名
   客户端验证：证书链 → CA 可信？域名匹配？未过期？
   服务器签名 → 用证书公钥验证（证明「我就是证书的主人」）
③ 双方从交换参数导出对称会话密钥 → 加密信道建立

认证的三重检查：证书链可信 + 域名匹配 + 签名有效
—— 三者齐 = 「对面确实是 example.com 的服务器」
```

**证书验证的细节是安全的全部**：证书链（你的证书 → 中间 CA → 根 CA）逐级验证、根 CA 必须在系统信任库、域名匹配（CN/SAN）、有效期、吊销状态（CRL/OCSP）——任何一环松掉就是 MITM 的入口。SNI（握手时明文发送的域名）是「同一 IP 多证书」的机制——也是 [ESNI/ECH 加密的对象]（隐私）。

## 3. 证书体系：信任链与自动化

```text
信任链：根 CA（操作系统/浏览器内置，离线保管）
        → 中间 CA（日常签发）
        → 端点证书（你的域名）

Let's Encrypt 的自动化（ACME 协议）：
  certbot renew                    # 申请/续期：验证域名所有权（TXT/HTTP challenge）→ 签发
  90 天有效期 + 自动续期           ★ 短有效期是「降低泄露危害」的设计
```

证书运维的纪律：**自动续期**（过期是最尴尬的故障——全站拒绝访问）、**到期监控**（外部探测证书有效期，[第 11 篇](../linux/11-ops-pitfalls.md)）、**私钥保护**（泄露即冒充——紧急吊销流程）。

## 4. HTTPS 部署的工程要点

```nginx
server {
    listen 443 ssl http2;
    ssl_certificate     /etc/letsencrypt/live/x/fullchain.pem;   # fullchain：含中间证书！
    ssl_certificate_key /etc/letsencrypt/live/x/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;               # 关旧协议（TLS1.0/1.1 有已知弱点）
    add_header Strict-Transport-Security "max-age=31536000" always;
}
server {                                          # HTTP → HTTPS 重定向
    listen 80; return 301 https://$host$request_uri;
}
```

- **fullchain 完整链**：只给端点证书（缺中间 CA）→ 部分客户端验证失败（「浏览器行、curl 报错」的经典）。
- **HSTS**：告诉浏览器「以后只许 HTTPS 访问我」——防降级与剥离攻击（首次访问前的窗口是弱点——预加载列表补）。
- **协议版本**：禁用 TLS1.0/1.1（用 sslscan/testssl.sh 验证配置）。
- **SNI 与多证书**：一台服务器多个域名的证书选择机制。

## 5. 攻击与防御的对位

| 攻击               | 手段                                 | 防线                                     |
| ------------------ | ------------------------------------ | ---------------------------------------- |
| 中间人（MITM）     | 伪造证书/ARP 劫持流量                 | 证书链验证 + HSTS + 证书透明度（CT 日志）|
| 降级攻击           | 诱导使用弱协议/弱套件                 | 禁旧协议 + TLS 1.3 的握手签名覆盖参数     |
| 重放               | 录制并重发合法请求                    | 非ces/时间戳/一次性 nonce                |
| 证书泄露           | 私钥被提取                            | 吊销 + 短有效期 + HSM/密钥管理            |
| 流量分析           | 不看内容看元数据（SNI/大小/时序）      | ECH/填充——部分缓解（元数据难以全遮）      |

「攻击面的诚实认知」：TLS 保护**传输中**的数据——**存储中的数据**（[数据库加密](../database/11-ops-pitfalls.md)）与**使用中的数据**（内存）是另外两个战场；**端点被攻破**（你的服务器/用户机器）则 TLS 毫无意义——安全是全链路的（[纵深防御](../linux/11-ops-pitfalls.md)）。

## 6. 陷阱清单

- 缺中间证书（fullchain 不完整）：「有的客户端能访问、有的报错」；SSL Labs 测试定位。
- 忘自动续期：证书过期全站拒绝访问（大型站点的年度新闻）；到期监控 + ACME 自动化。
- 混合内容（HTTPS 页面加载 HTTP 资源）：浏览器警告/拦截；全站资源 HTTPS 化。
- HSTS 缺失：SSL 剥离攻击的口子；先观察 max-age 再强制。
- 私钥进代码仓库/镜像（[秘密管理](../docker/11-pitfalls.md)）：泄露即冒充 + 紧急吊销。
- 信任自签证书当长期方案：内部 PKI 或公网证书；自签的信任分发是运维债务。
- 禁用证书验证（curl -k / verify=False 进生产代码）：等于关掉认证——「测试用参数」绝不能进生产路径。

## 7. 小结

- TLS 的三重防御对位三种攻击：加密防窃听、完整性防篡改、认证防冒充——混合加密（非对称换钥匙 + 对称加密）与前向保密。
- 握手的核心是「证书验证三查」（链可信/域名匹配/签名有效）+ 密钥交换——认证的三重检查缺一即 MITM 入口。
- 证书运维：ACME 自动续期 + 到期监控 + fullchain 完整——「过期」是最可预防的故障。
- 部署加固：禁旧协议、HSTS、混合内容清理——SSL Labs 的分级是配置的体检表。
- TLS 的边界：只保传输——存储/端点/元数据是另外的战场；安全是全链路工程。

## 8. 练习

**1.** 握手观察：用 Wireshark 抓一次 TLS 1.3 握手，识别 ClientHello（SNI/密码套件）、证书消息、Finished——对照「三重防御建立」的流程图；观察握手后数据变为「Application Data」（不可读）。

> [!TIP]
> 思路TLS 1.3 的握手更精简（证书在 ServerHello 后立即出现、大部分握手已加密）——对比 TLS 1.2 抓包看演化的痕迹。

**2.** 证书链解剖：`openssl s_client -connect example.com:443 -showcerts` 查看服务端给出的证书链；用 openssl x509 -text 读证书的 Subject/SAN/有效期/签发者——「一张证书里有什么」的完整解剖。

> [!TIP]
> 思路SAN（Subject Alternative Name）是「域名匹配」的现代字段（CN 已是兼容遗留）；签发者的路径与 Let's Encrypt 的中间 CA（R3/E1）对照——信任链的实物观察。

**3.** 配置体检：用 SSL Labs（在线）或 testssl.sh 给你的站点打分——修复发现的问题（旧协议/弱套件/缺 HSTS/链不完整）再复测——到 A 级的过程记录。

> [!TIP]
> 思路常见扣分点：支持 TLS1.0/1.1、弱套件（3DES/RC4）、缺 HSTS、证书链不全、DH 参数过弱——每一项都有对应的 nginx/apache 配置修复。

**4.** 中间人实验（隔离环境）：在本机 hosts 把某域名指到本地假服务器 + 自签证书 → 浏览器的「证书不受信任」警告——这正是 MITM 被证书系统拦下的现场；再理解「为什么不能随手点继续」。

> [!TIP]
> 思路浏览器警告的三个选项（返回/查看证书/继续）——「继续」是用户手动信任了假证书。企业的「自装根证书的代理」（审计型代理）就是「合法化的 MITM」——信任根的安装即信任的让渡。

**5.** 混合内容排查：对一个 HTTPS 页面跑「Mixed Content 扫描」（DevTools Console 的警告），修复所有 HTTP 资源引用——升级到「绿锁 + 无警告」的完整状态。

> [!TIP]
> 思路混合内容的分类：被动（图片可容忍但降级）与主动（脚本必须修）——主动混合内容默认被浏览器阻断。CSP 的 upgrade-insecure-requests 头可以批量升级。

**6.** 讨论：TLS 保护「传输」，但「端点被攻破」（服务器被入侵/用户机器有恶意软件）时一切加密失效——从「威胁模型的边界」角度分析「加密不是安全的一切」，并对照[纵深防御](../linux/11-ops-pitfalls.md)的完整清单（传输加密/存储加密/访问控制/监控/备份）——为什么每个防御层都要「假设上一层可能失守」？

> [!TIP]
> 思路威胁模型分层：网络窃听（TLS 管）、服务器入侵（最小权限/隔离/审计管）、用户设备（端点防护管）、内部人员（审计与权限管）——每层只防「本层的威胁」。纵深防御的哲学：**没有单点可靠，只有组合的韧性**——与[不可变基础设施](../docker/01-why-containers.md)、[备份演练](../database/11-ops-pitfalls.md)共同构成完整防线。
