「模型训不出来」的排查很少是理论问题——90% 是工程问题：数据管道错了、学习率不合适、过拟合没管、实验不可复现。本篇是**训练的工程手册**：调参的优先级、调试的标准动作、实验管理的纪律。

## 1. 训练前的检查清单

```text
□ 数据：划分隔离（train/val/test 三分）✓；标签抽查（随机看 50 个标注）✓
□ 归一化：统计量只来自训练集（[第 2 篇](02-linear-models.md)）✓
□ 数据管道：读入-增强-批处理跑一遍，肉眼检查 10 个 batch 的样本与标签
□ 类别分布：不平衡的指标预案（[第 4 篇](04-evaluation.md)）✓
□ 基线：线性/树模型/上一版模型的成绩记录在案（[第 2 篇](02-linear-models.md)）
```

**肉眼检查 batch** 是被低估的一步：增强后的图像、标签与内容对应、padding 位置——数据管道的错（错位/重复/泄漏）在Loss 曲线上永远只表现为「诡异」，在样本里一眼见底。

## 2. 超参数：优先级排序

| 优先级 | 超参数                  | 理由                                     |
| ------ | ----------------------- | ---------------------------------------- |
| ★★★    | **学习率**              | 影响收敛与否；其他一切的前提              |
| ★★★    | 模型容量（深度/宽度）    | 偏差-方差的源头（[第 1 篇](01-ml-overview.md)）|
| ★★     | batch size / epochs     | 与 lr 联动；早停的预算                    |
| ★★     | 正则化强度（dropout/WD） | 过拟合的旋钮                              |
| ★      | 优化器细节（momentum/beta）| Adam 默认值通常够                       |

**batch size 与 lr 的联动**：batch 翻倍 → lr 可近似线性放大（linear scaling rule）——大 batch 训练的标配。早停（early stopping）是「epochs 怎么定」的答案：监控验证指标、patience 轮不提升就停（省算力防过拟合双收益）。

## 3. 训练调试的五个标准动作

```text
① 看 loss 曲线形态：
   爆炸（NaN/发散）→ lr 太大/数据有 NaN → 降 lr、查数据
   不下降 → lr 太小/标签错/管道断 → 扫 lr、抽查 batch
   训练降验证升 → 过拟合 → 正则化三件套（[第 5 篇](05-nn-basics.md)）

② 过拟合一个小数据集（两三个 batch）：
   训练损失应该能压到 ~0 —— 压不到说明模型/代码有 bug（容量/梯度/管道）
   ★ 「先过拟合小数据」是验证「代码有学习能力」的最快测试

③ 梯度检查：数值微分 vs 反传梯度（[第 5 篇](05-nn-basics.md)练习 2）——手写层必做

④ 增强消融：关掉增强对比——增强有时反而伤（语义不匹配，[第 6 篇](06-cnn.md)）

⑤ 学习率扫描：lr 从小到大指数扫描，找 loss 下降最快的区间（[第 5 篇](05-nn-basics.md)练习 5）
```

调试的心法：**从「最小可复现」开始**——最小数据、最小模型、单卡，跑通再放大。「大模型大数据上调试」是算力与时间的双重浪费。

## 4. 实验管理：可复现的三件套

```python
# ① 随机种子全覆盖
import random, numpy as np, torch
def set_seed(seed=42):
    random.seed(seed); np.random.seed(seed)
    torch.manual_seed(seed); torch.cuda.manual_seed_all(seed)
# 数据加载的 worker 也要 seed；cudnn 确定性模式按需开（可能慢）

# ② 配置与代码同版本：用配置文件（yaml）记录一切超参 + git commit hash
# ③ 日志：tensorboard / wandb——loss 曲线、lr、梯度范数、样本预测可视化
from torch.utils.tensorboard import SummaryWriter
writer = add_scalar("train/loss", loss, step)
```

实验管理的三个教训：**「这次跑的好结果怎么复现？」没有 seed 与配置就是玄学**；**实验命名与记录（wandb）让「三个月前的最佳模型」可追溯**；**配置硬编码在脚本里 = 实验不可比**（一次只动一个变量）。与 [MLflow/模型注册](09-deployment.md)的衔接：实验 → 注册 → 部署的版本链。

## 5. 混合精度与分布式（一句话版）

```python
scaler = torch.cuda.amp.GradScaler()      # 混合精度：FP16 计算 + FP32 主权重
with torch.cuda.amp.autocast():
    loss = model(x)...                     # 显存减半、速度 ~2x（Tensor Core）
scaler.scale(loss).backward(); scaler.step(opt); scaler.update()

# 分布式：DDP（数据并行——每卡一份模型、各吃各的数据、梯度同步）
torchrun --nproc_per_node=8 train.py       # 单机 8 卡
```

混合精度（AMP）是**免费的午餐**（现代 GPU 的 Tensor Core 原生支持）——loss scaler 处理 FP16 的下溢。数据并行（DDP）是「大 batch 大模型」的标准起点——更深的并行（模型并行/ZeRO）属于 [LLM 训练](../llm/04-pretrain-sft-rlhf.md)的世界。

## 6. 陷阱清单

- 数据管道的静默错（标签错位/泄漏/重复样本）：肉眼检查 batch 是防线。
- 无基线直接训大模型：线性/树基线锚定「复杂度值不值」。
- 调参一次只动一个变量都做不到（多变量同时改）：实验失去可比性。
- 验证集参与训练决策后当测试集用：泛化虚高（[第 1 篇](01-ml-overview.md)）。
- 训练正常但推理差：预处理不一致（训练/推理的归一化与增强不同）——部署前核对预处理管道（[第 9 篇](09-deployment.md)）。
- 随机种子只设一半（numpy 设了 torch 没设）：复现失败；种子全覆盖。
- 忽略 checkpoint 策略：训练 8 小时崩溃从头再来；定期存档 + 最佳模型快照。

## 7. 小结

- 训练前五查：划分隔离、标签抽查、batch 肉眼检查、分布预案、基线记录——数据管道错误在样本里可见、在 loss 曲线上永远诡异。
- 超参优先级：lr 与容量 > batch/epochs 与正则 > 优化器细节；早停是 epochs 的答案。
- 调试五动作：loss 曲线形态、过拟合小数据、梯度检查、增强消融、lr 扫描——「最小可复现」是调试的起点。
- 实验管理三件套：种子全覆盖、配置进版本、日志系统——可复现是 ML 工程的底线。
- 混合精度与 DDP 是规模化标配；「训练-推理一致性」（预处理管道）是部署前必须核对的一致性。

## 8. 练习

**1.** 故意埋五个 bug 的训练脚本（归一化泄漏/忘 zero_grad/标签错位/lr 过大/增强错位），用第 3 节的动作逐个定位修复——把「调试动作」与「症状」做成你自己的对照表。

> [!TIP]
> 思路对照表的五对：泄漏→「训练好验证好、真实数据差」；忘 zero_grad→「loss 不降反跳」；标签错位→batch 肉眼可见；lr 大→曲线爆炸；增强错位→可视化样本。诊断动作与症状一一对应后，排查不再靠猜。

**2.** 过拟合小数据测试：构造 32 个样本的完美可分数据，验证你的模型/训练循环能把训练损失压到 <0.01——这是每次改代码后的「冒烟测试」。

> [!TIP]
> 思路压不下去的排查序：模型容量（参数够吗）→ 梯度（打印范数）→ 数据管道（标签对吗）→ 学习率。「过拟合能力」是训练代码的正确性证明。

**3.** 复现性实验：同一配置跑两次（只差 seed），记录最终指标的波动；再跑一次「不设 seed 全随机」——量化「实验噪声」，理解为什么「提升 0.3%」可能毫无意义。

> [!TIP]
> 思路实验噪声是「提升可信度」的底——低于噪声带的结果一律存疑（与[评估的统计显著性](04-evaluation.md)呼应）。论文复现难的一半原因在此。

**4.** 训练-推理一致性排查：训练时用了增强与归一化、推理代码忘了（或顺序不同）——构造这个 bug，观察精度跳水，再用「预处理函数共享」修复。

> [!TIP]
> 思路训练/推理的预处理必须同源（同一份代码/序列化管道）——「上线精度暴跌」的头部原因。ONNX 导出时把预处理固化进模型是彻底解法（[第 9 篇](09-deployment.md)）。

**5.** checkpoint 与断点续训：实现「每 epoch 存档（模型+优化器+epoch+随机状态）+ 崩溃后从存档恢复」，人为中断一次验证恢复后 loss 曲线无缝——把「训练是长跑」的工程意识写进代码。

> [!TIP]
> 思路恢复的完整状态 = 模型权重 + 优化器动量 + 学习率调度器状态 + 随机状态 + epoch 计数——漏一个就「恢复了个寂寞」。大模型训练的容错体系（[LLM 篇](../llm/04-pretrain-sft-rlhf.md)）是这个练习的工业级放大。

**6.** 讨论：为什么「实验管理」在 ML 团队的价值被低估？从「结果的可信度链（结果→配置→代码→数据）」「团队协作（实验可比）」「迭代速度（不再重复跑）」三个角度分析，并对照 [git 管理代码历史](../git/01-object-model.md)——实验管理是不是「ML 的 git」？

> [!TIP]
> 思路实验管理管的是「结果的可信度与可追溯」——与 git 管「代码的可追溯」同构，但多两维（配置×数据版本）。MLflow/W&B 的定位就是「ML 的版本控制 + CI」——没有它，ML 团队的知识沉淀靠聊天记录。
