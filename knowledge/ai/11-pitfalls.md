ML 项目的陷阱有一个共同的形：**问题藏在数据里、错误在评估时被掩盖、事故在部署后爆发**。本篇按六个类别汇编审查清单，附「结果好得离谱」的诊断路线——它的镜像问题是「结果差得离谱」。

## 1. 六类审查清单

### 1.1 数据（第 1 篇）

- [ ] 训练/验证/测试划分隔离且符合数据形态（时序/分组/分层）
- [ ] 标签质量抽查过（随机人工复核 50+ 条）
- [ ] 分布代表性核查（训练数据与线上分布的差异）
- [ ] 数据泄漏排查：时间窗、目标衍生物、分组信息（[第 1 篇练习 2](01-ml-overview.md)）
- [ ] 缺失值/异常值的处理策略有文档（不是静默删除）
- [ ] 数据版本可追溯（[第 9 篇](09-deployment.md)的 lineage）

### 1.2 特征与预处理（第 2 篇）

- [ ] 预处理参数只来自训练集（Pipeline 化）
- [ ] 类别编码无泄漏（目标编码 fit 训练折）
- [ ] 特征与目标的时序关系合法（没有「用未来预测过去」）
- [ ] 缩放/归一化按模型需要（线性/NN 需要、树不需要）
- [ ] 特征数量与样本量匹配（高维小样本的正则化预案）

### 1.3 建模（第 2、3、5 篇）

- [ ] 简单基线已建立并被比较（线性/GBDT）
- [ ] 过拟合控制（深度限制/正则化/早停——[第 5 篇](05-nn-basics.md)）
- [ ] 训练可复现（种子全覆盖/配置版本化，[第 8 篇](08-training-practice.md)）
- [ ] 随机对照（同配置多 seed 的指标波动已知）
- [ ] 模型复杂度与数据量匹配（小数据硬上大模型）

### 1.4 评估（第 4 篇）

- [ ] 指标与业务成本对齐（precision/recall 的跷跷板选边）
- [ ] 不平衡数据不用 accuracy；极端不平衡看 PR-AUC
- [ ] 评估含分布信息（CV 均值±方差，非单点）
- [ ] 阈值按业务成本校准（非默认 0.5）
- [ ] 概率校准检查（AUC 好 ≠ 概率准）
- [ ] 与基线的差距 > 实验噪声

### 1.5 部署（第 9 篇）

- [ ] 训练-推理预处理一致（同一管道/序列化）
- [ ] 推理延迟/资源满足 SLO（P99 而非均值）
- [ ] 模型版本化 + 可回滚（引用切换）
- [ ] 输入校验与异常处理（线上永远是脏数据）
- [ ] 降级方案（模型服务挂了业务怎么办）

### 1.6 监控与治理（第 9 篇）

- [ ] 数据漂移监控（PSI/分布对比 + 告警阈值）
- [ ] 线上效果回算路径（延迟标签的回流管道）
- [ ] 预测分布监控（置信度漂移作早期信号）
- [ ] 再训练触发机制明确（定期/漂移/人工）
- [ ] 模型决策的可解释性方案（[SHAP](03-trees-ensembles.md)）满足合规
- [ ] 公平性评估（不同群体的指标差异）

## 2. 「结果好得离谱」的诊断路线

```text
指标好到不合理（99.9%？）——按概率从高到低排查：
① 数据泄漏（第一嫌疑）
   → 特征里有目标衍生物/未来信息/分组标识
   → 消融测试：逐特征移除看指标跳水
② 评估集被污染
   → 测试集参与过调参/训练测试重叠（重复样本跨集）
   → 检查集合间重复行
③ 任务定义错误
   → 「预测退款」用的是退款金额、标签泄露在特征工程里
   → 重述任务：这个特征在预测时刻可获得吗？
④ 指标误用
   → 不平衡数据的 accuracy、AUC 的解读错误
⑤ 模型真的这么好（最后才信）
   → 用全新收集的数据复测——只有这个能毕业
```

镜像路线「结果差得离谱」：数据管道错（标签错位）→ 训练没收敛（lr/梯度）→ 评估代码 bug → 预处理不一致（[第 8 篇](08-training-practice.md)）→ 模型容量不足。

## 3. 反模式速查

| 反模式                                       | 一句话修复                                |
| -------------------------------------------- | ----------------------------------------- |
| notebook 直接改生产                          | 代码化 + 测试（[第 9 篇](09-deployment.md)鸿沟）|
| 「离线指标好」当上线依据                     | A/B + 漂移监控                             |
| 特征重要性当因果                             | SHAP 辅助 + 业务验证                       |
| 调参到测试集指标最好                          | 验证/测试分离的纪律                        |
| 模型文件裸存（无版本无元数据）                | 注册表 + lineage                           |
| 一个模型服务所有场景（不分群不校准）          | 分群评估 + 校准                            |
| 深度学习解决一切                             | 基线先行 + [表格看 GBDT](03-trees-ensembles.md)|
| 精度提升不与成本对照（延迟/维护/风险）        | 工程 ROI 评审                              |
| 人工特征无人解释（黑盒特征工程）              | 特征文档 + 合理性审查                      |
| 训练完就删数据管道（不可复现）                | 管道代码化 + 版本化                        |

## 4. 项目验收问题清单

```text
□ 这个模型解决的业务问题是什么？衡量标准是谁定的？
□ 数据从哪来？覆盖谁？缺了谁？（代表性）
□ 训练/验证/测试如何划分？为什么这样划分？
□ 特征在预测时刻真的可获得吗？（时间旅行检查）
□ 与什么基线比较？差距显著吗？
□ 最坏情况的预测会怎样？（边界与失败模式）
□ 模型错了谁受影响？影响多大？（风险面）
□ 漂移了怎么发现？多久能发现？
□ 怎么回滚？
□ 半年后谁维护？数据管道还活着吗？
```

十个问题的回答质量 = 项目的工程成熟度——**答不上「回滚」的 ML 项目是定时炸弹**（[部署](09-deployment.md)的版本管理）。

## 5. 小结

- 六类清单的分布规律：数据/评估类陷阱最高频（泄漏/不平衡/虚高），部署治理类最常被省略——ML 的事故多发生在「模型之外」。
- 「好得离谱」的五步诊断：泄漏 → 集合污染 → 任务定义 → 指标误用 → 才是真的；镜像诊断管「差得离谱」。
- 反模式的总根：**把 ML 当「训练模型」而不是「数据-模型-部署的持续系统」**——notebook 心态与部署现实的鸿沟。
- 验收十问是项目成熟度的试金石：回滚、漂移、代表性、风险面——工程问题先于模型问题。
- 与[软件工程清单](../c/14-pitfalls.md)的对照：ML 清单多出「数据与分布」维度——「数据的版本与漂移」是 ML 独有的工程对象。

## 6. 练习

**1.** 用六类清单审查一个真实的 ML 项目（kaggle 解决方案或公司项目），统计命中分布——对照「数据/评估类最高频」的预期，并找出清单本身遗漏的领域特定项。

> [!TIP]
> 思路领域特定项是清单演化的入口（时序任务的窗口泄漏/NLP 的模板泄漏/推荐的流行度偏差）——通用清单 + 领域补充是完整形态。

**2.** 「好得离谱」诊断实战：构造一个含三类泄漏（时间/目标衍生物/分组）的数据集与「完美模型」，用第 2 节路线逐步揪出——记录每一步的证据链。

> [!TIP]
> 思路证据链练习：泄漏的特征消融曲线（去掉泄漏特征指标跳水）是最有说服力的一环。诊断记录是 ML code review 的最佳教材。

**3.** 验收十问演练：对一个线上模型（或同学的项目）逐问打分（可回答/部分/不可回答）——「不可回答」的问题就是技术债清单。

> [!TIP]
> 思路十问里最容易答不上的是「回滚」与「半年后谁维护」——暴露的是「ML 项目当一次性实验」的组织心态。验收问卷新增的问题应该来自你们的事故复盘。

**4.** 建立一个「ML 事故复盘」文档模板：现象/数据证据/根因分类（用六类清单定位）/修复/预防机制——用一次真实（或构造）的「上线后精度衰减」走完全流程。

> [!TIP]
> 思路「上线后精度衰减」的根因通常是漂移（1.6 类）+ 预处理不一致（1.5 类）的组合——复盘模板把「组合事故」拆解到清单类别，预防机制才有着落点。

**5.** 反模式自查：反模式速查表里挑三条你踩过的（或身边常见的），写成团队 wiki 的「事故案例 + 正确姿势」条目——把个人经验转化为团队资产。

> [!TIP]
> 思路写案例的格式：「现象 → 排查弯路 → 根因 → 修复 → 以后怎么防」——比「不要 XX」的口号有效十倍。团队的知识库就是事故案例的复利。

**6.** 讨论：ML 工程与软件工程在「质量保证」上的根本差异是什么？软件的 bug 是「确定性的」（测试可复现），ML 的问题常是「统计性的」（指标波动/分布漂移/长尾失败）——从「测试金字塔在 ML 的变形」「验收标准的概率化」「监控即测试的延续」三个角度，分析 ML 工程师与软件工程师的能力差异。

> [!TIP]
> 思路ML 的质量保证是「概率化验收 + 持续监控」：测试从「断言相等」变成「断言分布」、上线从「终点」变成「监控的起点」。ML 工程师的能力差异：统计思维（不确定性下决策）+ 数据敏感（泄漏/漂移的嗅觉）+ 同样的软件工程底座。
