2017 年论文《Attention Is All You Need》提出 Transformer：去掉循环，只用注意力。它同时解决了长程依赖和并行化两个问题，此后一路成为几乎所有大模型（LLM）的底座。本章讲清它的核心机制，以及大模型时代应用层的三个关键词。

## 自注意力：每个位置看所有位置

序列里的每个 token 生成三个向量：**查询 Q**（我在找什么）、**键 K**（我有什么特征）、**值 V**（我的实际内容）。注意力就是"用 Q 去匹配所有的 K，按匹配度加权取 V"：

```python
import torch
import torch.nn.functional as F

# Q, K, V 形状均为 (seq_len, d)，由同一输入经三个不同的线性投影得到
scores = Q @ K.T / d ** 0.5          # 任意两个 token 之间的相关度
weights = F.softmax(scores, dim=-1)  # 每行 softmax：一组和为 1 的权重
out = weights @ V                    # 每个位置取"按相关度加权的信息"
```

对照第 7 章：RNN 里第 1 个词的信息传到第 100 个词要走 99 步，注意力下任意两个 token **一步直达**；RNN 逐步串行，注意力对整个序列**一次并行算完**。这是 Transformer 的两大胜利——长程依赖不再衰减，训练速度吃满 GPU。

decoder-only 结构还要加一道**因果掩码**：位置 t 只允许关注 t 之前的 token，否则训练时模型就"偷看答案"了；encoder 结构则双向放开。掩码实现上就是把 QK^T 矩阵中"未来"位置在 softmax 之前压成负无穷：

```python
n = scores.shape[-1]
mask = torch.triu(torch.full((n, n), float("-inf")), diagonal=1)
scores = scores + mask    # "未来"位置的分数变 -inf，softmax 后权重为 0
```

> [!NOTE]
> 缩放因子 √d 不是装饰：向量维度高时点积数值会很大，softmax 进入饱和区、梯度趋零。除以 √d 把分数拉回正常范围，是工程上必要的稳定措施。另外注意自注意力发生在**同一序列内部**——每个 token 看的是自己所在的这句话，跨句子的信息要靠模型架构的其他部分处理。

## 多头与位置编码

**多头注意力**：并行跑多组独立的 Q/K/V 投影（多个"头"），每个头在自己的低维子空间里关注不同的模式——有的头盯语法关系，有的头盯指代，有的头盯相邻词——结果拼接后再做一次线性变换。单头的表达力是"一种眼光"，多头是"多种眼光同时看"。

**位置编码**：注意力本身对顺序完全无感——把输入 token 打乱重排，每个 token 能获取的信息集合不变。但语言显然有顺序，所以必须把位置信息显式注入：原始论文用正弦函数，后来的模型发展出可学习位置编码、RoPE 等变体。一个直观验证：把"猫追狗"的位置编码换成"狗追猫"的，注意力结果应当随之改变——位置信息真的在起作用。

三种结构各占一摊：

| 结构 | 代表 | 特点 |
| --- | --- | --- |
| Encoder-only | BERT | 双向看上下文，适合理解类任务（分类、检索） |
| Decoder-only | GPT 系列 | 因果掩码只能看左侧，逐词生成，当今主流大模型的选择 |
| Encoder-Decoder | T5、原始 Transformer | 输入输出都是序列：翻译、摘要 |

不知道选哪个？做应用基本只会遇到 decoder-only 的 API；做检索召回可能碰上 encoder-only 的 embedding 模型；研究翻译摘要才需要 encoder-decoder 的完整形态。顺带记忆：ChatGPT 的"Chat"就是 decoder-only 逐词生成的直接体现——对话被当成"一问一答接着写"的文本。

## 一层 Transformer 长什么样

自注意力只是模块之一。完整的一层（以原始论文为例）：

```text
x → 多头自注意力 → 残差连接 + LayerNorm
  → 前馈网络 FFN（两层线性 + 激活）→ 残差连接 + LayerNorm → 交给下一层
```

两个细节值得注意：FFN 对每个位置独立做同样的变换，参数量通常占大头，注意力负责"在 token 之间搬信息"，FFN 负责"对每个位置加工"；FFN 的隐藏维通常是模型维度 d 的 4 倍，激活函数用的 GELU 是 ReLU 的近亲。残差连接和 LayerNorm（第 6、9 章的常客）保证几十上百层叠起来还训得动。Transformer 没有发明多少新零件，它的高明在于把已有零件组合得恰到好处。

## 生成是怎么发生的：自回归

GPT 类模型生成文本的方式叫**自回归**（autoregressive）：每次预测下一个 token，把新 token 拼回输入，再预测下一个——你在对话界面看到的逐字输出就是这么来的。控制生成随机性的两个常用旋钮：**温度**（低 = 保守稳健，高 = 发散有创造性）和 **top-p**（只从概率累积前 p 的候选词里采样）。工程上生成快靠的是 **KV 缓存**：已生成 token 的 K、V 不重复计算，每步只算新 token——读推理代码时遇到 `past_key_values` 就是它。

## 预训练-微调范式

Transformer 之前，每个任务从零训一个模型；之后范式变成了两段式：

- **预训练**：在超大语料上做"预测下一个词"——不需要人工标注，互联网文本本身就是标签，模型在过程中学到语法、事实知识和相当程度的推理模式
- **微调**：拿少量标注数据在预训练模型上继续训练，适配具体任务

预训练的产物习惯叫**基座模型**（base model）——它擅长"续写"，但不一定听话；经过指令微调的才有今天常见的对话形态。买来的 API 背后通常还叠了 RLHF 等多层加工。

这个范式后来继续演化：指令微调让模型学会"听懂人话"，人类反馈强化学习（RLHF）让输出对齐人类偏好。模型规模从数亿到数千亿参数量级不等，训练成本只有头部机构负担得起——于是产业分工自然形成：**基座模型**由大厂训练，应用层负责微调、适配和调用。

为什么"预测下一个词"这么朴素的目标威力这么大？为了把下一个词预测准，模型被迫隐式学会语法、常识、事实乃至推理——所有知识都被压缩进"接龙"这一个任务里。GPT 系列更进一步，把"任务"也统一成接龙：Prompt 就是一段前文，模型接着写就是回答；少样本示例（few-shot）直接写进 Prompt 就能生效。

## 从 BERT 到多模态：方向比名单重要

BERT（理解）与 GPT（生成）双雄并立了几年，此后"规模定律"（scaling laws）接管了叙事：算力、数据、参数量按对数增长，模型能力的提升出乎意料地**可预测**——这是各家敢持续堆算力的理论依据。今天的模型普遍走向多模态（图文音频混合输入输出）、更长上下文、更低推理成本。

具体哪个模型最强、参数多少、榜单如何，月月在变；不变的是方向和本节的机制。学会读架构图——有没有注意力、掩码怎么加、位置信息怎么注入——新模型出来，花十分钟就能看懂个大概。对学习者这是好消息：核心机制十年没换过，学一次够用很多年。

## Prompt / RAG / Agent

应用大模型的三层玩法，工程成本从低到高：

**Prompt（提示词）**：不动模型，把任务描述、示例、输出格式要求写进输入。成本低见效快，但受限于模型已有的知识和上下文窗口长度。写好 Prompt 的核心技巧：给任务角色、给示例（few-shot）、给明确的输出格式。工程师最容易上手的心智模型：把 Prompt 当"函数签名 + 文档 + 测试用例"来写。

**RAG（检索增强生成）**：让模型"开卷考试"——先从外部知识库检索相关片段，拼进上下文再生成：

```python
# RAG 骨架（伪代码）
chunks = retriever.search(question, top_k=5)     # 向量化检索相关文档片段
prompt = f"根据以下资料回答问题：\n{chunks}\n\n问题：{question}"
answer = llm.generate(prompt)                    # 带着证据作答，减少幻觉
```

它缓解两个顽疾：知识过时（模型训练截止日期之后的事它不知道）和幻觉（不懂装懂）——回答有据可查，还能给出出处。检索这步的常见实现：文档切块 → 嵌入模型编码成向量存进向量库 → 查询时算余弦相似度取 top-k。工程经验：**切块策略和检索质量往往比生成端的参数更影响 RAG 效果**——检索不到正确资料，模型再强也是巧妇难为无米之炊。

**Agent（智能体）**：让模型进入"思考 → 调用工具 → 观察结果 → 继续"的循环来处理多步任务：查数据库、调 API、跑代码，把 LLM 从"回答者"升级成"执行者"。工具调用的本质：把可用函数的"签名 + 说明"列给模型，模型输出结构化的调用请求，你的代码执行后把结果回填给它，循环直到任务完成——模型负责"决定调什么"，执行永远在你手里。

四种方式放在一起看：

| 方式 | 改什么 | 成本 | 典型场景 |
| --- | --- | --- | --- |
| Prompt | 只改输入 | 几乎为零 | 通用任务的快速适配 |
| RAG | 加检索、拼上下文 | 中 | 知识库问答、企业文档 |
| 微调 | 改模型权重 | 高 | 格式/风格/领域要求极高 |
| Agent | 加循环 + 工具 | 中高 | 多步任务、流程自动化 |

> [!TIP]
> 选型优先级基本固定：先把 Prompt 优化到位；解决不了知识问题再上 RAG；对输出格式/领域深度要求极高才考虑微调；任务需要多步执行才引入 Agent。大量项目的共同教训：一上来就微调，最后发现一份好的 Prompt 加几百条高质量标注样本就够了。

## 注意力的代价：上下文窗口

注意力要计算所有 token 两两之间的相关度，计算量和显存随序列长度**平方**增长——序列翻倍，开销约四倍。这解释了两件事：为什么上下文窗口长度是大模型的核心参数；为什么"让模型读完超长文档"背后是实打实的算力问题。滑动窗口、稀疏注意力等工程手段，本质上都是在给 O(n²) 打补丁。对工程师的启示：处理长文档时先想"能不能检索、能不能分段"，而不是把问题整个塞进上下文。
