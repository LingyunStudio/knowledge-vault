「notebook 里 95% 的模型」与「生产系统里可靠服务的模型」之间隔着一条鸿沟：**预处理一致性、推理性能、版本管理、监控漂移**。MLOps 就是填平鸿沟的工程学科——它把[实验管理](08-training-practice.md)延续到「线上服务的生命周期管理」。

## 1. 鸿沟的具体形态

```text
notebook 的隐含假设            生产的现实
预处理在内存里手搓              预处理必须与训练逐位一致（[第 8 篇](08-training-practice.md)）
单条推理无所谓延迟              P99 延迟是 SLO；GPU 批处理才经济
模型是一个 .pkl                 模型 = 权重 + 架构 + 预处理 + 版本（一个整体）
数据分布静止                    数据漂移：上线那天就开始失效
「训练好就结束了」                监控-再训练-发布的持续循环
```

第一鸿沟 **「训练-推理 skew」**（[第 8 篇练习 4](08-training-practice.md)）：训练与推理的预处理不一致（特征顺序/归一化参数/字符串编码）——线上精度暴跌的头号原因。解法：**预处理管道与模型一起序列化**（sklearn Pipeline/ONNX 图内预处理）。

## 2. 模型导出：从框架到部署格式

```python
# ONNX：跨框架的中间表示（图序列化——预处理可以进图！）
torch.onnx.export(model, dummy_input, "model.onnx",
                  input_names=["input"], output_names=["logits"],
                  dynamic_axes={"input": {0: "batch"}})   # 动态 batch

# TorchScript：PyTorch 自家的图表示（torch.jit.script/trace）
traced = torch.jit.trace(model, dummy_input)
```

| 格式           | 优点                       | 场景                              |
| -------------- | -------------------------- | --------------------------------- |
| ONNX           | 跨框架/跨硬件（ONNX Runtime）| 服务端部署、端侧多样硬件            |
| TorchScript/SafeTensors | PyTorch 原生       | torch 生态内部                     |
| TensorRT 引擎  | NVIDIA 极致优化             | GPU 推理的最后一公里                |
| CoreML/TFLite  | 苹果/移动端                 | 端侧部署                            |

导出的本质：**把「代码定义的模型」固化成「数据定义的计算图」**——部署环境不再需要训练框架与你的 Python 代码（依赖解耦 + 预处理一致性）。

## 3. 推理优化三板斧

| 手段       | 原理                                    | 代价                               |
| ---------- | --------------------------------------- | ---------------------------------- |
| **量化**   | FP32 → INT8/INT4（权重与激活低比特）     | 精度略降；需要校准数据集            |
| **蒸馏**   | 大模型当老师教小模型（软标签）           | 训练成本；精度损失换 5~10x 提速     |
| **剪枝**   | 删掉不重要的权重/通道                    | 需要微调恢复                        |
| **批处理** | 多请求合并成 batch（GPU 利用率）         | 延迟换吞吐（动态 batching）         |
| **编译**   | TensorRT/ONNX Runtime 图优化 + 算子融合   | 每硬件需编译；换图需重编译          |

量化的直觉：**神经网络对数值精度出乎意料地不敏感**——INT8 通常掉不到 1% 精度、换来 2~4 倍速度与 4 倍内存减半；LLM 时代的 INT4 量化让消费级显卡跑大模型（[LLM 篇](../llm/06-inference-decoding.md)）。服务的标准姿势：**动态 batching + 常驻编译引擎**（Triton/vLLM——吞吐的来源）。

## 4. 服务化：模型即 API

```text
请求 → [负载均衡] → [推理服务集群]（模型常驻显存，动态 batch）
                        ↓
                 [特征服务/预处理]（与训练一致的管道）
                        ↓
                 [模型仓库]（版本管理/回滚）
```

```python
# 最简形态：FastAPI 包一层
from fastapi import FastAPI
app = FastAPI()
model = load_model()                     # 启动时加载一次（常驻）

@app.post("/predict")
async def predict(req: Req):
    x = preprocess(req)                  # 与训练一致的预处理
    return model.predict(x)
```

推理服务的工程要点：**模型常驻**（启动加载一次，不是每请求加载——10 秒的加载 × 每请求 = 灾难）、**批处理**（GPU 吞吐）、**无状态水平扩展**（副本数按 QPS）、**健康检查**（[docker 篇](../docker/07-compose.md)的 healthcheck）。GPU 推理的批处理与显存管理是专门学问（vLLM 的 PagedAttention 是 LLM 服务的代表创新）。

## 5. 监控：漂移是常态

```text
数据漂移（data drift）：输入分布变了（新用户画像/上游字段变更）
概念漂移（concept drift）：输入与目标的关系变了（疫情改变消费行为）
表现：线上指标逐渐劣化（但代码一行没改！）
```

监控的三层：

1. **服务层**：QPS/延迟/错误率（普通 SRE 指标）。
2. **数据层**：输入特征分布与训练时的偏移（PSI/KS 检验；分布对比告警）。
3. **模型层**：线上预测的代理指标——延迟到达的真实标签（转化率/点击率）回算 AUC；或用「模型置信度分布漂移」作早期信号。

「模型会腐烂」是 ML 的物理定律：**上线即漂移开始**——再训练的触发（定期/漂移告警/人工审核）是 MLOps 闭环的驱动轮。

## 6. MLOps 闭环：版本管理 everything

```text
数据版本（DVC）→ 特征 → 训练（seed/配置[第 8 篇](08-training-practice.md)）→ 模型注册（版本+指标+ lineage）
→ 评估门禁 → 部署（金丝雀/灰度）→ 监控 → 触发再训练 →（循环）
```

模型版本管理的核心：**一个模型版本 = 数据版本 + 代码 commit + 超参 + 指标**的完整 lineage——「线上 1.2.0 为什么预测错了」能追溯到训练数据与代码（与 [git 的可追溯](../git/01-object-model.md)、[MLflow 模型注册](10-toolbox.md)）。发布策略：**影子模式**（新模型并行跑只记录不打分）→ **灰度**（5% 流量）→ 全量——ML 的 A/B 与回滚（[第 4 篇](04-evaluation.md)的离线-在线差异）。

## 7. 陷阱清单

- 预处理不一致（训练/推理两套代码）：skew 的头号；管道随模型序列化。
- 每请求加载模型：延迟灾难；常驻 + 预热。
- 无批处理的 GPU 推理：利用率 5%；动态 batching。
- 无监控裸奔上线：模型静默腐烂；漂移监控 + 线上指标回算。
- 回滚只有「重新训练」：版本化模型 + 引用切换（与 [docker tag](../docker/08-registry.md)、[git 回滚](../git/07-undo.md)同构）。
- 离线指标当线上承诺：分布漂移 + A/B 才是终审（[第 4 篇](04-evaluation.md)）。
- 量化/导出后不做精度回归测试：部署版与训练版逐位对比（黄金测试集）。

## 8. 小结

- notebook 与生产之间的鸿沟四件：预处理一致、推理性能、版本管理、漂移监控——MLOps 的四根支柱。
- 导出（ONNX/TorchScript）把「代码定义的模型」固化为「数据定义的图」——依赖解耦与预处理一致性的载体。
- 推理优化三板斧：量化（INT8/INT4）、蒸馏、批处理（GPU 吞吐的来源）+ 编译引擎（TensorRT/ORT）。
- 监控三层：服务指标、数据漂移（PSI/KS）、模型效果回算——「模型会腐烂」是常态，再训练是循环。
- MLOps 的版本链：数据→代码→模型→部署的全 lineage + 影子/灰度发布——「模型即版本化资产」。

## 9. 练习

**1.** 制造「训练-推理 skew」并修复：训练用 StandardScaler（内存里 fit）、推理服务用「重新 fit 的 scaler」——对比线上精度；再用「scaler 随模型 pickle/ONNX 图内归一化」修复。

> [!TIP]
> 思路skew 的修复方向是「预处理成为模型资产的一部分」——序列化在一起才不会漂移。特征顺序错位是这个家族的另一个高发成员（列名 → 位置的隐式依赖）。

**2.** 量化实验：把一个 ResNet 分类器做 FP32 与 INT8 量化（ONNX Runtime/TensorRT），对比模型大小、延迟、精度——画出「速度-精度」的交换点。

> [!TIP]
> 思路预期：体积 4x↓、延迟 2~3x↓、精度 <1% 降。校准集的代表性与量化敏感层（首末层）是细节坑——量化不是免费但接近免费。

**3.** 推理服务压测：给 FastAPI 模型服务做压测（无批处理 vs Triton 动态 batching），对比 QPS 与 P99 延迟——理解「GPU 吞吐靠批处理」的量化幅度。

> [!TIP]
> 思路GPU 单请求推理利用率常 <10%（算不满）——动态 batching 把吞吐抬 5~10x。延迟与吞吐的权衡曲线（batch 越大吞吐越高但单请求延迟升）是服务调参的主轴。

**4.** 漂移监控实验：用一个「季节性数据」模拟漂移（训练用夏季、推理喂冬季），计算输入特征的 PSI——设置告警阈值并验证它在真实漂移时触发。

> [!TIP]
> 思路PSI <0.1 稳定、0.1~0.25 观察、>0.25 显著漂移的经验线。漂移监控要选「有业务含义的特征」——全特征扫描会产生告警疲劳。

**5.** 实现模型版本切换与回滚：模型注册表（版本目录：模型+指标+元数据）、服务读「当前版本」配置、切换版本无需重启（热加载或双模型影子）——演练「回滚到上一版」的全流程计时。

> [!TIP]
> 思路回滚的快慢取决于「版本切换是引用切换还是重新部署」——与 [docker tag 回滚](../docker/08-registry.md)、[git revert](../git/07-undo.md) 同构。影子模式（新旧模型并行对比）是切换前的最后一道验证。

**6.** 讨论：为什么说「ML 系统的技术债在模型之外」（Google 的著名论文 Hidden Technical Debt in ML Systems）？从「数据依赖/特征纠缠/反馈回路/监控缺失」四个角度，对照一个只有 5% 是 ML 代码的系统图——分析为什么「模型只是冰山一角」，以及 MLOps 与 [传统 DevOps](../docker/08-registry.md) 的本质差异。

> [!TIP]
> 思路ML 系统的债主要在「数据管道的纠缠、特征的双向依赖、模型改变世界的反馈回路」——代码只是冰山水面部分。与 DevOps 的差异：ML 的资产多两维（数据+模型）且都会漂移——CI/CD 变成 CT（持续训练）。
