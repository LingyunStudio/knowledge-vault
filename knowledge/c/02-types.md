在大多数语言里，类型是「数据的种类」；在 C 里，类型只是**一段字节流的解读说明书**：占几个字节、按什么编码读、读到机器码里用什么指令处理。`int x = 65;` 和 `char c = 65;` 在内存里的字节是同一串，差别只在「读几个字节、怎么解读」。理解了这一点，C 类型系统的所有怪癖——隐式转换、溢出行为、`size_t` 的坑、浮点精度——都能推导出来，而不需要死记。

这一篇把类型系统拆成四块：整型的位级真相（补码）、无符号与有符号相遇时的转换规则、IEEE 754 浮点的结构与精度陷阱，以及把这些串起来的完整转换规则表。每一块都配它对应的经典事故——因为 C 类型系统的知识点几乎都是**从 bug 里长出来的**。

## 1. 整型：补码不是规定，是最优解

### 1.1 无符号整型：纯粹的二进制

`unsigned` 没有任何花样：N 位就是 0 到 2ᴺ−1 的直接二进制编码。

```text
uint8_t:  0     = 00000000
          5     = 00000101
          255   = 11111111
```

对无符号数的一切运算都定义良好：**加法溢出 = 对 2ᴺ 取模回绕**（标准明文规定），减法出负也是回绕。`0u - 1u` 得到 `UINT_MAX`，这不是错误，是定义。

### 1.2 有符号整型：补码的三个理由

有符号数的表示历史上有过三种方案：原码（最高位当符号位）、反码、**补码**（two's complement）。今天所有主流平台都用补码，C23 起标准也明确指定补码。它胜出的原因值得逐条理解，因为每一条都直接影响你写的代码：

```text
补码编码规则：非负数照常编码；负数 −x 的编码 = 2ᴺ − x
  3      = 00000011
  −3     = 11111101   （256 − 3 = 253）
  −1     = 11111111   （256 − 1 = 255：全 1）
  −128   = 10000000   （int8_t 的下限：没有对应的正数 128）
```

1. **硬件零成本**：加法器不用区分符号位，`5 + (−3)` 和 `5 + 253` 走同一条加法电路，进位自然丢弃后结果正确（2）。减法就是加负数，乘除也有整齐的规则。原码/反码都需要额外的符号处理电路。
2. **零只有一个**：原码里 `+0`（00000000）和 `−0`（10000000）是两个编码，比较逻辑要特判；补码里全 0 唯一地表示 0，判断相等就是纯粹的位比较。
3. **负数自然扩展**：8 位的 −3（11111101）扩展到 16 位只需把符号位向左复制（1111111111111101）——「符号扩展」是一条硬件指令的事。

代价藏在下限：N 位补码能表示 −2ᴺ⁻¹ 到 2ᴺ⁻¹−1，**负数比正数多一个**。`INT_MIN`（−2³¹）没有正数对应物，于是 `-INT_MIN` 和 `abs(INT_MIN)` 都是**溢出 + UB**——`abs` 返回负数不是 libc 的 bug，是这个不对称性的直接后果。

| 类型          | 典型宽度 | 范围                                                      |
| ----------- | ---- | ------------------------------------------------------- |
| `char`      | 8 位  | −128 \~ 127（有符号时）                                       |
| `short`     | 16 位 | −32768 \~ 32767                                         |
| `int`       | 32 位 | −2147483648 \~ 2147483647（±21 亿）                        |
| `long long` | 64 位 | −9223372036854775808 \~ +9223372036854775807（±9.2×10¹⁸） |
| `size_t`    | 64 位 | 0 \~ 18446744073709551615                               |

> [!TIP]
> 记住两个量级就够了：`int` 装不下 25 亿（10 位手机号的规模就会炸），`int64_t` 装不下 9.3×10¹⁸（一秒一个整数也要用 292 年才数完）。凡是计数、累加、可能相乘的量，默认 `int64_t`；凡是字节长度、数组下标，用 `size_t`。

### 1.3 位运算：在补码上工作

位运算是 C 贴近硬件的名片，但它们的行为要从补码角度理解：

```c
int x = -8;
x >> 1;          // 算术右移（多数平台）：-4，符号位复制——不是除以 2 的「向下取整」
-1 >> 1;         // 还是 -1：全 1 右移补 1
(unsigned)-8 >> 1;  // 逻辑右移：高位补 0，得到巨大的正数
```

- **右移有符号负数是实现定义**（主流编译器都是算术右移，但标准没保证）；对无符号数是明确的逻辑右移。
- **左移有符号数进入符号位是 UB**；左移无符号数是回绕。
- **取模与位与的关系**：`x % 64 == x & 63` 只对无符号或非负数成立。对负数，`-1 % 64 == -1`（C99 起商向零取整），而 `-1 & 63 == 63`——两者不等，混用是真实 bug 来源。

## 2. 隐式转换：事故的第一大来源

C 允许不同类型直接混合运算，编译器按一套固定阶梯**悄悄**转换类型。这套阶梯设计于 1970 年代，今天的它制造的事故比其他任何语言特性都多。

### 2.1 整数提升：比 int 窄的先变 int

任何比 `int` 窄的整型（`char`、`short`、位域）参与运算前**先提升为 `int`**：

```c
uint8_t a = 200, b = 100;
uint8_t c = a + b;      // a、b 先提升为 int：200+100=300 溢出了吗？没有！
printf("%d\n", c);      // 44：300 回绕到 uint8_t 是在「赋值截断」时才发生
if (a + b > 255) ...    // 这里比较的是 int 300 > 255：为真
```

提升的存在意味着：**窄类型运算的中间结果比它本身宽**。这既救过人（上例的 `if` 判断反而正确），也坑过人——`~(uint8_t)0` 得到的是 `int` 的 −1 而不是 255，因为先提升再取反。

### 2.2 通常算术转换：宽者胜，无符号胜

两个不同类型的操作数相遇时，按「谁更能装下谁」统一到同一类型，规则浓缩版：

1. 都比 `int` 窄 → 都提升为 `int`；
2. 否则**如果有一个是无符号且宽度 ≥ 对方 → 统一为无符号**；
3. 否则统一为更宽的有符号类型。

第 2 条是黄金陷阱。`unsigned` 与 `int` 相遇，`int` **先转成 unsigned 再比较**：

```c
int a = -1;
unsigned b = 1;
if (a < b)          // ❌ 直觉：−1 < 1 为真
    printf("less\n");
// 实际：a 转成 unsigned = 4294967295，4294967295 < 1 为假
```

这个规则的杀伤力在有符号/无符号**混用**的接口边界上最大。真实的变体：

```c
size_t n = 0;
for (int i = n - 1; i >= 0; i--) ...   // n-1 是 size_t 回绕：巨大无符号数

int len = -1;
if (len < sizeof(buf))     // ❌ len 转成巨大的 size_t，检查形同虚设
    memcpy(dst, src, len); // 传进去的是 2⁶⁴−1 级别的长度
```

第二条还是 **CVE 制造机**：无数个「长度检查」漏洞的根源都是「有符号 int 的长度 vs 无符号 size\_t 的容量」比较。防法只有一条：**比较双方类型必须一致**——长度一律 `size_t`，入口处先检查负值再转无符号，并给编译器加 `-Wsign-compare`（已含于 `-Wextra`）。

### 2.3 赋值与传参：窄化截断

把宽类型赋给窄类型是**直接截断高位**（无符号）或**实现定义**（超出范围的有符号目标）：

```c
int x = 300;
int8_t y = x;           // 300 = 0x12C，截断得 0x2C = 44
double d = 3.99;
int i = d;              // 向零截断得 3（不是四舍五入！）
```

### 2.4 完整的事故清单（每条都来自真实代码）

```c
/* 1. 倒数循环：size_t 永远 >= 0 */
for (size_t i = n - 1; i >= 0; i--) { ... }        // 死循环
// 修法①：正向遍历；修法②：i != SIZE_MAX 当哨兵；修法③：int 下标 + 判断

/* 2. 中间结果溢出：先乘后除 */
int avg = (a + b) / 2;        // a+b 可能溢出（a、b 都接近 INT_MAX 时）
int avg2 = a + (b - a) / 2;   // 安全写法（二分查找的经典 bug）

/* 3. strlen 返回 size_t，与 int 比较 */
int i;
for (i = 0; i < strlen(s); i++) ...   // 能跑但每轮 O(n)；且 i 与 size_t 比较有告警
size_t len = strlen(s);               // 先存下来，比较双方同类型

/* 4. atoi 不报告错误 */
int v = atoi("12abc");      // 12，静默吞掉尾巴
long v2 = strtol(s, &end, 10);        // end 指向没吃掉的部分，errno 报范围错误
if (end == s || *end != '\0' || errno == ERANGE) /* 输入非法 */;

/* 5. char 的符号是实现定义的 */
char c = getchar();          // getchar 返回 int：EOF(-1) 装进 char 后「看起来像」
if (c == EOF) ...            // 合法字符 0xFF 也可能变成 −1，EOF 检测失效
int ch = getchar();          // ✅ 唯一正确姿势：用 int 接
```

> [!WARNING]
> 第 5 条值得单独记：**`char` 是 signed 还是 unsigned 由实现定义**（x86 上常是 signed，ARM 上常是 unsigned）。所以任何「拿 char 存介于 0~~255 的字节」的代码都有平台差异——处理原始字节一律用 `unsigned char` 或 `uint8_t`。而 `getchar` 返回 `int` 而非 `char`，正是为了把「合法字符 0~~255」和「EOF −1」区分开。

## 3. 浮点：IEEE 754 的精度账本

### 3.1 结构：科学计数法的二进制版

`float`（32 位）与 `double`（64 位）都由三段组成：**符号位、指数、尾数**。

```text
float :  [1 位符号][8 位指数][23 位尾数]   ≈ 7 位十进制有效数字
double:  [1 位符号][11 位指数][52 位尾数]  ≈ 16 位十进制有效数字
```

它表示的数是 (−1)^符号 × 1.尾数 × 2^(指数−偏置)。两个关键推论：

1. **可表示的数在数轴上不均匀**：指数决定「这一段数轴上相邻两个可表示数的间距」。0 附近极密，1 附近间距约 2⁻²³（float），十亿附近间距约 2⁻²³×2³⁰≈64（float）——大数字连整数都表示不了：`float f = 16777217.0f;` 存进去变成 16777216（2²⁴ + 1 超出了尾数能分辨的范围）。
2. **1.xxxxx 的「1」不占位**（规范化数的隐含前导位），所以 23 位尾数实际提供 24 位精度。

### 3.2 0.1 + 0.2 ≠ 0.3：完整的因果链

这不是「浮点数不精确」的玄学，而是一个可以完整推导的事实：

```text
1. 十进制 0.1 = 1/10。二进制里 1/10 是无限循环小数：0.000110011001100…（循环 0011）
2. 存入 64 位 double 必须在 53 位有效数字处截断 → 存的是一个「比 0.1 略大」的近似值
3. 0.2 同理被近似，且误差方向、大小都不同
4. 两者相加，结果再舍入一次 → 得到的字节模式和「0.3 的近似值」不同
5. 所以 0.1 + 0.2 == 0.3 为假，打印出来是 0.30000000000000004
```

由此推出浮点的四条纪律：

1. **永远不用 `==` 比较浮点**。用容差：`fabs(a - b) < 1e-9`；更专业的做法是比 ULP（最后一位单位）。容差要随数量级缩放：`fabs(a - b) <= DBL_EPSILON * fmax(fabs(a), fabs(b)) * 4`。
2. **金额不用浮点**。用整数的最小货币单位（分）或十进制库。`0.1 元` 在浮点里存不下，每天对账差一分钱的事故每年都在发生。
3. **float 与 double 的取舍**：默认用 double（16 位有效数字，绝大多数场景的误差可忽略）；float 只在「内存/带宽是瓶颈且精度损失可接受」时用（图形、机器学习）。混合计算时 float 会自动提升为 double，代价不大；但 float 累加百万次的误差会显著积累。
4. **大数吃小数**：`1e20 + 1.0 - 1e20 == 0.0`。double 只有 16 位有效数字，1e20 量级上的「1」在第 21 位，加法时直接被舍掉。做求和时先加小的、或用 compensated summation（Kahan 求和）：

```c
double kahan_sum(const double *a, size_t n) {
    double sum = 0.0, c = 0.0;          // c 收拢每次被舍掉的误差
    for (size_t i = 0; i < n; i++) {
        double y = a[i] - c;
        double t = sum + y;             // 低位在这里丢失
        c = (t - sum) - y;              // 把丢失的部分抓回来
        sum = t;
    }
    return sum;
}
```

### 3.3 特殊值：inf、nan 与 −0.0

IEEE 754 专门留了编码表示异常值，它们的行为必须像背乘法表一样背下来：

```c
double inf = 1.0 / 0.0;        // +inf（注意：这是浮点除法，合法）
double nan = 0.0 / 0.0;        // NaN
nan == nan;                    // false！NaN 与任何值比较都是「无序」
isnan(nan);                    // ✅ 判 NaN 只能用 isnan/isfpclassify
1.0 / -0.0;                    // -inf：存在负零，-0.0 == 0.0 为真但符号不同
DBL_MAX * 2;                   // inf：上溢；DBL_MIN / 1e300 → 下溢渐进变 0
```

与整型最大的差别：**浮点溢出不是 UB，是定义良好的 inf/NaN 流**。这既是恩惠（计算不会崩），也是陷阱（inf/NaN 会顺着公式一路污染下游，最后在输出端才被发现）。防御姿势：关键计算路径上 `assert(isfinite(x))`，或开启 `-ffast-math` 前想清楚——它会破坏 NaN/inf 语义换速度，科学计算慎用。

## 4. 显式转换与转换的边界

显式 cast 不创造魔法，只是「按目标类型的规则重新解读或换算」，边界行为必须知道：

| 转换              | 行为                     | 事故点                 |
| --------------- | ---------------------- | ------------------- |
| `int → int8_t`  | 截断高位                   | 静默改值                |
| `double → int`  | 向零截断；超出 int 范围是 **UB** | `(int)1e18` 未定义     |
| `负数 → unsigned` | 模 2ᴺ 回绕成大正数            | 长度检查漏洞              |
| `指针 → 整数`       | 必须用 `uintptr_t`        | 存进 int 在 64 位截断     |
| `浮点比较`          | 按 IEEE 754 全序（NaN 除外）  | NaN 使所有比较为假，排序算法可能崩 |
| `void* → T*`    | C 里可以隐式转（C++ 不行）       | 转错类型 = 别名违规 UB      |

`(int)round(x)` 与 `(int)x` 的差别值得写进代码规约：后者向零截断，`-0.5` 变 `0` 而不是 `-1`；财务、分页、取整逻辑里混用两者是常见 bug。

## 5. 类型选择的工程规约

把前面所有结论压缩成一张可直接执行的选择表：

| 场景               | 类型           | 理由                                 |
| ---------------- | ------------ | ---------------------------------- |
| 数组下标、长度、内存大小     | `size_t`     | 与 `sizeof`/`strlen`/`malloc` 天然同类型 |
| 一般计数、小整数         | `int`        | 平台最优宽度，溢出风险低时最简洁                   |
| 可能大数量累加/乘法       | `int64_t`    | 21 亿的上限在真实数据面前不堪一击                 |
| 位宽敏感（协议、文件格式、哈希） | `uintN_t`    | 位级行为必须可复现                          |
| 原始字节流            | `uint8_t`    | 与 `char` 的符号实现定义性划清界限              |
| 存指针的整数           | `uintptr_t`  | 与指针同宽的唯一保证                         |
| 货币、需要精确十进制       | `int64_t`（分） | 浮点不可用于金额                           |
| 物理量、概率、平均值       | `double`     | 16 位有效数字覆盖绝大多数科学计算                 |

再加四条纪律：

1. **比较双方类型必须一致**，不一致就显式转换并说明理由；打开 `-Wsign-compare` 让编译器盯着。
2. **窄类型（char/short）只用于省内存的结构体字段和协议字节**，参与运算时心里默念「先提升为 int」。
3. **所有外部输入的数值解析用 `strtol` 系**，`atoi/sscanf` 只配写玩具代码。
4. **不写依赖溢出的有符号运算**；需要回绕语义就明写 `unsigned`（或 C23 的 `ckd_add` 做检查加法）。

## 6. 陷阱清单

- **`size_t i >= 0` 恒真**：无符号倒数循环死循环。倒数用 `while (i-- > 0)` 或正向遍历。
- **有符号/无符号混合比较**：负数变巨数。接口边界先验负，再统一类型。
- **`(a + b) / 2` 溢出**：改 `a + (b - a) / 2`。
- **`(int)(x)` 与 `(int)round(x)` 混淆**：截断 vs 四舍五入，方向感完全不同。
- **`char` 存字节**：符号实现定义。原始字节用 `uint8_t`。
- **`getchar()` 的返回值用 char 接**：EOF 与合法字符 0xFF 混淆，读循环提前终止或永不终止。
- **浮点用 `==` 比较**：用容差或 ULP。
- **金额用 double**：对账差分。用整数分。
- **大数组求和从大到小加**：精度逐位丢失。小数先行或 Kahan。
- **`atoi` 当解析器**：不报错、不验范围。用 `strtol` + end 指针 + errno。
- **假设 `-INT_MIN` 有意义**：补码不对称，它是 UB。
- **负数取模当位运算用**：`-1 % 64 == -1` 而 `-1 & 63 == 63`。

## 7. 小结

- 类型 = 尺寸 + 解读方式；C 的一切类型行为都可以从「字节怎么读」推导。
- 补码统治有符号整数因为硬件零成本、零唯一、符号扩展免费；代价是负数多一个——`abs(INT_MIN)` 是 UB。
- 无符号溢出是定义良好的回绕，有符号溢出是 UB；两者相遇时**有符号转无符号**，这是长度检查漏洞与倒数死循环的共同根源。
- 整数提升让窄类型先变 int 再运算；中间结果的宽度常常比变量本身宽——它既能救你也能坑你。
- IEEE 754 的可表示数在数轴上不均匀；0.1+0.2≠0.3 是二进制无法表示 1/10 的必然结果。浮点纪律：不用 ==、金额不用浮点、默认 double、警惕大数吃小数与 inf/NaN 污染。
- 转换的边界：double→int 超范围是 UB、指针存 int 必截断、char 的符号性随平台。
- 类型选择规约的骨架：下标用 `size_t`、计数用 `int64_t`、字节用 `uint8_t`、金额用整数分、物理量用 `double`，解析外部输入只用 `strtol` 系。

> 思路 5 = 00000101，取反 11111010，加 1 得 11111011 = 0xFB。−128 = 0x80，取反 0x7F，加 1 得 0x80——回到 −128 自己：取负溢出，有符号溢出是 UB。程序里 `int8_t v = -128; printf("%d", -v);` 在补码机器上很可能打印 −128，但这正是「UB 表现得像没事」的例子。

**2.** 解释为什么 `for (size_t i = strlen(s) - 1; i >= 0; i--)` 是死循环，给出三种正确倒数遍历写法。

> [!TIP]
> 思路 size\_t 无符号，`>= 0` 恒真；i 减到 0 后再减一回绕成 SIZE\_MAX。写法①`for (size_t i = strlen(s); i-- > 0;)`（先比较后减）；写法②用 `int64_t` 下标；写法③正向遍历配合反向逻辑。顺带注意 `strlen(s)` 为 0 时 `strlen(s)-1` 本身就回绕了。

**3.** 0.1 + 0.2 != 0.3 的原因五步推导，你自己写出每一步；再解释为什么 `0.5 + 0.25 == 0.75` 恒成立。

> [!TIP]
> 思路 0.5 = 2⁻¹、0.25 = 2⁻²、0.75 = 2⁻¹+2⁻² 都是二的幂的组合——二进制下能**精确**表示，加法也不产生新的舍入。规律：凡是 2 的负幂的组合（0.5、0.25、0.75、0.125）浮点都精确；十进制的「看起来简单」的 0.1、0.2 都是无限循环。

**4.** 写一个「安全的 atoi」：解析十进制整数，处理前导空白、正负号、非法字符、溢出（用 `strtol`），并给出三个测试用例验证。

> [!TIP]
> 思路骨架：`errno = 0; long v = strtol(s, &end, 10);` 之后检查 `end != s`（至少吃掉一位）、`*end == '\0'`（全部消费）、`errno != ERANGE`（范围），最后检查落在 int 范围内再收窄。测试：`"  -42"` 成功、`"12x"` 拒绝、`"99999999999999999999"` 拒绝。

**5.** 下面的平均值函数在什么输入下出错？给出两种修法并比较。

```c
int midpoint(int a, int b) {
    return (a + b) / 2;
}
```

> [!TIP]
> 思路 a+b 可能上溢（如 a=b=INT\_MAX）。修法①`a + (b - a) / 2`（b−a 不溢出，但负数时向零截断方向与预期不同，注意）；修法②用无符号做中间步：`(int)(((unsigned)a + (unsigned)b) / 2)`；修法③升宽 `((int64_t)a + b) / 2`。这是二分查找被写错几十年的经典案例（Java 标准库曾带此 bug 九年）。

**6.** 用 float 累加 10⁷ 个 1.0f，与 double 累加比较；再实现 Kahan 求和对比误差，解释误差从哪一步开始。

> [!TIP]
> 思路 float 到 2²⁴≈1677 万后就加不动了（1.0 已经小于当前量级的 ULP），结果停在 16777216；double 全程精确到 1e7。Kahan 的 c 变量从第一次舍入就开始工作。结论：float 的 24 位尾数决定了「千万量级累加整数」是它的能力边界。

**7.** 解释为什么 `if (x > 0 && x + y > 0)` 不能可靠防止 `x + y` 溢出，而 `if (x > 0 && y > INT_MAX - x)` 可以。

> [!TIP]
> 思路第一种写法在 x+y 已经溢出之后才比较——溢出本身已是 UB，编译器可以假设它不发生并把整个检查优化掉。第二种用「不可能溢出的减法」提前预判，所有运算都安全。这个模式叫「预判式溢出检查」，配合 `__builtin_add_overflow`（C23 `ckd_add`）是现代 C 的标准姿势。
