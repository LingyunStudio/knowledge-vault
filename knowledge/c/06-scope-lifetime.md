同一个变量名，在 C 里其实同时挂着三个互相独立的属性：**作用域**（源代码的哪些行能看见这个名字）、**存储期**（运行时它的内存活多久）、**链接**（链接器把不同文件里的同名符号算不算同一个东西）。初学者把它们搅在一起，是因为 `static` 这一个关键字在 C 里同时插手了三个维度——**static 局部变量、static 全局变量、static 函数**是三个不同的东西。

把三个维度拆开，C 的所有「名字问题」——遮蔽、重复定义、undefined reference、全局状态失控——都能归位。

## 1. 作用域：词法上的可见区

C 有四种作用域，后两种知道即可，前两种决定日常代码：

| 作用域     | 范围                     | 谁拥有                 |
| ------- | ---------------------- | ------------------- |
| 文件作用域   | 声明处到文件末尾               | 全局变量、函数             |
| 块作用域    | `{}` 内                 | 局部变量、参数             |
| 函数作用域   | 整个函数体                  | 只有 goto 的标签         |
| 函数原型作用域 | 函数声明的参数列表内             | 参数名（可省略，纯文档）        |

### 1.1 遮蔽：内层名字藏住外层名字

块作用域里声明与外层同名的变量，内层看见的是新的：

```c
int total = 100;                     // 文件作用域

void report(void) {
    printf("%d\n", total);           // 100：看见全局
    int total = 5;                   // 遮蔽开始
    printf("%d\n", total);           // 5：内层自己的
    if (total > 0) {
        int total = 1;               // 再遮一层
        printf("%d\n", total);       // 1
    }
}
```

遮蔽合法但危险：**外层同名变量在改动时，内层可能纹丝不动**，代码读起来「对」跑起来错。工程规约：开 `-Wshadow`（GCC/Clang），遮蔽直接当警告处理；命名习惯上避免内层复用外层概念名。

### 1.2 名字查找：从内向外，一锤定音

C 的查找规则是从当前块向外层逐级找，**找到第一个就用**——不比较类型，不继续向外匹配。于是类型不匹配的遮蔽还能制造「编译错误出现在千里之外」的事故：

```c
double compute(double x);

void caller(void) {
    int compute(int);        // ❌ 遮蔽了外层声明，且签名冲突
    compute(3.5);            // 报错点在这里，根因在上一行
}
```

## 2. 存储期：运行时的寿命

| 存储期           | 内存位置  | 诞生与死亡              | 谁拥有                        |
| ------------- | ----- | ------------------ | -------------------------- |
| static（静态）    | data/BSS | 程序启动 → 程序结束        | 全局变量、static 变量              |
| automatic（自动） | stack | 进入块 → 退出块          | 普通局部变量、参数                    |
| allocated（分配） | heap | malloc → free      | malloc 家族的产物                 |
| thread（线程）    | 线程局部存储 | 线程启动 → 线程结束        | `_Thread_local` 修饰的变量（C11）  |

三种容易踩的语义：

**① 全局变量的初始化必须是编译期常量**。C 没有动态初始化（那是 C++ 的特性），全局与 static 变量的初始化在 C 里只能用常量表达式：

```c
int table_size = 64;                 // ✅ 常量
double ratios[] = {0.1, 0.5};        // ✅ 常量初始化器
int limit = 2 * table_size;          // ✅ 常量表达式：允许
int bad = strlen("hi");              // ❌ 非常量：编译错误（C++ 里却合法）
```

初始化为 0 的全局变量根本不占可执行文件空间（进 BSS，装载时清零）；初始化非零的进 data 段，值直接存在文件里。这解释了「全局数组 = {0} 不让文件变大」的现象。

**② static 局部变量：块作用域 + 静态存储期**。它只在函数里可见，但活整个程序生命周期，初始化只执行一次：

```c
int next_id(void) {
    static int counter = 0;          // 首次执行到此处时初始化一次
    return ++counter;                // 之后每次调用延续上次的结果
}
```

**③ automatic 的诞生点就是声明行**——C99 之后声明可以随时出现在块中间，变量从声明处可见、到所在块结束死亡。「在块开头统一声明所有变量」是 C89 的残留习惯，现代 C 的建议恰恰相反：**尽可能晚声明、声明即初始化**，缩小变量「有效但未初始化」的窗口。

## 3. 链接：不同文件里的同名符号算不算同一个

| 链接属性     | 含义                                | 谁拥有                        |
| -------- | --------------------------------- | -------------------------- |
| external | 全程序唯一：所有文件里的同名 external 符号是同一个实体   | 全局变量（默认）、函数（默认）             |
| internal | 只在本翻译单元内唯一：static 前缀               | `static` 全局变量、`static` 函数   |
| none     | 没有链接概念                            | 局部变量、参数                     |

### 3.1 extern：声明与定义的分工

全局变量跨文件共享的正确姿势是「头文件声明、源文件定义」：

```c
/* config.h —— 只有声明（extern 告诉编译器：定义在别处，别分配内存） */
extern int g_verbose;
extern const char *g_config_path;

/* config.c —— 唯一的定义（分配内存、初始化） */
int g_verbose = 0;
const char *g_config_path = "/etc/app.conf";

/* 其他 .c：#include "config.h" 后直接用 */
```

漏写 extern 的后果是头文件里的定义被多个 .c 包含 → `multiple definition`（GCC 10+ 默认 `-fno-common` 后直接报错；老工具链可能静默合并，更糟）。

`extern` 在函数上没有意义——函数声明默认就是 external 的：

```c
/* math_utils.h */
int vec_add(const double *a, const double *b, double *out, size_t n);
/* 头文件里的函数声明天然是「对外接口」；定义放 math_utils.c */
```

### 3.2 static：文件私有化

给全局变量或函数加 `static`，它就从「全程序可见」收缩为「本文件私有」：

```c
/* parse.c */
static int skip_space(const char **p) { ... }   /* 内部工具：别的文件看不见 */

int parse_expr(const char *s) {                 /* 对外接口：不写 static */
    skip_space(&s); ...
}
```

这一对组合是 C 的「模块系统」：**不带 static 的是导出接口，带 static 的是私有实现**。它的三个实际收益：

1. **防命名冲突**：两个文件都可能有 `static int helper`，互不干扰；不带 static 就撞车。
2. **帮助优化器**：internal 链接的函数可以被内联、删除、改签名，不影响外部（external 函数理论上要遵守 ABI）。
3. **防误用**：接口面收窄后，调用方只能看见该看见的东西。

> [!TIP]
> 检验一个 .c 文件的封装质量：`nm file.o | grep ' T '` 列出所有 external 函数符号——这个列表越长，模块越失控。健康的模块通常只有少量 T 符号（真正的接口）和大量 t 符号（static 私有）。

### 3.3 头文件里的 static 函数：一个隐蔽的坑

在头文件里写 `static` 函数（想「内联小工具」）的后果：**每个包含它的 .c 都获得一份独立副本**——逻辑上无害但空间浪费，且没人调用时 `-Wunused-function` 会刷屏。正确姿势：小工具想跨文件共享，写成普通外部函数放 .c 里；纯内联用 `static inline`（C99 语义下不产生外部符号，是最干净的形式）。

## 4. 三个维度的不对齐：事故的地图

三个维度可以独立组合，而**所有经典事故都发生在它们不对齐的地方**：

```text
              作用域(谁能看见)      存储期(活多久)       对齐吗？
全局变量        文件(或全程序)        整个程序            ✅
static 局部    所在块               整个程序            ⚠️ 可见期 << 存活期
局部变量        所在块               所在块             ✅
malloc 内存    谁记得指针谁可见        free 前            ⚠️ 可见期 < 存活期（泄漏）
悬垂指针        ——                ——                ❌ 存活期已尽，可见期还在
```

- **static 局部变量**：函数返回后变量还活着，但作用域已收回——下次进函数又看得见。功能上它是一个「伪装成局部的全局」。
- **堆内存泄漏**：指针丢了但内存没释放——存储期远超作用域。泄漏检测见[第 7 篇](07-dynamic-memory.md)。
- **悬垂指针**：反向错位——作用域还在（指针变量看得见），存储期已尽（指向的内存死了）。这是[第 4 篇](04-pointers.md)三类事故里最阴的一类。

「static 局部变量是伪装的全局」值得展开，因为它引出 C 里最重要的架构话题——**全局可变状态**：

```c
/* 静态状态的问题：函数不再是纯函数 */
double running_avg(double x) {
    static double sum = 0;
    static size_t n = 0;
    sum += x; n++;
    return sum / n;                  /* 同一输入，不同结果——取决于历史调用 */
}
```

这个函数的三个工程代价：**不可重入**（两个线程同时调用就是数据竞争）；**不可测试**（测试间状态泄漏，用例顺序影响结果）；**不可组合**（想同时维护两条平均值就要复制整个函数）。修法是显式传状态：

```c
typedef struct { double sum; size_t n; } Avg;
double avg_next(Avg *a, double x) { a->sum += x; return ++a->n ? a->sum / a->n : 0; }
```

全局/static 可变状态不是禁区（日志级别、配置缓存是合理用例），但**每个用例都要过「重入、测试、并发」三问**。多线程下的 static 初始化与 `_Thread_local` 的适用场景，见[第 13 篇](13-tools-debugging.md)。

## 5. 头文件工程：声明与定义的分界线

多文件工程的全部规则可以压缩成一张表——**头文件里允许放什么**：

| 内容                | 允许？ | 理由                                |
| ----------------- | --- | --------------------------------- |
| 函数声明              | ✅   | 声明不产生符号，可无限重复                      |
| extern 变量声明       | ✅   | 同上                                 |
| 类型定义（struct/enum/typedef） | ✅   | 类型不产生符号，可重复（需一致）                   |
| 宏定义               | ✅   | 预处理期展开                             |
| static inline 小函数 | ✅   | 每单元一份副本，无外部符号                      |
| **函数定义**（函数体）     | ❌   | 多个 .c 包含 → multiple definition     |
| **全局变量定义**（无 extern） | ❌ | 同上                                 |

include guard 是防重复包含的标配（一个头文件被同一翻译单元包含两次会因类型重定义报错）：

```c
#ifndef MYAPP_CONFIG_H
#define MYAPP_CONFIG_H
/* ... 声明 ... */
#endif /* MYAPP_CONFIG_H */
```

循环包含（a.h 包含 b.h、b.h 包含 a.h）用**前置声明**解开：头文件里只需要「知道有这个类型」时，声明 `struct Player;` 而不是包含它的头文件。指针与前置声明就能配合；需要完整类型（访问成员、sizeof）才真正 include。

## 6. 陷阱清单

- 头文件里定义全局变量：multiple definition；声明用 extern，定义放 .c。
- 函数定义写进头文件（无 inline）：每个包含者一份定义，链接撞车。
- 内层遮蔽外层同名变量：开 `-Wshadow`；不同层避免重名。
- static 局部变量当缓存/计数器：函数失去可重入与可测试性；显式传状态。
- 全局变量用运行时值初始化：C 只接受常量表达式；运行时初始化在 main 开头显式做。
- 忘记 include guard：重复包含导致类型重定义错误。
- 头文件里的 static 函数：每单元一份副本 + 未用告警；改用 `static inline` 或移入 .c。
- tentative definition（`int x;` 出现在头文件被两个 .c 包含）：老工具链静默合并，新工具链报错——永远写 `int x = 0;` 在 .c、`extern int x;` 在 .h。
- 循环包含：用前置声明解开，只 include 真正需要的头。

## 7. 小结

- 名字的三个维度：作用域（词法可见区：文件/块）、存储期（运行寿命：static/automatic/allocated/thread）、链接（符号归属：external/internal/none）。static 关键字分别作用于三者，是三个不同的功能。
- 遮蔽规则「从内向外找到就用」配合 `-Wshadow` 管理；C 的查找不做类型匹配。
- 全局与 static 变量的初始化只接受常量表达式（无动态初始化）；static 局部变量是块作用域 + 静态存储期 + 一次初始化，本质是伪装成局部的全局，代价是重入性、可测试性、并发安全。
- 链接属性定义 C 的模块系统：无 static = 导出接口，static = 私有实现；extern 变量「头声明、源定义」是跨文件共享的唯一正确形态。
- 经典事故全部发生在「作用域与存储期不对齐」处：static 局部（可见期短于存活期，预期内）、泄漏（同上，失控）、悬垂（存活期先于可见期结束，致命）。
- 头文件只放声明、类型、宏与 static inline；include guard 防重复包含，前置声明解循环依赖。

## 8. 练习

**1.** 写出下面每行打印的值，并解释每一步发生了什么遮蔽。

```c
int x = 1;
void f(void) {
    printf("%d\n", x);        /* A */
    int x = 2;
    printf("%d\n", x);        /* B */
    {
        extern int x;
        printf("%d\n", x);    /* C */
    }
}
```

> [!TIP]
> 思路 A 打印 1（块声明前看见全局）；B 打印 2（局部遮蔽）；C 打印 1——`extern int x;` 是「引用全局的块内声明」，把全局重新引入当前作用域。这个技巧极少用，但它是「声明可以出现在块内」与链接属性的联合考试题。

**2.** 把第 4 节的 `running_avg` 改造成线程安全且可测试的版本，给出两种方案（显式状态结构、`_Thread_local`），并比较适用场景。

> [!TIP]
> 思路方案①传入 `Avg*`，状态所有权归调用方，天然线程隔离、可测；方案②把 static 换成 `static _Thread_local`——每线程独立一份，重入问题解决，但「测试间状态泄漏」仍在（同线程连续调用共享历史），且状态总量随线程数增长。工程默认选①，②适合「每个线程一份全局配置」类场景。

**3.** 有两个 .c 文件都想用同一个日志级别变量 `log_level`，写出全部代码：头文件、两个 .c 的相关片段，并说明如果把 `int log_level;` 直接放进头文件会发生什么。

> [!TIP]
> 思路 log.h 写 `extern int log_level;`，恰一个 .c（如 log.c）写 `int log_level = 2;`。放进头文件：GCC 10+ 链接报 multiple definition；老工具链（-fcommon）两个翻译单元的符号静默合并成同一个——「碰巧能用」的假象，一旦某处初始化非零值就出现初始化归属不明的问题。

**4.** 用 `nm` 验证 static 的效果：写一个 .c 内含一个外部函数与两个 static 函数，编译后列出符号表，解释 T/t 区别，并统计接口面。

> [!TIP]
> 思路外部函数是大写 T（Text 段、external 链接），static 函数是小写 t（internal）。接口面 = T 符号数；若一个模块有十几个 T，考虑收窄：哪些真的需要被外部调用？把剩下的改成 static，重复编译观察汇编差异（static 函数可被内联后删除）。

**5.** 解释下面代码的输出为什么是 `0 1 2 3` 而不是 `1 2 3 4`，并指出这个行为的名字。

```c
int counter(void) {
    static int n;
    return n++;
}
int main(void) {
    for (int i = 0; i < 4; ++i) printf("%d ", counter());
}
```

> [!TIP]
> 思路 `static int n;` 无初始化器 → 进 BSS，启动时清零（这就是「未初始化 static 变量自动为 0」的标准依据，与未初始化局部变量的 UB 形成对照）。`n++` 返回旧值再自增，所以首调返回 0。行为名：static 存储期 + 后缀自增语义。

**6.** 设计一个 C 模块的接口：一个固定容量环形缓冲区（ring buffer），给出 ring.h（类型 + 函数声明）与 ring.c（static 私有辅助）的骨架，遵守本篇的模块规约。

> [!TIP]
> 思路 ring.h：不透明指针 `typedef struct ring ring;` + `ring *ring_new(size_t cap); void ring_free(ring *); bool ring_push(ring *, int v); bool ring_pop(ring *, int *out);`。ring.c：struct 定义私有（指针字段 head/tail/count/cap），内部 `static size_t advance(size_t i, size_t cap)`。考点：不透明类型把存储期与布局细节全部锁进 .c，接口面只有 5 个函数——这是 C 里最接近「类」的模块形态。
