C 的控制流只有 if、switch、三种循环和 goto——半小时就能学完全部语法。但这一篇依然值得用整篇的篇幅，因为两件事把「语法都会」和「真的会写」分开了：**求值顺序**（哪些表达式里的先后是保证的、哪些是编译器随意的）和**未定义行为**（哪些写法让整段代码失去了任何保证）。前者决定了「这行代码到底算了什么」，后者决定了「这段代码到底还算不算数」。

## 1. 运算符：优先级不必背，三处必须防

完整优先级表可以查手册，真正需要刻进手指的是三个高频出错点：

```c
/* 1. 位运算的优先级低于比较运算 —— 反直觉第一名 */
if (flags & MASK == 0)      // ❌ 解析为 flags & (MASK == 0)，MASK==0 时恒取 flags&0=0
if ((flags & MASK) == 0)    // ✅ 位运算永远加括号

/* 2. 移位低于加法 */
1 << 2 + 3                  // ❌ 是 1 << 5 = 32，不是 (1<<2)+3 = 7

/* 3. 赋值不是「最低」的：三目、逗号更低 */
x = cond ? a : b = c        // ❌ 语法错误：解析为 x = (cond ? a : (b = c)) 的歧义
```

其他容易含糊的规则一句话版：单目 > 双目；算术 > 移位 > 关系 > 相等 > 位与 > 位异或 > 位或 > 逻辑与 > 逻辑或 > 三目 > 赋值 > 逗号。**任何混合两种以上运算符的表达式，写括号**——括号不花钱，读错代码要花钱。

## 2. 求值顺序：只有五个运算符有保证

这是 C 表达式里最深的一个坑。**除了下面五个场景，C 不保证任何求值顺序**：

| 场景                      | 保证                             |
| ----------------------- | ------------------------------ |
| `a && b`                | 先 a 后 b，且 a 为假时不求值 b           |
| `a \|\| b`              | 先 a 后 b，且 a 为真时不求值 b           |
| `a ? b : c`             | 先 a，再在 b/c 中选一个                |
| `a, b`（逗号运算符）           | 先 a 后 b                        |
| 函数调用 `f(a, b)` 的**函数体** | 进入函数体前，所有实参求值完毕（实参**之间**顺序仍不定） |

除了这五个地方，编译器想先算什么就先算什么。于是：

```c
i = i++ + 1;         // ❌ UB：i 被写两次且中间没有顺序保证
a[i] = i++;          // ❌ UB：读 a[i] 的 i 和 i++ 的写无顺序
printf("%d %d", ++i, ++i);  // ❌ 两个实参的求值顺序不定
f() + g();           // f 和 g 谁先跑不确定——两个都有副作用时就是 bug
```

C11 用「先序于」（sequenced before）取代了旧标准的「序列点」，规则更精确但结论相同：**一个表达式里，若同一对象被修改两次、或被修改的同时又被读取（且不是为了决定新值），就是 UB**。

有副作用时的唯一安全姿势：**拆成多条语句**。副作用的先后意图既然在你脑子里，就把它写进代码结构里。

> [!NOTE]
> 「实参之间顺序不定」有一个实际应用面：`printf("%d %d", f(), g())` 里若 f、g 都改全局状态（日志、errno），输出顺序不可依赖。这在调试「日志顺序不对」的问题时是常见原因。

### 2.1 短路求值：C 里最重要的惯用法

`&&`/`||` 的顺序保证不是语法细节，而是 C 一半代码骨架的承重墙——**守卫模式**：

```c
// 先判空再解引用：短路保证了 p 为 NULL 时绝不执行 p->next
if (p != NULL && p->next != NULL) ...

// 按代价从低到高排列检查
if (len > 0 && buf[0] == '{' && parse_header(buf) != NULL) ...

// 失败即退出的管道
FILE *f = fopen(path, "r");
if (f == NULL || fread(buf, 1, n, f) < n) {
    fprintf(stderr, "read failed\n");
    return -1;
}
```

第三种写法把「打开失败」和「读失败」合并进一个分支，是 C 错误处理的基本单元（[第 12 篇](12-errors-robustness.md)会把它与 goto cleanup 组合成完整模式）。

## 3. 控制流：语法全表与惯用法

### 3.1 if 与悬挂 else

else 总是配**最近的未配对 if**。嵌套时靠缩进判断归属必然出错，规则只有一条：**嵌套 if 必须配花括号**。

```c
if (a > 0)
    if (b > 0) printf("both\n");
else printf("?");        // ❌ 这个 else 属于内层 if，缩进是谎言
```

「相等比较写成赋值」是另一类永恒的坑：`if (x = 5)` 合法（值为 5 为真）。防御惯例是把常量放左边 `if (5 == x)`（Yoda 条件），但更现代的做法是开 `-Wall`（GCC 对赋值条件有 `-Wparentheses` 提示）。两个都要，但**别让 Yoda 条件伤害可读性**——它只对「常量与变量相等」有效，对两个变量无能为力。

### 3.2 switch：穿透是特性还是 bug

switch 的 case 只决定「从哪里跳进去」，不自动结束——这就是**穿透**（fallthrough）。三件事必须分清：

```c
switch (op) {
case '+':
    result = a + b;
    break;                       // 忘写 break = 穿透到下一 case（最高频 bug）
case '-':                        // 空壳 case：合法且常用——几个值共享一段逻辑
case '*':
case '/':
    result = apply(op, a, b);
    break;
default:
    result = 0;                  // default 不是必须放最后，但放最后最可读
}

/* 故意穿透：标注意图，让编译器和读者都闭嘴 */
switch (level) {
case 3:
    enable_l3();                 /* fall through */
case 2:
    enable_l2();                 /* fall through */
case 1:
    enable_l1();
    break;
}
```

现代编译器（GCC/Clang 的 `-Wimplicit-fallthrough`）会对未标注的穿透告警，`[[fallthrough]]` 属性（C23）是标准化的标注。**穿透要么删掉，要么标注**——中间状态的代码十年后没人敢动。

还有一个隐性限制：case 常量必须是**编译期整型常量**，所以 `case some_var:` 编不过。需要按字符串分支时 switch 无能为力（`strcmp` 不是常量表达式），老老实实 if 链或函数表（[第 9 篇](09-function-pointers.md)）。

### 3.3 goto：在 C 里它有正当职业

goto 滥用会造出面条代码，这个共识没错。但 C 没有异常、没有 defer、没有析构函数，**多层资源释放**的干净写法就是 goto：

```c
int load_config(const char *path) {
    int ret = -1;
    FILE *f = fopen(path, "r");
    if (!f) return -1;

    char *buf = malloc(4096);
    if (!buf) goto out_close;            // 只需释放 f

    if (fread(buf, 1, 4096, f) == 0) goto out_free;
    if (!parse(buf)) goto out_free;

    ret = 0;                             // 全部成功
out_free:
    free(buf);
out_close:
    fclose(f);
    return ret;
}
```

Linux 内核与几乎所有 C 大型项目都用这个模式：**goto 只向下跳到统一的清理出口**。它比重复写 free 块可靠（新增资源时只加一个标签）、比嵌套 if 层次浅。这是 C 里 goto 的唯一推荐姿势；向上跳、跨函数跳、跳进循环体，都是真正该被禁止的用法。

> [!TIP]
> 想要「离开作用域自动清理」而不想用 goto：C 有一个 GNU/Clang 扩展 `__attribute__((cleanup))`，C23 之外的主流编译器都支持。但它是非标准魔法，可移植项目仍以 goto cleanup 为事实标准。

### 3.4 循环与一个惊人的规则

三种循环的取舍一目了然：已知次数用 for，先判后做用 while，先做后判用 do-while（do-while 在宏定义里还有一个特殊用途，见[第 11 篇](11-preprocessor.md)）。真正惊人的是 C11 加的一条规则：

> 没有 I/O、没有 volatile 访问、且不做任何事情的循环，编译器可以**假设它必然终止**——于是「空转等待」可能被整体删除。

```c
while (!ready) {}              // ❌ -O2 下可能被删成没有：ready 非 volatile
while (!ready) ;               // 同上，空语句也救不了
while (!ready) __asm volatile("" ::: "memory");   // 阻止优化（内联汇编门槛高）
while (*(volatile int *)&ready == 0) ;            // volatile：每次真读内存
```

正确的工程答案是不写裸自旋：跨线程等待用 C11 `<threads.h>` 或平台的条件变量；真正的硬件轮询寄存器天然是 volatile（嵌入式场景）。这个例子预告了一个主题：**C 的「看起来在干活」和「真的在干活」之间隔着优化器**，而 volatile、原子操作这些关键字就是和优化器谈判的合同条款。

## 4. 未定义行为：一张分级清单

[第 1 篇](01-c-model.md)讲了 UB 的原理（编译器有权假设它不发生），这一篇把常见的 UB 按危害排序汇总，作为全书其他篇目的索引：

| 层级  | 行为                     | 典型场景                     | 去处                                                    |
| --- | ---------------------- | ------------------------ | ----------------------------------------------------- |
| ★   | **越界访问**（数组/指针越界）      | 下标计算错误、`strlen` 差 1      | [第 4 篇](04-pointers.md)、[第 5 篇](05-arrays-strings.md) |
| ★   | **解引用空/悬垂指针**          | 返回局部地址、free 后使用          | [第 4 篇](04-pointers.md)、[第 7 篇](07-dynamic-memory.md) |
| ★   | **缓冲区溢出**              | `strcpy/sprintf/gets` 家族 | [第 5 篇](05-arrays-strings.md)                         |
| ★★  | **有符号整数溢出**            | `(a+b)/2`、移位构造           | [第 2 篇](02-types.md)                                  |
| ★★  | **未初始化读取**             | 忘记初始化的结构体字段、malloc 未填满   | [第 7 篇](07-dynamic-memory.md)                         |
| ★★  | **求值顺序违规**             | `i++ + i++`、实参副作用        | 本文第 2 节                                               |

| ★★★ | **数据竞争**               | 多线程无同步共享变量               | [第 13 篇](13-tools-debugging.md)                       |

### 4.1 为什么「看起来能跑」更危险

UB 的表现分三种：崩溃（最好）、静默出错（危险）、**恰好正确**（最危险）。第三种来自「今天这台机器、这个编译器、这个优化级别下，UB 恰好无害」。它带来的工程后果是：

- 换编译器版本（优化器更新后对 UB 的利用更激进）→ 上线即崩；
- 加一行无关代码，打乱栈布局 → 覆盖某块「看似还好」的内存 → 玄学 bug；
- `-O0` 测试全过、`-O2` 交付失败——因为优化器在 `-O2` 才把「假设 UB 不发生」用足。

所以 C 的测试纪律是：**必须在开启 sanitizer 和优化的配置下测试**（`-O2 -fsanitize=address,undefined`），而不是「跑通了就行」。

### 4.2 两个「人人都会踩」的特例

**除零的分级**：整数除法 `x / 0` 是 UB；但**浮点**除以零是定义良好的 ±inf/NaN（[第 2 篇](02-types.md)）。同一个 `/` 运算符，两种类型两种命运。

**移位的边界**：`x << n` 要求 n 在 `[0, 位宽)` 内且结果不溢出（有符号时）。`1 << 32` 在 32 位 int 上是 UB——而且**编译器在常量折叠时报错、运行时却静默给出平台相关结果**，这种「编译期严、运行期松」的错位让 bug 在测试里躲过。用类型系统防它：移位位数用无符号类型表达，且永远先验证范围。

```c
uint32_t shift_left(uint32_t x, unsigned n) {
    assert(n < 32 && "shift count out of range");
    return n < 32 ? (x << n) : 0;
}
```

## 5. 表达式的正确姿势：把规则翻译成习惯

1. **混合运算加括号**，尤其是位运算与比较混排。
2. **副作用不与其他东西共处一行**：`i++` 单独写，不塞进其他表达式。
3. **守卫顺序 = 短路顺序**：先廉价后昂贵，先判空后解引用，先验长度后取下标。
4. **switch 的穿透要么删除要么标注**；default 必须写，哪怕只放 `assert` 和 abort——新增枚举值时它会替你抓漏网。
5. **goto 只用于向下跳到清理出口**；其他跳转一律拆函数。
6. **开 `-Wall -Wextra -Werror`**：这一章的绝大多数 UB 与运算符错误，编译器其实都会喊——问题从来是没人听。

## 6. 陷阱清单

- `flags & MASK == 0`：位运算优先级低于比较，必须加括号。
- `i = i++ + 1`、`a[i] = i++`、`f(i++, i++)`：同一表达式内写读交错，UB。
- `if (x = 5)`：赋值当条件，恒真；开警告。
- switch 忘 break：静默穿透；故意穿透必须注释标注。
- 空的忙等待循环：C11 下可被优化器整体删除；用 volatile/原子/条件变量。
- 整数除零是 UB，浮点除零是 inf：同符号不同命。
- `1 << 32`、`x << 负数`：移位位数越界，UB。
- 未初始化的局部变量：读取是 UB，值是「恰好在那里的垃圾」——声明即初始化。
- 悬挂 else：嵌套 if 必须配花括号。
- `abs(INT_MIN)`、`INT_MIN / -1`：补码不对称造成的溢出，UB。

## 7. 小结

- 优先级表不用背，三个高频点必须防：位运算低于比较、移位低于加法、三目与赋值的边界；拿不准就加括号。
- 只有 `&&`、`||`、`?:`、逗号和函数体入口提供求值顺序保证；其余场景副作用的先后完全交给编译器。同一表达式内对同一对象的重复写/读写交错是 UB。
- 短路求值的守卫模式（先判空后解引用、先廉价后昂贵、失败即退出）是 C 错误处理与防御式编程的骨架。
- goto 在 C 里的正当职业只有一个：多层资源释放时向下跳到统一清理出口。switch 穿透要么删除要么显式标注。
- C11 允许优化器删除「无副作用且可能不终止」的循环——忙等待必须用 volatile、原子或阻塞原语。
- UB 分级清单是全书的索引：越界与悬垂最常见，溢出与求值顺序次之，别名与数据竞争最深。「测试通过」必须在 `-O2` + sanitizer 的配置下才算数。

## 8. 练习

**1.** 求值顺序：用两个各自打印一行并返回值的函数做实参调用 `f(g(), h())`，在不同编译器/优化级别下观察顺序。结论是什么？

> [!TIP]
> 思路 GCC 与 Clang 可能给出不同顺序，同一编译器不同版本也可能变。结论：实参间顺序是「未指定」，任何依赖它的代码都是错的。需要顺序就先算进具名变量再传。

**2.** 把下面的「单行炫技」拆成安全语句，并指出原来的问题。

```c
*x++ = *y++ + *z++;
```

> [!TIP]
> 思路两个自增有顺序问题吗？`*y++` 与 `*z++` 修改的是 y、z 两个对象，互不冲突，合法；但若 x 与 y 指向同一数组且区间重叠（如 memcpy 的别名问题），行为未指定/UB。拆开后每个动作一目了然，也便于加边界检查。

**3.** 实现一个「跳表式清理」的文件解析函数：打开文件、分配缓冲区、解析、成功或失败都要正确释放资源。故意在每一层制造失败，验证所有路径都无泄漏（配合 `-fsanitize=address`）。

> [!TIP]
> 思路 goto cleanup 模式（见 3.3 节示例）。ASan 的 LeakSanitizer 会在退出时报告泄漏路径。测试矩阵：fopen 失败 / malloc 失败 / fread 失败 / parse 失败 / 全部成功，五条路径都必须干净。

**4.** 解释为什么 `while (!flag) ;` 在 `-O2` 下会变成死循环或空操作，而 `while (*(volatile int *)&flag) ;` 不会。真正的多线程等待应该怎么写？

> [!TIP]
> 思路优化器看到 `flag` 无 volatile/原子限定、循环体无副作用，按 C11 6.8.5p6 有权假设循环终止，于是把读操作提出循环或整个删除。volatile 强制每次真实访存。多线程正确姿势是 C11 `atomic_bool` + `cnd_wait` 条件变量——自旋既烧 CPU 又有可见性问题。

**5.** 写一个函数 `int clamp(int v, int lo, int hi)`，要求任何输入（包括边界值的极端组合）都不触发 UB。测试 `clamp(INT_MIN, INT_MIN, INT_MAX)` 一类边界。

> [!TIP]
> 思路朴素写法 `if (v < lo) return lo; if (v > hi) return hi; return v;` 本身安全（纯比较），但要防止调用方传 `lo > hi` 的契约破坏。引申：`lo + (v - lo) % (hi - lo)` 一类的「聪明写法」在 INT\_MIN 处全是 UB。教训：边界函数的正确性来自「只做不会溢出的运算」。

**6.** 在 Compiler Explorer 上对比 `for (int i = 0; i < n; ++i) sum += i;` 在 `-O0` 与 `-O2` 的汇编输出，解释你看到的差异。

> [!TIP]
> 思路 `-O2` 下优化器识别出等差数列求和公式，把 O(n) 循环折叠成 O(1) 的 `n*(n-1)/2`（乘法+移位）。这直观展示了「编译器有权重写代码，只要可观测行为相同」——而当 UB 出现时，「可观测行为相同」的约束就松绑了。
