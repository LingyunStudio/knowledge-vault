学 C 的真正门槛不是指针语法，而是脑子里缺一张「机器实际在干什么」的地图。Python 帮你把对象放在堆上、把类型记在对象头里、把内存回收藏在运行时里；C 把这一切全部掀开：**类型只是对一段字节的解读方式，内存是一排编了号的字节，编译器把你的代码逐字翻译成机器指令**。没有人替你管理任何东西——这既是 C 的力量来源，也是它所有事故的来源。

这一篇先建立三张底图，后面十三篇全部铺在它们上面：**翻译模型**（你的代码如何变成可执行文件）、**内存模型**（程序运行时字节放在哪里）、**契约模型**（标准承诺什么、不承诺什么）。这三张图立住了，指针、内存管理、链接这些「难点」都只是图上的局部放大。

## 1. C 的定位：一笔清醒的交易

1972 年 C 为重写 UNIX 而生，它的设计目标今天一个字都没变：**用一门高级语言的写法，产出接近手写汇编的机器码**。为了这个目标，C 做了几个延续至今的决策：

| 决策                 | 换来的好处                        | 付出的代价                      |
| ---------------- | ----------------------------- | --------------------------- |
| 极小的运行时（几乎无库依赖）  | 能写操作系统、驱动、嵌入 8 位单片机           | 没有垃圾回收、没有边界检查、没有运行时异常       |
| 类型系统只到「字节大小」这一层 | 编译器极简单，程序员完全控制布局              | 类型错误大多不报错，靠 UB 条款甩锅给程序员     |
| 直接暴露指针           | 可以精确操作内存、写零开销的数据结构            | 野指针、越界、悬垂成为半个世纪的事故来源        |
| 没有内建字符串/数组长度     | 数组就是连续字节，零包装开销                | 缓冲区溢出成为安全漏洞的头号来源            |
| 大量行为留给实现或未定义     | 编译器可以为每个平台生成最优代码              | 同一段代码在不同编译器/优化级别下表现不同       |

理解这张表比记住任何语法都重要。C 不是「有缺点的现代语言」，而是一台**刻意不装护栏的机床**：它的每个「缺点」都是某种自由的另一面。你写 C 的时候，实际上是在说「我知道每个字节在干什么」——说错了，机器不会拦你。

> [!NOTE]
> C 至今统治的领域恰好是这张表优势最大的地方：操作系统内核、语言运行时（CPython、Lua）、数据库引擎（SQLite、PostgreSQL）、嵌入式固件、高频交易系统。反过来，业务逻辑、字符串密集的应用、需要快速迭代的 Web 服务，用 C 是自讨苦吃——选 C 之前先问一句：**我真的需要控制到字节吗？**

## 2. 翻译模型：你的代码经历的四个阶段

`gcc hello.c -o hello` 一条命令背后是四个完全独立的阶段。亲手把每个阶段拆开看一次，是理解 C 的第一课：

```bash
gcc -E hello.c -o hello.i    # 1. 预处理：展开 #include 和宏，输出仍是 C 代码
gcc -S hello.i -o hello.s    # 2. 编译：C 翻译成汇编，输出人类可读的汇编
gcc -c hello.s -o hello.o    # 3. 汇编：汇编翻译成机器码，输出目标文件
gcc hello.o -o hello         # 4. 链接：把目标文件和库拼成可执行文件
```

### 2.1 预处理：文本替换，与 C 语言无关

预处理器只做**字面文本操作**：把 `#include <stdio.h>` 替换成头文件的全文（几万行），把宏替换成展开后的文本。它不理解 C 的语法，不认识变量，更不做类型检查。

```c
#include <stdio.h>          // ← 变成 stdio.h 的全文粘贴进来

#define SQR(x) x * x         // ← 纯文本替换

int main(void) {
    int r = SQR(2 + 3);      // 展开成 2 + 3 * 2 + 3 = 11，不是 25！
    return r;
}
```

预处理后的 `hello.i` 有几千行——绝大部分来自 `stdio.h` 的粘贴。这个阶段的所有陷阱（宏展开的优先级、重复包含、条件编译）单独放在[第 11 篇](11-preprocessor.md)讲。

### 2.2 编译：翻译单元是 C 的「最大作用域」

编译器一次只看**一个 .c 文件展开头文件后的整体**，这个整体叫**翻译单元**（translation unit）。这是 C 里最重要的组织概念：

- 函数和变量在每个翻译单元里**定义**（分配存储）或仅**声明**（告诉编译器「这东西在别处，长这样」）。
- 编译器对 `extern` 声明的符号只检查调用姿势是否匹配声明，**不检查定义是否真的存在、类型是否真的一致**——这事归链接器，而链接器的检查能力弱得多。
- 所以「两个 .c 文件里同名函数签名不一致」这类错误能一路绿灯跑进运行时。预防手段在[第 6 篇](06-scope-lifetime.md)和[第 10 篇](10-header-linking.md)。

```bash
gcc -S -O2 -masm=intel hello.c -o hello.s   # 看编译器生成的汇编
gcc -O2 -fverbose-asm hello.c -S -o - | less  # 带注释的汇编
```

能大致读懂编译器吐出的汇编（哪怕只看函数名和调用），你的调试能力会上一个台阶：很多「不可能发生」的 bug，在汇编层面一眼就能看穿——比如优化把变量放进寄存器导致断点看不到值，比如空循环被整体删除。

### 2.3 汇编与目标文件：符号的仓库

汇编器产出**目标文件**（.o / .obj）。它已经是机器码，但不是完整程序——它内部是一张**符号表**：

```bash
$ gcc -c math_utils.c && nm math_utils.o
0000000000000000 T vec_add        ← T：本文件定义（Text 段）
                 U cos            ← U：未定义，等着链接器去别处找
0000000000000040 T vec_dot
0000000000000000 D global_tol     ← D：已初始化的全局变量（Data 段）
0000000000000004 B counter        ← B：未初始化的全局变量（BSS 段）
```

`U`（undefined）符号就是目标文件留下的「欠条」：`vec_add` 里调用了 `cos`，但 `cos` 的机器码不在这里。补齐欠条正是下一步链接的工作。

### 2.4 链接：把欠条对上号

链接器扫描所有目标文件和库，把每个 `U` 符号和某处的定义对上，拼出最终的可执行文件。链接错误是初学者第二大障碍（第一大是指针），它们的含义其实非常直白：

```text
undefined reference to `vec_add'
    → 声明过（所以编译过了）、但没有目标文件提供定义：
      忘了编译某个 .c？忘了链某个库？函数名拼错？

multiple definition of `counter'
    → 两个目标文件都定义了同名强符号：
      典型原因：在头文件里写了全局变量定义，被两个 .c 包含
```

> [!WARNING]
> C 链接器有一个古老而危险的兜底行为：对**函数**的重复弱定义、以及历史上某些平台对未初始化全局变量（ tentative definition）的重名，可能**静默合并**而不是报错。现代工具链（`-fno-common`，GCC 10 起默认）已改为报错，但读老代码、用老工具链时要警惕「两个文件各自的全局变量悄悄变成同一个」这种事故。

静态库（.a，归档的目标文件集合）与动态库（.so/.dll）的区别、链接顺序为什么是「被依赖的放后面」、以及 `ldd`/`ldconfig` 这些运维命令，都归入[第 10 篇](10-header-linking.md)。

## 3. 内存模型：一切只是编号的字节

C 对内存的看法只有一句话：**内存是一大片连续编号的字节，每个字节有自己的地址**。其他一切——变量、数组、结构体、函数——都建立在这句话上。

### 3.1 对象、值与表示

标准里的「对象」（object）指**一块有类型、有大小、生命周期的内存区域**。区分三个容易混淆的东西：

```c
int x = 65;
// x 是对象：栈上 4 个字节的区域
// 65 是它的值：按 int 的方式解读这 4 个字节得到的数
// 它的字节表示：41 00 00 00（小端机器上）
```

同一份字节可以有多种解读——这正是指针强转、联合体这些「危险操作」的底层原理，也是它们危险的根源：

```c
int x = 1;
unsigned char *p = (unsigned char *)&x;
printf("%02x %02x %02x %02x\n", p[0], p[1], p[2], p[3]);
// 小端机器输出：01 00 00 00 —— 最低有效字节在最低地址
```

> [!NOTE]
> **字节序**（endianness）只在多字节类型的存储层面出现。x86/ARM 主流是小端（低字节放低地址）；网络协议传统上是大端（所以有 `htonl/ntohl`）。写成文件或发上网络的二进制数据必须约定字节序，否则跨平台读出来就是错的。

### 3.2 进程的地址空间：五段布局

可执行文件被操作系统装载后，进程的虚拟地址空间是一张标准地图。后面讲作用域、`malloc`、栈溢出、段错误时，这张图会被反复引用：

```text
高地址 ┌──────────────────────────┐
      │ 命令行参数 / 环境变量        │
      ├──────────────────────────┤
      │ 栈 stack ↓ 向低地址生长      │  局部变量、函数调用帧；默认约 1~8 MB
      │      …                    │
      │ （栈与堆之间的巨大空洞）       │  ← 两头相向生长，中间是空的
      │      …                    │
      │ 堆 heap ↑ 向高地址生长       │  malloc 的地盘；由分配器向内核申请
      ├──────────────────────────┤
      │ BSS                       │  未初始化/初始化为 0 的全局与 static：装载时清零
      ├──────────────────────────┤
      │ 数据段 data                │  已初始化的全局与 static：从可执行文件读入
      ├──────────────────────────┤
      │ 代码段 text（通常只读）       │  机器指令；写字进这里 → 段错误
      └──────────────────────────┘
低地址
```

五个区的关键事实：

| 区       | 放什么                | 生命周期         | 典型事故             |
| ------- | ------------------ | ------------ | ---------------- |
| text    | 机器指令、字符串字面量（多数平台）  | 整个进程         | 往字符串字面量里写 → 段错误   |
| data    | 初始化非零的全局/static    | 整个进程         | 初始化依赖别的全局变量的顺序问题 |
| bss     | 未初始化或 = 0 的全局/static | 整个进程，启动清零  | 误以为「全局数组自动有初值」以外的值 |
| heap    | malloc 的分配         | malloc 到 free | 泄漏、悬垂指针、双重释放     |
| stack   | 局部变量、函数帧           | 函数返回即消失      | 返回局部变量地址、大数组栈溢出  |

**「返回局部变量的地址」为什么必错**，在这张图上一目了然：函数返回时它的栈帧整体作废，那块内存随时会被下一次函数调用覆盖。

```c
int *bad(void) {
    int local = 42;
    return &local;          // ❌ 返回指向栈帧的指针，调用方拿到的是废墟
}
```

编译器对这种错误会发警告（`-Wreturn-local-addr`），但**拦不住你**——C 的护栏靠你自己装，具体工具见[第 13 篇](13-tools-debugging.md)。

### 3.3 栈的大小是有限的

栈不是无限伸展的，Linux 默认约 8 MB（`ulimit -s` 可查）。它决定了你的递归深度上限和局部数组的尺寸上限：

```c
int main(void) {
    int big[1 << 20];       // 4 MB：很多平台能过，更大的会直接爆栈
    static int safer[1 << 22];  // 16 MB：挪进 BSS，不占栈
    return 0;
}
```

「深递归 + 大局部数组」是栈溢出的两大来源。爆栈的表现通常是段错误——但发生在栈保护页上的越界有时会静默踩踏别的数据，这类「玄学 bug」用地址对照五段布局就能定位。

## 4. 契约模型：标准、实现与未定义行为

C 语言由 ISO 标准定义（C89/C99/C11/C17/C23 是主要版本）。但标准不是一份可执行文件——它约束的是**编译器作者**，不是机器。你实际写代码时签的是三方契约：

- **标准**规定了「所有实现必须一致」的行为，也把大量行为**下放**：有的交给「实现定义」（implementation-defined，编译器必须文档化其选择，如 `int` 的字节数）、有的交给「未指定」（unspecified，几种合法结果任选）、最狠的一部分交给「未定义」（undefined behavior，简称 UB）。
- **UB 的真实含义**不是「运行会出错」，而是「标准不提供任何保证」。编译器**有权假设 UB 永不发生**，并基于这个假设做优化——这才是 UB 可怕的地方：它不是地雷，是_COMPILER 的通行证。

```c
int overflow_check(int a, int b) {
    if (a + b < a)          // 意图：检测加法溢出
        return -1;
    return a + b;
}
```

有符号溢出是 UB，所以编译器有权把 `a + b < a` 化简为 `0`（假设加法不溢出，则它不可能小于 a），整个检查被**删除**——你写的防溢出代码在 `-O2` 下消失得无影无踪。这不是编译器 bug，是你先违反了契约。

> [!WARNING]
> 初学者对 UB 最危险的两个误解：①「UB 就是崩溃」——不，UB 常常表现为**看似正常**，然后在换编译器、开优化、改一行无关代码后引爆；②「先写完再修 UB」——UB 在优化器眼里是「许可令」，越早修越好。让工具替你盯住它：`-fsanitize=undefined` 能在运行时当场抓住大多数 UB（见[第 13 篇](13-tools-debugging.md)）。

全书会不断回到这个主题：整型溢出（[第 2 篇](02-types.md)）、越界与悬垂（[第 4 篇](04-pointers.md)、[第 7 篇](07-dynamic-memory.md)）、字符串无终结符（[第 5 篇](05-arrays-strings.md)）、求值顺序（[第 3 篇](03-operators-control.md)）。每一类 UB 都有对应的工具与写法规约——**C 的安全不是靠小心，是靠流程**。

## 5. 可移植性：一份代码，四种整数

C 的设计目标是横跨从 8 位单片机到 64 位服务器的所有机器，所以它**故意不固定**许多类型的大小：

| 类型        | 标准的下限    | 你电脑上（LP64） | 典型 32 位（ILP32） | 典型 8 位单片机 |
| --------- | -------- | ---------- | -------------- | --------- |
| `char`    | ≥ 8 位    | 8 位        | 8 位            | 8 位       |
| `short`   | ≥ 16 位   | 16 位       | 16 位           | 16 位      |
| `int`     | ≥ 16 位   | **32 位**   | 32 位           | **16 位**  |
| `long`    | ≥ 32 位   | **64 位**   | 32 位           | 32 位      |
| `long long` | ≥ 64 位 | 64 位       | 64 位           | 64 位      |
| 指针        | 实现定义     | 8 字节       | 4 字节           | 2~4 字节    |

三条工程结论直接从这里推出：

1. **不要假设 `int` 是 32 位**。需要固定位宽时用 `<stdint.h>` 的精确类型：`int32_t`、`uint64_t`、`uintptr_t`（能装下指针的整数）。这是现代 C 代码的标配。
2. **`sizeof` 的返回类型是 `size_t`**（无符号，宽度随平台）。拿它和 `int` 比较会触发隐式转换，是无数「倒数循环」bug 的根源（详见[第 2 篇](02-types.md)）。
3. **指针大小 ≠ int 大小**。把指针存进 `int` 在 64 位平台必然截断；要存就存 `uintptr_t`。

```c
#include <stdint.h>
#include <stddef.h>

size_t len;                 // 数组长度、内存大小的唯一正确类型
int64_t  offset;            // 需要符号的计数
uint32_t hash;              // 位宽敏感的哈希值
uintptr_t addr_as_int;      // 指针与整数互转的合法容器
```

## 6. 标准与库：你的工具箱里到底有什么

### 6.1 版本演化：该用哪个 C

C 的版本号至今仍是工程现实——不同编译器默认档位不同，老代码遍地 C89。你需要的是一张「什么特性从哪来」的速查表：

| 版本  | 年份    | 你真正会用到的东西                                            |
| --- | ----- | ---------------------------------------------------- |
| C89 | 1989  | 基础语法；函数参数声明在括号后面（K&R 风格的残留）；`int f();` 表示「参数未指定」      |
| C99 | 1999  | `//` 注释、`stdint.h` 定宽整数、`long long`、变长数组 VLA、`inline`、声明可以混在语句中 |
| C11 | 2011  | `_Generic`、多线程 `<threads.h>`、原子操作 `<stdatomic.h>`、匿名结构体/联合体、边界检查接口 Annex K |
| C17 | 2018  | 纯缺陷修订，无新特性                                             |
| C23 | 2024  | `bool`/`true`/`false` 成关键字、`constexpr`、`ckd_add` 检查溢出、空参数括号 `()` 终于等于 `(void)` |

三条选型建议：**新项目用 `-std=c17` 起步**（兼容面与工具支持最平衡）；**读老代码要认识 C89 的两种函数声明风格**；**别用 VLA 和 Annex K**——前者在 C11 退化为可选且是栈溢出隐患，后者绝大多数平台没实现，安全替代是显式传长度（[第 5 篇](05-arrays-strings.md)）。

### 6.2 libc 全景：29 个头文件的地图

「标准库」其实就是一组头文件 + 一个库文件（libc）。全部由编译器厂商或系统提供，没有第三方依赖。按用途分组记，比逐个头文件背有效得多：

| 用途         | 头文件                                | 关键角色                                        |
| ---------- | ---------------------------------- | ------------------------------------------- |
| 输入输出       | `stdio.h`                          | `printf/scanf` 家族、`FILE*`、文件读写               |
| 内存与工具      | `stdlib.h`、`string.h`              | `malloc/free`、`strtol`、`qsort`；`memcpy/strcmp/memset` |
| 类型与尺寸      | `stdint.h`、`stddef.h`、`limits.h`   | 定宽整数、`size_t`、`NULL`、各类型上下限                  |
| 数学         | `math.h`、`fenv.h`、`complex.h`      | `sin/pow/sqrt`、浮点环境、复数                       |
| 断言与诊断      | `assert.h`、`errno.h`               | `assert`、错误码                                 |
| 字符分类       | `ctype.h`                          | `isdigit/isalpha/tolower`                    |
| 时间         | `time.h`                           | `time_t`、`clock`、格式化时间                       |
| 可变参数       | `stdarg.h`                         | 实现你自己的 `printf` 式接口                          |
| 多线程（C11）   | `threads.h`、`stdatomic.h`          | `thrd_create`、原子类型——很多平台仍用 pthread 替代        |

两个初学者最容易误解的事实：

1. **libc 里没有字符串类型、没有动态数组、没有哈希表、没有正则**。`string.h` 只有「以 `\0` 结尾的字节序列」的操作函数。任何更高级的数据结构要么手写，要么引第三方（glib、sds）——这正是 C 世界里每个项目都自带一份 `util.c` 的原因。
2. **`stdio.h` 的 `printf/scanf` 是有运行时开销和类型安全隐患的接口**。`printf("%d", 3.14)` 不崩溃、不报警（默认档位），只是输出垃圾——因为参数按 `%d` 的约定从寄存器/栈上按 int 解读。GCC 的 `-Wformat` 能静态检查多数情况，这是必须开的理由之一。

> [!TIP]
> 想知道某个函数「标准怎么说」：`man 3 printf`（Linux/macOS 自带手册页，第 3 节是库函数）比搜索引擎快且权威。Windows 上可查 cppreference 的 C 页面。养成「先查标准语义再写」的习惯，能避开一大半网上流传的错误写法。

## 7. 一段代码的完整一生

把前面的图串起来，跟踪一段 6 行程序从按键到输出经历的全部环节：

```c
#include <stdio.h>

int main(void) {
    printf("hello, %d\n", 6 * 7);
    return 0;
}
```

```text
1. 预处理   hello.c → hello.i    粘贴 stdio.h 全文（数千行），得到一个翻译单元
2. 编译     hello.i → hello.s    6*7 在优化后被折叠成 42；printf 调用留下符号欠条 printf@plt
3. 汇编     hello.s → hello.o    生成机器码 + 符号表：T main，U printf，U _GLOBAL_OFFSET_TABLE_
4. 链接     hello.o + libc → hello
            从动态库的桩（stub）补上 printf 的地址，写入入口 _start
5. 装载     内核把 hello 映射进虚拟地址空间：text/data/bss 各就各位，
            栈上布好 argv/envp，堆从 brk 起点待命
6. 启动     CPU 跳到 _start → __libc_start_main 初始化运行时 → 调用 main
7. 执行     main 调 printf → 经 PLT 跳入 libc → write 系统 syscall → 内核把字节交给终端
8. 退出     main 返回 0 → __libc_start_main 收尾 → exit_group 系统调用 → 进程消失
```

两个值得记住的细节：**main 之前发生了大量事**（动态链接器解析库、C 运行时初始化全局构造、清零 BSS），所以「程序还没开始就段错误」是真的可能；**`return 0` 的返回值会变成进程的退出码**（`echo $?` 可见），这是 C 程序与 shell 之间最古老的接口。

## 8. 什么时候不该用 C

以 C 开篇的教程更要有说「不」的自觉：

1. **字符串/集合密集的业务逻辑**：每拼一个字符串都要手动管理内存，开发效率与出错率都是灾难。
2. **需要快速迭代验证想法**：没有包管理生态（vcpkg/Conan 之外），没有 REPL，编译-链接循环慢。
3. **内存布局无关紧要、但安全要求高的服务**：现代替代品（Rust、Go）用更少的事故预算达到同样的吞吐。
4. **只有你一个维护者的小脚本**：Python 十分钟的事，C 要一下午——省下的那点运行时间毫无意义。

反过来说，当你需要**读写内核、写语言运行时、压榨每一条指令、与硬件寄存器对话、或者真正理解所有语言底下发生了什么**时，C 仍是不可替代的那门课——而且哪怕你永远不写 C，这门课也会永久改变你写任何语言的方式：你终于知道那个「变量」底下是什么。

## 9. 陷阱清单

- **以为 `gcc hello.c` 只是一步**：实际是四步，链接错误和编译错误的症状完全不同——分不清阶段就无从下手。
- **在头文件里写全局变量定义**：`int counter;` 出现在头文件里，被两个 .c 包含后（旧工具链）可能静默合并或直接报 multiple definition。头文件只放声明（`extern int counter;`）。
- **假设 `int` 32 位、`long` 32 位、指针能塞进 int**：换平台就炸。用 `<stdint.h>` 的定宽类型。
- **把 UB 当「会不会崩」的赌局**：UB 是优化器的自由通行证，`-O2` 下的行为可以和 `-O0` 完全不同。
- **忽略编译器警告**：C 的警告几乎都是未来的段错误。基线配置 `-Wall -Wextra`，见[第 13 篇](13-tools-debugging.md)。
- **返回局部变量的地址/引用**：栈帧随函数返回作废。这个错误有专门的警告，但同类变体（返回指向局部数组的指针、在结构体里存栈指针）要靠理解布局来防。
- **以为数组传参还带长度**：数组做参数退化为指针（[第 5 篇](05-arrays-strings.md)），长度必须自己带。

## 10. 小结

- C 是「用高级语法写汇编」的合约语言：极小运行时 + 直接暴露内存 + 大量行为下放给实现和 UB，换来对机器的完全控制。
- 编译分四阶段：预处理（文本粘贴）、编译（翻译单元 → 汇编）、汇编（目标文件 + 符号表）、链接（补齐符号欠条）。翻译单元是 C 组织代码的最大单位。
- 进程地址空间是五段布局：text（指令与字面量）、data/bss（全局与 static）、heap（malloc）、stack（局部变量与调用帧）。每类变量的位置决定它的生命周期与事故模式。
- 标准通过「实现定义 / 未指定 / 未定义」三级下放行为；UB 意味着编译器可以假设它不发生——防 UB 要靠工具链与写法规约，不靠小心。
- 类型大小随平台浮动是特性不是缺陷：需要确定位宽时用 `<stdint.h>`；一切尺寸与下标用 `size_t`。
- 一段 C 程序的一生横跨预处理、编译、链接、装载、运行时启动、系统调用八个环节——「main 之前」和「main 之后」都有大量机制在工作。

## 11. 练习

**1.** 用 `gcc -E` 预处理一个只含 `#include <stdio.h>` 的文件，数一下展开后的行数。解释为什么一个「空」程序其实有几千行。

> [!TIP]
> 思路 `#include` 是字面粘贴：stdio.h 及其递归包含的所有头文件（stddef.h、bits/types.h 等）全部展开。这几千行里绝大部分是**声明**（函数原型、类型定义、宏），没有定义——它们只是让编译器认识 `printf` 的「目录」，真正的机器码在 libc 里，链接时才补上。

**2.** 写一个返回局部变量地址的函数，分别用 `-O0` 和 `-O2` 编译运行，观察结果差异，并用 `-Wreturn-local-addr` 看警告。

> [!TIP]
> 思路 `-O0` 下返回的栈地址「看起来还能读到 42」，因为栈帧还没被覆盖——这是最危险的假象；`-O2` 下编译器可能直接删除该函数或返回 NULL。教训：UB 的表现随优化级别变化，「测过了」不等于「对的」。

**3.** 用 `nm` 查看两个 .o 文件的符号表，人为制造一个 `undefined reference` 和一个 `multiple definition`，并分别说出三种修法。

> [!TIP]
> 思路 undefined reference：忘了编译某个 .c / 忘了把 .o 加进链接命令 / 忘了 `-l` 链库 / 函数名拼写不一致。multiple definition：两个 .c 定义了同名全局变量 / 头文件里写了定义 / 应该加 `static` 限成内部链接。

**4.** 打印 `sizeof(int)`、`sizeof(long)`、`sizeof(void *)`、`sizeof(size_t)`，与表格里的 LP64 数据模型对照；再在在线编译器（如 Compiler Explorer）选 32 位目标再看一遍。

> [!TIP]
> 思路 64 位 Linux 上分别是 4、8、8、8；32 位上是 4、4、4、4。`long` 和指针跟随平台位宽变化，这正是「可移植代码用 `int32_t`/`uintptr_t`/`size_t`」的动机。

**5.** 下面这段「防溢出」代码在 `-O2` 下为什么失效？给出正确写法（提示：无符号运算不溢出，或者用 `__builtin_add_overflow`）。

```c
int add(int a, int b) {
    if (a + b < 0) return -1;   // 意图：检测溢出
    return a + b;
}
```

> [!TIP]
> 思路有符号溢出是 UB，编译器假设它不发生，于是 `a + b < 0` 中「溢出后变负」这个前提被删掉，条件被优化成恒假，检查消失。正确写法：`if ((b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b))`（先用不溢出的运算预判），或用 GCC/Clang 内建 `__builtin_add_overflow(a, b, &r)`，C23 起有标准 `<stdckdint.h>` 的 `ckd_add`。

**6.** 画出下面程序的内存布局图，标注每个变量所在的段，并指出哪一行会触发什么错误。

```c
#include <stdio.h>
#include <stdlib.h>

int counter;                    // A
static double ratio = 0.5;      // B

char *make(void) {
    char buf[32];
    sprintf(buf, "item-%d", counter++);
    return buf;                 // C
}

int main(void) {
    char *p = make();
    printf("%s\n", p);          // D
    return 0;
}
```

> [!TIP]
> 思路 A 在 BSS，B 在 data，`buf` 在栈。C 行返回栈上数组的地址——悬垂指针；D 行大概率打印出乱码或旧帧残留，也可能「恰好」还对。修法：`static char buf[32]`（有线程安全代价）或由调用方传入缓冲区。这类「从段归属判断事故」的练习是后面所有内存篇的基本功。
