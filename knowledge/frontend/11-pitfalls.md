前端的陷阱分布有清晰的层次：**语言机制层**（引用/闭包/异步）、**平台交互层**（DOM/事件/存储/网络）、**工程层**（构建/依赖/交付）。本篇把全书汇编成六类审查清单，附性能排查路线与安全检查单。

## 1. 六类审查清单

### 1.1 语言与基础（第 5 篇）

- [ ] const/let 全覆盖（无 var）；对象数组赋值清楚是引用
- [ ] `===` 统一；`??` 与 `||` 按语义选（0/"" 是合法值时用 ??）
- [ ] 回调中的 this（箭头函数/bind）核查；循环闭包用 let
- [ ] 异步无依赖串行 → Promise.all 并行；fetch 判 res.ok
- [ ] 解构/可选链的默认值语义核对；JSON 序列化的边界（方法/循环引用）知情

### 1.2 DOM 与渲染（第 3、4、6 篇）

- [ ] 用户输入只进 textContent（innerHTML 的 XSS 面为零）
- [ ] 动画只动 transform/opacity；样式批量更新（读写分离）
- [ ] 布局用 flex/grid（无 float hack/绝对定位布局/魔法数字）
- [ ] box-sizing: border-box 全局；rem 单位体系；:focus-visible
- [ ] 事件委托覆盖动态子元素；防抖/节流治理高频事件
- [ ] 图片有 alt + 尺寸 + lazy；长列表虚拟化

### 1.3 网络与安全（第 10 篇）

- [ ] 统一 API 封装（认证/错误/取消/超时）；三层错误分离
- [ ] 无字符串拼 SQL/拼 HTML 的输入通道；动态列名白名单
- [ ] CSP 响应头存在；第三方脚本有 SRI/审计
- [ ] 认证方案明确（HttpOnly cookie 优先 / localStorage 的 XSS 权衡已评估）
- [ ] CSRF 防线（SameSite + token）与 CORS 配置正确
- [ ] 缓存策略：指纹文件 immutable、HTML no-cache、API 不缓存用户数据

### 1.4 状态与框架（第 9 篇）

- [ ] 状态不可变更新（无 push/原地改后 setState）
- [ ] 列表 key 稳定唯一（非下标）
- [ ] effect 依赖如实（stale closure 排查）；清理函数归还资源
- [ ] 卸载后 setState 防护（AbortController）
- [ ] 服务端状态与客户端状态分离（Query vs useState）
- [ ] 派生数据渲染期计算（「你未必需要 effect」）

### 1.5 可访问性与体验

- [ ] 语义标签 + 标题层级 + label 关联（[第 2 篇](02-html.md)）
- [ ] 键盘可达（Tab 遍历过、focus 样式在、交互用 button/a）
- [ ] 表单校验双端（HTML 内置 + 服务端）
- [ ] 加载/空/错误三态 UI 齐全；骨架屏优于白屏
- [ ] prefers-reduced-motion 尊重（动画的关灯开关）

### 1.6 工程与交付（第 8 篇）

- [ ] TypeScript strict；边界运行时校验（zod）
- [ ] lock 文件进库；CI 用 npm ci；依赖升级有节奏
- [ ] 代码分割（路由级）+ 体积监控
- [ ] Lighthouse 基线（性能/可访问性/SEO 三项达标）
- [ ] 错误监控接入（window.onerror/上报）；关键路径有 e2e 冒烟

## 2. 性能排查路线

```text
慢在哪一段？DevTools Performance + Network 先分诊：
├── 加载慢
│   ├── Network waterfall：谁阻塞？（渲染阻塞 script/大图/串行请求）
│   ├── 体积：bundle 分析 → 分割/摇树/压缩图片（webp/avif）
│   └── 服务器：TTFB 长 → 缓存/CDN（[第 10 篇](10-http-storage.md)）
├── 交互卡（点击/输入响应慢）
│   ├── 长任务（Performance 的红色块）→ 拆分/Worker/防抖
│   └── 频繁重排 → 批量样式/transform（[第 6 篇](06-dom-events.md)）
├── 滚动/动画掉帧
│   ├── 布局抖动（layout thrashing）→ 读写分离
│   └── 大面积重绘 → will-change/合成层/减层
└── 内存涨不停（泄漏）
    ├── 忘清理（定时器/监听/闭包持有）→ heap snapshot 对比
    └── 无限增长的数组/Map → 状态治理
```

性能优化的元纪律：**先测量（Performance/Network 面板）、一次改一项、回归验证**——与[所有语言的 profiler 文化](../c/13-tools-debugging.md)同源。「感觉慢」不是性能问题，「performance 面板的证据」才是。

## 3. 安全检查单（上线前必过）

```text
□ 所有用户输入的渲染走安全通道（textContent/框架转义/白名单消毒）
□ CSP 响应头配置（先 report-only 观察再强制）
□ 认证：HttpOnly cookie（或 localStorage 的风险评估记录）
□ CSRF：SameSite + token/Origin 校验
□ 所有 API 的服务端鉴权（前端隐藏 ≠ 权限；[第 10 篇](10-http-storage.md)）
□ HTTPS 全站 + HSTS
□ 依赖审计（npm audit）+ 无已知高危
□ 敏感数据不在 URL/localStorage 明文
□ 第三方脚本清单化（每个都是供应链面）
```

## 4. 前端测试的分级策略

| 层级       | 工具               | 测什么                       | 比例   |
| ---------- | ------------------ | ---------------------------- | ------ |
| 单元       | vitest             | 纯函数/工具/状态逻辑          | 最多   |
| 组件       | testing-library    | 组件行为（渲染/交互/无障碍查询）| 中     |
| 集成       | testing-library    | 页面流程（表单提交流）        | 少     |
| E2E        | Playwright         | 关键路径冒烟（登录/下单）      | 最少   |

测试的分寸：**testing-library 的哲学是「按用户可见行为测」**（getByRole/ getByText——不测实现细节）；E2E 只保关键路径（脆、慢、贵）。无障碍测试可以自动化一部分（axe-core 扫描语义缺失）。

## 5. 反模式速查

| 反模式                                    | 一句话修复                              |
| ----------------------------------------- | --------------------------------------- |
| jQuery 式 DOM 拼接混进 React              | 声明式重构；ref 只留给受控例外           |
| 全局 CSS 覆盖组件库样式（!important 战争） | 主题变量/样式方案（[第 3 篇](03-css-basics.md)）|
| 巨型组件（500 行 render）                  | 拆组件/自定义 hook                       |
| props 钻井（逐层透传）                     | 组合（children）/context（真全局才用）   |
| 把接口数据存进全局状态库                   | 服务端状态用 Query（[第 9 篇](09-react.md)）|
| 图片原图直出（3MB 的 jpg）                 | 压缩/webp/尺寸响应式/lazy                |
| 轮询 setInterval 拉数据                     | WebSocket/SSE 或带退避的轮询             |
| console.log 留在生产                        | 统一日志门面 + 构建剥离                  |
| 「在 Chrome 里测过了」                      | 关键路径多浏览器 + 特性检测              |
| 依赖未审计直接 npm install                 | audit/锁定/最小化                        |

## 6. 小结

- 六类清单覆盖前端全域：语言基础、DOM 渲染、网络安全、状态框架、可访问性、工程交付——「语义/安全/性能」三条线贯穿。
- 性能的元方法：面板证据驱动 + 分诊路线（加载/交互/滚动/内存四段）——测量文化优先于技巧记忆。
- 安全检查单的骨架：输入渲染安全、CSP、认证存储、CSRF、服务端鉴权、HTTPS、依赖审计——上线前过一遍是流程不是仪式。
- 测试的分级：单元多、组件中、E2E 少；「按用户可见行为测」的哲学让测试不随实现腐烂。
- 前端质量的特殊性：运行环境不可控 + 代码对用户可见 + 即时发布——工程化清单是适应这三点的产物。

## 7. 练习

**1.** 用六类清单审查一个你写过的前端项目（或本教程练习产物），统计命中数分布——最弱的类别回到对应篇目补课。

> [!TIP]
> 思路自查的典型分布：可访问性与安全类最弱（教学代码普遍忽视）。「语义/安全」是审查清单里最不该空的两栏。

**2.** 给一个页面跑 Lighthouse：记录性能/可访问性/SEO 三项分数与 Top 改进项；按清单修一轮（图片/lazy/对比度/语义）再跑——前后对比表。

> [!TIP]
> 思路Lighthouse 的可访问性项与[第 2 篇](02-html.md)的语义纪律一一对应（对比度/alt/label/层级）——工具把审查自动化了大半。

**3.** 演练一次「性能急救」：故意在一个列表页埋三处问题（同步大 script/未压缩大图/1000 项无虚拟化渲染），用第 2 节的路线诊断修复，记录每步的指标变化。

> [!TIP]
> 思路急救的顺序感：先 Network 还是先 Performance？症状定方向——「白屏久」看加载、「滚动卡」看渲染。诊断路线的价值在于不乱枪打鸟。

**4.** 给你的项目接入错误监控（window.onerror + unhandledrejection 上报到本地接口），制造三类错误（同步异常/Promise 拒绝/资源加载失败）验证捕获——总结每类的堆栈质量。

> [!TIP]
> 思路三类错误的堆栈形态不同（Promise 拒绝最容易「无声消失」）——监控的价值在「用户侧的错误你看不见」。source-map 上传让压缩堆栈还原。

**5.** 用 testing-library 给一个表单组件写测试：渲染（role/label 查询）、交互（userEvent 输入提交）、错误态——故意改组件实现（不改变行为）验证测试不红。

> [!TIP]
> 思路「改实现测试不红」是行为测试的验收标准——按 role/label 查询天然抗实现重构。对比「按 className 查询」的脆性。

**6.** 讨论：前端「三足」（性能/安全/可访问性）为什么后两者常被牺牲？从「需求显性度」「故障的可见性」「上线压力」三个角度分析，并给出你团队里让三者「制度化」的机制（清单/Lighthouse 门槛/审查分工）。

> [!TIP]
> 思路性能问题用户秒感知（制度化自然）、安全与可访问性问题「不爆发就没人看见」——制度化（门槛/清单/CI）是把「看不见的风险」变成「流程的硬约束」。工程成熟度的标志正是「不见血的地方也有纪律」。
