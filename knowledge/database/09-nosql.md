NoSQL 不是"新的一代数据库"，而是围绕具体问题的专门工具：Redis 求快，MongoDB 求模式灵活，时序库求写入吞吐。这一篇带过它们的思路与边界，重点回答一个实际问题：什么时候该把它们加进架构。

## Redis：内存键值

所有数据放内存，命令执行单线程（新版本网络 I/O 多线程化，但命令执行仍串行，天然无锁竞争），读写亚毫秒级。它真正的威力不止"缓存字符串"，而在**数据结构**——每种结构背后是一类现成的业务问题：

| 结构 | 典型场景 |
| --- | --- |
| String | 缓存对象 JSON、计数器、分布式锁 |
| Hash | 对象的字段级读写：改一个字段不用整存整取 |
| List | 轻量队列，量大或要求可靠时换专业消息队列 |
| Set | 去重、标签、共同好友（交集） |
| ZSet | 排行榜：按分数排序、按名次取区间 |
| Stream | 带消费组的事件流，轻量版消息队列 |

命令行感受一下，排行榜用 ZSet 两条命令就成型：

```bash
> SET session:42 '{"uid":42}' EX 3600     # 写会话并设 1 小时过期，到点自动删除
> INCR pageview:home                      # 原子自增：并发下计数不重不漏
> ZADD leaderboard 980 "alice"            # 排行榜记分
> ZREVRANGE leaderboard 0 9 WITHSCORES    # 取分数最高的前 10 名
```

缓存的标准姿势是 **cache-aside**：读时先查缓存，未命中查库并回填；写时更新库、删缓存（是删不是改——并发写时"改缓存"容易把旧值写回去，删掉等下次读回填更安全）：

```text
读路径：查缓存 → 命中返回 / 未命中 → 查主库 → 回填（带 TTL）→ 返回
写路径：更新主库 → 删除对应缓存键
```

所有 key 都要设 TTL——不设过期时间的缓存，迟早把内存吃穿。单命令的原子性还让 Redis 能客串分布式锁，`SET NX` 是最朴素的实现：

```bash
> SET lock:order:42 "holder-uuid" NX EX 10   # 键不存在才写入：拿到锁，10 秒自动释放防死锁
```

> [!TIP]
> 两个高频事故提前备好预案：**缓存穿透**（查询根本不存在的 key，每次都打到库）用空值短 TTL 缓存或布隆过滤器挡；**缓存雪崩**（大批 key 同时过期，数据库瞬间被打满）给 TTL 加随机抖动错峰，热点数据用逻辑过期。

> [!WARNING]
> Redis 的持久化（RDB 快照 / AOF 日志）默认配置下不保证零丢失，主从复制是异步的，读从库还可能读到旧值。把它当缓存，丢了能从库里重建；把主数据放进去，就得接受"故障后少一部分"的可能。纪律只有一条：**Redis 里的数据原则上都必须能从主存储重建。**

## MongoDB：文档模型

数据存成 JSON 风格的文档（BSON），一个对象连同它的子结构存在一起：

```json
{
  "name": "张三",
  "tags": ["rust", "db"],
  "address": { "city": "杭州", "zip": "310000" }
}
```

查询对嵌套字段和数组成员一视同仁，聚合管道把"筛选 → 分组 → 排序"串成流水线：

```javascript
db.users.find({ tags: "rust", "address.city": "杭州" })   // tags 是数组也能按成员匹配

db.orders.aggregate([
  { $match: { status: "paid" } },                          // 先筛
  { $group: { _id: "$user_id", total: { $sum: "$amount" } } },  // 再按用户汇总
  { $sort: { total: -1 } },                                // 降序
  { $limit: 10 }
])
```

性能模型和关系型一脉相承：MongoDB 同样靠 B+ 树索引，同样讲最左前缀，同样要防逐条查询——所谓"文档数据库不用优化"，是没写过大查询的人才信的话。

```javascript
db.orders.createIndex({ user_id: 1, created_at: -1 })   // 复合索引：顺序同样决定能不能用上
```

核心思路：**用嵌套代替 JOIN**。关系型里拆成三张表的数据，这里一个文档整读整写，一次读就是一次 IO。"一起读写的放一起"是文档建模的核心判断，和关系型"每个事实存一份"是两种世界观——前者为读优化，后者为一致性优化，数据边界一旦需要跨文档关联，文档模型的优势就迅速流失。

"模式灵活"指字段可以各行不同、随加随用，但别误解成"没有模式"：**你只是把模式从数据库搬进了应用代码**。字段名打错照样静默写进一个新字段，没有数据库替你拦；数据质量的担子从约束转移到了代码规范和团队纪律上。索引、聚合管道都有，4.0 起支持多文档事务，但复杂关联和强事务依然不是它的主场——文档的切分边界设计直接决定性能。

## 时序数据库

监控指标、传感器数据这类"只追加、按时间查、过期即弃"的数据，交给时序库（InfluxDB、TimescaleDB——后者是 PostgreSQL 扩展，可以一库两用）：按时间自动分区、列式压缩（同类指标压缩率极高）、保留策略自动过期、降采样预聚合（原始数据攒 7 天，之后只留每分钟的均值）。

```sql
-- TimescaleDB：把普通表变成时序表，按天自动切块（chunk）
SELECT create_hypertable('metrics', 'ts', chunk_time_interval => INTERVAL '1 day');
```

这些能力关系型不是不能模拟，只是数据量上去后分区维护和压缩成本都不划算——判断标准还是那句话：查询模式单一固定时，专用工具才划算。

## 一致性常识：复制与取舍

这些分布式存储普遍走"一主多从、异步复制"：写落在主节点，从节点异步追赶。由此而来的默认语义叫**最终一致**——写完立刻去读，可能读到旧值，稍等片刻才一致。业务能容忍的（点赞数、浏览量）这不是问题；不能容忍的（库存、余额）要么读主库、要么把这些数据留在关系型里用事务管。MongoDB 提供写关注级别（write concern）让每次写声明"确认到什么程度才算成功"，Redis 则要靠部署配置（WAIT 命令、同步复制方案）补齐——总之**一致性是需要显式购买的东西，不是默认赠送的**。CAP 取舍听上去玄，落到选型就是一句话：分区容错没法放弃，剩下的是"网络分区时拒绝服务（保一致）"还是"继续服务（冒旧数据风险）"的选择，金融选前者，社交信息流选后者。

## 关系型 vs NoSQL

| 维度 | 关系型 | Redis | MongoDB |
| --- | --- | --- | --- |
| 数据模型 | 表，先定模式 | 键 → 结构 | 文档，模式灵活 |
| 查询能力 | SQL，表达力最强 | 按键取，无关联查询 | 聚合管道，弱关联 |
| 事务 | 强 | 单命令原子 / MULTI 顺 | 4.0+ 多文档，非默认 |
| 扩展方向 | 先垂直，水平需分库分表 | 天然分片 | 天然分片 |
| 定位 | 主存储，默认答案 | 缓存与实时结构 | 特定读写模式的主存储 |

## 什么时候不该用关系型

数据没有复杂关联、读写模式单一固定、规模大到单库扛不住水平分片刚需——三者占齐时，NoSQL 的取舍才开始划算。反过来，出现这些信号就该留在关系型（或回到关系型）：

- 查询条件灵活多变：今天按 A 查、明天按 B+C 组合查
- 需要跨实体的事务与强一致：钱、库存、配额
- 报表和多表关联分析是常态
- 团队没有该 NoSQL 的运维经验——它的代价不只是授权，还有备份、监控、踩坑经验

> [!NOTE]
> 实战中最常见的形态是组合拳：主数据在 PostgreSQL/MySQL，热点读靠 Redis 挡，行为日志进时序库或消息队列，搜索交给全文引擎。NoSQL 是给关系型补短板的组件，不是"二选一"的对立面——先想清楚每类数据的一致性与查询要求，再决定它住在哪。
