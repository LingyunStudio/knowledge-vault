NoSQL 常被讲成「SQL 的替代品」，这是理解它的最大误区。NoSQL 的本质是：**为特定访问模式放弃关系模型的某些保证，换取专项性能或扩展性**——Redis 放弃复杂查询换内存级速度，MongoDB 放弃严格 schema 换文档灵活性，Cassandra 放弃跨行事务换海量写入。**按问题选工具，而不是按潮流选阵营**。

## 1. Redis：内存数据结构服务器

Redis 不只是「缓存」——它是**内存里的数据结构库**，每种结构对应一类问题：

| 结构          | 语义                     | 经典用途                          |
| ------------- | ------------------------ | --------------------------------- |
| `STRING`      | 字节串 + 原子计数         | 缓存、计数器（INCR）、分布式锁     |
| `HASH`        | 字段-值表                 | 对象缓存（user:42 的字段）        |
| `LIST`        | 双端链表                  | 消息队列、最新列表                 |
| `SET`         | 无序去重集合              | 标签、共同好友（SINTER 交集）      |
| `ZSET`        | 分数排序的集合            | ★ 排行榜、延迟队列、滑动窗口限流   |

```bash
SET session:abc "user=42" EX 3600        # 带过期：会话/验证码的标准形态
INCR page:home:views                     # 原子自增（并发安全）
ZADD leaderboard 9800 "alice"            # 排行榜：分数 + 成员
ZREVRANGE leaderboard 0 9 WITHSCORES     # Top 10
EXPIRE cache:key 60                      # TTL：缓存的生命周期
```

### 1.1 缓存模式与三大故障

「数据库前挡一层 Redis」的读模式叫 **Cache-Aside**（旁路缓存）：读时先查缓存、未命中查库并回填；写时更新库、删缓存。三大经典故障：

| 故障     | 场景                                | 对策                                     |
| -------- | ----------------------------------- | ---------------------------------------- |
| 缓存穿透 | 查询**不存在**的 key（恶意刷）→ 全打到 DB | 空值短缓存 / 布隆过滤器 / 参数校验         |
| 缓存击穿 | **热点 key 过期瞬间**万请求打 DB      | 热点不过期 / 互斥锁（单飞重建）            |
| 缓存雪崩 | **大批 key 同时过期**               | 过期时间加随机抖动 / 多级缓存 / 熔断降级   |

TTL 的设计是缓存的灵魂：**过期时间带抖动**（基础 ± 随机）防雪崩；**缓存与 DB 的一致性**走「更新 DB 后删缓存」（不是更新缓存——并发写会乱序）+ 短 TTL 兜底——「最终一致」的缓存纪律。

### 1.2 Redis 的持久化与定位

Redis 有持久化（RDB 快照/AOF 日志）——但它的定位是「可容忍少量丢失的高性能层」：**缓存丢了可重建（无所谓）**；**把 Redis 当主存储**（订单等）就要认真对待持久化与故障转移，那通常意味着「该用数据库的活用了 Redis」。Redis 的甜区：**可重建的数据、低延迟要求、简单访问模式**。

## 2. MongoDB：文档模型

```javascript
// 一篇「文章」及其评论作为一份文档（嵌套）
{
  _id: ObjectId("..."),
  title: "Hello",
  author: { id: 42, name: "alice" },
  tags: ["db", "nosql"],
  comments: [                             // 一对少：嵌进文档
    { user: "bob", text: "nice", at: ISODate("...") }
  ]
}
```

MongoDB 的模型：**JSON 文档 + 无固定 schema**——一行数据（文档）自带全部结构，读单条聚合数据免 JOIN。查询语法是 JSON 式的（`db.articles.find({"tags": "db"})`），索引机制与 SQL 同源（B 树）。

**嵌入（embed）vs 引用（reference）**是 Mongo 的 schema 设计核心（与 [关系库的范式](../database/05-schema.md)呼应）：

- **嵌入**：一起读的数据嵌在一起（文章+评论前 10 条）——一次读取、无 join；代价是文档 16MB 上限、更新嵌套字段复杂。
- **引用**：存 `_id` 分两次查——像关系库；跨文档「事务」（4.0+ 支持多文档事务但代价高）。
- 判据：**访问模式决定嵌入边界**——「总是整体读」的嵌、「独立更新/大量共享」的引用。

Mongo 的甜区：**内容管理（灵活字段）、事件记录（schema 演化快）、单聚合对象为主的应用**；弱区：多实体复杂关联分析（JOIN 弱——聚合管道可做但费劲）、强事务多表业务（主库仍推荐关系型）。

## 3. CAP：分布式的白话三选二

```text
C（一致性）：所有节点同一时刻看到相同数据
A（可用性）：每个请求都有响应（可能不是最新）
P（分区容忍）：网络断开（节点分裂）时系统仍能运作

CAP：分区（P）在分布式系统里必然发生 → 实际是「分区时选 C 还是 A」
  CP：分区时拒绝服务保一致（ZooKeeper/多数分布式库）
  AP：分区时继续服务保可用（可能读到旧值）（Cassandra/多数 NoSQL）
```

白话版：**网络一定会断，断的时候你要么停服务保正确（CP），要么继续服务冒陈旧风险（AP）**——单机数据库没有这个问题（P 不存在，天然 CA）。CAP 不是「选型公式」而是「故障时的行为预期」：Redis 主从是 AP（故障切换可能丢尾），关系库主从半同步配置可以偏向 CP——「你的一致性需求 + 故障时的业务表现」才是选型语言。

## 4. 选型决策树

```text
数据的访问模式是？
├── 需要 SQL/多表关联/强事务 → 关系型（PostgreSQL/MySQL）★ 默认
├── 键值访问 + 低延迟 + 可重建 → Redis（缓存/会话/计数/排行榜）
├── 文档形态 + schema 快速演化 + 单聚合读取 → MongoDB
├── 海量写入（日志/指标）+ 按时间/key 范围查 → Cassandra/TimescaleDB
└── 全文搜索/复杂聚合分析 → Elasticsearch（旁路索引，非主库）
```

组合常态（[第 1 篇](01-db-model.md)的回归）：**PostgreSQL 主库 + Redis 缓存 + ES 搜索**——每种引擎守自己的专项，主数据仍归关系型（有唯一真相源）。

## 5. 陷阱清单

- Redis 当主数据库（无认真持久化与容量规划）：丢数据事故；Redis 管「可重建」的数据。
- 缓存与 DB 一致性用「更新缓存」：并发写乱序；「更新库 + 删缓存」+ 短 TTL。
- 无 TTL 的缓存键堆积：内存满触发淘汰策略把热键也逐出；所有缓存键带 TTL。
- 穿透/击穿/雪崩无预案：高流量下的 DB 崩溃三连；空值缓存/互斥/抖动。
- MongoDB 万物嵌套（文档巨大逼近 16MB）：嵌入边界按访问模式；大数组引用化。
- 用 CAP 当选型公式（「我们要 CA」）：P 不可选；按「故障时的业务表现」谈一致性。
- NoSQL 引入后主数据无真相源：多库写同一事实；主库归关系型，其他是派生视图。

## 6. 小结

- NoSQL = 专项工具：Redis 换速度、Mongo 换 schema 灵活、Cassandra 换写入吞吐——「按访问模式放弃部分保证」是本质，不是 SQL 替代品。
- Redis 的五种结构对应五类问题；缓存三故障（穿透/击穿/雪崩）各有标准对策；TTL 抖动与「更新库删缓存」是一致性纪律。
- Mongo 的核心决策是嵌入 vs 引用（按访问模式）；甜区在文档形态与 schema 演化快的场景。
- CAP 的白话版：「分区发生时保一致还是保可用」——它是故障行为预期，不是选型公式；单机无此问题。
- 现代架构默认组合：关系主库 + Redis + ES——专项引擎守专项，主数据有唯一真相源。

## 7. 练习

**1.** 用 Redis 实现三个组件：带 TTL 的会话存储、原子计数接口限流器（INCR + EXPIRE）、ZSET 排行榜（含并列名次语义的讨论）——每个组件写出关键命令序列与过期/并发考量。

> [!TIP]
> 思路限流器的窗口语义（固定窗口的临界双倍问题 → 滑动窗口 ZSET 方案）；排行榜并列用 ZSET 的同分数排序（字典序）——每个「简单组件」都有一层并发/语义设计。

**2.** 给一个「商品详情页」设计缓存：Cache-Aside 流程、TTL 抖动、防穿透（空值缓存）、防击穿（热点互斥重建）——用伪代码写出读路径的完整逻辑。

> [!TIP]
> 思路读路径的分支树：命中→返回；未命中→锁竞争→单飞重建→其他等待者重试。把「三大故障的对策」组装进一个函数，是缓存工程的综合考题。

**3.** 对比同一「博客系统」在 PostgreSQL 与 MongoDB 的建模：文章/评论/标签。写出两种 schema 与各自的核心查询，分析「评论分页」「标签聚合」「改标题」的操作成本。

> [!TIP]
> 思路PG：三表 join（规范）；Mongo：评论嵌入（分页要 slice）+ 标签数组多键索引。聚合查询的 Mongo aggregation pipeline 比 SQL GROUP BY 啰嗦——「关联分析是关系型的主场」在代码量上可见。

**4.** 演练「缓存与数据库不一致」：模拟「更新 DB 成功、删缓存失败」的时序，讨论三种缓解（重试队列/短 TTL 兜底/binlog 订阅删除）的取舍。

> [!TIP]
> 思路删除失败是常态而非异常——「短 TTL 兜底 + 订阅 binlog 异步删」把一致性从「尽力」升级为「机制」。缓存一致性的尽头是「可容忍窗口」的业务定义。

**5.** 用 CAP 白话分析三个故障场景：Redis 主从切换丢 1 秒数据、Mongo 副本集选举期间不可写、PostgreSQL 同步复制主库故障后从库拒绝服务——各属于 C 还是 A 的选择？业务上可接受吗？

> [!TIP]
> 思路每个场景问「分区/故障时系统做了什么选择」：丢尾数据=选 A、拒绝写入=选 C。「可接受性」由业务（会话丢失 vs 订单丢失）决定——CAP 的落地是业务对话。

**6.** 讨论：为什么「组合使用」（PG+Redis+ES）比「一个 NoSQL 全包」更常见？从「唯一真相源」「各引擎的专项优化」「运维复杂度」三角度分析，并说明你如何在「工具数量」与「专项收益」之间划线。

> [!TIP]
> 思路真相源唯一是审计/恢复/一致性的锚；专项引擎的性能是通用引擎难及的。划线的信号：数据副本同步的复杂度开始超过专项收益——每加一个引擎都是一份一致性债务。
