索引是**用写入与空间换查询速度**的结构化交易（[第 5 篇](05-schema.md)反范式的近亲）：没有索引的查询是全表扫描（O(n)），有索引是 B 树查找（O(log n)）——千万行的表，前者分钟级、后者毫秒级。但索引不是免费的：每个索引都要在每次写入时维护。本篇讲机制、设计与诊断。

## 1. B 树：为什么是 O(log n)

```text
B 树（简化示意，按 user_id 建索引）：
                [ 40 | 75 ]
               /     |      \
      [10|25]     [55|60|70]    [80|95]        ← 内部节点：键 + 分支指针
      /  |  \       ...
   叶子层: [1|3|5|8|10|12|25|...] → 行指针     ← 叶子：键 + 行位置（有序链表）
```

查找 `id = 60`：从根出发逐层二分（3~4 次节点访问）→ 叶子 → 行——**树高即 IO 次数**（千万行的 B 树通常 3~4 层，每层一次页读取）。范围查询（`BETWEEN`/`ORDER BY`）同样高效：叶子层是有序链表，定位起点后顺链扫描。

这就是「WHERE 条件走索引」的判定标准：**条件必须能利用键的有序性**——等值、前缀、范围可以；「中间的 %」、对列做函数运算不能（第 5 节）。

## 2. 聚簇索引与二级索引（InnoDB 模型）

```text
InnoDB（MySQL）的两种索引：
聚簇索引（主键）：叶子 = 完整行数据。表即索引（按主键物理排序存储）。
二级索引（name）：叶子 = 索引列 + 主键值。查 name 后再回主键树取整行（回表）。
```

两个工程推论：

1. **按主键查询最快**（一次树）；二级索引多一次「回表」。
2. **主键应当有序且短**：随机主键（UUID v4）导致 B 树插入点随机（页分裂、缓存失效）——UUIDv7/自增的有序性（[第 5 篇](05-schema.md)）正是为此。

PostgreSQL 的堆表模型不同（索引都存行指针，无聚簇概念）——**「回表」的代价在两家的实现里权重不同**，优化结论要按数据库核实。

## 3. 复合索引与最左前缀

```sql
CREATE INDEX idx_user_created ON orders (user_id, created_at);
```

复合索引是**按列序排的多级排序**（先按 user_id 排、同 user_id 内按 created_at 排）。于是：

```sql
WHERE user_id = 5                              -- ✅ 走索引（最左列）
WHERE user_id = 5 AND created_at > '2026-09-01' -- ✅ 两列都利用
WHERE created_at > '2026-09-01'                -- ❌ 不走此索引（跳过了首列！）
WHERE user_id = 5 ORDER BY created_at          -- ✅ 排序也免了（索引有序）
```

**最左前缀原则**：索引 (a, b, c) 支持 a、a+b、a+b+c 的查询——不支持 b、c 或 b+c。由此推出设计法：

- **等值列在前、范围列在后**：`(user_id, created_at)` 而不是反过来（等值列先「钉死」前缀，范围列才能继续用有序性）。
- **一个 (a,b) 复合索引 ≈ 同时服务 a 与 a+b 两类查询**——索引不是越多越好，而是「一组复合索引覆盖多类查询」。
- 区分度高的列放前（低区分度列如 status 放后或单独评估）。

## 4. 覆盖索引：免回表的极速形态

```sql
-- 查询只需要索引里已有的列：
SELECT user_id, created_at FROM orders WHERE user_id = 5;
-- (user_id, created_at) 索引本身包含这两个列 → 索引扫描即完成，无需回表（Index Only Scan）
```

覆盖索引（covering index）把「查索引 → 回表」的两步变成一步——热点查询（仪表盘计数、列表页的字段）值得为它多索引几个列。`INCLUDE` 列（PG 11+）是「只为覆盖、不参与查找」的附加列专用语法。

## 5. EXPLAIN：与优化器对话

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 5 ORDER BY created_at DESC LIMIT 10;
```

```text
Limit (cost=0.43..12.20 rows=10) (actual time=0.03..0.08 rows=10)
  → Index Scan using idx_user_created on orders
       Index Cond: (user_id = 5)                     ← ✅ 索引命中
       (actual rows=10 loops=1)
```

读计划的关键字段：

| 看什么                       | 含义                                             |
| ---------------------------- | ------------------------------------------------ |
| `Seq Scan` vs `Index Scan`    | 全表扫描（大数据表上=警报）vs 索引查找             |
| `Index Cond` / `Filter`       | 索引内命中 vs 扫描后再过滤（Filter 多=索引没充分利用）|
| `rows=估算 vs actual`         | 估算偏差大 → 统计信息过期（ANALYZE 表）            |
| `Nested Loop / Hash Join`     | [第 3 篇](03-joins.md)的算法选择                  |
| `cost`                        | 代价估算（相对值，非毫秒）                          |

优化流程：**EXPLAIN ANALYZE → 找 Seq Scan/大 Filter/估算偏差 → 加索引或改写 → 再 EXPLAIN 验证**——「改 SQL → 测」循环必须由计划驱动，不靠猜（[第 2 篇](02-sql-select.md)的 OFFSET 案例就是用计划验证的）。

## 6. 索引失效的六类现场

```sql
-- ① 对索引列做函数/运算
WHERE DATE(created_at) = '2026-09-19'      -- ❌ 改：created_at >= '2026-09-19' AND < '2026-09-20'
WHERE price * 2 < 100                      -- ❌ 改：price < 50

-- ② 前缀通配符（B 树按前缀排序，%开头无法定位）
WHERE name LIKE '%son'                     -- ❌ 后缀搜索：反转列技巧/全文索引/trigram

-- ③ 隐式类型转换
WHERE phone = 13800138000                  -- ❌ phone 是 varchar：转类型 + 索引失效

-- ④ OR 混合（一侧无索引 → 全扫）
WHERE a = 1 OR b = 2                       -- 两侧各有索引时可用（bitmap）；否则改 UNION

-- ⑤ 低区分度列单独索引
WHERE status = 'active'                    -- 90% 行都满足 → 优化器宁可全表扫描

-- ⑥ 最左前缀断裂
-- 见第 3 节
```

「函数包列」的通用修法是**把运算移到常量侧**或建**函数索引**（`CREATE INDEX ON t (DATE(created_at))`——PG 支持，查询写法要匹配）。

## 7. 索引的成本与生态

每个索引的成本：**每次 INSERT/UPDATE 删改都要维护**（B 树插入 + 可能页分裂）、占空间（可达数据本身大小）。索引不是越多越好：

- 写密集表慎加索引；「查询慢才加、加完看写入影响」是迭代节奏。
- 定期检查**未使用的索引**（PG 的 `pg_stat_user_indexes`）——无人使用的索引是纯负担，DROP。
- 特殊索引类型：HASH（等值）、GIN（JSONB/全文/数组）、GiST（范围/地理）、**部分索引**（`WHERE deleted_at IS NULL` 的部分索引——软删除场景的精确索引）。

## 8. 陷阱清单

- 复合索引列序随缘：等值前、范围后、区分度高的前。
- 函数包索引列：改写条件或函数索引。
- 前缀 % 的 LIKE 当可索引：换方案（反转/trigram/全文）。
- 隐式转换毁索引：比较双方类型一致（[第 2 篇](02-sql-select.md)）。
- 不看 EXPLAIN 凭感觉加索引：计划驱动优化；ANALYZE 更新统计。
- 索引堆积不清理：写放大与空间；pg_stat 找未使用索引。
- 忘记软删除的索引配合：`WHERE deleted_at IS NULL` 的部分索引。

## 9. 小结

- B 树索引 = 树高即 IO 次数的有序结构：等值/范围/排序全靠「键的有序性」；失效的六类现场全是「有序性被破坏」的变体。
- 聚簇与二级的差异推出「主键短而有序」与「回表」概念；覆盖索引（Index Only Scan）是热点查询的免回表形态。
- 复合索引的最左前缀 + 「等值前、范围后」设计法：一组复合索引覆盖多类查询优于多个单列索引。
- EXPLAIN ANALYZE 是优化的方向盘：Seq Scan 警报、估算偏差、算法选择——计划驱动而非猜测驱动。
- 索引是写入税：查询慢才加、加完测写入、未使用即清理；软删除与部分索引是现代搭配。

## 10. 练习

**1.** 造一张 100 万行表（generate_series），分别对「有索引列」「无索引列」「函数包裹的索引列」跑同量级查询，用 EXPLAIN ANALYZE 记录三者耗时与扫描方式。

> [!TIP]
> 思路预期：索引 O(log n) 毫秒、全表扫描百毫秒、函数包裹退化成全扫。「六类失效」不用背——做一遍就永久记得。

**2.** 为查询集设计索引：`(a) WHERE status AND created_at`、`(b) WHERE user_id ORDER BY created_at`、`(c) WHERE user_id AND status`——给出最少索引数方案并验证（提示：复合索引的列序与覆盖）。

> [!TIP]
> 思路`(user_id, status, created_at)` 一个索引可同时服务 b 与 c（等值列都在前）；a 的 status 低区分度单独评估。索引设计是「查询集 → 索引集」的映射问题。

**3.** 对比「深分页 OFFSET」与「游标分页」的 EXPLAIN（[第 2 篇](02-sql-select.md)练习 5 的落实验证）：记录两版的执行计划与耗时曲线（页越深差距越大）。

> [!TIP]
> 思路OFFSET 的耗时随页深线性增长（丢弃行数增长）；游标几乎恒定。EXPLAIN 里 OFFSET 版的「rows removed」就是被浪费的工作量。

**4.** 实验「写放大」：对同一张表建 0/1/5/10 个索引，各插入 10 万行计时——画出索引数与写入耗时曲线。

> [!TIP]
> 思路曲线陡增处即「索引税」的体感。结论沉淀为设计纪律：写密集表的每个索引都要有明确的查询受益者。

**5.** 找出系统里（或造出）一个「估算偏差」的执行计划：表频繁写入后不 ANALYZE，EXPLAIN 的 rows 估算 vs actual 差一个量级；执行 ANALYZE 后对比——理解统计信息是优化器的眼睛。

> [!TIP]
> 思路优化器按统计估算代价选计划——统计过期会让它「选错索引/算法」。autovacuum/analyze 的配置与大批量导入后手动 ANALYZE 的习惯由此而来。

**6.** 讨论：为什么「加索引」不能当性能问题的万能药？从「写入税」「重复索引」「优化器选择」「真正的瓶颈可能在别处（N+1/锁/配置）」四个角度，给出一个「加索引前的问题清单」。

> [!TIP]
> 思路清单：这条查询真的慢吗（观测）？计划显示索引能帮上吗（EXPLAIN）？有没有更根本的改写（分页方式/查询结构）？写入代价可接受吗？——「测量→计划→改写→索引」的顺序，索引是最后一步而非第一步。
