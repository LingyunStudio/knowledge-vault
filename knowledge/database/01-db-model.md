为什么需要数据库？把数据存进文件（[C 篇的 IO](../c/05-arrays-strings.md)、[python 篇](../python/10-files-context.md)）不就行了？这个问题的答案定义了数据库的全部价值：**持久化**（崩溃后数据完好）、**并发**（百个用户同时读写不出乱子）、**查询**（从亿行中毫秒级找出你要的）。本篇建立数据库世界的三张底图——它解决什么、关系模型长什么样、SQL 与 NoSQL 如何选。

## 1. 文件方案的三个崩溃点

设想用 CSV 文件 + 自写代码管理一个电商的订单数据，很快遇到三堵墙：

```text
墙① 崩溃一致性：写一半断电 → 文件半行、引用错乱 —— 恢复要自己写检查与修复逻辑
墙② 并发损坏：两个请求同时写 → 互相覆盖（read-modify-write 的竞态）
墙③ 查询低效：找「上个月买过 A 产品的上海用户」→ 全文件扫描，亿行 = 分钟级
```

数据库在每一堵墙前都有机制化的答案（后面各篇展开）：

| 墙         | 数据库的机制                            | 本教程对应篇              |
| ---------- | --------------------------------------- | ------------------------- |
| 崩溃一致性 | 事务（ACID）+ WAL/redo log + 恢复        | [第 7 篇](07-transactions.md) |
| 并发       | 锁与 MVCC + 隔离级别                     | [第 7 篇](07-transactions.md) |
| 查询       | 声明式 SQL + 优化器 + 索引（B 树）        | [第 2 篇](02-sql-select.md)、[第 6 篇](06-index.md) |

「数据库 = 管理好的数据 + 一层软件保证」——**它是一个承诺系统**：只要你在事务里操作，数据库用工程手段兑现「数据不丢、并发不乱、查询够快」。这份承诺的代价是数据库进程本身（资源占用、运维成本）——所以小到 SQLite（单文件嵌入式）、大到分布式集群，按需求规模选形态。

## 2. 关系模型：表、行与约束

关系模型（Codd, 1970）把数据组织成**表（relation）**：行（记录）× 列（字段），核心是「数据的一致性由约束保证」：

```sql
CREATE TABLE users (
    id       BIGINT PRIMARY KEY,              -- 主键：唯一标识一行
    email    VARCHAR(255) NOT NULL UNIQUE,    -- 非空 + 全表唯一
    name     VARCHAR(100) NOT NULL,
    age      INT CHECK (age >= 0),            -- 值域约束
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id       BIGINT PRIMARY KEY,
    user_id  BIGINT NOT NULL REFERENCES users(id),  -- 外键：必须指向存在的用户
    amount   NUMERIC(10,2) NOT NULL CHECK (amount > 0),
    status   VARCHAR(20) NOT NULL DEFAULT 'pending'
);
```

关系模型的四个支柱概念：

1. **主键（PRIMARY KEY）**：行的唯一身份——查询、更新、外键引用都靠它。
2. **外键（FOREIGN KEY）**：表间引用的完整性——「订单的 user_id 必须真实存在」由数据库强制（应用层漏判也坏不了数据）。
3. **约束（NOT NULL/UNIQUE/CHECK）**：把业务规则下沉到存储层——脏数据在写入时被拒绝而不是查询时被发现。
4. **类型系统**：每列强类型（数值/文本/时间）——比较与索引的行为可预期。

「约束即契约」的哲学与 [C 结构体](../c/08-structs-unions.md)的布局契约、[Rust 的类型系统](../rust/01-getting-started.md)一脉相承：**错误尽早暴露在写入端**。

## 3. SQL：声明式查询的语言

SQL 的革命性在于**声明式**：你说「要什么」，不说「怎么拿」：

```sql
SELECT u.name, COUNT(o.id) AS order_count, SUM(o.amount) AS total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at >= '2026-09-01'
GROUP BY u.id
HAVING COUNT(o.id) >= 3
ORDER BY total DESC
LIMIT 10;
```

这段话的执行方式（先扫描谁、怎么连接、用不用索引）由**优化器**决定——你写意图，它选路径。对比文件方案的手写循环：声明式把「查询策略」从应用代码剥离到数据库的专业领域（代价是复杂 SQL 的优化不可控——[第 6 篇](06-index.md)的 EXPLAIN 就是与优化器对话的语言）。

SELECT 的子句逻辑顺序（不是书写顺序）：FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT——记住执行序，「为什么 WHERE 里不能用别名」这类问题自动消解。

## 4. 谱系：SQL 与 NoSQL 的地形图

| 类型         | 代表                | 数据模型             | 强项                        | 弱项                       |
| ------------ | ------------------- | -------------------- | --------------------------- | -------------------------- |
| 关系型       | PostgreSQL、MySQL、SQLite | 表 + SQL         | 复杂查询、事务、一致性、生态 | 水平扩展 historically 弱    |
| 文档型       | MongoDB             | JSON 文档            | 灵活 schema、嵌套读、水平扩展 | 跨文档事务弱（已改善）、join 弱 |
| 键值型       | Redis、DynamoDB     | key → value          | 极快读写（内存/简单模型）    | 只有 key 查询、无复杂查询   |
| 宽列          | Cassandra           | 行键 → 列簇           | 海量写入、线性扩展           | 查询模式受限                 |
| 搜索引擎      | Elasticsearch       | 倒排索引的 JSON       | 全文检索、聚合分析           | 不是主数据源（一致性弱）     |
| 图            | Neo4j               | 节点 + 边            | 深度关系遍历                 | 通用查询弱                  |

选型的元规则：**关系型是默认答案**——绝大多数应用的主体数据（用户/订单/内容）都有「结构 + 关联 + 事务」需求，这正是关系型的主场；NoSQL 是**特定问题的专项工具**：缓存与会话（Redis）、日志与物联网写入（Cassandra）、全文搜索（ES）、灵活嵌套的文档（MongoDB）。「NoSQL 替代 SQL」是一个时代的误会——现代架构通常是 **PostgreSQL 做主库 + Redis 做缓存 + ES 做搜索**的组合（[第 9 篇](09-nosql.md)展开）。

## 5. 主流关系库的定位

| 数据库     | 定位                  | 特点                                        |
| ---------- | --------------------- | ------------------------------------------- |
| SQLite     | 嵌入式/单文件          | 零运维、随应用走；移动端、桌面、小站点的默认  |
| PostgreSQL | 功能最全的开源关系库   | 类型丰富（JSONB/数组/范围）、扩展性强、标准严格 |
| MySQL      | 互联网行业老牌         | 生态成熟、复制方案多；InnoDB 为主力引擎       |
| 商业（Oracle/SQL Server） | 企业遗留与特定行业 | 成本高、与厂商生态绑定                      |

学习策略：**SQL 语法 90% 通用，10% 方言**——本教程以 PostgreSQL/MySQL 兼容写法为主，方言差异在[第 8 篇](08-advanced-sql.md)汇总。SQLite 的「零成本」让它成为学习与单机应用的完美起点（[python 篇](../python/10-files-context.md)的 sqlite3 就是它）。

## 6. 陷阱清单

- 用文件/内存结构当数据库：崩溃与并发两手空空；有持久状态就上数据库（SQLite 也算）。
- 把约束留个应用层：脏数据从旁路写入；约束下沉到 schema。
- 「NoSQL 万能」或「SQL 落伍」：按数据形态与查询模式选型；主库默认关系型。
- SQL 性能靠猜：优化器与 EXPLAIN 是对话对象（[第 6 篇](06-index.md)）。
- 忽视 NULL 的语义（三值逻辑）：NULL 与比较、聚合的交互有独立规则（[第 2 篇](02-sql-select.md)）。
- 一开始就分布式/分库分表：先榨干单机（索引/读写分离），绝大多数应用到不了分库的规模。

## 7. 小结

- 数据库对文件方案的三胜：崩溃一致性（事务+恢复）、并发（锁+MVCC）、查询（SQL+优化器+索引）——它是一个「承诺系统」。
- 关系模型四支柱：主键身份、外键引用完整性、约束即契约、列强类型——错误在写入端暴露。
- SQL 是声明式的：写意图、优化器选路径；子句执行序 FROM→JOIN→WHERE→GROUP→HAVING→SELECT→ORDER→LIMIT。
- 谱系选型：关系型做主库是默认，NoSQL 是专项工具（缓存/搜索/海量写/文档）；现代架构多为组合。
- SQLite 起步、PostgreSQL/MySQL 进阶、方言差异集中在 10%——学习的重心在通用 SQL 与数据库思维。

## 8. 练习

**1.** 用 SQLite（或任意数据库）重现「文件方案的三个崩溃点」：写脚本向 CSV 并发追加 1000 行（两个进程），对比向表插入的行数正确性——用实验体会「并发保护」的价值。

> [!TIP]
> 思路Python 多进程同时 append 同一 CSV：行交错/覆盖；同时 INSERT 同表：SQLite 用锁排队，行数精确 2000。这个实验把「数据库值 100 倍复杂度」的理由变成亲历。

**2.** 写出用户-订单-商品-订单项四张表的 CREATE TABLE（含主键/外键/CHECK），并故意插入违反约束的数据观察报错——总结每类约束拦截了什么错误。

> [!TIP]
> 思路订单项 = 订单与商品的多对多桥表（[第 5 篇](05-schema.md)展开）。实验：外键指向不存在的用户（拒绝）、amount=-1（拒绝）、重复 email（拒绝）——三类脏数据在门口被拦。

**3.** 把下面的需求翻译成 SQL（只写查询，不查表结构）：「2026 年注册、且订单总数超过 5 笔的用户姓名与总消费，按总消费降序前 10」——遇到不确定的子句语义就查手册。

> [!TIP]
> 思路需要 JOIN + WHERE（注册时间）+ GROUP BY + HAVING（笔数）+ ORDER + LIMIT——一次覆盖 SELECT 篇与聚合篇的主干。写不出来是正常的，这正是接下来两篇的内容。

**4.** 安装 SQLite 并用 `sqlite3` 命令行完成：建表、插入、查询、`.schema` 查看结构、`.mode column` 美化输出——掌握「最小可用的数据库环境」。

> [!TIP]
> 思路SQLite 单文件零安装（各平台自带或一条命令），`sqlite3 test.db` 即进入。工具链的摩擦越小，练习频率越高。

**5.** 调研你熟悉的一个产品（或设想的产品），列出它的三类数据（如：用户订单、会话缓存、全文搜索），为每类选数据库并说明理由——用本篇的谱系表做支撑。

> [!TIP]
> 思路典型组合：订单（PostgreSQL/MySQL：事务与关联）、会话（Redis：低延迟 KV）、商品搜索（ES：全文与聚合）。「按数据特征分库」是现代架构的默认思维。

**6.** 讨论：为什么「数据库是承诺系统」这个视角比「数据库是存数据的软件」更有工程价值？从「事务承诺换来应用代码简化」的角度，分析如果你的应用把「一致性保证」自己写（如文件锁 + 手动校验）会多出哪些代码与风险。

> [!TIP]
> 思路自己写一致性 = 重造 WAL、锁管理、恢复逻辑——且大概率有并发漏洞。把「难而通用的问题」交给专门系统、应用专注业务逻辑——工程分层的基本原理在存储领域的体现。
