数据库是大多数系统的「最后一道持久防线」——它的运维标准必须高于应用：**备份必须可恢复、慢查询必须可观测、故障必须可切换**。本篇覆盖数据库运维的四条主线（备份/性能/复制/监控），并把全书陷阱汇编成审查清单。

## 1. 备份：唯一不可妥协的事

```bash
# PostgreSQL 逻辑备份（SQL 级，跨版本友好）
pg_dump -Fc mydb > mydb-$(date +%F).dump          # 自定义格式（可选择性恢复）
pg_restore -d mydb_new mydb-2026-09-19.dump

# 物理备份（文件级，大库/PITR 用）：基础备份 + WAL 归档 → 任意时间点恢复
# MySQL：mysqldump（逻辑）/ XtraBackup（物理）
```

备份的三条铁律：

1. **恢复演练才是备份的验收**：没有恢复过的备份只是「心理安慰」——定期在测试环境执行完整恢复并计时（RTO：多久能恢复；RPO：能容忍丢多少）。
2. **3-2-1 原则**：3 份副本、2 种介质、1 份异地——备份与主库同机等于没备份（机器炸全没）。
3. **备份加密与权限**：备份文件包含全部数据（比数据库更「集中」的秘密）——加密存储、访问受限。

「删库跑路」类事故的防线不在「小心删」而在**备份的存在**（[git 篇](../git/01-object-model.md)的镜像：内容寻址的历史 + 异地副本）。

## 2. 慢查询治理：观测驱动的性能

```sql
-- PG：慢查询日志（超过 200ms 记录）
log_min_duration_statement = 200
-- MySQL：slow_query_log + long_query_time = 0.2
```

治理流程（与[第 6 篇](06-index.md)的 EXPLAIN 闭环）：

```text
慢日志捕获 → 按频率×耗时排序（pt-query-digest/pg_stat_statements 聚合）
→ Top N 逐条 EXPLAIN ANALYZE → 加索引/改写/缓存 → 回归验证
```

`pg_stat_statements`（PG）这类**统计视图**的价值是「聚合视角」：单条查询看 EXPLAIN，重复执行的查询看总耗时与调用次数——「每秒 1000 次的 5ms 查询」比「每天一次的 5s 查询」更值得优化。

除 SQL 本身外的性能信号：**连接数**（max_connections 水位，[第 10 篇](10-orm-access.md)池容量）、**锁等待**（长事务/死锁频率）、**缓存命中率**（shared_buffers 命中低=内存不足）、**复制延迟**（主从架构的读新鲜度）。

## 3. 复制：冗余与读写分离

```text
主库（写）──流复制/WAL──→ 从库（读）
   │                          │
  唯一写入口              读请求分流（报表/查询）/ 故障接替
```

- **异步复制**（默认）：主提交不等从——主库宕机可能丢最后一段（AP 取向，[第 9 篇](09-nosql.md)的 CAP）。
- **同步复制**：至少一个从库确认才提交——不丢但主库写延迟受从库牵制（CP 取向）。
- **读写分离**的坑：复制延迟下的「写后读不一致」（写完主库立刻读从库读到旧值——用户改头像「没生效」）——对策：写后读走主库（会话级粘性）或版本戳校验。

故障切换（failover）的自动化（ Patroni/云厂商高可用）是把「从库提升为主库」流程化——**自动切换的前提是故障检测可靠**（误切换比宕机更糟——脑裂双主）。运维视角的清单：切换演练定期做、半同步/仲裁机制明确、应用层的连接串支持发现新主。

## 4. 监控指标：数据库的体检单

| 维度       | 指标                             | 警报信号                          |
| ---------- | -------------------------------- | --------------------------------- |
| 连接       | 当前连接数/max                    | >80%；连接等待事件                 |
| 性能       | 慢查询数、QPS、p95 延迟           | p95 突增                            |
| 锁         | 锁等待数、死锁频率、长事务        | 长事务 > 1h（MVCC 膨胀，[第 7 篇](07-transactions.md)）|
| 存储       | 磁盘水位、表/索引膨胀、WAL 生成量 | >80%（[第 6 篇](06-index.md)的 vacuum 配合）|
| 复制       | 复制延迟（字节/秒）               | 延迟持续增长                        |
| 命中       | 缓存命中率                        | <95%（内存不足信号）                |

磁盘是数据库的「氧气」：**满盘 = 数据库停摆**（写不了 WAL）——80% 告警线（[linux 篇](../linux/11-ops-pitfalls.md)）对数据库要提到 70%。

## 5. 高危操作清单

```sql
-- 这些操作在业务库上要先三思（锁表/重写全表）：
ALTER TABLE big_table ADD COLUMN ... NOT NULL DEFAULT ...;   -- 旧 PG/MySQL 会重写全表（锁）！
CREATE INDEX ON big_table (...);            -- 锁写——用 CREATE INDEX CONCURRENTLY（PG）
ALTER TABLE ... SET TYPE ...;               -- 全表重写
DROP TABLE / TRUNCATE;                      -- 物理删除（备份的用武之地）
UPDATE 大表无索引 WHERE                      -- 全表锁行 + 长事务（分批执行！）
```

大表 DDL 的纪律：**了解本库的 DDL 锁语义**（PG 的 CONCURRENTLY、MySQL 8 的 online DDL）、低峰执行、有回滚预案。大批量 UPDATE 的分批模式（每批 1 万行 + 提交）避免长事务与主从延迟风暴（[第 7 篇](07-transactions.md)的事务最小化在 DDL/DML 的延伸）。

## 6. 五类陷阱审查清单

### 6.1 数据安全

- [ ] 备份存在、定期恢复演练、3-2-1、加密
- [ ] 最小权限账号（应用不给 superuser）；审计敏感表访问
- [ ] 秘密不进代码（连接串走环境/secret，[第 10 篇](10-orm-access.md)）
- [ ] 高危 DDL/DML 有流程（事务包裹、备份先行、低峰窗口）

### 6.2 性能

- [ ] 慢查询日志开启且有治理节奏
- [ ] EXPLAIN 进过日常（新查询上线前看计划）
- [ ] 索引有审查（未使用清理/写放大评估）
- [ ] 分页/大查询的深翻页方案（游标分页）

### 6.3 并发

- [ ] 事务范围最小；无事务内外部调用
- [ ] 关键读改写有锁策略（FOR UPDATE/乐观锁）
- [ ] 死锁错误可重试；锁等待有监控
- [ ] 批处理分批提交（长事务红线）

### 6.4 可用性

- [ ] 复制存在且延迟受监控；切换方案演练过
- [ ] 连接池参数评审过（容量/recycle/timeout）
- [ ] 磁盘/连接/复制延迟有告警（70%/80% 线）
- [ ] 迁移有 expand-migrate-contract 纪律

### 6.5 设计（回指前篇）

- [ ] 约束下沉（NOT NULL/UNIQUE/CHECK/FK）（[第 5 篇](05-schema.md)）
- [ ] 类型正确（金额 NUMERIC、时间 TIMESTAMPTZ）
- [ ] NULL 语义与三值逻辑的坑规避（[第 2 篇](02-sql-select.md)）
- [ ] 缓存层的一致性策略（[第 9 篇](09-nosql.md)）

## 7. 小结

- 备份三铁律：恢复演练是验收、3-2-1、加密受限——「删库」的防线是备份不是小心。
- 性能治理是观测闭环：慢日志 → 聚合统计（pg_stat_statements）→ EXPLAIN → 索引/改写 → 回归——「按频率×耗时排序」找到真热点。
- 复制的取舍：异步（性能/可能丢尾）vs 同步（不丢/延迟受制）；读写分离的写后读一致性要用会话粘性解决；切换要演练。
- 监控体检单六维（连接/性能/锁/存储/复制/命中）——磁盘 70% 线、长事务红线、连接水位是三大高频警报。
- 高危操作的机制化谨慎：DDL 锁语义、分批提交、备份先行——「三思」变成流程才可靠。

## 8. 练习

**1.** 做一次完整备份-恢复演练：pg_dump 备份 → 新库 pg_restore → 校验行数与抽样数据一致 → 计时。写出 RTO/RPO 的定义并用你的演练数据填写。

> [!TIP]
> 思路恢复计时的每一个环节（传输/建库/导入/校验）都是 RTO 的组成——「备份 5 分钟、恢复 5 小时」的方案要重设计。演练频率写入运维日历。

**2.** 治理一轮慢查询：开启慢日志/统计视图 → 跑一段模拟负载 → 找出 Top 3 → EXPLAIN → 修复（索引/改写）→ 复测。产出「优化前后对比表」。

> [!TIP]
> 思路对比表字段：SQL、调用次数、修复前均值、修复后均值、手段。用数据说话的优化记录是团队知识库的高价值条目。

**3.** 搭一个主从复制（PG 流复制），写后读从库验证延迟（写一条立刻查从库，观察延迟窗口），再制造主库故障演练手动切换——记录延迟观察与切换步骤。

> [!TIP]
> 思路延迟窗口实验直接演示「写后读不一致」的用户体验——「写后读走主库」的需求从体验里长出来。手动切换演练是自动切换（Patroni）的必经前置。

**4.** 设计监控看板：为你的数据库选 8 个核心指标（本篇第 4 节选），定义每个的告警阈值与响应动作——说明为什么「长事务 >1 小时」值得一条独立告警。

> [!TIP]
> 思路长事务的连锁反应（锁持有 + MVCC 膨胀 + 复制延迟）让它成为「单指标多后果」的警报点——监控设计的价值排序：后果乘数大的指标优先。

**5.** 演练「大表加列」的 expand-migrate-contract：100 万行表加一个带默认值的 NOT NULL 列——对比直接 ALTER 与四步法的锁行为（EXPLAIN/文档对照），记录分批回填的脚本要点。

> [!TIP]
> 思路PG 11+ 的元数据默认值优化让「加带默认值列」秒完成——版本差异直接影响 DDL 策略。「锁语义按版本核实」是 DDL 操作的前置步骤。

**6.** 讨论：为什么数据库运维的标准要「高于应用运维」？从「数据的不可再生性」「故障的放大半径」「恢复的时间成本」三个角度分析，并对照 [git 的异地备份](../git/01-object-model.md)与 [docker 镜像仓库](../docker/08-registry.md)——「冗余与演练」在三种系统里的共同哲学。

> [!TIP]
> 思路代码丢了仓库还有（可重写）、镜像丢了可重建（确定性构建）——只有数据库里的**用户数据**不可再生。三种系统的共同哲学：重要资产的「副本 + 演练 + 可追溯」缺一不可——演练是把纸面安全变成真实能力的唯一途径。
