事务是数据库承诺的兑现机制（[第 1 篇](01-db-model.md)）：**一组操作要么全成、要么全不成**——中间状态对他人不可见、崩溃后不残留半成品。本篇讲它的四层结构：ACID 的含义、应用层怎么用、并发会出什么事（现象）、数据库怎么防（隔离与锁）。

## 1. ACID：四个承诺的白话版

经典案例：转账 = A 扣 100 + B 加 100——两条 UPDATE 必须同生共死。

| 性质           | 白话                                   | 兑现机制                       |
| -------------- | -------------------------------------- | ------------------------------ |
| Atomicity 原子性 | 全成或全不成，没有中间态                | undo/回滚日志                   |
| Consistency 一致性 | 约束始终成立（余额不为负等）           | 约束 + 事务边界                  |
| Isolation 隔离性 | 并发事务互不干扰（各自像独占执行）        | 锁与 MVCC（本篇核心）            |
| Durability 持久性 | COMMIT 后断电也不丢                     | WAL（先写日志再写数据）          |

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;          -- 或 ROLLBACK;
```

**原子性靠回滚**、**持久性靠 WAL**、**隔离性靠下面的隔离级别**——一致性则是前三者加你的约束共同达成的业务结果。

## 2. 应用层的事务纪律

```python
# python 的 psycopg 风格
with conn.transaction():                      # 上下文管理器：异常自动 ROLLBACK
    deduct_balance(user, 100)
    create_order(...)
    add_order_items(...)                      # 任何一步抛异常 → 全部回滚
```

纪律清单：

1. **事务范围最小化**：只包数据库操作——事务里做 HTTP 调用/发消息/sleep 是反模式（连接与锁被长期占用，[第 10 篇](10-orm-access.md)的连接池被拖垮）。
2. **先验证后提交**：UPDATE 前的 SELECT 与 UPDATE 之间数据可能被别人改（下节的丢失更新）——关键场景用 `SELECT ... FOR UPDATE` 或乐观锁。
3. **交互式手动事务的两步纪律**（[第 2 篇](02-sql-select.md)）：BEGIN → UPDATE → 确认影响行数 → COMMIT/ROLLBACK。
4. **跨库/跨服务不是本地事务**：微服务间用 Saga/最终一致——本地事务的承诺不跨进程。

## 3. 并发四大现象：两个事务同时跑会怎样

两个并发事务 T1（读账户、改余额）与 T2 交错，可能出现的四种「不愉快」：

| 现象                     | 描述                                          | 严重度             |
| ------------------------ | --------------------------------------------- | ------------------ |
| 脏读 dirty read          | 读到**别人未提交**的数据（别人回滚你就读了空气） | 最严重（一般已杜绝）|
| 不可重复读 non-repeatable| 同一事务内**两次读同一行结果不同**（别人改了并提交）| 中                 |
| 幻读 phantom             | 同一条件**两次读行数不同**（别人插入/删除了符合条件的行）| 中               |
| 丢失更新 lost update     | 两人同时读 → 各自改 → **后提交覆盖前者的修改**   | 高（计数器/库存的经典事故）|

**丢失更新**值得演一遍：T1 读 stock=10 → T2 读 stock=10 → T1 写 9 → T2 写 9（本应 8）——「读-改-写」三步不原子。这是并发编程（[C 篇](../c/01-c-model.md)的数据竞争）在数据库里的镜像，解法也是同构的：锁或原子操作。

## 4. 隔离级别：现象的防控阶梯

| 级别                 | 脏读 | 不可重复读 | 幻读      | 代价             |
| -------------------- | ---- | ---------- | --------- | ---------------- |
| READ UNCOMMITTED     | 可能 | 可能       | 可能      | 最低             |
| READ COMMITTED       | ✅杜绝 | 可能       | 可能      | 低               |
| REPEATABLE READ      | ✅   | ✅杜绝      | PG 杜绝/MySQL 大部分 | 中（快照开销）|
| SERIALIZABLE         | ✅   | ✅         | ✅杜绝    | 高（冲突回退）    |

各库默认：**PostgreSQL/Oracle 为 READ COMMITTED，MySQL/InnoDB 为 REPEATABLE READ，SQLite 串行化**（单写者）。实用建议：**默认级别 + 明确的加锁动作**（FOR UPDATE/乐观锁）处理关键路径，而不是全局升到 SERIALIZABLE（冲突回退风暴）。

## 5. MVCC：不锁的读

现代数据库（PG/InnoDB）的隔离性主要靠 **MVCC（多版本并发控制）**而非读写锁：

```text
每行保存版本链（带事务 ID）：
读事务按「快照」看到自己开始时已提交的版本 → 读不加锁、读写不互相阻塞
写事务创建新版本 → 旧版本等无读者后由 vacuum/清理回收
```

推论：**读永远不阻塞写、写不阻塞读**（PostgreSQL 的招牌）——高并发的读写共存由此实现。代价：旧版本需要清理（PG 的 vacuum/膨胀问题）、快照长事务会阻碍清理（长事务是运维红线，[第 11 篇](11-ops-pitfalls.md)）。

## 6. 写冲突的两把锁：悲观与乐观

### 6.1 悲观锁：先锁再改（SELECT FOR UPDATE）

```sql
BEGIN;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;   -- 锁住这行（别人 FOR UPDATE 会等）
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

FOR UPDATE 给行上写锁直到事务结束——「读改写」变成原子。适用：**冲突概率高、持锁时间短**（秒杀扣库存的核心行）。纪律：**锁内不做慢操作**（[linux 篇](../linux/07-processes.md)锁内不调未知代码的同款）、**多行锁定顺序全局一致**（防死锁）。

### 6.2 乐观锁：版本号校验（不锁，提交时验证）

```sql
UPDATE cart SET quantity = 3, version = version + 1
WHERE id = 10 AND version = 7;          -- ★ 版本不对 = 别人改过 → 影响 0 行 → 重试
```

乐观锁用「读时记版本、写时验版本」替代锁——冲突时 UPDATE 影响 0 行，应用层重读重试。适用：**冲突概率低**（购物车编辑、CMS 内容）——无锁开销，冲突风暴时重试成本高（与 [CAS 原子操作](../cpp/13-concurrency.md)同思想）。

| 维度     | 悲观（FOR UPDATE）       | 乐观（版本号）             |
| -------- | ------------------------ | -------------------------- |
| 冲突概率高 | ✅（一次锁定完成）        | ❌（重试风暴）             |
| 冲突概率低 | ❌（白付锁开销）          | ✅（无锁）                 |
| 跨进程/长事务 | ❌（锁持有风险）      | ✅（无锁可跨请求）          |

## 7. 死锁：循环等待的数据库版

```text
T1 锁了行 A 想锁行 B；T2 锁了行 B 想锁行 A → 互相等待 → 死锁
数据库的解法：死锁检测器杀掉其中一个（报 deadlock 错误，回滚重试）
```

预防与应对：**多行更新按固定顺序**（如按 id 升序）、事务尽量短、**应用层对死锁错误重试**（死锁不是 bug，是并发竞争的正常结果——可重试性要设计进错误处理，[第 12 篇](../c/12-errors-robustness.md)的可恢复错误分类）。

## 8. 陷阱清单

- 事务里做 HTTP/RPC/sleep：锁与连接长期占用；事务只包数据库操作。
- 「读-改-写」三步无保护：丢失更新；FOR UPDATE 或版本号。
- 全局调高隔离级别治并发：冲突回退风暴；默认级别 + 关键路径显式加锁。
- 长事务/忘提交的连接：MVCC 版本堆积（PG 膨胀）+ 锁持有；连接池超时兜底。
- 死锁错误不重试：可重试错误要设计进调用链。
- 靠应用层「先查后改」保证一致性：查询与写入之间的竞态；数据库层锁定才是原子。
- 跨服务的「分布式事务」用本地事务硬凑：Saga/最终一致的领域。

## 9. 小结

- ACID 的实现分工：原子性靠回滚、持久性靠 WAL、隔离性靠 MVCC/锁、一致性是业务结果——事务是「一组操作的系统级原子性」。
- 应用纪律：事务范围最小、关键读改写显式加锁、死锁可重试、跨服务不走本地事务。
- 四大现象与隔离阶梯：默认 READ COMMITTED/REPEATABLE READ + 关键路径显式锁，优于全局串行化。
- MVCC 让读写互不阻塞（快照读），代价是版本清理与长事务敏感——高并发的机制基础。
- 写冲突两把锁：悲观 FOR UPDATE（高冲突、短临界区）与乐观版本号（低冲突、可跨请求）——与并发编程的锁/CAS 完全同构。

## 10. 练习

**1.** 用两个数据库会话（两个终端）复现丢失更新：都 BEGIN → 都读 stock → 都 UPDATE → 观察「后写覆盖前写」；再用 FOR UPDATE 重做验证原子。

> [!TIP]
> 思路两个 psql 终端手动交错是最直观的复现方式。「读改写竞态」亲眼见过一次，锁的意义就不再是文档语言。

**2.** 实验 READ COMMITTED 的不可重复读：会话 A 两次 SELECT 之间，会话 B 改数据并提交——观察 A 的两次结果不同；切 REPEATABLE READ 重做对比。

> [!TIP]
> 思路PG 的 REPEATABLE READ 是快照隔离（两次读一致）——「隔离级别不是抽象概念而是可观察行为」。各库默认值的差异也在此实验里显形。

**3.** 实现乐观锁的完整循环：version 列 + UPDATE WHERE version=? → 冲突时（影响 0 行）重试三次的代码；模拟并发冲突（两个会话）观察重试路径。

> [!TIP]
> 思路重试要「重读数据重算」（不能拿旧值硬写）——乐观锁的重试是业务级重算。与 [CAS 的循环重试](../cpp/13-concurrency.md)同构。

**4.** 制造一次死锁：会话 A 锁行 1 后锁行 2，会话 B 反序（先 2 后 1）——观察死锁错误；改成「两会话都按 id 升序」验证预防，并给应用加上死锁重试。

> [!TIP]
> 思路死锁错误（PG: deadlock detected）是可重试的——「按序访问 + 重试」两件套是并发数据访问的标配。错误分类（可重试与否）在此落地。

**5.** 验证「事务里做慢操作」的代价：事务内 SELECT FOR UPDATE 一行 → sleep 30 秒 → 期间另一个会话尝试 FOR UPDATE 同一行（阻塞）——理解「锁持有时间 = 并发瓶颈」。

> [!TIP]
> 思路被阻塞者的 `lock_wait` 状态与超时表现（lock_timeout）是可观测证据。「事务里不调外部服务」的纪律由此可推导——不是教条是锁经济学。

**6.** 讨论：为什么「先 SELECT 检查再 UPDATE」在并发下不可靠，而应用代码里「if (stock > 0)」看着却是对的？从「检查与动作之间的时间窗」出发，对照 [TOCTOU](../linux/08-network-remote.md)（检查与使用竞态）与 [CAS 的原子性](../cpp/13-concurrency.md)——「检查-动作原子化」的通用模式有哪几种实现？

> [!TIP]
> 思路原子化方案：数据库单条条件 UPDATE（WHERE stock > 0）、FOR UPDATE、乐观版本、应用层分布式锁。通用原理：检查与动作必须同处一个原子单元——文件锁、数据库锁、CAS、令牌都是它的不同实现。
