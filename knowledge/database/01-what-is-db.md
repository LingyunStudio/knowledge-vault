数据库解决的不是"怎么存数据"——文件系统早就能存了——而是三件文件做不到的事：**按条件快速找、多人并发读写不出错、断电重启后数据依然自洽**。几乎所有业务系统的地基都是这三件事，这一篇先建立全景地图，后面的篇章再逐层展开。

## 为什么不直接用文件

几千行的 JSON、一个 CSV，就是"数据库"的原始形态，小工具用它们毫无问题。但需求一升级，文件立刻露馅：

| 需求 | 文件的做法 | 数据库的做法 |
| --- | --- | --- |
| 找出金额大于 100 的订单 | 全量读进内存，自己写循环过滤 | 索引直接定位，毫秒级返回 |
| 两个用户同时写 | 后写的覆盖先写的，或文件损坏 | 锁与 MVCC 保证互不踩踏 |
| 写到一半断电 | 文件半残，内容自相矛盾 | 事务回滚，数据回到一致状态 |
| 十几张表互相关联 | 自己写胶水代码拼数据 | JOIN 一条语句完成 |

这些不是"性能优化"，是**正确性问题**。数据库真正的价值在于：把并发控制、崩溃恢复、快速检索这些极难写对的东西做成可信的基础设施，让应用层不必重新发明。写一个"按文件名找文件"的程序很容易，写一个"百万并发下不丢数据"的存储系统很难——这就是要不要用数据库的全部理由。

## 一条 SQL 的旅程

把后续各章串起来的骨架：一条 SQL 从客户端到磁盘大致走这些站。

```text
客户端 → 连接器 → 解析器 → 优化器 → 执行器 → 存储引擎 → 磁盘
```

1. **连接器**验证身份、管理会话——连接是贵资源，应用端用连接池复用（[程序访问数据库](10-orm-access.md)）
2. **解析器**把 SQL 文本变成内部结构，语法错误在这一步报出
3. **优化器**决定执行方案：用哪个索引、多表连接按什么顺序（[索引](06-index.md)和[SQL 进阶](08-sql-advanced.md)的 EXPLAIN 看的就是它的决定）
4. **执行器**按计划调用存储引擎取数、改数
5. **存储引擎**管数据在磁盘上怎么放、怎么加锁、怎么写日志（InnoDB 是 MySQL 的一个存储引擎；SQLite、PostgreSQL 则是引擎和数据库一体的架构）

改数据的语句多一步：修改先写日志（WAL/redo），再落数据页。日志先行是数据库的命门——崩溃后重放日志就能恢复到一致状态，持久性的底气全在这层日志上。理解这条流水线，后面每章的知识都能挂到对应的站点上。

## 关系型：表格不是限制，是承诺

关系型数据库（SQLite、PostgreSQL、MySQL）把数据组织成行与列：先定义表结构（schema），再放数据，类型不符、约束不满足就拒绝写入。这套"死板"恰恰是价值所在：

- **模式即文档**：看 schema 就知道系统存了什么，新人接手不用逐行翻代码猜字段
- **约束前置**：`NOT NULL`、`UNIQUE`、外键在写入时就把非法数据挡在门外，而不是等应用层某个忘了检查的分支放行
- **SQL 是声明式的**：你描述"要什么"，不指挥"怎么取"；走不走索引、按什么顺序扫，是优化器的事

```sql
CREATE TABLE customers (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);
CREATE TABLE orders (
    id          INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(id),  -- 外键：客户必须存在
    amount      DECIMAL(10,2) NOT NULL CHECK (amount > 0),  -- 金额必须为正
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

感受一下声明式查询的味道——统计今年每个客户的消费总额：

```sql
SELECT c.name, SUM(o.amount) AS total
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= '2024-01-01'
GROUP BY c.name
ORDER BY total DESC;
```

这十几行怎么逐层读，本篇不展开——从下一篇起一章一个部件地拆。这里只需要记住：SQL 是 SQLite、PostgreSQL、MySQL 通用的标准语言（方言差异存在，骨架一致），学会了到处能用，这也是"默认关系型"的隐性红利：招人、换库、找工具，生态都最厚。

> [!NOTE]
> "关系"指的不是表间外键关联，而是数学上的 relation——一组元组的集合，一张表就是一个关系。这套理论来自 1970 年 Codd 的论文，SQL 是它在工程上的实现。

## 事务：ACID 在保证什么

经典例子是转账：A 扣 100、B 加 100，两条语句之间断电，钱凭空消失。事务把这组操作捆成**要么全成、要么全不算**的单元：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;    -- 任何一步失败就 ROLLBACK，两边都不会"只改一半"
```

ACID 四个字母各管一件事：

| 字母 | 全称 | 保证 |
| --- | --- | --- |
| A | Atomicity 原子性 | 全做或全不做，不存在"扣了款没到账"的中间状态 |
| C | Consistency 一致性 | 前后都处于合法状态，约束、外键不会被打破 |
| I | Isolation 隔离性 | 并发事务互不干扰，看不到对方的中间状态 |
| D | Durability 持久性 | COMMIT 返回即落盘，断电重启也不丢 |

其中原子性和持久性由日志（undo/redo）实现，隔离性靠锁与多版本并发控制（MVCC），细节在[事务与并发](07-transactions.md)展开。还要知道事务的边界：**数据库事务只在单个数据库内有效**。跨服务、跨库的"分布式事务"是另一个世界的难题，主流做法是消息队列加最终一致，而不是硬上两阶段提交。

> [!TIP]
> 判断一个场景要不要事务，就问一句：**有没有多条写入必须同生共死**？有（订单和库存、账户和流水），就别用没有事务的存储硬扛——事后写补偿逻辑的复杂度远超想象。

## NoSQL 的分工

NoSQL 不是一种数据库，是一类"不把关系模型当默认答案"的存储，各自为特定问题而生：

| 类型 | 代表 | 擅长 | 典型场景 |
| --- | --- | --- | --- |
| 键值 | Redis | 亚毫秒读写单个 key | 缓存、会话、排行榜 |
| 文档 | MongoDB | 结构多变的 JSON 整读整写 | 内容管理、用户画像 |
| 时序 | InfluxDB、TimescaleDB | 海量按时间的写入与聚合 | 监控指标、传感器数据 |
| 列族 | Cassandra | 超大规模写入，按行键查询 | 日志、消息 |

共同取舍：**放弃一部分 SQL 的表达力（尤其是跨表 JOIN 与强事务），换写入吞吐、水平扩展或模式灵活**。这个取舍值不值，取决于你的查询模式，不取决于流行度——2010 年代"去关系型"的风潮之后，业界重新收敛到"主数据放关系型、NoSQL 做专项"的组合打法。

## 选型的第一张地图

默认答案非常明确：**关系型**。结构化数据、复杂查询、事务一致，加上最厚的生态与人才储备——绝大多数业务系统从头到尾只需要它。NoSQL 的正确用法是"叠加"，不是"替代"：

- 热点读太慢 → 加一层 Redis 缓存，主数据仍在关系型（见[NoSQL 一览](09-nosql.md)）
- 海量追加的日志、指标 → 时序库或列族接手
- 单机工具、桌面应用 → SQLite 直接上场，零配置零运维，认真用它能撑起相当大的系统
- 全文检索、模糊匹配需求冒头 → 先看 PostgreSQL 自带能力，再考虑专门引擎

反过来，当你发现自己在 NoSQL 里手写"按条件关联查询"的胶水代码时，那就是该回到关系型的信号。

> [!WARNING]
> 在生产库上手写改数据的 SQL 之前，先 `BEGIN`，执行后确认影响行数无误再 `COMMIT`。很多客户端默认自动提交——你敲下回车的瞬间，UPDATE 已经落库，没有后悔键。
