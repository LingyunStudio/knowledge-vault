[所有权](04-ownership.md)的 Move 语义解决了「谁负责释放」，但如果**每次使用都要转移所有权**，代码会变成所有权的接力赛：

```rust
let s = String::from("hello");
let len = calc_len(s);          // 所有权交出去
println!("{s}");                // ❌ s 已经没了——只想算个长度而已！
```

借用的答案是：**「借用」而不是「拥有」**——`&s`（不可变引用）让函数临时使用数据、用完归还，所有权仍在原处。

## 1. 引用：& 与 &mut

```rust
fn calc_len(s: &String) -> usize {      // 借用：只是「看向」数据
    s.len()
}                                        // s（引用）离开作用域——但它不拥有数据，什么都不释放

let s = String::from("hello");
let len = calc_len(&s);                  // &s：把引用交给函数（所有权不动）
println!("{s} {len}");                   // ✅ s 仍然可用
```

`&s` 创建一个指向 s 的**引用**——它的语义是「临时访问权」：可以读（&）或写（&mut），但**不负责释放**（所有者负责）。与 [C 的指针](../c/04-pointers.md)的对照：引用也是地址，但 Rust 的引用**永远有效**（借用检查器保证不悬垂）且**解引用透明**（`s.len()` 自动解引用）。

`&mut` 是可变借用——允许修改被借的数据：

```rust
fn append_world(s: &mut String) {
    s.push_str(", world");               // 通过可变借用修改本体
}

let mut s = String::from("hello");
append_world(&mut s);                    // ★ s 必须先声明 mut；借用时也要 &mut
println!("{s}");                         // hello, world
```

三重显式性：变量 `mut`（本体可变）、参数 `&mut`（借出写权）、调用 `&mut`（授予写权）——**可变性在三处可见**，读代码的人不用猜「这个函数会不会改我的数据」（[C++ 的 const&](../cpp/02-references-auto.md) 契约的强化版）。

## 2. 借用两条铁律

```rust
let mut s = String::from("hello");

// 铁律①：不可变借用可以同时存在多个
let r1 = &s;
let r2 = &s;
println!("{r1} {r2}");                   // ✅ 多个读者无冲突

// 铁律②：可变借用必须独占（有 &mut 时不能有其他任何借用）
let r1 = &mut s;
// let r2 = &s;                          // ❌ cannot borrow as immutable while borrowed as mutable
// let r3 = &mut s;                      // ❌ 同理
```

铁律的总纲一句话：**「要么多个只读、要么一个可写」**。这不是风格偏好而是数据竞争的定义——编译期数据竞争自由（[第 1 篇](01-getting-started.md)的核心命题）就建立在这条规则上：多线程共享可变引用在编译期被拒。

违反铁律的典型现场（读写同时）：

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];                        // 不可变借用还在用
v.push(4);                                // ❌ 可变借用：push 可能扩容导致重新分配
println!("{first}");                      //    → first 指向的内存可能失效！
```

这段代码的「危险」在 C++ 里真实存在（push 可能 realloc，first 变悬垂）——但 C++ 编译器不吭声；Rust 在编译期拒绝。**修复的方式是调整作用域**：

```rust
let first = &v[0];
println!("{first}");                      // first 的最后一次使用在这里
v.push(4);                                // ✅ 借用已结束（NLL）
```

## 3. NLL：借用活到「最后一次使用」

借用检查的旧模型是「词法作用域」（借用活到作用域结束），现代 Rust 用 **NLL（Non-Lexical Lifetimes）**：**借用结束于最后一次使用**——而不是块的结尾。上面修复例就是 NLL 的功劳（first 的借用结束于 println，之后的 push 不冲突）。

NLL 的工程含义：**借用的「作用域」可以比变量作用域小**——把「使用」和「修改」在代码里排序（读的部分先写完），很多借用冲突自动消失。诊断借用冲突的技巧：**找到借用从创建到最后使用的区间**（编译器报错里的 `borrow later used here`），缩短它或消除重叠。

## 4. 悬垂的编译期杜绝

```rust
fn dangle() -> &String {                 // ❌ 返回引用但数据会释放
    let s = String::from("hello");
    &s                                    // s 离开作用域就没了 → 引用悬垂
}                                        // 编译错误：missing lifetime specifier + cannot return reference
```

[所有权篇](04-ownership.md)的悬垂案例在借用侧的再现——借用检查器把「引用的生命周期不能超过被借数据」作为硬约束（[第 6 篇](06-lifetimes.md)把这条约束的标注规则讲全）。C++ 里这段代码是 UB；Rust 里是编译错误——**悬垂指针这一类问题在语言层面不存在了**。

## 5. 函数签名的设计惯例

```rust
// 读数据 → 借不可变引用（所有权不动、无拷贝）
fn print_all(items: &Vec<String>) { ... }

// 改数据 → 借可变引用
fn normalize(items: &mut Vec<String>) { ... }

// 转移/构造 → 收所有权
fn into_upper(s: String) -> String { ... }

// 惯用优化：&str 优于 &String、&[T] 优于 &Vec<T>（接受更宽的输入类型，[第 8 篇](08-collections.md)）
fn print_all(items: &[String]) { ... }   // ★ 惯用签名
```

签名设计的默认阶梯：**能借就不收、只读不写、宽类型（&str/&[T]）优先**——收所有权（String）只出现在「要存储/要转换」的真实需求。这个惯例让 API 的调用方负担最小（不用交出所有权）。

## 6. 陷阱清单

- 为绕借用检查到处 clone：性能税 + 设计回避；识别「真实需求是借用还是转移」。
- 忘了 mut 三处一致（变量/参数/调用）：编译错误的三连报。
- 在借用存活期间修改数据（读写交错）：调整使用顺序（NLL）或收窄借用区间。
- 引用当所有权用（存 &String 到结构体长期持有）：生命周期纠缠（[第 6 篇](06-lifetimes.md)）；长期持有考虑所有权或克隆。
- 大量「函数返回引用」的设计：生命周期标注复杂化；返回所有权（String）往往更简洁。
- 忽略 &str/&[T] 的宽签名惯例：接口不必要的类型耦合。

## 7. 小结

- 借用 = 「不转移所有权的临时访问」：& 只读（可多个）、&mut 可写（必须独占）——两条铁律就是数据竞争的编译期定义。
- 可变性三重显式（mut/&mut/&mut）让「会不会改」在签名与调用处全部可见——契约的可读性强化。
- NLL 让借用活到最后一次使用：借用冲突的修复常是「排序使用区间」；诊断靠编译器的 borrow 区间标注。
- 悬垂引用在语言层不存在（借用不超被借数据）——C/C++ 的悬垂类问题被编译期消灭。
- 签名惯例：能借不收、只读优先、&str/&[T] 宽类型——所有权只出现在真实的转移需求处。

## 8. 练习

**1.** 复现「读写交错」的借用冲突（first 借用 + push），用三种方式修复：调整使用顺序（NLL）、先 push 后借、克隆值——对比三种的语义差异与适用。

> [!TIP]
> 思路修复①利用 NLL（零成本）、②改变了逻辑顺序（可能改变行为）、③付出拷贝成本——「修借用错误」也要做工程权衡。编译器建议往往指向①。

**2.** 把一段「到处 String 传参」的代码重构为借用签名（&str 参数、&Vec/&[T]），统计重构后调用方的 clone 消失数——量化「借用签名」的接口友好度。

> [!TIP]
> 思路重构的判据：函数内部不拥有就不收所有权。&str 让调用方传 String/字面量/&str 都行——「宽输入类型」是 Rust API 的 generosity。

**3.** 对照 C++：把 [C++ 的引用参数](../cpp/02-references-auto.md)（const string& 与 string&）与 Rust 的 &String/&mut String 并排——分析「C++ 的 const 可被 const_cast 绕过 vs Rust 的 &mut 编译期独占」的契约强度差异。

> [!TIP]
> 思路C++ 的 const 是「单向承诺」（可绕过、需自律），Rust 的 & 是「互斥的权限」（编译器仲裁）——同一意图（只读访问）的两代实现。契约强度决定并发安全的可推导性。

**4.** 借用区间诊断练习：写一个编译失败的片段（跨大区间借用），读编译器的 borrow/borrow later used 标注，通过「移动使用位置」修复——训练 NLL 诊断法。

> [!TIP]
> 思路编译器的标注（first borrowed here / later used here）画出借用的生命周期区间——缩短区间的手法：提前使用、拆块、把计算内联。区间思维是 NLL 时代的核心技能。

**5.** 设计一个「图形编辑器」的最小接口：Shape 列表，需要「读列表渲染」「修改某个形状」「添加形状」三个操作——设计函数签名（借用 vs 所有权的选择），说明每个签名的决策理由。

> [!TIP]
> 思路渲染 `&[Shape]`（只读借用）、修改 `&mut Shape` 或 `&mut Vec<Shape>`（写借用）、添加 `&mut Vec<Shape>` + `Shape`（收新形状的所有权）。签名即文档：调用方从签名就能推断副作用。

**6.** 讨论：借用规则「要么多读要么一写」为什么在人类直觉上「过于严格」（明明可以两个函数一个读一个写不同字段）？从「字段级借用」（Rust 的 disjoint borrow 对结构体字段是允许的）与「跨函数边界的保守」分析——编译器的检查粒度、局限性（借用检查器的已知痛点）与工程应对（拆结构体/RefCell/重新设计）。

> [!TIP]
> 思路Rust 在同函数内能做字段级借用（disjoint），跨函数边界靠签名（&self 与 &mut self 互斥）——粒度的边界决定了「误报」的形状。工程应对的层次：先拆数据结构（让借用天然分离）＞内部可变性（RefCell，[第 12 篇](12-smart-pointers.md)）＞克隆。每个层级的代价递增。
