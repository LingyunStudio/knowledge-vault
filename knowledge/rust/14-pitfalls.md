Rust 的陷阱与 [C 的陷阱](../c/14-pitfalls.md)性质相反：C 的坑是「编译器不管」的（UB/内存），Rust 的坑是「绕过编译器」的（clone 滥用/unwrap 满天飞/unsafe 逃生舱）——**Rust 的坏代码通常能编译通过且逻辑正确，只是丢掉了语言的价值**。本篇按六类汇编审查清单，附借用错误的诊断路线。

## 1. 六类审查清单

### 1.1 所有权与借用（第 4、5 篇）

- [ ] 无论证的 clone（每个 clone 都该有理由：需要两份/借不开/跨线程）
- [ ] 函数签名遵循「能借不收」：&str/&[T] 宽类型、&self 读、&mut self 写
- [ ] 无悬垂风险的设计（返回引用前确认数据来源；长期持有用所有权）
- [ ] 无 Rc<RefCell> 的滥用（出现即审查数据流设计）
- [ ] Drop 中的清理完整且不 panic
- [ ] 结构体字段所有权正确（String 而非 &str 默认；引用字段有寿命理由）

### 1.2 类型与模式（第 2、3、7 篇）

- [ ] 整数溢出语义显式（checked/saturating/wrapping——不依赖构建模式）
- [ ] as 转换的截断风险评估（try_from/try_into 优先）
- [ ] match 穷尽（`_` 兜底的使用有意识——新变体提醒是否被吞）
- [ ] 无 unwrap/expect 的「无论证」使用（panic 白名单明确）
- [ ] 派生按语义（Eq+Hash 成对、Clone 需要、Default 合理）
- [ ] 类型转换走 From/Into/TryFrom 体系

### 1.3 集合与字符串（第 8 篇）

- [ ] 热路径 with_capacity 预分配
- [ ] String/str 的选择正确（参数 &str、存储 String）；无 UTF-8 边界 panic 的可能
- [ ] HashMap 的 entry API（无「contains+insert」双哈希）；key 的 Eq+Hash 成对
- [ ] 集合选型符合访问模式（Vec/VecDeque/BTreeMap/HashMap）
- [ ] 无「contains 再 insert」的竞态模式；get 与索引的 panic 边界核查

### 1.4 错误处理（第 9 篇）

- [ ] 库错误用精确类型（thiserror）、应用用 anyhow+context
- [ ] ? 的传播链完整（错误上下文不丢失）
- [ ] panic 不出现在库的公共 API 路径
- [ ] 错误信息含现场（路径/参数/值）
- [ ] 可重试错误（死锁/超时/临时失败）在设计上可重试

### 1.5 并发与异步（第 13 篇）

- [ ] 共享可变状态全部 Arc<Mutex> 或 RwLock（无裸 static mut/unsafe）
- [ ] channel 优先于共享；「通信优于共享」的评审意识
- [ ] 临界区最小（锁内无 IO/sleep/重计算）；多锁定序
- [ ] async 内无阻塞调用（spawn_blocking 兜底）；无锁跨 await
- [ ] 任务有取消/超时语义；join/abort 的生命周期管理
- [ ] 死锁/竞争的可重试设计

### 1.6 工程与生态（第 1 篇）

- [ ] cargo clippy + fmt 进 CI（零警告基线）
- [ ] Cargo.lock 提交；依赖审计（cargo audit）
- [ ] 测试覆盖核心逻辑（#[test] 内建；单测/集成测试分层）
- [ ] unsafe 块有 SAFETY 注释且最小化（能用安全代码不用 unsafe）
- [ ] 文档注释（///）覆盖公共 API；示例可运行（doctest）
- [ ] 错误类型对库使用者友好（可 match、可转换）

## 2. 借用检查器报错的诊断路线

```text
报错拿到手，按序四问：
① 这个值的所有者是谁？（谁创建、谁拥有）
② 我要的是所有权、借用还是克隆？
   （后面还用原值→借用/克隆；数据就此交付→所有权）
③ 借用的区间到哪结束？（NLL：最后一次使用——能否缩短/重排）
④ 数据的生命周期够长吗？（活过借用的使用期——否则改数据流）

常见报错 → 处方速查：
├── cannot borrow as mutable (borrowed as immutable)
│     → 缩短不可变借用区间 / 读写分批 / 重新设计数据流
├── value borrowed after move
│     → 后面还用吗？用→clone/借用；不用→把 move 移到最后
├── cannot return reference to local variable
│     → 返回所有权 / 引用作为参数传入 / 生命周期重新设计
├── closure may outlive the current function
│     → move 关键字（所有权进闭包）
└── type annotations needed
      → 显式标注目标类型（turbofish / let 标注）
```

诊断的元心法（与 [C 篇三问](../c/04-pointers.md)对照）：**编译器永远是对的**——报错描述的「借用/移动关系」是真实的数据流问题；你的任务是重新设计数据流，而不是与编译器辩论。

## 3. 反模式速查

| 反模式                                       | 一句话修复                                     |
| -------------------------------------------- | ---------------------------------------------- |
| `.clone()` 满天飞                             | 找到真实的所有权需求；借用优先                  |
| `unwrap()` 满天飞                             | `?` + 错误类型；unwrap 要有论证注释             |
| `Rc<RefCell<...>>` 贯穿全项目                 | 数据流重设计（[第 12 篇](12-smart-pointers.md)坏味道清单）|
| `unsafe` 逃生舱                               | 90% 有安全替代（借用/智能指针/重设计）          |
| String 参数（应 &str）/返回 &String（应 String） | 签名惯例（[第 5 篇](05-borrowing.md)）          |
| 泛型套泛型的过度抽象（trait 套 trait 套关联类型）| YAGNI；具体类型起步、需要时再抽象               |
| 阻塞调用进 async                              | spawn_blocking（[第 13 篇](13-concurrency.md)）|
| 巨型 match 不拆（+ 守卫嵌套深）                | 拆函数/用表驱动（[第 9 篇](../c/09-function-pointers.md)函数表对照）|
| 忽略 clippy 的 warning                        | clippy 的 lint 是惯用法教学                     |
| 优化先行（手写 unsafe/裸指针「更快」）          | 先 benchmark；零成本抽象大概率已最快            |

## 4. 学习阶段自测

```text
□ 阶段一：能读基本代码；对借用错误不再恐慌（知道「编译器是对的」）
□ 阶段二：能独立设计所有权流向（函数签名先想参数/返回的借用关系）
□ 阶段三：枚举+match 建模成习惯；错误处理用 thiserror/? 组合
□ 阶段四：泛型/trait 设计接口；迭代器链替代手写循环
□ 阶段五：并发不恐惧（channel/Arc<Mutex> 的选型直觉）；async 有纪律
□ 阶段六：读编译器报错如读设计文档；重构大代码依赖编译器信心
```

每个阶段的「毕业标准」不是记住语法，而是**思维方式的迁移**——从「写完让编译器挑刺」到「设计时就把所有权讲清楚」。

## 5. 小结

- Rust 的审查清单六类：所有权借用（clone/unwrap 纪律）、类型模式（溢出/穷尽）、集合字符串（预分配/UTF-8）、错误处理（链路/分级）、并发异步（共享纪律/无阻塞）、工程生态（clippy/测试/unsafe 治理）。
- 借用报错的诊断四问（所有者/需求类型/区间/寿命）+ 五条常见报错速查——诊断的核心是「重新设计数据流」而非对抗编译器。
- 反模式的总根：「绕过编译器」（clone/unwrap/unsafe/Rc<RefCell> 滥用）——每一条都放弃了 Rust 的部分价值。
- 学习阶段的毕业标准是思维迁移：所有权设计先于代码、编译器是评审伙伴。
- 与 C 篇清单的镜像关系：C 的清单防「编译器不管的」、Rust 的清单防「绕过编译器的」——两份清单合起来是系统编程的完整风险地图。

## 6. 练习

**1.** 用六类清单审查一个 Rust 项目（自己的练习代码或开源 crate），统计命中分布——预期「错误处理与并发」是新手项目的重灾区，验证或修正这个预期。

> [!TIP]
> 思路清单的命中分布是「学习进度」的透视镜：1.1/1.2 类命中说明所有权未内化，1.5 类命中说明并发经验缺失——回对应篇目补课的精确地图。

**2.** 借用诊断实战：收集你遇到过（或故意构造）的 5 个借用错误，按第 2 节四问逐个诊断并修复——记录「每个错误的真实数据流问题」而非「绕过技巧」。

> [!TIP]
> 思路诊断记录的格式：报错 → 四问答案 → 数据流问题的本质 → 设计级修复。绕过技巧（clone）要标注「这是妥协」并说明代价。

**3.** clone 审计：grep 项目里的 clone，分类（必要的业务拷贝/绕过借用检查/深拷贝替代设计）——统计三类比例，把「绕过型 clone」逐个重构为借用/所有权调整。

> [!TIP]
> 思路绕过型 clone 的信号：clone 完原值不再用（应该 move）、clone 只为传参（应该借用）。「clone 消失数」是所有权设计能力进步的量化指标。

**4.** unsafe 审计：找一个使用 unsafe 的 crate（或标准库源码），读 SAFETY 注释与不变量说明——理解「unsafe 是封装契约的工具」（如 String::from_utf8_unchecked 的前提），写一段「什么时候可以写 unsafe」的判据。

> [!TIP]
> 思路安全 Rust 的边界内绝大多数需求可满足；unsafe 的正当形态是「封装成安全接口」（标准库的模式）——裸露的 unsafe 是红旗。SAFETY 注释的严谨度是库质量的信号。

**5.** 为你的 Rust 团队写「代码准入规约」：从清单挑 CI 可自动项（clippy 零警告/测试覆盖/audit）与评审项（所有权设计/错误链/unsafe 审批）各 5 条——对照 [C 篇准入规约](../c/14-pitfalls.md)的练习，比较两语言自动化能力的差异。

> [!TIP]
> 思路Rust 的 CI 可自动化比例显著高于 C（类型系统本身是半个评审员）——「clippy 零警告 + cargo test + audit」三件套能拦截的类别，在 C 需要 sanitizer+评审。自动化的覆盖率是语言工程成熟度的标尺。

**6.** 讨论：Rust 社区常说「borrow checker 是老师不是警察」——结合你三个阶段的学习体验，分析这句话的机制根源（编译器报错的教育性设计：解释/建议/文档链接）与设计哲学（把「正确性规则」做成「教学界面」），对照 [git 的报错体验](../git/02-daily-workflow.md)与 [TS 类型错误](../frontend/08-modules-tooling.md)——「错误信息即教程」的设计能推广到哪些工具？

> [!TIP]
> 思路Rust 编译器的报错是「可执行的教程」（why 不稳定/建议修复/相关文档链接）——把学习曲线转化为「每次报错都是一次微课」。推广方向：任何「规则复杂但规则本身可讲清」的领域（linter/CI/架构约束）都可以用「解释性错误」降低合规成本——工具的 UX 即教学设计。
