栈的接口小得几乎不像一个数据结构：五个操作，没有一个是需要想清楚才能用的。但它保证的那一条性质——**最近的、尚未了结的事情最先被处理**——是所有「回退/回溯/取消」机制的基石：撤销、括号配对、表达式求值、深度优先搜索、函数返回、异常传播、浏览器后退。没有这条性质，这些场景要么写不出来，要么必须自己维护一套等价的状态机。

栈还有第二种身份常被混为一谈：我们自己写的数据结构，和操作系统、编译器维护的「进程栈」。前者讲清楚了，才能理解后者为什么有 8 MB 的上限、递归为什么会「爆栈」、以及把递归改成显式栈究竟换来了什么。

## 1. LIFO：栈保证的到底是什么

### 1.1 「最近的、尚未了结的」优先

栈的语义是一句话：**被压入的元素中，只有最后压入的那个可以被访问**；出栈顺序恰好是入栈顺序的逆序。大量问题天然带有这种嵌套结构：

| 场景    | 「最近的、尚未了结的」指的是   |
| ----- | ---------------- |
| 括号匹配  | 最近一个还没配对的左括号     |
| 函数返回  | 最近一次被调用、还没返回的函数  |
| 撤销    | 最近一次做过、还没被撤销的操作  |
| DFS   | 最近一个被发现、还没探索完的节点 |
| 表达式求值 | 最近的、操作数已经凑齐的运算符  |

它们的共性是：**当前要处理的对象由历史决定，而且历史可以撤销**。用只能访问栈顶的容器承载它们，代码里就不必显式维护「我处理到哪儿了」——容器本身记住了。

### 1.2 五个操作的接口

接口只有五个操作：`push(x)` 把 x 放到栈顶，`pop()` 弹出并返回栈顶元素（栈空时是错误），`peek()` 只看栈顶不弹出（也叫 `top()`），`is_empty()` 判空，`size()` 返回元素个数。两个设计决定值得单独说：

- **`pop()` 在空栈上必须报错，不能返回 `None`**。返回 `None` 会把逻辑错误变成一个「值」，让 bug 顺着数据流漂到很远的地方才发作（几十行后某个 `None` 参与运算时抛类型错误，出错点早已消失）。Python 的 `list.pop()` 抛 `IndexError`，Java 的 `ArrayDeque::pop` 抛 `NoSuchElementException`，C++ 的 `vector::pop_back()` 在空容器上是未定义行为——越安全的语言实现越倾向于报错。
- **不提供「访问第 i 个元素」**。这条看似限制，实际是整个结构价值的来源。

### 1.3 接口窄为什么是好设计

接口宽度决定了调用方能依赖多少东西，也决定了实现方能改动多少东西。栈只有五个操作，收益有三层：

1. **不变式自动成立**。栈的唯一不变式是「元素按 LIFO 顺序进出」；只要接口里没有随机访问、没有中间插入，就没有任何操作能破坏它。反面教材是 Java 的 `Stack`：它继承自 `Vector`，因此白送了 `get(i)`、`insertElementAt`、`setElementAt`。接口一宽，「栈」的约束就只存在于文档里，编译器不再保护你——这也是官方推荐用 `ArrayDeque` 替代 `Stack` 的原因之一（另一个原因：`Stack` 的每个方法都是 `synchronized` 的，单线程下纯属开销）。
2. **实现可以自由替换**。底层从动态数组换成链表、换成定长数组、换成两个栈拼装，调用方一行都不用改。C++ 的 `std::stack` 干脆就是个**适配器（container adaptor）**：`std::stack<T>` 默认架在 `std::deque<T>` 上，也可写成 `std::stack<T, std::vector<T>>`，成员函数全部由底层容器转发。
3. **用错变得困难**。没有随机访问，写不出「按下标乱序访问」；没有遍历接口，写不出「遍历时修改」的 bug（对比 [第 06 篇](06-hash-table.md) 里字典遍历时修改的坑）。

代价同样直接：**需要随机访问、遍历、查找或两端操作时，栈帮不上忙**，这时该换成数组（[第 02 篇](02-array-dynamic-array.md)）或双端队列（[第 05 篇](05-queue-deque.md)）。

### 1.4 一条不变式

> [!IMPORTANT]
> **栈的不变式**：从空栈开始只做 push，那么接下来的 pop 序列必然是 push 序列的严格逆序；任何时刻，栈中最「新」的元素是唯一可读的元素。所有依赖回退/回溯/取消的算法，正确性都能归约到这条不变式上。

推论：一个序列能否由某组 push/pop 操作从空栈产生，是可以判定的——用同一个栈模拟一遍即可。第 5 节的括号匹配就是它的一个特例。

## 2. 三种实现骨架

### 2.1 动态数组：默认答案

把数组的**尾部**当栈顶，push 是尾插，pop 是尾删。它是绝大多数语言的默认选择，因为尾部操作的常数因子最小：写入位置紧挨上一个元素（同一条缓存行、顺序访存），扩容只在满载时发生，代价由 [第 01 篇](01-complexity-analysis.md) 的摊还分析兜底（n 次 push 总代价 O(n)，摊还 O(1)），空间最多浪费一倍。Python 里这个结构就是 `list`：`append(x)` 是 push，`pop()` 是 pop，判空写 `not stack`。**不要自己用 Python 类实现它**——内置 `list` 是 C 实现，常数因子比任何手写类小一个数量级。一个容易漏的细节：`list.pop()` 内部会清空被弹出的槽位，否则那个对象会被底层数组的引用扣住、无法回收；自己实现动态数组栈时这一行不能省。

### 2.2 单链头插：最坏 O(1) 的保证

把链表的**头部**当栈顶：push 在头节点前插入，pop 摘掉头节点，两者都是最坏的 O(1)——不是摊还，是每一次（[第 03 篇](03-linked-list.md) 有头插头删的完整代码）。代价有三项：每元素多一个指针（8 字节）外加分配器元数据（glibc 每个块至少 16 字节），一个存 `int` 的链表栈实际每元素可能占 40 字节；每次 push 一次 `malloc`，延迟不可预测（可能触发系统调用或 GC），实时系统最怕这个；节点散落在堆各处，每次 pop 都是一次随机访存（约 100 纳秒，够 CPU 执行几百条指令）。它唯一不可替代的场景是**元素很大且数量不可预知**：动态数组扩容时要整体拷贝元素，链表只搬指针。

### 2.3 定长数组：嵌入式与内核

容量在编译期确定，不做任何动态分配，因此没有分配失败的可能，内存开销完全可预测——嵌入式固件、实时系统、内核栈都这么做。代价是**必须显式处理溢出**：C 里没有异常，越界写不会报错，只会安静地写坏相邻内存；如果那片内存恰好是返回地址，攻击者就能控制执行流（经典的栈缓冲区溢出攻击）。所以定长栈的 push 必须返回错误码：

```c
/* fixed_stack.c —— 定长栈：容量编译期确定，push 返回错误码，绝不静默溢出
 * 编译：gcc -std=c11 -Wall -Wextra -o fixed_stack fixed_stack.c
 */
#include <stdio.h>
#include <stdbool.h>
#include <stddef.h>

#define STACK_CAPACITY 8

typedef enum { STACK_OK = 0, STACK_FULL, STACK_EMPTY } StackStatus;

typedef struct {
    int data[STACK_CAPACITY];   /* 定长数组：空间编译期确定，不需要 malloc */
    size_t top;                 /* 下一个空槽的下标；0 表示空栈 */
} Stack;

static const char *stack_strerror(StackStatus s) {
    switch (s) {
    case STACK_OK:    return "ok";
    case STACK_FULL:  return "stack overflow";
    case STACK_EMPTY: return "stack underflow";
    }
    return "unknown";
}

void stack_init(Stack *s) { s->top = 0; }
bool stack_is_empty(const Stack *s) { return s->top == 0; }
size_t stack_size(const Stack *s) { return s->top; }

StackStatus stack_push(Stack *s, int value) {
    if (s->top == STACK_CAPACITY) return STACK_FULL;   /* 唯一的溢出出口 */
    s->data[s->top++] = value;
    return STACK_OK;
}

StackStatus stack_pop(Stack *s, int *out) {
    if (s->top == 0) return STACK_EMPTY;
    *out = s->data[--s->top];
    return STACK_OK;
}

StackStatus stack_peek(const Stack *s, int *out) {
    if (s->top == 0) return STACK_EMPTY;
    *out = s->data[s->top - 1];
    return STACK_OK;
}

int main(void) {
    Stack s;
    int v;
    stack_init(&s);
    for (int i = 0; i < STACK_CAPACITY; i++) stack_push(&s, i * i);

    /* 第 9 次 push 必须返回错误，而不是写坏相邻内存 */
    printf("溢出时 push -> %s (size = %lu)\n",
           stack_strerror(stack_push(&s, 999)), (unsigned long)stack_size(&s));
    printf("弹出顺序: ");
    while (stack_pop(&s, &v) == STACK_OK) printf("%d ", v);
    printf("\n空栈 pop -> %s, 空栈 peek -> %s\n",
           stack_strerror(stack_pop(&s, &v)), stack_strerror(stack_peek(&s, &v)));
    return 0;
}
```

三点设计说明：`top` 是「下一个空槽的下标」而非「栈顶下标」，于是 `top == 0` 直接表示空、`top == STACK_CAPACITY` 直接表示满，两个边界都不需要特判；`pop`/`peek` 通过出参返回结果、返回值留给状态码，是 C 里「一个返回值干两件事」的标准写法；除了这几个函数，**没有任何代码能改动 `top`**，容量上限在 `#define` 里，编译器能静态检查调用点上游有没有容量判断。

| 实现       | push            | pop     | 空间开销             | 溢出行为          |
| -------- | --------------- | ------- | ---------------- | ------------- |
| 动态数组（尾部） | 摊还 O(1)，最坏 O(n) | O(1) 最坏 | 最多 2n 槽位         | 自动扩容；只在分配失败时崩 |
| 单链头插     | O(1) 最坏         | O(1) 最坏 | 每元素 1 指针 + 分配器开销 | 分配失败返回 NULL   |
| 定长数组     | O(1) 最坏         | O(1) 最坏 | 恰好 n 槽位，无额外开销    | 必须显式报错，否则越界写  |

> [!WARNING]
> 上面出现的 `stack overflow` 是**定长栈的逻辑溢出**：push 满了，返回错误码就能处理。它与第 3 节的进程栈溢出完全不是一回事——后者是内存越界，进程直接死。名字撞车，含义相反。

## 3. 调用栈与栈帧

### 3.1 栈帧里有什么

函数调用是栈在硬件层面的存在形式。每次调用，机器在进程的**调用栈（call stack）**上压入一个**栈帧（stack frame）**，返回时弹出。栈帧里通常有：

```text
栈底（高地址）  main 的栈帧
                ----------------------------------------------
                f(3) 的栈帧
                   返回地址      → f(2) 里调用 f(3) 的下一条指令
                   参数 n = 3     x86-64 上前 6 个整型参数走寄存器，更多才写进栈
                   保存的寄存器  rbx、rbp、r12-r15 等「被调用者保存」的寄存器
                   局部变量      数组、取地址的变量；没取地址的会留在寄存器里
                   对齐填充      栈指针要保持 16 字节对齐
                ----------------------------------------------
                f(2) 的栈帧
                ----------------------------------------------
                f(1) 的栈帧
栈顶（低地址，rsp 指向这里）—— 栈向低地址方向生长
```

**帧的大小决定能递归多深**，这点常被忽略：进程栈大小固定（Linux 默认 8 MB，Windows 主线程默认 1\~2 MB），所以「最多递归多少层」等于「栈大小除以每帧字节数」。帧里只有几十字节的函数能递归十万层；帧里放了 8 KB 局部数组的函数，8 MB 栈只够约 1000 层。

### 3.2 深度上限从哪里来

Python 和 C 的递归上限来源完全不同，混为一谈会写出错误的「修复」方案。

**Python 是软限制（计数器）**：CPython 自己数递归深度，默认 1000，超了抛 `RecursionError`。它不以真实内存用量为判据，因为执行一层 Python 递归可能消耗好几层 C 栈（`ceval` 主循环、C 扩展、`__getattr__` 钩子都会加帧），用计数器更保险。

```python
import sys

def count_down(n):
    return 0 if n == 0 else 1 + count_down(n - 1)

print("默认上限:", sys.getrecursionlimit())          # CPython 是 1000
try:
    count_down(100_000)
except RecursionError as e:
    print("深递归后果:", type(e).__name__, "-", e)
```

实测：默认上限 1000，实际可用 997 层（解释器启动时已经占了几层），再深就是 `RecursionError: maximum recursion depth exceeded`。

**C 是硬限制（内存边界）**：没有计数器，栈指针越过栈底就是访问保护页，操作系统直接终止进程。把上面 `count_down` 的写法搬到 C 里，每帧带一个 8 KB 的局部数组（`volatile char pad[8192];`），并去掉终止条件，实测结果是：在默认 2 MB 栈（MinGW-w64 默认值）上，进程在约 200 层时被终止——没有异常、没有堆栈信息、`main` 的 `printf` 永远执行不到。同一份代码在 Linux 的 8 MB 栈上能跑到约 1000 层；把 `pad` 改成 64 KB 就只剩约 128 层。

> [!CAUTION]
> **不要用 `sys.setrecursionlimit` 去「修复」深递归**。它只改计数器，不动真实内存：调大之后 Python 会先把 C 栈用尽，进程收到段错误直接崩溃——比 `RecursionError` 糟糕得多（后者是可捕获、可定位的异常，前者连 traceback 都没有）。要处理 10 万层的递归，唯一的办法是改成显式栈（第 4 节）。

### 3.3 栈溢出与堆溢出的区别

两个词都常被简写成「溢出」，故障模式却相反：

| <br /> | 调用栈                           | 堆                                          |
| ------ | ----------------------------- | ------------------------------------------ |
| 谁在管    | 操作系统按线程分配，线程私有                | 运行时分配器，进程内共享                               |
| 典型大小   | Linux 8 MB、Windows 1\~2 MB，固定 | 可用物理内存与地址空间，GB 级                           |
| 分配代价   | 移动一个栈指针，纳秒级                   | 走分配器，几十到几百纳秒                               |
| 耗尽时    | 段错误，进程被终止，**无法捕获**            | `malloc` 返回 NULL 或抛 `MemoryError`，**可以处理** |
| 与递归的关系 | 递归深度就是栈用量                     | 无关                                         |

「递归太深」和「内存不够」是两类完全不同的问题：前者用显式栈或改迭代解决，后者用减少分配、流式处理、换内存结构解决。数据结构意义上的「栈」与操作系统意义上的「栈内存」只是恰好同名——后者之所以叫栈，是因为它的使用方式符合 LIFO。

### 3.4 尾调用优化

**尾调用（tail call）**指函数的最后一个动作是调用另一个函数，且返回值直接作为自己的返回值，不再被加工。`return g(n - 1, acc + n)` 是尾调用，`return 1 + h(n - 1)` 不是（还要再加 1）。尾调用之后当前帧就没有任何用处了，可以被**直接复用**（覆盖）而不是新压一帧——尾递归于是在栈上等价于循环，空间 O(1)，这就是**尾调用优化（tail call optimization, TCO）**。它的现实分布很不均匀：Scheme、Erlang、Lua 的语言规范强制要求；C/C++ 的 gcc/clang 在 `-O2` 下常把自尾递归变成循环，但这是优化不是保证；Kotlin 需要写 `tailrec` 关键字且只支持自尾递归；Python、Java、Rust、Go、JavaScript 都不保证。Python 明确不做，理由之一是 TCO 会破坏 traceback（帧被覆盖后回溯里看不到中间调用）。结论：**在 Python 里手写尾递归没有任何好处**，它照样吃满 1000 层栈；写成循环（套路①）更短更快更清楚。

## 4. 递归改迭代：两类通用套路

递归改迭代不是一件事，而是两个可判定的形态。判断依据只有一个：**递归调用之后还有没有活要干**。有活要干，就必须把「活是什么」自己存起来。

### 4.1 套路①：尾递归形态 → 循环 + 累积变量

如果递归调用是函数的最后一步，中间结果必然是通过参数往下传的。把这个参数提升为循环外的累积变量，递归调用就变成了对参数的赋值：

```python
def sum_rec(n, acc=0):
    """尾递归形态：中间结果 acc 作为参数往下传，返回值不再被上层加工。"""
    return acc if n == 0 else sum_rec(n - 1, acc + n)


def sum_iter(n):
    """套路①：参数变成循环变量，递归调用变成对循环变量的赋值。"""
    acc = 0
    while n:
        acc, n = acc + n, n - 1
    return acc


assert sum_rec(100) == sum_iter(100) == 5050
try:
    sum_rec(10 ** 6)                 # Python 不做尾调用优化，尾递归照样吃栈
except RecursionError:
    print("Python 不做尾调用优化：尾递归一样爆栈")
```

### 4.2 套路②：需要「恢复现场」→ 显式栈 + 阶段标记

如果递归调用之后还有活要干，递归版靠**返回地址**记住「回到哪一行」。迭代版必须自己记住，做法是往栈里存「节点 + 阶段标记」。以二叉树的中序遍历为例：

```python
class TreeNode:
    def __init__(self, val, left=None, right=None):
        self.val, self.left, self.right = val, left, right


def build():
    #        4
    #      /   \
    #     2     6
    #    / \   /
    #   1   3 5
    return TreeNode(4, TreeNode(2, TreeNode(1), TreeNode(3)),
                    TreeNode(6, TreeNode(5)))


def inorder_rec(root):
    out = []
    def walk(node):
        if node:
            walk(node.left)
            out.append(node.val)
            walk(node.right)
    walk(root)
    return out


def inorder_stack(root):
    """套路②：显式栈 + 阶段标记。0 = 刚入栈，1 = 左子树已完成。"""
    out, stack = [], [(root, 0)]
    while stack:
        node, stage = stack.pop()
        if node is None:
            continue
        if stage == 0:                    # 逆序压栈，出栈顺序才是「左 → 中 → 右」
            stack.extend([(node.right, 0), (node, 1), (node.left, 0)])
        else:
            out.append(node.val)          # 左子树处理完了，输出自己
    return out


if __name__ == "__main__":
    root = build()
    assert inorder_rec(root) == inorder_stack(root) == [1, 2, 3, 4, 5, 6]
    deep = TreeNode(0)                    # 10 万层的链：递归版必爆（见 3.2），显式栈没事
    for i in range(1, 100_000):
        deep = TreeNode(i, None, deep)
    assert inorder_stack(deep)[:3] == [99_999, 99_998, 99_997]
    print("显式栈版与递归版结果一致，且能处理 10 万层的深链")
```

三种写法的关系值得说透：

- `inorder_stack` 是**通用翻译模板**：阶段 0 表示「刚进这个节点，左子树还没做」，阶段 1 表示「左子树做完了，该输出自己，然后转右子树」。栈里同时存了节点和「我停在哪一步」，与机器栈里的返回地址一一对应；这个模板对前序、中序、后序都成立。
- 中序还能**进一步压缩掉阶段标记**：中序的节奏是「左子树一做完就输出自己」，所以只要把「一路向左」的祖先链压进栈，出栈顺序天然就是中序，每个栈项只存一个节点指针就够（教科书上的迭代中序就是这个写法）。**这个技巧不能平移到后序**：后序要等左右子树都完成才输出自己，光靠节点指针无法区分「刚从左子树回来」还是「刚从右子树回来」，必须额外存阶段标记（或存一个 `last_visited` 指针）。
- 递归版更短，而且在语言支持的情况下更快（函数调用本身不贵，压帧只是移动栈指针）。它的问题只有一个：**深度由操作系统决定**。

### 4.3 显式栈换来了什么

| <br />  | 递归（机器栈）                          | 显式栈（堆）                   |
| ------- | -------------------------------- | ------------------------ |
| 容量上限    | Linux 8 MB、Windows 1\~2 MB，固定    | Python 的 `list` 能装几千万个元素 |
| 超限后果    | 段错误（C）或 `RecursionError`（Python） | `MemoryError`，可捕获处理      |
| 每帧开销    | 几十到几百字节，编译器决定                    | 每项至少一个元组对象，几十字节起         |
| 可中断/可恢复 | 不能（除非语言支持协程）                     | 能：栈本身就是数据，可以存盘、分片、续跑     |

第三项是真实代价：显式栈的每一项都是堆对象，同一段逻辑的显式版本内存开销通常是递归版的 3\~10 倍。所以「递归改迭代」不是无条件的优化，它交换的是**深度上限**：牺牲常数，换掉天花板。而最后一项才是显式栈最有价值的性质——递归一旦开始跑就必须跑完（状态在机器栈里，你拿不到）；显式栈的状态是你自己的数据结构，于是可以「跑到一半保存起来，下次接着跑」（流式 JSON 解析器）、可以「把深递归拆成多轮、分给多个时间片」（游戏引擎与手动协程），也可以序列化后传给另一台机器。

## 5. 括号匹配

**为什么必须用栈**：括号的合法性定义为「最近一个还没配对的左括号必须最先被配对」，这是一个嵌套结构，配对顺序正是 LIFO 顺序。只用计数器为什么不行：`"([)]"` 左右括号数量完全平衡，却不合法，因为 `[` 和 `)` 的配对交叉了。要发现这种错误，必须记住「最近未闭合的是哪一种括号」——也就是必须有一个栈。

```python
PAIRS = {")": "(", "]": "[", "}": "{"}


def check_brackets(text):
    """返回 (是否合法, 出错位置(1 起), 说明)。合法时位置为 0。"""
    stack = []                                  # 存 (左括号, 下标)
    for i, ch in enumerate(text):
        if ch in "([{":
            stack.append((ch, i))
        elif ch in PAIRS:
            if not stack:
                return False, i + 1, "第 %d 位多了个 '%s'" % (i + 1, ch)
            left, pos = stack.pop()
            if left != PAIRS[ch]:
                return False, i + 1, "第 %d 位的 '%s' 没闭合就遇到 '%s'" % (pos + 1, left, ch)
    if stack:                                   # 报最早那个没闭合的左括号
        return False, stack[0][1] + 1, "第 %d 位的 '%s' 没有闭合" % (stack[0][1] + 1, stack[0][0])
    return True, 0, "合法"


if __name__ == "__main__":
    assert check_brackets("")[0] is True
    assert check_brackets("([)]")[0] is False    # 计数完全平衡，但仍然不合法
    assert check_brackets("(]") == (False, 2, "第 1 位的 '(' 没闭合就遇到 ']'")
    assert check_brackets("((")[1] == 1          # 报最早没闭合的那个
    print("括号匹配：", check_brackets("([)]"))
```

四个工程要点：**三类失败要分开报**（栈空时遇到右括号、栈顶类型不匹配、扫完栈非空），它们指向不同的用户错误，混在一起会让调试变痛苦；**栈里存下标而不是只存字符**，否则报不出错误位置——这与第 7 节「单调栈存值还是存下标」是同一个决策，**只要结果需要位置或距离，就必须存下标**；**未闭合时报最早还是最近那个**，本实现报最早那个（`stack[0]`），因为它最接近「这段代码从哪儿开始错的」，报最近那个同样合理但要在一个项目里统一；**复杂度**是时间 O(n)、空间 O(n) 最坏（全是左括号），只允许一种括号时计数器能把空间降到 O(1)，代价是失去错误定位能力与多类型括号支持。

## 6. 表达式求值

### 6.1 后缀表达式：把运算顺序写进序列

中缀表达式 `1 + 2 * 3` 需要一张优先级表才知道先算乘法。**后缀表达式（逆波兰表达式，Reverse Polish Notation, RPN）**把同一件事写成 `1 2 3 * +`：不需要任何优先级规则，从左往右扫，遇到运算符就取最近的两个操作数算——「谁先凑齐谁先算」这个顺序已经被编码进序列本身。

```python
def eval_postfix(tokens):
    """逆波兰表达式求值。tokens 形如 ['3', '4', '+']、['2', '3', 'u-', '*']。"""
    st = []
    for tok in tokens:
        if tok == "u-":                          # 一元负号：只有一个操作数
            st.append(-st.pop())
            continue
        if tok in ("+", "-", "*", "/", "^"):
            b, a = st.pop(), st.pop()            # 先弹出的是右操作数
            if tok == "+":
                st.append(a + b)
            elif tok == "-":
                st.append(a - b)
            elif tok == "*":
                st.append(a * b)
            elif tok == "^":
                st.append(a ** b)
            else:
                q = abs(a) // abs(b)             # 向零截断，与 C 的整数除法一致
                st.append(-q if (a < 0) != (b < 0) else q)
        else:
            st.append(int(tok))
    if len(st) != 1:
        raise ValueError("表达式不合法，栈里剩 %d 个值" % len(st))
    return st[0]


assert eval_postfix(["3", "4", "+"]) == 7
assert eval_postfix(["1", "2", "+", "3", "*", "4", "-"]) == 5
assert eval_postfix(["-100", "7", "/"]) == -14    # Python 的 -100 // 7 得到 -15
assert eval_postfix(["2", "3", "u-", "*"]) == -6
assert eval_postfix(["2", "3", "2", "^", "^"]) == 512
```

注意 `b, a = st.pop(), st.pop()` 的顺序：**先弹出的是右操作数**。减法与除法不可交换，写反了会得到一个「大部分测试能过、负数和除法结果全错」的 bug——这是 RPN 求值最高频的错误。

### 6.2 中缀转后缀：调度场算法

**调度场算法（shunting-yard algorithm）**解决的是：如何一次线性扫描就把带括号、优先级、结合性的中缀表达式转成后缀。只需要一个运算符栈，规则四条：

1. 遇到操作数：直接进输出队列。
2. 遇到 `(`：压入运算符栈。它的优先级视为最低——压它的时候不弹任何东西。
3. 遇到 `)`：不断弹出栈顶运算符进输出队列，直到遇到 `(`；然后丢弃这个 `(`。如果栈里根本没有 `(`，说明括号不匹配。
4. 遇到运算符：当栈顶运算符**优先级更高**，或**优先级相同且当前运算符是左结合**时，弹出栈顶进输出队列（循环，可能弹多个）；然后把这个运算符压栈。扫描结束后把栈里剩下的依次弹出。

这四条规则就是「优先级 + 结合性」在栈操作上的完整编码：优先级决定「能不能弹」，结合性决定「同级弹不弹」。右结合的幂运算 `^` 同级时不弹，于是 `2^3^2` 得到 `2 3 2 ^ ^`（即 `2^(3^2)`）而不是 `(2^3)^2`。还有一个坑：**一元前缀负号不能按规则 4 处理**——`-2` 里的 `-` 是前缀运算符，压栈时它的右操作数还没被解析，按「先弹后压」办会把操作数弹到运算符前面去，产出不合法的后缀；正确做法是前缀运算符**直接压栈，不弹任何东西**。

```python
PREC = {"+": 1, "-": 1, "*": 2, "/": 2, "u-": 3, "^": 4}
RIGHT_ASSOC = {"^"}                  # 幂右结合：2^3^2 是 2^(3^2)
PREFIX_OPS = {"u-"}                  # 前缀运算符：压栈时不弹任何东西


def tokenize(expr):
    """切词，并把 '-' 区分为二元减法还是一元负号。"""
    tokens, prev, i = [], None, 0
    while i < len(expr):
        ch = expr[i]
        if ch.isspace():
            i += 1
        elif ch.isdigit():
            j = i
            while j < len(expr) and expr[j].isdigit():
                j += 1
            tokens.append(expr[i:j])
            prev, i = "num", j
        else:
            tokens.append("u-" if ch == "-" and (prev is None or prev in "+-*/^(")
                          else ch)
            prev, i = ch, i + 1
    return tokens


def infix_to_postfix(expr):
    """调度场算法：中缀表达式 → 后缀表达式。"""
    out, ops = [], []
    for tok in tokenize(expr):
        if tok[0].isdigit():
            out.append(tok)                          # 操作数直接输出
        elif tok == "(":
            ops.append(tok)
        elif tok == ")":
            while ops and ops[-1] != "(":
                out.append(ops.pop())
            if not ops:
                raise ValueError("括号不匹配：多余的 ')'")
            ops.pop()                                # 丢弃配对的左括号
        elif tok in PREFIX_OPS:
            ops.append(tok)                          # 前缀运算符不弹栈，直接压
        else:
            # 栈顶优先级更高，或同级且当前是左结合 → 栈顶可以先算
            while (ops and ops[-1] != "("
                   and (PREC[ops[-1]] > PREC[tok]
                        or (PREC[ops[-1]] == PREC[tok] and tok not in RIGHT_ASSOC))):
                out.append(ops.pop())
            ops.append(tok)
    while ops:
        if ops[-1] == "(":
            raise ValueError("括号不匹配：多余的 '('")
        out.append(ops.pop())
    return out


def calc(expr):
    return eval_postfix(infix_to_postfix(expr))      # eval_postfix 见 6.1


if __name__ == "__main__":
    cases = {"1+2*3": 7, "(1+2)*3": 9, "2^3^2": 512, "-2^2": -4, "10-2-3": 5,
             "8/2/2": 2, "100/7": 14, "-(3+4)*2": -14, "2*-3": -6, "3-(-2)": 5}
    assert all(calc(e) == w for e, w in cases.items())
    assert infix_to_postfix("2^3^2") == ["2", "3", "2", "^", "^"]   # 右结合
    print("全部 %d 个表达式通过，2^3^2 的后缀为 %s" % (
        len(cases), " ".join(infix_to_postfix("2^3^2"))))
```

这段代码要和 6.1 拼起来才能跑（`calc` 用的是那里的求值函数）。测试用例本身就是这套规则的说明书：`-2^2` 得到 -4（一元负号优先级低于幂）、`10-2-3` 得到 5（左结合）、`2^3^2` 得到 512（右结合）。

### 6.3 编译器为什么也要做这件事

「中缀转后缀」听起来像计算器的小把戏，它其实是编译器前端的核心动作：

**中缀是给人看的，后缀是给机器算的**。中缀需要一张优先级与结合性表，求值时还要在表达式里来回跳跃（括号可能跨很远）；后缀是一条线性序列、一个操作数栈、一次扫描，没有回溯也没有递归，转换的代价在解析期一次付清。**它把语法与求值分离**：真实编译器不生成后缀，而是生成 AST 或三地址码，但构造它们用的还是同一个运算符栈（或等价的递归下降）——这就是**中间表示（IR）**的最简形态，而解析器里的显式栈与递归下降里的调用栈，正是第 4 节套路②的两种形态。**后缀还是「在线」的**：构建 AST 要先读完整棵树才能求值，RPN 序列可以边生成边求值，这是早期 Turbo Pascal 之类单遍编译器能在几十 KB 内存里工作的原因。

> [!CAUTION]
> **不要用 `eval` 求值用户输入**。`eval` 执行的是完整的 Python 语法，不是「数学表达式」：`eval("__import__('shutil').rmtree('/')")` 会在你的权限范围内递归删除根目录。即使不考虑安全，`eval("9**9**9")` 也会尝试构造一个约 3.7 亿位的十进制整数，把内存和 CPU 一起吃满（拒绝服务）。安全替代按严格程度递增：`ast.literal_eval`（只解析字面量、不做运算）、白名单化的 `ast.parse` 节点遍历、或本篇这种自己写的 tokenizer 加调度场（只支持你定义的运算符，攻击面为零）。数学表达式求值的正确工具是解析器，不是语言解释器。

## 7. 单调栈

### 7.1 模板：下一个更大元素

**单调栈（monotonic stack）**不是新的容器，而是「栈 + 一条保持栈内元素单调的规则」。它以 O(n) 解决一整类看起来需要 O(n²) 的问题：**对每个元素，找左边或右边第一个满足某种比较关系的元素**。以「下一个更大元素」为例：对每个下标 `i`，求最小的 `j > i` 使 `a[j] > a[i]`，不存在则记 -1。

```python
def next_greater(nums):
    """每个元素的下一个更大元素的值，没有则 -1。"""
    res, stack = [-1] * len(nums), []    # 栈里存下标，对应的值从栈底到栈顶递减
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:
            res[stack.pop()] = x         # 弹出的下标，答案就是当前元素
        stack.append(i)
    return res


def daily_temperatures(temps):
    """每日温度：还要等几天才更暖，没有更暖的日子记 0。"""
    res, stack = [0] * len(temps), []
    for i, t in enumerate(temps):
        while stack and temps[stack[-1]] < t:
            j = stack.pop()
            res[j] = i - j               # 结果要的是「距离」，所以必须存下标
        stack.append(i)
    return res


if __name__ == "__main__":
    assert next_greater([2, 1, 2, 4, 3, 1]) == [4, 2, 4, -1, -1, -1]
    assert next_greater([5, 4, 3, 2, 1]) == [-1, -1, -1, -1, -1]   # 递减：全都没有
    assert next_greater([1, 1, 1]) == [-1, -1, -1]                 # 相等不算更大
    assert daily_temperatures([73, 74, 75, 71, 69, 72, 76, 73]) == [1, 1, 4, 2, 1, 1, 0, 0]
    print("下一个更大元素 / 每日温度：全部用例通过")
```

**正确性论证**（这是单调栈唯一真正需要理解的地方）：

> 设下标 `j` 在遍历到 `i` 时因为 `a[j] < a[i]` 被弹出。考虑任何 `i' > i`：若 `a[i'] > a[j]`，那么 `i` 本身也满足 `a[i] > a[j]` 且 `i < i'`，所以 `i'` 不可能是 `j` 的下一个更大元素（`i` 更靠前且已经满足条件）。因此 **`j` 一旦被弹出，对之后的所有元素都永远不会是答案**，丢弃它是安全的。

再看留在栈里的元素为什么递减：如果栈中存在 `j < k` 且 `a[j] <= a[k]`，遍历到 `k` 时 `j` 就会被弹出。所以栈内从栈底到栈顶必然严格递减——**栈里装的是「还没找到更大元素，而且离自己最近的障碍越来越大」的那些位置**。

### 7.2 摊还论证：为什么是 O(n)

每个下标恰好被 `append` 一次，也至多被 `pop` 一次；`while` 循环的每次迭代都对应一次 `pop`，所以内层循环在整个算法中的总迭代次数不超过 n：总代价是 `n 次 append + 至多 n 次 pop + n 次比较 = O(n)`，每个元素的摊还代价是 O(1)。这不是「平均情况 O(1)」——**对任意输入序列，总时间都是 O(n)**。这是摊还分析（[第 01 篇](01-complexity-analysis.md)）在算法设计上最典型的应用：用一个额外的栈，把「每个元素可能要和后面所有元素比较」的 O(n²) 变成「每个元素只进出栈一次」的 O(n)。代价是 O(n) 辅助空间：数组单调递减时，栈里装着全部元素。

### 7.3 柱状图中最大的矩形

给定柱状图的高度数组，求能勾勒出的最大矩形面积。朴素想法是枚举左右边界，O(n²)。单调栈的视角是：**枚举每根柱子作为矩形的高度，向左右扩展到第一个比它矮的柱子为止**——于是问题变成「对每根柱子，找左边和右边第一个更矮的柱子」，正是单调栈的原型。

```python
def largest_rectangle(heights):
    """柱状图中最大的矩形面积：把每根柱子当高度，向两侧扩到第一个更矮的。"""
    h = [0] + list(heights) + [0]     # 哨兵：左边保证栈不空，右边保证全部弹出
    stack, best = [], 0
    for i, x in enumerate(h):
        while stack and h[stack[-1]] > x:
            j = stack.pop()
            left = stack[-1]          # 弹出后的新栈顶 = 左边第一个更矮的柱子
            best = max(best, h[j] * (i - left - 1))
        stack.append(i)
    return best


if __name__ == "__main__":
    assert largest_rectangle([2, 1, 5, 6, 2, 3]) == 10     # 5×2，中间那两根高的撑不起来
    assert largest_rectangle([2, 4]) == 4                  # 2×2
    assert largest_rectangle([5, 5, 5]) == 15 and largest_rectangle([]) == 0
    assert largest_rectangle([9, 0, 9]) == 9               # 0 必须把两边隔开
    print("柱状图最大矩形：全部用例通过")
```

三个设计细节：**面积公式是高乘以左右边界差**——`h[j] * (i - left - 1)`，`i` 是右边第一个更矮的位置，`left` 是左边第一个更矮的位置，两者之间（不含端点）都是高度不小于 `h[j]` 的柱子，宽度正好是 `i - left - 1`；**两端的 0 是哨兵**——左端的 0 保证栈不空（`left = stack[-1]` 一定安全），右端的 0 保证所有柱子在最后一轮都被弹出，没有哨兵就得在循环外再写一遍最容易漏的清栈逻辑；**这里弹栈的触发条件是「栈顶比当前高」**，与 7.1 的「栈顶比当前矮」相反，判断方法不是背「递增栈还是递减栈」，而是问：弹出一个元素时，谁提供了它需要的边界信息？

### 7.4 接雨水

同一道题有两个都很漂亮的解法，差别恰好是「竖着切」与「横着切」。

```python
def trap_two_pointers(height):
    """按列算：每列的水 = min(左最高, 右最高) - 自身高度。O(n) 时间、O(1) 空间。"""
    lo, hi = 0, len(height) - 1
    left_max = right_max = water = 0
    while lo < hi:
        if height[lo] < height[hi]:
            # 右侧一定有一根不低于 height[hi] 的柱子，所以 lo 的水位由 left_max 定死
            left_max = max(left_max, height[lo])
            water += left_max - height[lo]
            lo += 1
        else:
            right_max = max(right_max, height[hi])
            water += right_max - height[hi]
            hi -= 1
    return water


def trap_stack(height):
    """按层算：栈内存还在积水的柱子，高度单调不升。O(n) 时间、O(n) 最坏空间。"""
    stack, water = [], 0
    for i, x in enumerate(height):
        while stack and height[stack[-1]] < x:
            bottom = height[stack.pop()]        # 凹槽底
            if not stack:
                break                           # 左边没有墙，这层水不存在
            left = stack[-1]
            water += (i - left - 1) * (min(height[left], x) - bottom)
        stack.append(i)
    return water


if __name__ == "__main__":
    cases = [[0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1], [4, 2, 0, 3, 2, 5],
             [], [3, 3, 3], [5, 0, 5]]
    for a in cases:                      # 两种视角互为对照，不需要额外参考实现
        assert trap_two_pointers(a) == trap_stack(a), a
    assert trap_two_pointers(cases[0]) == 6
    print("接雨水：双指针与单调栈在 %d 组输入上结果一致" % len(cases))
```

**双指针（按列算）**：每列的水位是 `min(左边最高, 右边最高) - 自身高度`。巧妙处在于不需要真的算出右边最高：当 `height[lo] < height[hi]` 时，`hi` 所在位置就是 `lo` 右侧一根不低于 `height[hi]` 的柱子，而左侧最高 `left_max` 已经维护好了，于是 `min(左最高, 右最高)` 就等于 `left_max`，可以立刻结算 `lo` 这一列。**单调栈（按层算）**：栈里存「还在积水的柱子」，高度单调不升；遇到更高的柱子 `x` 时把凹槽底 `bottom` 弹出，此时新栈顶 `left` 与当前 `x` 就是凹槽的左右墙，横向补一层水：宽度 `i - left - 1`，深度 `min(height[left], x) - bottom`。两者答案必然相同，分解方式不同：双指针竖着切（每列贡献多少水），单调栈横着切（每个凹槽里每层水有多少）——**同一问题被两种结构分别解决，说明栈在这里承担的是「记住尚未结算的边界」这个角色**，凡是「还没找到对手的元素」需要暂存，单调栈就适用。

## 8. 栈与队列的互相模拟

### 8.1 两个栈实现队列

队列要 FIFO，栈只能 LIFO。解法是两个栈：`in` 栈负责入队（只压不弹），`out` 栈负责出队（只弹不压）。

```python
class QueueByTwoStacks:
    """两个栈实现队列：in 只管入队，out 只管出队。"""

    def __init__(self):
        self._in, self._out = [], []

    def enqueue(self, x):
        self._in.append(x)                       # O(1)

    def _shift(self):
        if not self._out:                        # 只在 out 空时一次性搬完
            while self._in:
                self._out.append(self._in.pop())  # 逆序两次 = 正序
            # 如果每次 dequeue 都搬，队头会被压到栈底，顺序就错了

    def dequeue(self):
        self._shift()
        if not self._out:
            raise IndexError("dequeue from empty queue")
        return self._out.pop()                   # 摊还 O(1)

    def is_empty(self):
        return not self._in and not self._out


if __name__ == "__main__":
    q = QueueByTwoStacks()
    q.enqueue(1); q.enqueue(2)
    assert q.dequeue() == 1                      # 队头，而不是 2
    q.enqueue(3)
    assert [q.dequeue(), q.dequeue()] == [2, 3] and q.is_empty()

    q, moves = QueueByTwoStacks(), 0             # 统计搬家次数
    for i in range(1000):
        q.enqueue(i)
    for i in range(1000):
        if not q._out:
            moves += len(q._in)
        assert q.dequeue() == i
    assert moves == 1000                         # 每个元素一生只搬一次
    print("1000 次入队 + 1000 次出队，总搬家次数 =", moves)
```

**均摊 O(1) 的论证**：搬家条件是「`out` 为空」。搬完之后，`out` 里的元素只会被 `pop`（离开队列），不会回到 `in`；而 `in` 里剩下的元素是搬家之后才入队的，各自等下一次搬家。于是**每个元素一生最多被搬一次**，n 次入队的搬家总量不超过 n，加上每次操作的 O(1)，n 次入队加 m 次出队的总代价是 O(n + m)，均摊每次 O(1)。代价在最坏单次延迟：某一次 `dequeue` 可能触发搬 n 个元素的操作，耗时 O(n)——这与动态数组扩容是同一种长尾（[第 02 篇](02-array-dynamic-array.md)），对延迟敏感的场景不可接受。

### 8.2 两个队列实现栈

反过来用队列模拟栈。核心技巧是：**每 push 一个元素，就把它「翻」到队首**，于是队首永远等于栈顶，pop 直接出队即可。

```python
from collections import deque


class StackByTwoQueues:
    """两个队列实现栈：push 时把新元素翻到队首，pop 直接出队。"""

    def __init__(self):
        self._q1 = deque()            # 主队列，队首永远等于栈顶
        self._q2 = deque()            # 辅助队列

    def push(self, x):
        self._q2.append(x)                        # 新元素先进辅助队列
        while self._q1:
            self._q2.append(self._q1.popleft())   # 旧元素整体排到它后面
        self._q1, self._q2 = self._q2, self._q1   # 交换引用，O(1)
        # 代价：每次 push 都要搬 size 个元素 → 单次 O(n)，且无法摊还

    def pop(self):
        if not self._q1:
            raise IndexError("pop from empty stack")
        return self._q1.popleft()                 # O(1)

    def top(self):
        if not self._q1:
            raise IndexError("top from empty stack")
        return self._q1[0]

    def is_empty(self):
        return not self._q1


if __name__ == "__main__":
    s = StackByTwoQueues()
    s.push(1); s.push(2)
    assert s.top() == 2 and s.pop() == 2
    s.push(3)
    assert [s.pop(), s.pop()] == [3, 1] and s.is_empty()

    n, total, s = 500, 0, StackByTwoQueues()      # 统计搬家次数
    for i in range(n):
        total += len(s._q1)                       # push 时要搬走的旧元素个数
        s.push(i)
    assert total == n * (n - 1) // 2              # n(n-1)/2，不是 O(n)
    print("%d 次 push 共搬家 %d 次 = n(n-1)/2" % (n, total))
```

**为什么这里拿不到均摊 O(1)**：第 k 次 push 要搬 k−1 个元素，第 k+1 次 push 又要搬 k 个——新增的那个元素也立刻被算进下一轮的搬运量，所以「一个元素一生只搬一次」的性质不成立。n 次 push 的搬运总量是 `1 + 2 + ... + (n-1) = n(n-1)/2 = Θ(n²)`，均摊到每次 push 是 Θ(n)，实测 500 次 push 搬家 124750 次。两点延伸：**其实一个队列就够了**（push 直接入队，pop 时把前 n−1 个元素出队再入队，转一圈后剩下的那个就是栈顶，代价同样是每次 pop O(n)，说明「两个队列」不是必要条件）；**方向是不对称的**——队列能用两个栈以摊还 O(1) 模拟，栈用队列模拟却是实打实的 Θ(n) 每次操作，因为栈的操作只依赖一端、队列的操作依赖两端，栈是更容易被组装出来的那个。工程上两者都不会这么做，语言实现里栈和队列都直接建在数组或双端队列上（[第 05 篇](05-queue-deque.md)）；这两个练习的价值在于看清 LIFO 与 FIFO 的接口约束有多强，以及摊还分析的前提有多容易被破坏。

## 9. 工程应用

下面每个场景都能回答同一个问题：**为什么栈是对的容器**。

| 场景            | 为什么栈是对的容器                                                |
| ------------- | -------------------------------------------------------- |
| 编辑器撤销/重做      | 「撤销」的定义就是取消最近一次操作，正是 LIFO；重做栈是版本历史的另一条轨道                 |
| JSON / 表达式解析器 | 语法本身就是嵌套结构，栈深对应嵌套深度；递归下降用调用栈，显式栈版本能把状态存起来                |
| 深度优先搜索        | DFS 的定义是「沿一条路走到底再回溯」，回溯点就是「最近一个还没探索完的节点」                 |
| 编译器符号表        | 作用域是嵌套的（进入压入、离开弹出），名字查找「由内向外」就是从栈顶往下扫                    |
| 异常栈回溯         | 传播异常就是沿调用栈不断弹帧找 handler；`try/finally` 的语义是「无论怎么弹，这段都要执行」 |
| 浏览器历史         | 后退栈与前进栈；实际实现是「历史数组 + 当前下标」，但心智模型仍是两个栈                    |
| 函数调用 / 协程切换   | 调用栈是一等公民；协程是「可以暂停的调用栈」，切换协程就是换一个栈指针                      |

几条值得展开的细节。**撤销/重做**的形状是两个栈加一条规则：执行新操作时**必须清空重做栈**，否则历史出现分叉，`redo` 出来的状态无法确定——这和「显式栈可恢复」是同一件事的两面，栈里装的是历史，历史必须是线性的。**解析器**有两种写法，对应第 4 节的两类套路：递归下降直接用调用栈存状态，代码短、可读性高，但无法中途暂停，嵌套太深还会爆栈（这也是许多语言规范规定嵌套层数上限的原因）；显式栈版本把「当前期望的下一个 token」压进自己的栈，代价是代码更长，收益是**可以在任意 token 边界暂停和恢复**，流式 JSON 解析器能一边收网络包一边解析，靠的就是这个。**符号表**不是「用栈还是用哈希表」的二选一，而是两者组合：每一层作用域内部用哈希表（层内查找 O(1)），层与层之间用栈（进出 O(1)），而「由内向外查找」就是把栈从顶到底扫一遍、每层查一次哈希。

**协程**则是这套抽象在系统层面的放大：有栈协程（Go 的 goroutine、Lua 的 coroutine）维护独立可增长的栈，切换代价是换一个栈指针；无栈协程（Rust 的 async、JS 的 generator、Python 的 `async`）把「帧里的东西」在编译期提升成堆上的状态机——**这正是第 4 节「显式栈 + 阶段标记」在编译器里被自动化的样子**。手写两次显式栈遍历，再回来看 `await`，会发现它们是同一件事。

## 10. 陷阱

> [!WARNING]
> **`list.pop()` 是 O(1)，`list.pop(0)` 是 O(n)**。Python 的 `list` 在头部删除或插入要整体搬移后面的所有元素。把 `list` 当队列用（`append` + `pop(0)`）会让本该 O(n) 的遍历变成 O(n²)：n = 10⁵ 时是 5×10⁹ 次元素搬移。队列要用 `collections.deque` 的 `popleft()`，它是真正的 O(1)（[第 05 篇](05-queue-deque.md)）；`insert(0, x)` 同理。

> [!CAUTION]
> **深递归不是「调大限制」能解决的问题**。Python 改 `sys.setrecursionlimit` 只改计数器，真实的内存边界不动：调大之后 C 栈先被用尽，进程直接段错误，比 `RecursionError` 糟糕得多。C 更是没有软限制——栈指针越界就是访问保护页，进程立刻被终止。正确的做法是改成显式栈迭代（第 4 节），或者换成不依赖递归的算法（例如 Morris 遍历可以把中序的空间降到 O(1)，[第 07 篇](07-binary-tree-traversal.md)）。

**别把「栈」和「堆内存」混为一谈**。两者只是同名，语义完全不同：

| <br /> | 栈（调用栈）                | 堆（heap）                  |
| ------ | --------------------- | ------------------------ |
| 是什么    | 线程私有的一块连续内存，按 LIFO 使用 | 进程共享的内存池，由分配器管理          |
| 谁决定大小  | 操作系统与线程创建参数           | 可用物理内存与地址空间              |
| 分配与释放  | 移动栈指针，函数返回自动回收        | `malloc`/`free`、GC，代价高得多 |
| 失败模式   | 越过边界即段错误              | 分配失败返回 NULL 或抛异常         |

一句话：**显式栈本身是堆上的对象**。把递归改成显式栈，本质是把状态从「线程的栈」搬到「堆」，用更慢的分配换更大的容量和可中断性。

其余三条：**单调栈里存值还是存下标**——只存值就丢掉了位置信息，`i - j`（每日温度）、`i - left - 1`（柱状图宽度）都算不出来，默认存下标，需要值时用 `nums[stack[-1]]` 现取，存值还会让等值元素的处理变得含混；**单调栈的比较符号决定语义**——`<` 还是 `<=` 决定求的是「严格更大」还是「大于等于」，直接改变重复元素上的答案，写之前先想清楚重复元素该怎么算再选符号；**递归改显式栈时漏阶段标记**——后序遍历是重灾区，只靠节点指针无法区分「刚从左边回来」和「刚从右边回来」，漏了标记就会重复输出或死循环，判断标准是「递归版在调用点之后有几个不同的动作，就需要几个阶段」。

## 11. 小结

- 栈只有五个操作，保证的性质是「最近的、尚未了结的」最先被处理；所有回退/回溯/取消类机制都建立在这条性质上。
- 窄接口带来三个好处：不变式自动成立、实现可自由替换、用错变得困难（Java 的 `Stack` 继承 `Vector` 是接口过宽的反面教材）。
- 三种实现：动态数组（默认，摊还 O(1)、缓存友好）、单链头插（最坏 O(1)，代价是每元素一个指针和一次 malloc）、定长数组（嵌入式与内核，必须显式处理逻辑溢出）。
- 调用栈的深度上限不是常数，而是「栈大小除以帧大小」；Python 的 1000 层是解释器计数器（可捕获的 `RecursionError`），C 的爆栈是内存越界（不可捕获的段错误）。栈内存与堆内存的故障模式相反：栈溢出立即崩溃不可恢复，堆分配失败可以处理。
- 递归改迭代有两个可判定的形态：尾递归形态改成循环加累积变量；需要恢复现场时用显式栈加阶段标记（中序能压缩掉标记，后序不能）。
- 括号匹配必须用栈，因为多类型括号的合法性无法用计数器表达（`"([)]"` 计数平衡却不合法）；后缀表达式则把优先级与结合性一次性编码进序列，调度场算法用一个运算符栈完成转换，前缀负号必须「直接压栈不弹栈」。
- 单调栈 O(n) 的全部理由是：被弹出的元素永远不会再成为后续元素的答案，加上「每个元素最多进出栈一次」，得到摊还 O(1)。
- 队列能用两个栈以摊还 O(1) 模拟（每个元素一生只搬一次家），栈用队列模拟却是 Θ(n) 每次操作，方向不对称。

## 12. 练习

**1.** 「只用计数器就能检查括号是否匹配」对单类型括号成立，对多类型括号不成立。给出一个计数上完全平衡但不合法的输入，并说明为什么必须用栈才能发现它。

> [!TIP]
> 思路`"([)]"`：左右括号总数平衡，各类括号数量也都平衡，但配对关系交叉了。计数器只记录「未闭合的数量」，丢掉了「未闭合的是哪一类、以及它们的顺序」——而顺序正是合法性的定义（最近未闭合的必须最先闭合）。栈顶恰好保存了「最近未闭合的那一个」，所以能发现交叉；「栈空时遇到右括号」和「扫完栈非空」这两种情况，计数器同样测不出来。

**2.** 把二叉树的后序遍历写成显式栈版本，并说明为什么中序的「压缩版」（只压左链、出栈即输出）在后序上失效。

> [!TIP]
> 思路后序要等左右子树都处理完才能输出自己，所以「刚从左子树回到某节点」和「刚从右子树回到某节点」必须区分。中序靠「左子树一做完就立刻输出自己」这个固定节奏，一个状态就够；后序需要 (节点, 阶段) 二阶段标记，或记录 `last_visited` 指针判断右子树是否已访问。用模板写：阶段 0 压入「右子树、自身阶段 1、左子树」，阶段 1 压入「右子树、自身阶段 2」，阶段 2 输出自己。

**3.** 设计一个支持 `push`、`pop`、`min` 三种操作都为 O(1) 的栈（最小栈），说明 `pop` 之后 `min` 怎么恢复，并分析空间代价。

> [!TIP]
> 思路两个同步的栈：数据栈 `data` 与「当前最小值栈」`mins`。`push(x)` 时 `mins` 压入 `min(x, mins[-1])`，`pop` 时两栈同弹；因为 `mins` 栈顶始终等于 `data` 当前的最小值，`min()` 就是 `mins[-1]`，O(1)。空间代价是每元素一个额外记录，O(n)。可以只在 `x <= mins[-1]` 时才压入 `mins`、`pop` 时判断再决定是否弹 `mins`，平均省一半空间，但单调递减输入下最坏仍是 O(n)。

**4.** 求每个元素**左边**第一个比它小的元素（而不是右边第一个更大的）。栈的单调性要怎么改？弹出时机是否变化？

> [!TIP]
> 思路两种改法：①把遍历方向反过来（从右往左），问题就与「下一个更大元素」同构；②保持从左往右，把「递减栈」换成「递增栈」——遍历到 `x` 时把所有 `>= x` 的栈顶弹出（它们对后面更小的元素不可能有用），此时栈顶就是左边第一个比 `x` 小的元素。核心判据始终是同一句话：**弹出时机由「当前元素是否使栈顶元素失去成为答案的资格」决定**，而不是死记「递减栈」或「递增栈」。

**5.** 调度场算法里右结合运算符同级不弹栈。分别写出 `2^3^2` 在「同级也弹」和「同级不弹」两种实现下的后缀结果，并说明哪个符合数学约定。

> [!TIP]
> 思路同级也弹得到 `2 3 ^ 2 ^`，即 `(2^3)^2 = 64`；同级不弹得到 `2 3 2 ^ ^`，即 `2^(3^2) = 512`。数学约定（以及 Python、Ruby、Haskell 的幂运算）是右结合，答案是 512。同一套规则下左结合的 `-` 必须同级就弹：`10-2-3` 若同级不弹会得到 `10 2 3 - -` = 11，而正确结果是 5。所以「结合性」这一个比特编码的就是「同级弹不弹」这一个动作。

**6.** 用栈实现撤销/重做。回答两个问题：为什么执行新操作时必须清空重做栈？为什么重做栈里的操作在重做之后要重新压回撤销栈？

> [!TIP]
> 思路清空重做栈：重做栈代表「从当前状态可以前进到的未来」，用户一旦做了新操作，当前状态就变了，那些未来不再是从这个状态出发能到达的，保留它们会让重做产生与历史不一致的状态（历史分叉）。重新压回撤销栈：撤销/重做只是「当前状态指针」在两个方向上移动，任何一次状态迁移都必须能反向迁移——`undo` 把操作从撤销栈搬到重做栈，`redo` 就必须把它搬回去，否则第二次 `redo` 会找不到操作。

**7.** 两个栈实现的队列，单次 `dequeue` 最坏代价是 O(n)。在延迟敏感的场景（比如每帧要处理一批请求的游戏服务器）怎么规避？

> [!TIP]
> 思路两个方向：①**主动预搬**——在队列空闲时（或每帧的固定阶段）检查 `out` 是否为空而 `in` 非空，提前搬过去，把 O(n) 的代价摊到空闲时间上，让真正的 `dequeue` 永远只做 O(1)；②**换结构**——直接用环形缓冲区（数组加头尾指针）实现队列，所有操作都是最坏 O(1)（[第 05 篇](05-queue-deque.md)），从根上消除长尾。这个取舍是通用的：要么把长尾挪到能承受的时间点，要么换成没有长尾的数据结构。

**8.** 一棵 n = 10⁶ 的二叉树，深度可能达到 10⁶（极端退化成链）。递归遍历和显式栈遍历各自的代价是什么？如果必须保留递归写法，有办法让它安全吗？

> [!TIP]
> 思路递归版：Python 默认 1000 层直接 `RecursionError`；C 里每帧若 64 字节，8 MB 栈只能撑约 13 万层，10⁶ 层必然爆栈。显式栈版：时间同为 O(n)，额外空间 O(深度) 最坏 10⁶ 项——但 Python 的每项是元组对象，10⁶ 项约几十到上百 MB，比机器栈帧大好几倍，这是真实代价。让递归安全的办法：①在独立线程里跑（先 `threading.stack_size(64 * 1024 * 1024)`，再用 `threading.Thread` 启动），把栈上限从 8 MB 抬到几十 MB——只是抬高天花板，没有消除；②用 Morris 遍历把空间降到 O(1)（[第 07 篇](07-binary-tree-traversal.md)），代价是遍历过程中会临时修改树结构。选哪条取决于「树的形状能否预期」和「内存与栈深度哪个约束更紧」。
