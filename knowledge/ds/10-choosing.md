前面九篇是零件目录，本篇是装配手册。数据结构选型不靠背复杂度表，靠的是给问题画一张**操作画像**：每种操作各占多少比例、数据量级多大、有无顺序要求——画像一清，答案基本自己浮出来。

## 选型四问

1. **主导操作是什么？** 查找多还是插入多？要随机下标还是按键取值？
2. **要不要顺序？** 只要"存在性"→ 哈希；要范围查询、最大最小、排名 → 有序结构（树/跳表）；只关心极值 → 堆
3. **数据规模与到达方式？** 一次性全量（可排序/建堆）还是流式（要摊还友好、TopK）；内存装得下吗（装不下考虑外存/B+ 树）
4. **键的形态？** 可哈希吗？有前缀语义吗（Trie）？是区间/集合关系吗（线段树、并查集）？

## 常用场景速查

| 场景            | 首选           | 理由                 |
| ------------- | ------------ | ------------------ |
| 去重 / 存在性      | 哈希集合         | O(1) 判存            |
| 键值映射          | 哈希表          | 点查最快               |
| 有序映射 / 范围查询   | 平衡树 / 跳表     | 中序有序、前驱后继 O(log n) |
| 反复取最值 / TopK  | 堆            | O(log n) 维护极值      |
| 撤销 / 括号 / DFS | 栈            | 最近优先               |
| 公平排队 / BFS    | 队列           | 先来先服务              |
| 前缀匹配 / 补全     | Trie         | O(L) 与词库大小无关       |
| 动态连通性         | 并查集          | 近 O(1) 合并查询        |
| 依赖调度 / 判环     | 拓扑排序         | DAG 线性化            |
| 无权最短路         | BFS          | 首次到达即最短            |
| 带权最短路（无负权）    | Dijkstra + 堆 | 贪心正确性有保证           |

## 主流语言容器对照

| 需求   | Python               | C++             | Rust       |
| ---- | -------------------- | --------------- | ---------- |
| 动态数组 | list                 | vector          | Vec        |
| 双端队列 | deque                | deque           | VecDeque   |
| 哈希映射 | dict                 | unordered\_map  | HashMap    |
| 有序映射 | （用 sortedcontainers） | map（红黑树）        | BTreeMap   |
| 优先队列 | heapq（模块）            | priority\_queue | BinaryHeap |
| 有序集合 | sortedcontainers     | set             | BTreeSet   |

三件值得记住的实现细节：

- Python dict/set 底层是**开放寻址**哈希表，键插入不保序——要插入序用 dict 的保序特性（3.7+ 保证）或 collections.OrderedDict
- C++ unordered\_map 链地址 + 树化防碰撞攻击，map 是红黑树；Rust std 的 HashMap 用**随机盐的 SipHash** 防哈希 DoS，可换 faster hash（如 fxhash）提速
- 这些容器的性能特征会随实现细节变化，**关键路径的选型要实测**，不要背表

## 组合结构三板斧

单一结构不够时，经典组合拳——这也是面试设计题的骨架：

1. **哈希 + 双向链表 = LRU 缓存**：哈希 O(1) 定位节点，链表 O(1) 摘除/插头维护"最近使用"
2. **哈希 + 数组 = O(1) 随机删除的集合**：数组存元素（尾部交换删除），哈希记下标
3. **对顶堆 = 流式中位数**：大顶堆装较小一半，小顶堆装较大一半，平衡两堆大小即可 O(log n) 取中位

> [!WARNING]
> 最后一个工程忠告：**先让正确的版本跑起来、量出瓶颈，再换结构**。把 O(n) 查找换成 O(1) 哈希很简单；反过来为了不存在的"快"引入复杂结构，换来的往往是 bug。数据结构优化永远排在 profile 之后，不在之前。
