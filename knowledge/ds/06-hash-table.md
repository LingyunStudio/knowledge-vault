在哈希表之前，「按键找值」只有两条路：逐个比较的 O(n)，或者先排序再二分的 O(log n)。哈希表走了第三条路——把键交给一个函数算出下标，**用一次计算替代一整轮搜索**。这一个想法支撑起了当代软件里最高频的数据结构：语言里的字典和集合、数据库的哈希索引与哈希连接、缓存的键路由、编译器的符号表、去重与计数。

代价是它把「最坏情况」交了出去：平均 O(1)，最坏 O(n)。哈希表的所有设计——哈希函数、冲突处理、容量策略——都是围绕「如何让最坏情况尽可能不出现，出现时也不至于太惨」展开的。

## 1. 三件套与一个绕不过去的矛盾

一个哈希表由三部分组成：

| 组件        | 职责                  | 设计要点                      |
| --------- | ------------------- | ------------------------- |
| 哈希函数 h(k) | 把任意键映射到 0 … m−1 的下标 | 确定性（同键同值）、均匀、快、抗构造        |
| 桶数组       | 存放位置，下标即哈希值         | 容量 m 通常是 2 的幂或质数          |
| 冲突处理      | 两个键落到同一个桶时怎么办       | 链地址法 或 开放寻址法——这是一切性能差异的源头 |

**冲突不可避免**，这不是实现不够聪明，而是数学事实：键的取值空间（所有可能的字符串）是无限的，桶的数量是有限的，从无限到有限的映射必然多对一（鸽巢原理）。所以每个哈希表实现都必须回答「撞了怎么办」，而答案只有两大类：

| <br />  | 链地址法（chaining）                   | 开放寻址法（open addressing）                |
| ------- | -------------------------------- | ------------------------------------- |
| 冲突时的动作  | 挂在同一个桶的链表（或树）里                   | 按探测序列找下一个空位                           |
| 负载因子 α  | 可以 > 1                           | 必须 < 1（满了就无处可放）                       |
| 空间      | 每元素额外一个指针（8 字节起）                 | 数组本身，无额外指针                            |
| 缓存      | 差（节点散落，指针追逐）                     | 好（顺着连续数组探测）                           |
| 删除      | 直接摘链，简单                          | 需墓碑标记，否则探测链断裂                         |
| 对哈希函数质量 | 要求较低（碰撞只是链变长）                    | 要求高（碰撞会连锁占用别人的位置）                     |
| 代表实现    | Java HashMap、C++ `unordered_map` | Python dict、Rust `HashMap`、Redis dict |

后文第 3、4 节会给出两派的完整实现，第 5 节算清楚「为什么开放寻址必须把负载因子压在 0.75 以下」，第 6 节看三种语言标准库的真实做法。

## 2. 哈希函数：均匀比快更重要

### 2.1 四条要求

1. **确定性**：同一个键必须永远得到同一个值——否则存进去就找不回来。
2. **均匀性**：输出应尽可能均匀地落在桶空间中，且**相似输入要产生不相似的输出**（雪崩效应：改变输入一个比特，输出约一半比特翻转）。
3. **计算快**：哈希表每次查找都要算一次，哈希函数本身太贵的话，O(1) 的好处会被吃掉。
4. **抗构造**：给定哈希函数，攻击者不应能轻易造出一堆全部撞到一起的键。

第 2 条和第 4 条常被低估。举个具体例子：如果键是连续整数，而哈希函数是 `k % m` 且 m = 2⁸ = 256，那么所有键的**低 8 位**决定位置；如果键都是 1000 的倍数（比如以毫秒为单位的整数 ID 都对齐到 4 的倍数），那大半桶永远空着——均匀性被输入的规律性击穿。这是「除法散列要选质数」和「2 的幂做容量时必须把高位混进来」的根本原因。

### 2.2 三种经典构造

**除法散列**：`h(k) = k mod m`。最简最快，但对 m 敏感：m 取 2 的幂等于只看低位；m 取 10 的幂等于只看十进制低位。所以传统实现取 **m 为质数**（且远离 2 的幂），让键的各个位都参与决策。

**乘法散列**：`h(k) = floor(m · frac(k · A))`，其中 A 取无理数黄金比例 0.6180339887…（Knuth 推荐）。好处是**对 m 不敏感**，m 可以取 2 的幂（从而用位运算和移位实现），而分布仍接近均匀。

**字符串哈希**：把字符串看成多项式并取模：

```python
def poly_hash(s, base=131, mod=(1 << 61) - 1):
    """多项式滚动哈希：h = (s0*base^(L-1) + s1*base^(L-2) + ... + sL-1) mod p"""
    h = 0
    for ch in s:
        h = (h * base + ord(ch)) % mod
    return h
```

`base` 取一个大于字符集大小的质数（如 131、1\_000\_003），`mod` 取大质数（2⁶¹ − 1 是常见选择，乘法用 Python 的大整数不会溢出；C 里需要注意溢出与 2⁶¹−1 的快速取模技巧）。这个写法的进阶用途是**滚动哈希**：从 `h(s[i:i+L])` 能在 O(1) 内算出 `h(s[i+1:i+L+1])`，字符串匹配的 Rabin-Karp 算法就建立在这上面（[第 15 篇](15-strings.md)）。

> [!WARNING]
> 多项式滚动哈希可以用「构造碰撞」攻击。给定 base 和 mod，攻击者能解出多组同哈希字符串（对固定指纹的碰撞是代数问题，难度不高）。用于安全场景必须**随机化 base**（每次运行随机取），或改用密码学哈希。这不是理论洁癖：EthCC 曾出现过基于哈希碰撞的合约攻击，Git 的 SHA-1 碰撞也已是现实。

### 2.3 位运算优化与「扰动」

当容量 m 取 2 的幂时，`k mod m` 退化成 `k & (m - 1)`，一次与运算，比除法快数倍——**代价是只用到了键的低位**。Java 8 的解法是加一步「扰动」，把高位混进低位：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

`h >>> 16` 取高 16 位，异或到低 16 位，于是低位里也含有高位的信息。代价是一条移位和一条异或——非常划算。Python 的字符串哈希（SipHash）和 Rust 的 SipHash 本身就有雪崩性质，不需要这一步额外扰动。

### 2.4 通用哈希与随机化

理论上最漂亮的方案是**通用哈希族**：预先随机挑选一族哈希函数中的一个，可以证明对**任意**固定输入集合，碰撞总数的期望都是最优的。最简单的构造是 `h(k) = ((a·k + b) mod p) mod m`，其中 p 是大质数，a、b 在 \[1, p−1] 中随机取。

这个思想在工程上的落地就是**随机盐**：哈希表初始化时生成一个随机种子，混进哈希计算。这样攻击者无法离线构造出「全部撞车」的键集合——因为他不知道种子。代价是哈希值不可复现，因此**不能把 Python 的 `hash()` 结果持久化**（它默认每次进程启动都不一样，见第 7 节）。

## 3. 链地址法：撞了就挂链

最直观的方案：每个桶存一个链表头，冲突的键依次挂在链上。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define NBUCKET 1024      /* 取 2 的幂仅为示例；实际用质数更好 */

typedef struct Node {
    char *key;
    int value;
    struct Node *next;
} Node;

typedef struct {
    Node **buckets;
    size_t count;
} ChainMap;

static unsigned hash_str(const char *s) {
    unsigned h = 2166136261u;             /* FNV-1a 32 位初始值 */
    for (; *s; s++) {
        h ^= (unsigned char)*s;
        h *= 16777619u;                   /* FNV 质数 */
    }
    return h;
}

ChainMap *cm_new(void) {
    ChainMap *m = malloc(sizeof *m);
    if (!m) return NULL;
    m->buckets = calloc(NBUCKET, sizeof(Node *));
    if (!m->buckets) { free(m); return NULL; }
    m->count = 0;
    return m;
}

void cm_free(ChainMap *m) {
    for (size_t i = 0; i < NBUCKET; i++) {
        Node *p = m->buckets[i];
        while (p) { Node *nx = p->next; free(p->key); free(p); p = nx; }
    }
    free(m->buckets);
    free(m);
}

/* 返回 1 表示新增，0 表示覆盖了已有键 */
int cm_put(ChainMap *m, const char *key, int value) {
    unsigned idx = hash_str(key) & (NBUCKET - 1);
    for (Node *p = m->buckets[idx]; p; p = p->next) {
        if (strcmp(p->key, key) == 0) { p->value = value; return 0; }
    }
    Node *n = malloc(sizeof *n);
    if (!n) return -1;                    /* 分配失败 */
    n->key = strdup(key);
    if (!n->key) { free(n); return -1; }
    n->value = value;
    n->next = m->buckets[idx];            /* 头插：O(1)，但新元素总在链首 */
    m->buckets[idx] = n;
    m->count++;
    return 1;
}

int cm_get(const ChainMap *m, const char *key, int *out) {
    unsigned idx = hash_str(key) & (NBUCKET - 1);
    for (const Node *p = m->buckets[idx]; p; p = p->next) {
        if (strcmp(p->key, key) == 0) { *out = p->value; return 1; }
    }
    return 0;
}
```

这段代码里藏着链地址法的全部工程要点：

- **查找代价 = 1 次哈希 + 1 次数组访问 + 遍历链长**。平均链长就是负载因子 α，所以平均代价约 1 + α（成功查找约 1 + α/2）。
- **头插 O(1)，但插入顺序与遍历顺序相反**，而且同一键被覆盖时不改变位置（所以 Python 的 dict 保序特性不是链地址法能提供的，见第 6 节）。
- **每个元素一次独立 malloc**：节点散落在堆的各处，遍历时全是随机访存。这是链地址法最大的性能软肋。
- **`strcmp` 在哈希值相同时才执行**，但每次键比较是 O(L)，别忘了把它算进复杂度。

### 3.1 树化：链太长时的兜底

链表退化到 O(n) 是现实的威胁——要么是哈希函数差，要么是被攻击。Java 8 的对策是：**单条链长度 ≥ 8 且总容量 ≥ 64 时，把链表转成红黑树**（查找从 O(链长) 变 O(log 链长)）；链再短回 6 个元素时退化回链表（用两个阈值留迟滞，避免在临界点反复转换）。

为什么阈值是 8？在理想随机的哈希下，一个桶里 8 个元素的概率约 6×10⁻⁸；也就是说正常情况下永远转不了树，这个机制纯粹是为「出了事别崩」准备的——这就是「工程上的防御性设计」的样子：平时不花成本，坏情况下保命。

> [!NOTE]
> 树化不能解决哈希碰撞攻击（数据全撞进一个桶时，树化后是 O(log n) 而不是 O(1)，但至少不是 O(n)），真正治本的是第 7 节的随机盐。Java 的树化是为了兜底，不是为了安全。

## 4. 开放寻址法：冲突了就换个位置

开放寻址法把元素**全部存在一个数组里**，不放指针。碰撞时不挂链，而是按一个**探测序列**找下一个空位：

- **线性探测**：`i, i+1, i+2, …`（对容量取模）。实现最简单，缓存最友好。
- **二次探测**：`i, i+1², i+2², i−2², i+3², i−3²…`，缓解线性探测的聚集。
- **双重散列**：`i, i+h₂(k), i+2·h₂(k), …`，用第二个哈希函数决定步长，分散性最好。

### 4.1 聚集：线性探测的代价

线性探测会形成**聚集（clustering）**：如果一个位置的元素被删或长链延伸，后续插入都会顺着往后挤，把「连续占用段」越拉越长。任何散列到这段区间内的键都要一路挤过去——平均探测次数因此比链地址法增长快得多。二次探测能打散「主聚集」，但仍有「次聚集」（散列到同一初始位置的键走同一条路径）。双重散列基本消除聚集，代价是每次探测要算两次哈希。

### 4.2 删除与墓碑

开放寻址不能把元素直接置空：假设哈希到桶 i 的键 A 插在 i+2（因为 i、i+1 被占），删除 i+1 的元素后置空，那么查找 A 时会在 i+1 处遇到空位而**提前判定「不存在」**——探测链断了。

标准解法是**墓碑（tombstone）**：删除时写入一个特殊标记（如 `DELETED`），查找时墓碑视为「继续探测」，插入时可以复用墓碑位置。墓碑过多会让表「假满」，所以需要在墓碑占比高时重建。

### 4.3 完整实现

下面是一个可运行的开放寻址哈希表（线性探测 + 墓碑 + 自动扩容），也是本板块少数几段「完整设施而非片段」的代码，值得通读：

```python
class Tombstone:
    """墓碑标记：表示这个位置曾有元素，现已删除。"""


class OpenHashTable:
    EMPTY = None
    DELETED = Tombstone()

    def __init__(self, capacity=8, max_load=0.7):
        self._slots = [self.EMPTY] * capacity   # 槽位：None / 墓碑 / (key, value)
        self._used = 0                          # 真实元素个数
        self._dead = 0                          # 墓碑个数
        self._max_load = max_load

    def _probe(self, key, slots):
        """线性探测，返回 (是否找到, 槽下标)。"""
        m = len(slots)
        i = hash(key) & (m - 1)
        first_dead = -1
        for _ in range(m):
            slot = slots[i]
            if slot is self.EMPTY:
                # 遇到空位说明后面不可能有该键；优先复用更早发现的墓碑
                return (False, first_dead if first_dead >= 0 else i)
            if slot is self.DELETED:
                if first_dead < 0:
                    first_dead = i
            elif slot[0] == key:
                return (True, i)
            i = (i + 1) & (m - 1)
        # 全表探测完（都是墓碑）
        return (False, first_dead)

    def _resize(self, capacity):
        old = self._slots
        self._slots = [self.EMPTY] * capacity
        self._used = self._dead = 0
        for slot in old:
            if slot is not self.EMPTY and slot is not self.DELETED:
                self._insert_raw(slot[0], slot[1])

    def _insert_raw(self, key, value):
        _, i = self._probe(key, self._slots)
        self._slots[i] = (key, value)
        self._used += 1

    def put(self, key, value):
        if (self._used + self._dead) / len(self._slots) >= self._max_load:
            self._resize(len(self._slots) * 2)
        found, i = self._probe(key, self._slots)
        if found:
            self._slots[i] = (key, value)          # 覆盖
            return
        if self._slots[i] is self.DELETED:
            self._dead -= 1                        # 复用了墓碑
        self._slots[i] = (key, value)
        self._used += 1

    def get(self, key, default=None):
        found, i = self._probe(key, self._slots)
        return self._slots[i][1] if found else default

    def delete(self, key):
        found, i = self._probe(key, self._slots)
        if not found:
            return False
        self._slots[i] = self.DELETED
        self._used -= 1
        self._dead += 1
        # 墓碑过多会拖慢探测，按 1/4 阈值重建
        if self._dead > len(self._slots) // 4:
            self._resize(len(self._slots))
        return True

    def __len__(self):
        return self._used

    def __contains__(self, key):
        return self._probe(key, self._slots)[0]


if __name__ == "__main__":
    t = OpenHashTable()
    for i in range(100):
        t.put(f"key{i}", i * i)
    assert t.get("key42") == 42 * 42
    assert "key99" in t
    assert t.delete("key42") and "key42" not in t
    assert t.get("key42") is None
    t.put("key42", -1)                       # 复用墓碑
    assert t.get("key42") == -1
    assert len(t) == 100
    print("ok, 槽位数 =", len(t._slots))
```

几个必须理解的设计点：

- **扩容条件是「元素 + 墓碑」与容量的比值**，不是元素个数。只按元素算会让墓碑堆满整张表，查找退化。
- **`_probe` 要记住第一个墓碑的位置**，插入时优先复用，而不是插到更远的空位——否则墓碑会越来越多。
- **容量始终取 2 的幂**，所以取模可以用 `& (m - 1)`；同时哈希值的高位被丢掉，实际实现里需要 `hash()` 自身有良好雪崩（Python 的内置 `hash()` 满足）。
- **删除是「标记」而非「清除」**，所以迭代顺序、内存占用都不会立刻改变。

> [!WARNING]
> 开放寻址最常见的两个 bug：①删除时直接置空（探测链断裂，后续键「消失」）；②扩容时没有重新插入所有元素（漏掉墓碑处理或直接 `copy` 槽位数组，导致探测序列错乱）。这两个 bug 的共同特征是「小数据量测试全过、数据量上来后偶发查不到」——写开放寻址一定要写压力测试。

## 5. 负载因子：那个必须被压住的数字

负载因子 α = 元素数 / 桶数，是哈希表唯一的「健康指标」。理论上的期望探测次数（Knuth 的结果，假设完全随机散列）：

| 负载因子 α | 链地址：成功查找 | 链地址：失败查找 | 线性探测：成功 | 线性探测：失败 |
| ------ | -------- | -------- | ------- | ------- |
| 0.5    | 1.25     | 0.5      | 1.5     | 2.5     |
| 0.75   | 1.375    | 0.75     | 2.5     | 8.5     |
| 0.9    | 1.45     | 0.9      | 5.5     | 50.5    |
| 0.99   | 1.495    | 0.99     | 50.5    | 5000.5  |

（链地址成功 ≈ 1 + α/2，失败 ≈ α；线性探测成功 ≈ (1 + 1/(1−α))/2，失败 ≈ (1 + 1/(1−α)²)/2）

这张表解释了三个工程决策：

1. **链地址法能容忍 α > 1**：性能随 α 线性劣化，不会崩。Java HashMap 默认阈值 0.75，Redis 的 dict 在 α = 1 时开始扩容，某些实现甚至允许 α = 5。
2. **开放寻址必须把 α 压到 0.75 以下**：α = 0.9 时失败查找要探 50 次，α = 0.99 时要探 5000 次——曲线是 (1−α)⁻² 量级，接近满表时性能断崖式崩塌。Rust 的 `HashMap` 阈值是 87.5%（7/8），已经算激进；Python dict 用 2/3。
3. **扩容的摊还分析**：和动态数组同款。容量翻倍、重新散列全部元素，单次扩容代价 O(n)，但因为容量翻倍，n 次插入里只发生 O(log n) 次扩容，总量 O(n)，摊还 O(1)。

**重新散列（rehash）的代价常被低估**：不仅是 O(n) 次插入，还要对每个键重算哈希——如果键是长字符串、哈希函数是 SipHash，这是一笔可观的 CPU 开销。所以已知规模时应当**预留容量**（Python 没有直接的 `reserve`，但可以用 `dict.fromkeys(keys)` 一次性构造；C++ 用 `reserve()`，Rust 用 `HashMap::with_capacity`）。

> [!TIP]
> 判断要不要预留容量：估算最终元素数 n，看 n 与默认初始容量的比值。默认 8 桶的表插到 10 万条，会经历 14 次扩容、总量约 2n 次重新插入。在热路径上（比如每次请求都构造一次映射）这个开销完全可以用一次 `with_capacity` 省掉。

## 6. 三种真实实现的内幕

标准库的实现细节决定了你在实践中感知到的行为差异——尤其是「顺序」。

### 6.1 Python dict：紧凑布局与插入序

CPython 3.6 起，dict 用**两个数组**替代了原来的稀疏哈希表：

```text
dk_indices: [ -, 2, -, 0, -, -, 1, - ]   ← 稀疏的索引表（1 字节/项起）
dk_entries: [ (h0,k0,v0), (h1,k1,v1), (h2,k2,v2) ]  ← 紧凑的条目数组
```

- `dk_indices` 是哈希桶，存的是「条目数组的下标」而不是指针（小字典里 1 字节，省内存）。
- `dk_entries` 按**插入顺序**紧凑排列，所以要遍历时顺序扫描这个数组即可——**这就是 Python 3.7 起 dict 保证插入序的底层原因**（它是紧凑布局的副产品，后来被写进语言规范）。
- 删除时 `dk_indices` 里写入 `DKIX_DUMMY`（墓碑），条目数组保持紧凑；扩容重建时压缩掉空洞。
- 相比旧的稀疏表，内存省了 20%\~25%，遍历更快（连续内存、无空洞）。
- 容量也是 2 的幂，增长策略是 `used * 3 ≥ 容量 * 2` 时扩容（即 α > 2/3）。

### 6.2 C++ `unordered_map`：链地址 + 节点分配

- 桶数组 + 每个元素独立节点（链地址法），默认 `max_load_factor()` = 1.0。
- **迭代器在 rehash 时全部失效**，但**指向元素的指针/引用不失效**（节点不搬家）——这与 `vector` 的行为正好相反，是面试和代码评审里的高频考点。
- 每个元素一次堆分配，遍历是随机访存，所以在「元素少、访问频繁」的场景往往输给排序数组或 `flat_map`。许多项目用开放寻址的第三方实现（absl::flat\_hash\_map、boost::unordered\_flat\_map）替换它，常见有 2\~3 倍吞吐差距。
- `std::map`（红黑树）与它的选择标准不是「快慢」而是「要不要有序」：需要按序遍历、前驱后继、范围查询（`lower_bound`）时用 `map`/`set`，否则用哈希版本。

### 6.3 Rust `HashMap`：SwissTable 与 SIMD

Rust 标准库的 `HashMap` 基于 hashbrown（Google SwissTable 的移植）：

- **开放寻址 + 二次探测**，但探测是**按 16 个槽为一组**做的：每个槽有一个控制字节（存哈希的高 7 位），用 SIMD 一条指令并行比较 16 个控制字节，一次就能筛出候选槽，把「平均探测 2\~3 次」压缩成「1 次 SIMD 比较 + 极少数精确比较」。
- 阈值 87.5%（7/8），靠 SIMD 的高速探测撑住高负载。
- 默认哈希是 **SipHash-1-3，每个 HashMap 实例一份随机种子**（`RandomState`）——这是防哈希碰撞攻击的默认姿势。SipHash 比 FNV 慢 2~3 倍，对性能敏感且输入可信的场景（如内部整数键）可以换成 `FxHashMap`、`ahash` 等更快但无抗攻击性的实现。
- 继承自 Rust 的安全设计：`HashMap<K, V>` 要求 `K: Hash + Eq`，且哈希契约由 trait 保证，不容易写错。

三种实现的横向对照：

| <br /> | Python dict             | C++ unordered\_map        | Rust HashMap                  |
| ------ | ----------------------- | ------------------------- | ----------------------------- |
| 冲突处理   | 开放寻址（线性探测的变体 + 扰动）      | 链地址                       | 开放寻址（SwissTable，16 槽 SIMD 探测） |
| 负载因子阈值 | 2/3                     | 1.0（可调）                   | 7/8                           |
| 保序     | 保证插入序                   | 无序（rehash 后顺序会变）          | 无序                            |
| 默认抗攻击  | 是（字符串哈希随机盐，2.3+ / 3.3+） | 否（`std::hash` 可预测）        | 是（SipHash + 随机种子）             |
| 最坏情况   | O(n)                    | O(n)（可树化兜底的是 Java 不是 C++） | O(n)                          |

## 7. 安全：哈希碰撞攻击（HashDoS）

如果哈希函数是公开且确定的，攻击者可以离线造出成千上万个**全部散列到同一个桶**的键（比如 HTTP 表单的字段名）。服务器把它们逐个插入哈希表，每次插入都退化成遍历整条链，于是 n 个键的插入变成 O(n²)。2011 年这个手法一次性打穿了 PHP、Java、Python、Ruby、ASP.NET 等主流运行时：**几万个精心构造的参数，就能让一个 8 核服务器 CPU 打满**。

对策有三层：

1. **随机盐**：哈希表启动时随机生成种子，混入哈希计算。攻击者无法离线构造碰撞。Python 3.3+ 对 str/bytes 默认启用（`PYTHONHASHSEED` 控制），Rust 每个 `HashMap` 一份种子，Java/HashMap 至今没有（需要应用自己加）。
2. **强哈希**：用密码学强度的哈希（SipHash、xxHash 带种子）替代 `h = h*31 + c` 这类线性结构——线性哈希有代数结构，容易被解出碰撞。
3. **树化/限流兜底**：Java 的树化把最坏从 O(n) 降到 O(log n)；限流（单个请求的参数个数上限）则从入口挡住攻击。

> [!CAUTION]
> 启用了随机盐的一个副作用：**Python 的 `hash()` 结果不能跨进程使用**。把 `hash(s)` 写进数据库、缓存键、分片规则里，下次启动就全对不上了。需要稳定哈希时用 `hashlib.sha256(s.encode()).digest()` 或 `zlib.crc32`，不要用内置 `hash()`。此外，跨进程/跨语言一致性要求用显式的算法（MD5、SHA-1、MurmurHash），它们在所有平台上结果一致。

## 8. 键的契约

哈希表对键的要求可以浓缩成一句话：**相等的键必须有相等的哈希，且键在表内的生命周期里不能变**。

```python
# Python 的两条契约
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, other):                 # 相等：坐标相同
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)

    def __hash__(self):                      # 必须同时实现，且只依赖参与 __eq__ 的字段
        return hash((self.x, self.y))

p, q = Point(1, 2), Point(1, 2)
assert p == q and hash(p) == hash(q)
assert {p: "a"}[q] == "a"                    # 靠哈希找到槽，靠 == 确认是同一个键
```

四条实战规则：

- **只重写 `__eq__` 不重写 `__hash__`，会让对象变得不可用**：Python 会把 `__hash__` 置为 `None`（不可哈希），这是刻意的保护。
- **可变对象当键是灾难**：修改字段会改变哈希值，导致原来的槽位再也找不到，表现为「明明在字典里却查不到」和「同一个键出现两份」。
- **`__hash__` 里用到的字段，`__eq__` 里也必须用到**（反之可以宽松些）。否则相等的对象哈希不同，字典会分裂。
- **别用浮点数和 NaN 当键**：`0.0 == -0.0` 且哈希相同（会互相覆盖）；`nan != nan` 且 `hash(nan)` 的行为在 Python 版本间变过（3.10 起按对象身份计算），语义含混。需要精度容忍的话，把数值先规范化（`round`）或转成十进制字符串。

> [!NOTE]
> 「哈希值相同」不等于「相等」：哈希只是把候选集缩小到一个桶，最终判断必须靠相等比较。所以 `__hash__` 可以粗糙（只要保证相等者哈希相等），但 `__eq__` 必须准确。反过来，如果 `__hash__` 总是返回 0，正确性没问题，但所有键挤在一个桶里——哈希表退化成链表。

## 9. 应用模式：哈希表的六种用法

哈希表在实际代码里的用法几乎都能归到这六类：

| 模式     | 做法           | 复杂度变化                  | 例子               |
| ------ | ------------ | ---------------------- | ---------------- |
| 去重/存在性 | `set` / `in` | O(n²) → O(n)           | 数组去重、URL 去重、日志去噪 |
| 计数     | 键 → 次数       | O(n²) → O(n)           | 词频、异常检测、投票       |
| 分组     | 键 → 列表       | 排序分组 O(n log n) → O(n) | 按用户分组事件、字母异位词    |
| 配对查找   | 边遍历边查「搭档」    | O(n²) → O(n)           | 两数之和、互补商品、补集查询   |
| 映射/索引  | 键 → 对象       | 线性查找 → O(1)            | 数据库主键缓存、路由表、符号表  |
| 记忆化    | 参数 → 结果      | 指数 → 多项式               | 递归 DP、斐波那契、编辑距离  |

数据库里的**哈希连接（hash join）**是第 4 类在系统层面的放大版：把较小的表建成哈希表（构建阶段），再扫描大表逐行探测（探测阶段），把 O(n·m) 的嵌套循环连接变成 O(n + m)。而当连接条件需要范围（`a.id BETWEEN b.lo AND b.hi`）或需要有序输出时，数据库会改用排序归并连接——**这正好是哈希表的能力边界：只擅长「等值」，不擅长「范围与顺序」**。

## 10. 什么时候不该用哈希表

1. **需要顺序或范围查询**：最大值/最小值、前驱/后继、「大于 x 的最小键」、按序遍历、TopK。哈希表无序，这些操作要么 O(n) 全扫，要么得额外维护结构。有序结构（平衡树、跳表、B 树）才是这些操作的主场，见 [第 08 篇](08-bst-balanced-trees.md)。
2. **需要最坏情况下有保证**：实时系统、硬性延迟上限、航天/医疗等场景，O(n) 的最坏情况不可接受。（替代：平衡树的最坏 O(log n)）
3. **对抗性输入且无法加盐**：哈希函数固定且输入由外部控制时，性能可能被人为搞崩。
4. **n 很小**：n < 10 时，数组线性扫描往往更快——没有哈希计算、没有间接访存、代码还简单。哈希表的价值随 n 增长才体现。
5. **键很大且哈希昂贵**：每次查找都要读完整键算哈希，O(L) 的常数会很痛。可以考虑 Trie（共享前缀）或先哈希一次再当键（注意碰撞风险）。
6. **内存极度受限**：每个桶都有空槽开销（开放寻址按容量算，链地址按节点指针算）。布隆过滤器这类概率结构能用更少内存换「可能存在」的答案（[第 16 篇](16-advanced-structures.md)）。

## 11. 陷阱清单

- **遍历时修改**：Python 会直接抛 `RuntimeError: dictionary changed size during iteration`；C++/Java 里则可能是未定义行为或 `ConcurrentModificationException`。要改就先收集键再改，或用「构造新字典」的写法。
- **`dict.get(k, [])` 做默认值累积**：`d.get(k, []).append(x)` 只对**已存在**的键有效——默认值那个空列表每次都是新的，append 完就丢了。正确写法是 `d.setdefault(k, []).append(x)` 或 `defaultdict(list)`。
- **`defaultdict` 的隐性副作用**：`d[k]` 会**插入**一个默认值，「只读查询」也会改变字典大小，在遍历中触发 RuntimeError。
- **浮点键的精度**：`0.1 + 0.2 != 0.3`，用计算得到的浮点数当键会出现「看起来一样却查不到」。
- **`hash(-1) == hash(-2) == -2`**（Python 里 −1 被映射为 −2，因为 −1 是 CPython 的错误标记）。这是个有趣但真实存在的坑。
- **把元组当键时，元组里的元素必须都可哈希**；`(1, [2])` 会抛 `TypeError: unhashable type`。
- **字典不保证内存及时归还**：删除大量元素后容量不缩（Python 的 dict 只在扩容时重建）。长期存活的大字典删空后仍占着内存，需要显式重建。
- **C++ 的迭代器失效规则与 `vector` 相反**：`unordered_map` rehash 只失效迭代器，不失效指针/引用；`map` 则连删除都只失效被删元素的迭代器。混淆这两条是常见 bug 来源。

## 12. 小结

- 哈希表用「一次计算」替代「一轮搜索」，代价是把最坏情况交给运气：平均 O(1)、最坏 O(n)。所有设计都在缩小最坏情况的发生概率和后果。
- 冲突不可避免（鸽巢原理），两派解法各有性格：链地址法容忍高负载、实现简单、抗噪，但内存散、缓存差；开放寻址法紧凑、缓存友好，但必须把负载因子压在 0.75 以下且删除需要墓碑。
- 期望探测次数的公式说明了阈值从哪来：线性探测的失败查找按 (1−α)⁻² 增长，α = 0.9 时已是 50 次，α = 0.99 时 5000 次。
- 扩容的生命周期与动态数组同构：翻倍 + 重新散列 ⇒ 摊还 O(1)。已知规模时预留容量可以省掉全部扩容开销（以及重新哈希的 CPU）。
- 哈希函数的关键性质是均匀与抗构造，而不是「快」；2 的幂容量必须把高位混入低位（扰动），安全场景必须随机盐。
- 三种主流实现的选择差异：Python dict 紧凑布局顺带白送了插入序，C++ `unordered_map` 是链地址 + 节点分配（rehash 失效迭代器但不失效指针），Rust 用 SwissTable 的 SIMD 探测把高负载变得可行。
- 键的契约是「相等者同哈希、生命周期内不变」；可变键、浮点键、NaN 键都是真实事故来源。
- 哈希表擅长等值查找的六类模式（去重、计数、分组、配对、索引、记忆化），不擅长顺序与范围——那是有序结构的地盘。

## 13. 练习

**1.** 为什么除法散列建议把桶数 m 取质数，而 2 的幂容量的实现必须加扰动？分别举一个输入规律导致分布劣化的例子。

> [!TIP]
> 思路取 m = 2 的幂时，`k mod m` 只由键的**低位**决定：若键都是 4 的倍数（对齐的整数 ID），低两位恒为 0，只有 1/4 的桶会被用到。取质数时，键的各个位通过模运算混合，规律性输入不会形成简单的周期。而 2 的幂方案想同时拿到「位运算快」和「分布均匀」，就必须用 `h ^ (h >>> 16)` 之类的扰动把高位折进低位。

**2.** 开放寻址的哈希表删除元素时，为什么不能直接置空？构造一个具体例子说明后果。

> [!TIP]
> 思路假设容量 7，键 A 哈希到 3，但 3 被人占着，于是线性探测插到 4；键 B 插在 3。若删除 B 后把 3 置空，查找 A 时从 3 出发，发现空位就直接返回「不存在」——A 明明还在表里。墓碑的作用是标记「这里曾经有东西，探测要继续」，同时让插入能复用该位置。

**3.** 用负载因子表格说明：为什么 Java HashMap 的默认阈值是 0.75，而 Python dict 用 2/3、Rust 用 7/8？它们各自的选择和冲突处理方式有什么关系？

> [!TIP]
> 思路链地址法对 α 不敏感（α = 1 时成功查找也只要 1.5 次），所以 Java 可以把阈值定在 0.75 换取更少扩容；Python 用线性探测，失败查找对 α 极度敏感（α = 0.9 → 50 次），必须更保守（2/3）；Rust 靠 16 槽 SIMD 并行探测把探测成本压低，因而敢用 7/8 换取内存效率。结论：阈值不是拍出来的，是「探测成本曲线 × 内存开销」的平衡点。

**4.** 实现一个「按插入序遍历」的哈希表思路：为什么 Python 的 dict 能免费获得这个特性，而 C++ 的 `unordered_map` 不能？

> [!TIP]
> 思路Python 的紧凑布局把条目按插入顺序紧凑排列在 `dk_entries` 里，桶数组只存下标，遍历条目数组天然就是插入序（删除会在桶里留下 DKIX\_DUMMY，但条目数组仍保持相对顺序，重建时压缩）。C++ 的链地址法里元素位置由桶下标和链内位置决定，rehash 还会重排，所以顺序既无序也无保证；要保序得用独立的链表或向量记录顺序。

**5.** 下面的代码想统计词频，但结果不对，找出问题并修正。

```python
from collections import defaultdict

counts = defaultdict(int)
words = ["a", "b", "a"]
for w in words:
    counts[w] = counts[w] + 1
print(dict(counts))

# 版本二：试图用 get 累积，但会丢数据
groups = {}
for w in words:
    groups.get(w, []).append(w)      # 有问题
print(groups)
```

> [!TIP]
> 思路第一段其实是对的（`defaultdict(int)` 的 `counts[w]` 会返回 0 并插入）。第二段才是 bug：`dict.get(k, [])` 在键不存在时返回一个**临时**空列表，append 后再没有任何引用，写入丢失。修正：`groups.setdefault(w, []).append(w)`，或改用 `defaultdict(list)` 写 `groups[w].append(w)`。另外要注意 `defaultdict` 的坑：`counts[w]` 这种只读访问也会插入键。

**6.** 用 10⁶ 个短字符串构建哈希表，估算预留容量与不预留容量的时间差距来自哪几部分。

> [!TIP]
> 思路三部分：①扩容时的数组分配与拷贝（约 2n 次槽位写入）；②重新散列时对每个键重算哈希（SipHash 量级，10⁶ 次）；③扩容期间的分配器压力与缓存失效。前两项的常数在 Python/Rust 里都不小，预留容量能把它们一次省掉。这也解释了为什么写性能敏感代码时「一次分配够」比「让它自己长」快得多。

**7.** 设计一个「带过期时间的内存缓存」，用哈希表作为底层，需要考虑哪些问题？（提示：哈希表本身不管时间。）

> [!TIP]
> 思路三件事：①过期策略——惰性删除（读时判断过期）+ 定期清理（扫一部分键）是 Redis 的做法；②容量上限与淘汰策略（LRU/LFU，需要哈希表 + 双向链表/计数结构配合，见 [第 16 篇](16-advanced-structures.md)）；③并发访问——多线程/多协程下的锁粒度（分片锁：把键按哈希分成 N 个桶，每个桶独立的锁，把锁竞争降到 1/N）。这三个都是「哈希表之外」的设计，恰恰是工程实现的真正难点。

**8.** 假设你要给一个「用户 ID（32 位整数）→ 用户信息」的映射选结构，数据量 10⁴，需要支持「查询某个 ID」和「按 ID 升序输出全部用户」。分别给出两种方案并比较。

> [!TIP]
> 思路①哈希表 + 输出时排序：查询 O(1)、插入 O(1)，输出 O(n log n)（一次性）。②有序结构（BTreeMap/红黑树/有序数组）：查询 O(log n)，输出 O(n) 直接顺序遍历。选择取决于「查询与有序输出的比例」：查询远多于有序输出时选方案 ①（也更省内存），需要频繁范围查询或多路遍历时选 ②。若两者都要极致，可以用哈希表 + 有序索引的双结构（代价是两倍内存与写入时的一致性维护）。
