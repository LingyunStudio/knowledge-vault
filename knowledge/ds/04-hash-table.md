哈希表是工程中用得最多的数据结构，没有之一：平均 O(1) 的插入、删除、查找。它把"按键找值"从 O(n) 的遍历、O(log n) 的搜索树，直接砍到常数——原理是把键喂给一个哈希函数，算出数组下标直达。

## 三件套：函数、桶、冲突

1. **哈希函数** `h(key) → 0..m-1`：把任意键映射到桶下标。要均匀、要快、确定性（同键必同值）。
2. **桶数组**：下标即位置，理想情况下每个键落进自己的桶。
3. **冲突处理**：键空间无限、桶数有限，两个键落进同一个桶不可避免——这是哈希表所有设计的核心矛盾。

两种主流的冲突处理方案，取舍正好相反：

| <br /> | 链地址法                 | 开放寻址法                     |
| ------ | -------------------- | ------------------------- |
| 做法     | 桶里挂链表（或红黑树）          | 冲突了就探测下一个空位（线性/二次探测）      |
| 负载因子   | 可 > 1，性能随其缓慢劣化       | 必须 < 1（满则无处可放），通常 0.7 就扩容 |
| 缓存     | 差（跳节点）               | 好（顺着连续数组探测）               |
| 删除     | 简单                   | 需要墓碑标记，否则探测链断裂            |
| 代表     | Java HashMap（树化阈值 8） | Python dict、Redis 字典      |

## 负载因子与扩容

负载因子 α = 元素数 / 桶数。链地址法下 α 就是平均链长——查找代价约 1 + α；开放寻址下 α 越大探测链越长，性能悬崖式下跌。

所以哈希表必须**扩容再哈希**：桶数翻倍（选 2 的幂，可用位运算代替取模），所有元素重新计算新下标。摊还分析与动态数组同款——单次操作仍是 O(1) 摊还。

```python
d = {}
d["rust"] = 1          # 插入，摊还 O(1)
_ = d["rust"]          # 查找 O(1) 平均
d.pop("rust")          # 删除 O(1) 平均
# 预知规模时用容量提示，避免中途扩容（Python 可用 dict.fromkeys 预热，C++ 用 reserve）
```

> [!TIP]
> 什么时候哈希会退化成 O(n)？①哈希函数把键挤在少数桶里；②恶意构造的碰撞输入（哈希碰撞 DoS，所以主流实现给键加了随机盐）；③开放寻址在高负载下探测链失控。key 是可控字符串时，选个分布好的哈希（如 SipHash、xxHash）不是玄学，是安全。

## 键的要求：可哈希

- 键必须**不可变且稳定**：哈希值在生命周期内不能变。Python 里 tuple 能当 key、list 不能；自定义对象默认按 id 哈希，重写 `__eq__` 就必须同步重写 `__hash__`
- 等值即同键：`a == b` 必须推出 `h(a) == h(b)`，反过来不要求（哈希相同≠相等，那是冲突）
- 浮点数当键要小心精度；集合键用规范化形式（如路径先 resolve 再哈希）

## 典型应用模式

1. **去重与存在性判断**：`if x in seen`——O(1) 替代列表的 O(n) 扫描
2. **计数**：词频、字母异位词分组，`Counter` 一行
3. **两数之和式配对**：遍历时查"我需要的搭档是否已出现过"，把 O(n²) 变 O(n)
4. **索引加速**：哈希表 + 其他结构的组合拳——LRU = 哈希表 + 双向链表；字符串查找 = 哈希 + 链地址

> [!NOTE]
> 需要顺序、范围查询（"大于 x 的最小键"）时别用哈希表——它天生无序。那是有序结构的地盘：二叉搜索树、跳表、B+ 树（见第 05 篇）。
