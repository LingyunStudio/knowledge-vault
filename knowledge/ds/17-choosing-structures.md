认识十六种结构不等于会选结构。真实需求从来不会自带标签说「我需要一棵红黑树」，它只交给你一堆操作、规模和约束——选型的任务是从这些画像反推出结构，再用结构组合补齐单一结构的短板。这一篇把前十六篇收束成三件趁手的工具：一条决策树、一张场景速查表、一组可跑的组合结构实现；然后讨论复杂度表格不覆盖的那部分——缓存、分配、内存、并发与序列化，以及性能工作该按什么顺序做。

## 1. 选型方法论：操作画像四问

拿到一个需求，先别想结构名，先回答四个问题。四问的顺序有讲究：前两问淘汰掉大半候选，后两问在剩下的里面挑。

### 1.1 第一问：主导操作是什么，各占多少

把可能的操作列出来，估一下每种操作的频率。占比不同，答案完全不同：同样是「键 → 值」的映射，90% 查询加 10% 写入适合哈希表，而「建好之后几乎只读」就该考虑排序数组——省掉所有动态维护的开销。

| 操作画像        | 指向的结构         | 原因                                                    |
| ----------- | ------------- | ----------------------------------------------------- |
| 查找、存在性占绝对主导 | 哈希集合 / 哈希映射   | 平均 O(1)，写一次读万次最划算（[第 06 篇](06-hash-table.md)）         |
| 更新与查询交错出现   | 平衡树、堆等动态结构    | 每次更新增量维护，查询永远便宜                                       |
| 建好之后只读      | 排序数组 + 二分、前缀和 | 只付一次预处理，查询快且缓存友好（[第 02 篇](02-array-dynamic-array.md)） |
| 以遍历为主       | 数组            | 连续内存的顺序扫描是所有结构里最快的                                    |

一个实用技巧：不要笼统地说「查询多」，给出量级——「每秒 10⁴ 次 get、10² 次 put、每小时一次全量遍历」。量级直接决定了哪个操作的复杂度是分子、哪个只是分母。

### 1.2 第二问：要不要顺序——要哪种强度的顺序

「有序」不是开关，是分档的旋钮。需求越弱，可选的结构越多、越便宜：

```text
存在性（在不在）          → 哈希集合          最便宜：O(1)，但完全无序
极值（最大 / 最小 / 前 K 个）→ 堆              中间：只保证堆顶，O(log n)
排名 / 第 k 小 / 前驱后继   → 有序结构          中间：全序，O(log n) 但维护更贵
任意范围 [lo, hi] 查询     → 平衡树 / B 树     最贵：全序 + 范围分裂
```

原则是**用能覆盖需求的最弱保证**。只要反复取最值，就不该付平衡树的全序维护税（旋转、颜色修复都要钱）；反过来需要「大于 x 的最小键」时，堆帮不了你，它只认识堆顶。第 4.3 节的对顶堆就是这个原则的标本：把中位数的「全序需求」降级成两个「最值需求」。

### 1.3 第三问：规模多大，数据怎么到达

同一份操作画像，规模和到达方式不同，答案也不同。

- **一次性全量 vs 流式**：数据能一次拿全，才有「先排序再二分」「预处理前缀和」这类静态路线；数据一条条到达、不能回头，就只剩增量结构（堆、在线哈希、在线统计）。
- **n 的大小**：n ≤ 50 时，数组线性扫描几乎总是赢——没有哈希计算、没有间接访存、代码还最简单（[第 01 篇](01-complexity-analysis.md) 的警告）。复杂度是趋势语言，n 小的时候趋势还没发生。
- **内存装得下吗**：条数 × 每条字节数，先算账再动手。第 5.3 节给出 Python 与 C 的对比数字，演练三演示「装不下」时的正规动作。
- **访问分布**：10% 的热键承担 90% 的访问时，任何结构都行——最坏情况极少发生；反倒是「访问均匀、每条都是冷数据」的结构选型才值得斤斤计较。

### 1.4 第四问：键长什么样

- **可哈希吗**：列表、字典当不了键；可变对象当键违反「键在表内不可变」的契约（[第 06 篇](06-hash-table.md) 第 8 节），表现为「明明在字典里却查不到」。
- **稠密小整数吗**：键是 0 到 n−1 的整数时，直接拿数组下标当键，连哈希都省了。
- **有前缀语义吗**：自动补全、最长前缀匹配、按前缀批量统计——这类需求是 Trie 的主场（[第 10 篇](10-trie.md)）。
- **是区间或集合关系吗**：「这些点谁被哪些区间覆盖」指向线段树，「谁和谁是一伙的」指向并查集（[第 11 篇](11-union-find.md)、[第 16 篇](16-advanced-structures.md)）。
- **键很大吗**：每次查找都要付 O(L) 的哈希与比较（L 是键长）。键是长字符串时，可以先算一次 128 位指纹当键——但要做碰撞概率的账（演练三算过一遍）。

### 1.5 决策树：把四问变成一条路径

```text
【Q1】需要什么意义的「顺序」？
 ├─ 键值序：范围查询、前驱后继、第 k 名、按序遍历、排名
 │   ├─ 数据静态（建好后不再增删）→ 排序数组 + 二分            （02、14）
 │   └─ 数据动态（增删频繁）→ 平衡树 / 跳表 / B 树             （08）
 ├─ 位置序：先来后到、撤销回溯、按位置增删
 │   ├─ 后进先出（撤销、括号、DFS 回溯）→ 栈                  （04）
 │   ├─ 先进先出（排队、BFS、公平调度）→ 队列                 （05）
 │   └─ 两端进出 → 双端队列                                   （05）
 └─ 都不要 → 【Q2】
【Q2】只要反复取「当前最值」或前 K 个吗？
 ├─ 是 → 流式或反复增删 → 堆；静态数据一次性 → 快速选择        （09、14）
 └─ 否 → 【Q3】
【Q3】主要操作是「按键等值查」吗（存在性、键值映射、计数）？
 ├─ 是 →
 │   ├─ 键是稠密小整数 → 直接用数组下标当键                   （02）
 │   ├─ 键带前缀语义（补全、最长前缀、前缀统计）→ Trie        （10）
 │   └─ 一般可哈希键 → 哈希映射 / 哈希集合                    （06）
 └─ 否 → 【Q4】
【Q4】问题的本质是「关系」而非「键」吗？
 ├─ 谁与谁同组（动态连通）→ 并查集                            （11）
 ├─ 谁依赖谁（调度顺序、判环）→ 图 + 拓扑排序                 （12）
 └─ 谁离谁近（距离与路径）→ BFS（无权）/ Dijkstra（非负权）   （12、13）
```

注意这棵树的出口大多数是「哈希」「数组」「堆」「栈」「队列」这几个朴素答案——真实系统里绝大多数容器就该是它们。决策树更大的价值在于**排除**：从头走一遍，确认你手里那个复杂结构（平衡树、线段树、并查集）确实非用不可。

> [!NOTE]
> 操作画像会漂移：一个接口从读多写少变成写多读少，当初的最优结构就不再最优。重新检查选型的最佳时机是画像刚变的时候，不是性能已经崩了的时候——结构迁移在还有测试保护时是半天的工作，在线上事故之后是两周的整改。

### 3.1 三条忠告

**第一，不要背表，背「操作画像 → 结构家族」。** 容器名随语言、随版本变（Java 早年用 `Vector` 后来是 `ArrayList`），但「需要 O(1) 定位的动态集合 → 哈希家族」「需要键值序 → 平衡树家族」这类映射十年不变。背表的人换个语言就要重学，背映射的人五分钟就能查到对应的名字。

**第二，关键路径要实测。** 同名结构在不同语言里的常数差 2 到 10 倍：`heapq` 每个操作都要穿过解释器边界，C++ `priority_queue` 的比较函数可以内联；Python 的常数在第 01 篇已经反复强调。正确姿势是在目标数据分布、目标机器上用 `timeit` 或基准框架量，别把另一台机器、另一门语言的实测当结论。

**第三，接口长得像，复杂度契约可以完全不同。** 三个真实的坑：

- C++ `map::operator[]` 对不存在的键会**插入**一个默认值——「只读查询」悄悄改变 `size()`，还可能触发重平衡。纯查询必须用 `find()` 或 `at()`。
- C++ `set::erase(key)` 返回的是**删除元素的个数**（0 或 1），而 `erase(iterator)` 返回下一个迭代器——重载之间语义两回事，签名记混就写出「以为删了其实没删」的代码。
- Python `dict.setdefault(k, default)` 的 `default` 是普通实参、**调用时求值**：`d.setdefault(k, [])` 即使键已存在，也先新建一个空列表再丢弃。高频路径上这是白白的分配；要延迟构造用 `defaultdict`，或先判 `in`。

还有一个方向性的：同样是「堆」，Python `heapq` 默认最小、C++ 和 Rust 默认最大。把一个语言的 TopK 模板原样抄到另一个语言，比较器方向就反了——这种「默认值差异」不会报错，只会悄悄给你错的答案。

## 4. 组合结构：单一结构不够用的时候

单一结构都有短板：哈希表会定位但无序，链表可以 O(1) 拆装但难定位，数组定位快但中间增删要搬迁。组合的通用模式是：**链式或有序的结构管形状，哈希表管定位**——哈希表几乎是万能的「第二结构」，因为它把「按值找位置」从 O(n) 压到 O(1)。

组合结构的心脏是**不变式**：单结构的不变式由标准库替你守着，组合结构的不变式只能自己守。破坏它不会立刻报错，只会在某个未来时刻悄悄给出错误结果——所以下面每个组合都显式写出不变式，并在测试里断言它。

### 4.1 哈希表 + 双向链表 = LRU 缓存

需求：容量受限的缓存，`get` 命中并刷新为「最新」，`get` 未命中返回空，`put` 写入，满了淘汰「最旧」，两个操作都要 O(1)。

从操作反推结构：按 key 定位 → 哈希表 O(1)；「摘除任意节点、插到最新端、删最旧端」三个动作 → 双向链表 O(1)。两个设计问题必须想透：

- **为什么节点必须双向？** 删除任意节点要把它的前驱和后继接起来，单向链表找前驱需要 O(n)。（「复制后继的值再删后继」的技巧在这里失效：缓存节点被哈希表引用着，偷换值会破坏定位，而且对尾节点无效。）头尾都要动，所以配上首尾哨兵，把边界分支全部消掉（[第 03 篇](03-linked-list.md) 第 4 节）。
- **为什么哈希表存节点引用而不是值？** 「命中即移到最新」要求从 key 一步跳到链上那个节点。若哈希表存值，每次命中都要从头扫描链表找到它再搬运——O(n)，整个设计当场作废。一句话：**哈希表存「位置」，链表存「次序」**。

```python
class _Node:
    __slots__ = ("key", "value", "prev", "next")

    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev = self.next = None


class LRUCache:
    """哈希表 + 双向链表：get/put 平均 O(1)。

    不变式 I1：head 到 tail 的节点按「最近使用」从新到旧排列。
    不变式 I2：self.map 的每个键恰对应链表上一个节点，反之亦然。
    """

    def __init__(self, capacity):
        if capacity < 0:
            raise ValueError("capacity 不能为负")
        self.cap = capacity
        self.map = {}                                # key -> 节点引用（不是值）
        self.head, self.tail = _Node(), _Node()      # 哨兵：head 侧是最新
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node):                         # 摘除：只动 4 个指针
        node.prev.next, node.next.prev = node.next, node.prev

    def _push_front(self, node):                     # 头插：成为「最新」
        first = self.head.next
        node.prev, node.next = self.head, first
        self.head.next = first.prev = node

    def _touch(self, node):
        self._remove(node)
        self._push_front(node)

    def _evict_lru(self):
        lru = self.tail.prev                         # I1 保证它最旧
        self._remove(lru)
        del self.map[lru.key]                        # I2：链表删，哈希也删

    def get(self, key, default=None):
        node = self.map.get(key)
        if node is None:
            return default
        self._touch(node)                            # 命中即刷新为最新
        return node.value

    def put(self, key, value):
        if self.cap == 0:                            # 容量为 0：一律拒绝
            return
        node = self.map.get(key)
        if node is not None:                         # 已有键：改值 + 刷新，不淘汰
            node.value = value
            self._touch(node)
            return
        if len(self.map) >= self.cap:
            self._evict_lru()
        node = _Node(key, value)
        self.map[key] = node
        self._push_front(node)

    def __len__(self):
        return len(self.map)

    def _keys_new_to_old(self):
        out, p = [], self.head.next
        while p is not self.tail:
            out.append(p.key)
            p = p.next
        return out

    def _check_invariant(self):
        keys = self._keys_new_to_old()
        assert len(keys) == len(self.map) <= self.cap
        assert set(keys) == set(self.map)            # I2：一一对应
        p, n = self.head.next, 0                     # 双向链一致
        while p is not self.tail:
            assert p.prev.next is p and p.next.prev is p
            p, n = p.next, n + 1
        assert n == len(keys)


if __name__ == "__main__":
    # 基本路径：命中刷新、淘汰最旧
    c = LRUCache(2)
    assert len(c) == 0 and c.get("x") is None                 # 空：查不到
    c.put("a", 1); c.put("b", 2)
    assert c.get("a") == 1 and c._keys_new_to_old() == ["a", "b"]
    c.put("c", 3)                                             # 淘汰 b（最旧）
    assert c.get("b") is None and c.get("a") == 1
    c.put("a", 10)                                            # 已有键：改值不淘汰
    assert len(c) == 2 and c.get("a") == 10

    # 容量 1：第二次 put 必然淘汰
    c1 = LRUCache(1)
    c1.put(1, "v1"); c1.put(2, "v2")
    assert len(c1) == 1 and c1.get(2) == "v2" and c1.get(1) is None

    # 容量 0：拒绝一切写入
    c0 = LRUCache(0)
    c0.put(1, "v")
    assert len(c0) == 0 and c0.get(1) is None

    # 压力对照：与「时间戳 + min 淘汰」的朴素实现比
    import random
    ref, cache, now = {}, LRUCache(50), 0
    for _ in range(20000):
        op = random.random()
        k = random.randrange(100)
        if op < 0.2:                                          # get
            now += 1
            v1 = cache.get(k)
            if k in ref:
                v2 = ref[k][0]
                ref[k] = (ref[k][0], now)
            else:
                v2 = None
            assert v1 == v2
        else:                                                 # put
            now += 1
            cache.put(k, k * 2)
            ref[k] = (k * 2, now)
            if len(ref) > 50:
                oldest = min(ref, key=lambda x: ref[x][1])
                del ref[oldest]
        cache._check_invariant()
    print("LRU ok")
```

复杂度：`get` 平均 O(1)、最坏 O(n)（哈希冲突，[第 06 篇](06-hash-table.md)）；`put` 平均 O(1)；空间 O(capacity)。每一步操作都在维护那两条不变式——`_evict_lru` 里「链表删一个、哈希删一个」就是 I2 的全部成本。

> [!NOTE]
> Python 3.7+ 的 dict 自带插入序，可以只用 dict 写出 O(1) 的 LRU：命中时 `d.pop(k)` 再 `d[k] = v`，淘汰时取 `next(iter(d))`。这是 dict 紧凑布局白送的一条「隐形链表」（[第 06 篇](06-hash-table.md) 第 6.1 节）。但它依赖语言特性；双向链表版本在任何语言里都成立，也是面试与通用缓存库的形态。

> [!WARNING]
> 组合结构的经典 bug 是「只更新一半」：链表删了节点、哈希表忘了删（或反过来），之后 `get` 会返回一个已经从链上摘掉的孤儿节点。两条不变式必须写成测试里的断言（上面的 `_check_invariant`），而不是注释里的愿望。

### 4.2 哈希表 + 数组 = O(1) 随机删除的集合

需求：随机模拟、对象池、抽样——要同时支持 O(1) 增、O(1) 删任意元素、O(1) **等概率随机取一个**。内置 `set` 只有前两个：`random.choice` 不接受 set，转成列表要 O(n)。

推理：数组本来支持 O(1) 随机下标，但删中间要搬移。而哈希表知道每个元素的下标之后，「删中间」可以变成「把尾部元素搬到洞里再缩一格」——这就是 **swap-pop**（C++ 的 erase-swap 惯用法、Rust 的 `Vec::swap_remove` 是同一招）。

```python
import random


class SwapPopSet:
    """哈希表 + 数组：add / discard / contains / 随机取一个，平均 O(1)。

    不变式：对每个下标 i，pos[items[i]] == i，两个结构互相指认。
    代价：discard 用「尾部交换」补洞，遍历顺序被打乱且不稳定。
    """

    def __init__(self):
        self.items = []      # 元素本体，紧凑排列
        self.pos = {}        # 元素 -> 在 items 里的下标

    def add(self, x):
        if x in self.pos:
            return False
        self.pos[x] = len(self.items)
        self.items.append(x)
        return True

    def discard(self, x):
        i = self.pos.pop(x, None)
        if i is None:
            return False
        last = self.items.pop()              # 先摘尾
        if i < len(self.items):              # 删的不是尾：尾元素搬到洞里
            self.items[i] = last
            self.pos[last] = i
        return True

    def __contains__(self, x):
        return x in self.pos

    def __len__(self):
        return len(self.items)

    def random_member(self):
        """等概率随机取一个成员；空集合抛 IndexError。"""
        return random.choice(self.items)

    def _check_invariant(self):
        assert len(self.items) == len(self.pos)
        for i, x in enumerate(self.items):
            assert self.pos[x] == i


if __name__ == "__main__":
    s = SwapPopSet()
    assert len(s) == 0 and 1 not in s                         # 空
    assert s.discard(1) is False                              # 删不存在的元素
    assert s.add(1) is True and s.add(1) is False             # 重复 add
    assert len(s) == 1 and 1 in s                             # 单元素
    s.discard(1); assert len(s) == 0 and 1 not in s

    # 一万次随机操作与内置 set 对照
    ref, r = set(), SwapPopSet()
    for _ in range(10000):
        op, x = random.randrange(3), random.randrange(500)
        if op == 0:
            assert r.add(x) == (x not in ref)
            ref.add(x)
        elif op == 1:
            assert r.discard(x) == (x in ref)
            ref.discard(x)
        else:
            assert (x in r) == (x in ref)
        assert len(r) == len(ref)
    r._check_invariant()
    assert set(r.items) == ref                                # 内容一致
    members = [r.random_member() for _ in range(200)]
    assert all(m in ref for m in members)                     # 随机抽取不出界
    print("SwapPopSet ok")
```

复杂度：四个操作全部平均 O(1)；空间 O(n)。

这个结构的全部秘密是那条不变式：`discard` 搬动尾部元素时**必须同步更新它的 `pos`**，漏了这一行，下次 `discard` 那个被搬动的元素就会删错下标——症状是「删了 A 却把 B 删了」，而且只在 A 被删过之后才触发。

顺序被打乱是这个结构的**明码标价**：遍历 `items` 得到的既不是插入序也不是值序，且每次删除都会变。什么时候可以接受——语义里根本没有顺序的场景（随机模拟、池、存在性判断）；什么时候不可以——需要按插入序或值序遍历时，换 4.1 节的哈希 + 双向链表（那正是「保序版的 swap-pop」），或真有序结构。

### 4.3 对顶堆 = 流式中位数

大顶堆装较小的一半，小顶堆装较大的一半，两个堆顶把中位数夹在中间：`add` O(log n)、查询 O(1)，内存 O(n)。完整实现、两条不变量（值域不交叉、大小差不超过 1）与实测对比见 [第 09 篇](09-heap-priority-queue.md) 第 8.3 节——那里给出了它与「每来一个数就整体排序」的实测差距（2 万次插入：0.019 秒对 10 秒量级）。它是 1.2 节「用最弱的顺序保证」原则最好的实战标本：中位数看起来需要全序，实际只需要两个最值。

### 4.4 哈希表 + 环形缓冲 = 最近 N 条 / 滑动窗口

需求：判断「最近 N 条记录里见过 x 吗」（去重、限流、防重放），要求判断 O(1)、内存 O(N)。环形缓冲负责「谁最旧」（满了自动挤掉，[第 05 篇](05-queue-deque.md) 第 8 节），哈希表负责「在不在」——职责划分与 4.1 节完全同构：链式结构管次序，哈希表管定位。

```python
from collections import deque

seen = set()
recent = deque(maxlen=64)          # 环形缓冲：满了自动挤掉最旧

def seen_recently(x):
    """最近 maxlen 条里见过 x 吗？是则 True，否则记录并返回 False。"""
    if x in seen:
        return True
    if len(recent) == recent.maxlen:
        seen.discard(recent[0])    # 即将被挤掉的最旧元素，先从集合摘除
    recent.append(x)
    seen.add(x)
    return False

assert not seen_recently("a") and seen_recently("a")
for i in range(100):
    seen_recently(i)
assert "a" not in seen and len(seen) == 64      # a 早已被挤出窗口
assert not seen_recently("a")
```

`deque(maxlen=N)` 的自动淘汰是双刃剑：被挤掉的元素不会通知你，所以写入前要先读出 `recent[0]` 手动从 `seen` 摘除——否则集合只进不出，越积越大。这又是「两个结构只更新一半」的变体。若窗口还要求统计（最近 N 条的平均值、计数），在环形缓冲上直接维护滚动和即可，同样是 O(1) 更新。

### 4.5 哈希表 + 有序结构 = 带排名的双索引

需求：「按 ID 查分数」（等值）与「按分数查排名、取前 K」（有序）同时高频。哈希表答不了第二问，有序结构答第一问要 O(log n) 还要求键可比——那就让**两个索引各答一半**。

代价在写入端：一次逻辑更新要同时动两个结构（旧条目从有序索引摘出、新条目插回，哈希表同步改值），必须同生同死。这就是数据库「二级索引」的代价模型：每多一个索引，每次写入多一次 O(log n) 的维护和一份内存；读性能是买来的。

```python
from bisect import bisect_left, insort


class Leaderboard:
    """双索引：按 ID 查分（哈希）+ 按分数排名（有序数组）。

    不变式：board 恰好是 scores 全部条目的 (-分数, id) 升序排列。
    排名规则：分高在前；同分按 id 字典序在前。
    """

    def __init__(self):
        self.scores = {}     # user_id -> score
        self.board = []      # 升序的 (-score, user_id)，越靠前名次越高

    def update(self, user_id, delta):
        old = self.scores.get(user_id)
        if old is not None:                      # 旧条目先摘出有序索引
            self.board.pop(bisect_left(self.board, (-old, user_id)))
        new = old + delta if old is not None else delta
        self.scores[user_id] = new
        insort(self.board, (-new, user_id))      # 再插回新位置

    def score(self, user_id):
        return self.scores.get(user_id)

    def rank(self, user_id):
        """1 起始的名次；未上榜抛 KeyError。"""
        s = self.scores[user_id]
        return bisect_left(self.board, (-s, user_id)) + 1

    def top(self, k):
        return [uid for _, uid in self.board[:k]]

    def __len__(self):
        return len(self.scores)

    def _check_invariant(self):
        assert self.board == sorted(((-s, u) for u, s in self.scores.items()))


if __name__ == "__main__":
    lb = Leaderboard()
    assert lb.top(3) == [] and len(lb) == 0                   # 空
    lb.update("alice", 50)
    assert lb.rank("alice") == 1 and lb.top(5) == ["alice"]   # 单元素
    lb.update("alice", -20)
    assert lb.score("alice") == 30                            # 分数回退
    try:
        lb.rank("nobody")
        raise AssertionError("应当抛 KeyError")
    except KeyError:
        pass

    lb.update("bob", 30); lb.update("carol", 30); lb.update("dave", 90)
    assert lb.top(4) == ["dave", "alice", "bob", "carol"]     # 同分按 id 升序
    assert lb.rank("dave") == 1 and lb.rank("bob") == 3 and lb.rank("carol") == 4

    # 三千次随机更新后与暴力重算对照
    import random
    lb2 = Leaderboard()
    for _ in range(3000):
        lb2.update(random.randrange(60), random.randint(-5, 20))
        lb2._check_invariant()
    ref = sorted(((-s, u) for u, s in lb2.scores.items()))
    assert lb2.board == ref and lb2.top(10) == [u for _, u in ref[:10]]
    print("Leaderboard ok")
```

复杂度：按 ID 查分 O(1)；`rank` O(log n)；`top(k)` O(k)；`update` 是 O(log n) 的查找加 O(n) 的搬移（list 版本，memmove 是 C 级速度，n = 10⁵ 时实测单次约 30 微秒，够不够用看写入频率，演练一算这笔账）。把有序索引换成平衡树或跳表，`update` 变 O(log n)。Redis 的有序集合（zset）就是这个组合的工业级版本：哈希表 + 跳表（[第 08 篇](08-bst-balanced-trees.md) 第 7 节）。

两个必须定死的边界：**同分并列的次序**（这里用 id 字典序，不定义清楚 `rank` 就不稳定）和**分数回退**（`update` 的对偶情形——先摘旧再插新，顺序不能反，否则有序索引里会出现同一个 id 的两份）。

## 5. 复杂度之外：同一张表上决定胜负的东西

复杂度表说两个结构「都是 O(n)」时，实测可以差 10 倍；说 O(1) 时，差距可以更大。这一节列出会改写复杂度结论的六个因素，每个都给出具体后果。

### 5.1 缓存局部性

CPU 一次取一整条缓存行（64 字节），L1 命中约 1 纳秒，去主存约 100 纳秒——差两个数量级（[第 01 篇](01-complexity-analysis.md) 第 3 节）。数组的顺序访问一次缓存行喂 8\~16 个元素；链表的指针追逐让每个节点都变成一次独立的主存访问。后果：同样是 O(n) 的遍历，数组比链表快 10 倍以上；B+ 树把节点做成一整页（16 KB），本质就是「让每次昂贵的 I/O 带回一批键」（[第 08 篇](08-bst-balanced-trees.md) 第 8 节）。工程动作：能装进数组的形态（扁平哈希表、结构数组）优先，指针结构留给语义确实需要的场景。

### 5.2 分配次数与分配器压力

每次堆分配几十纳秒起步，多线程下分配器还有锁竞争；更隐蔽的是分配出来的节点散落在堆各处，反过来恶化 5.1 的缓存表现。后果：链地址哈希表插 10⁶ 个元素就是 10⁶ 次 malloc 加 10⁶ 次随机写（[第 06 篇](06-hash-table.md) 第 3 节的软肋）；高频请求路径上每次构造临时 dict/list，profile 里「分配」自己就是前几名。工程动作：已知规模就预留容量（C++ `reserve`、Rust `with_capacity`）；节点用对象池或 arena 复用；热路径上复用容器（`clear()` 后再用，而不是扔掉新建）。

### 5.3 内存占用

三种开销叠加：指针开销（链表每节点 8 字节起步）、空槽开销（负载因子 2/3 意味着 1/3 的槽是空的，[第 06 篇](06-hash-table.md) 第 5 节）、对象头开销（Python 每个对象 16\~28 字节起步）。同样存 10⁷ 条 int 到 int 的映射，差距是这样的：

```text
每条「键 → 值」条目的真实内存（10^7 条 int→int 的量级估算，随实现浮动）：
  C 开放寻址哈希表    ≈ 16 B/条    → 约 160 MB
  C++ unordered_map  ≈ 40 B/条    → 约 400 MB（每元素一个节点 + 桶数组）
  Java HashMap       ≈ 50~80 B/条 → 约 0.5~0.8 GB（Entry 对象头 + 引用 + 装箱）
  Python dict        ≈ 100 B/条   → 约 1 GB（条目 24 B×1.5 负载 + 两个 int 对象 56 B）

  （Python 的算法：紧凑条目 (哈希, 键, 值) 共 24 B，除以负载因子 2/3，
    再加两个 28 B 的 int 对象——「以对象为单位估算」，见第 01 篇第 5 节）
```

后果：同一份数据，C 扁平表 160 MB 装得下、Python dict 已经到 1 GB——「能不能装下」的账必须按对象算，不能按机器字算。

> [!WARNING]
> 估算内存时最常见的错误是用「元素逻辑大小」代替「容器真实开销」。一个 8 字节的键值对在 Python 里是 100 字节量级，差 12 倍。做容量规划时先在一个真实小样本上用 `sys.getsizeof` 加对象开销实测，再线性外推。

### 5.4 并发

单线程的复杂度表在并发下会重写。锁的谱系与各自的适用条件：

- **全局锁**：最简单，但吞吐不随核数增长——16 核机器上，锁竞争加缓存行弹跳，吞吐可能停在单核水平。
- **分片锁**：按哈希分 N 片、每片一把锁，竞争降为 1/N（Java 早期 `ConcurrentHashMap` 的分段思想）。代价：跨片操作（`size()`、全表遍历、迁移）需要聚合，变贵。
- **读写锁**：读多写少的缓存合适；写一频繁，读者就饥饿，反而不如全局锁。
- **无锁**：只有「单变量能表达的状态」现实可行——CAS 计数器、无锁栈。树和哈希表的无锁版本极难，实践中的替代是「不可变快照 + 原子替换」（copy-on-write），适合读极多、改动成批的场景。

后果示例：给 dict 套一把全局锁做成线程安全缓存，p99 延迟在 8 核下可能比单线程还差 5 倍——复杂度没变，是锁排队变了。

### 5.5 序列化与持久化

哈希表的遍历顺序不稳定：Python dict 保插入序，但删除重插就变；`set` 和多数语言的哈希表连这个都不保证；跨进程更没有意义（`PYTHONHASHSEED` 每次启动都不同，[第 06 篇](06-hash-table.md) 第 7 节）。后果：把「内存里的顺序」当持久化格式或同步依据的代码，进程一重启就全量误判为脏数据；拿 `set` 的顺序做对照测试，会随机挂。正确姿势：序列化前显式排序（`sorted(d.items())`）或直接用键值对数组；树、链表这类指针结构序列化时用「下标数组」替代指针，读回来按下标重建（[第 07 篇](07-binary-tree-traversal.md) 第 7 节）。

### 5.6 GC 压力

大量短命对象（每次请求构造临时容器、自动装箱）让 minor GC 高频触发，p99 出现规律性毛刺；老年代里的大哈希表每轮 major GC 都要扫一遍。后果：Java 里 `Map<Integer, Integer>` 的每次读写都在分配 Integer 对象，高 QPS 服务 GC 占掉 20% CPU 并不罕见。工程动作：复用容器、用原始类型特化容器（fastutil、Eclipse Collections）、对象池。Rust 没有 GC，但引用计数更新与 drop 链仍是真实的常数开销——天下没有免费的堆。

| ----------------- | ---------------- | ----------------------- | --------------------------------------------------------------- |
| 用 `list` 当队列      | 吞吐随积压线性恶化        | `pop(0)` 每次整体前移 O(n)    | `collections.deque.popleft()`，O(1)（[第 05 篇](05-queue-deque.md)） |
| 用哈希表做范围查询         | 「查大于 x 的最小键」全表扫  | 哈希只保等值，无序               | 平衡树、跳表、B 树（[第 08 篇](08-bst-balanced-trees.md)）                  |
| 用全排序解决 TopK       | 高频调用下 CPU 打满     | O(n log n) 的重复劳动        | 容量 K 的小顶堆，O(n log K)（[第 09 篇](09-heap-priority-queue.md)）       |
| 用嵌套字典模拟有序结构       | 代码三层缩进，复杂度说不清    | 拿「键的分段」硬凑顺序             | 键元组化压成一层，或换真有序容器                                                |
| 热路径上反复构造容器        | profile 里一半时间在分配 | 每次请求 new 一套 dict/list   | 预留容量、复用与池化（5.2 节）                                               |
| 为「未来可能的性能」提前上复杂结构 | 代码难懂，收益为零        | 画像还没出现就先优化              | 先朴素实现，画像明确后再换（第 7 节）                                            |
| 用链表替换数组求快         | 反而慢了 10 倍        | O(1) 插入前先付 O(n) 定位与指针追逐 | 数组搬移的 C 级常数通常更快（[第 03 篇](03-linked-list.md) 第 7 节）              |
| 忘了哈希键的可变性契约       | 「明明在字典里却查不到」     | 字段变更改变哈希值，槽位失联          | 用不可变键或冻结快照（[第 06 篇](06-hash-table.md) 第 8 节）                    |
| 把 `in list` 放进循环  | n = 10⁵ 时跑到分钟级   | 循环乘线性扫描 = O(n²)         | 换 `set` 或 `dict` 判存在（[第 01 篇](01-complexity-analysis.md) 第 7 节） |

这九条共享同一个根因：**对操作的量级判断错了**——把 O(n) 的操作当 O(1) 用，或者反过来。写代码时问一句「这个操作在什么结构上是 O(1)」，比背清单更有用。

## 7. 性能工作的正确顺序

优化最大的浪费不是选错结构，而是在瓶颈不在这里时拼命优化。正确顺序是一串固定动作：

```text
第 0 步  建立可复现基准：固定输入、固定环境，记录当前耗时与 p95/p99
第 1 步  测量：cProfile / py-spy（Python），perf record + 火焰图（C/C++/Rust）
第 2 步  定性瓶颈：输入翻倍，耗时 ×2 → 常数问题；×4 → O(n²)；
         ×2.2 左右 → O(n log n)——先分清量级问题与常数问题
第 3 步  量级问题 → 换算法 / 换数据结构（收益 10~1000 倍）
第 4 步  常数问题 → 缓存布局、预分配、批处理、减少分配（收益 1.5~10 倍）
第 5 步  还不够 → 并行 / 异步（受 Amdahl 定律封顶：串行占 10%，上限就是 10 倍）
```

测量工具怎么读：`cProfile` 里 `tottime` 是函数**自身**耗时（不含子调用），`cumtime` 是含调用链的总账——找「自己就是热点」的函数看前者，找「值得整个砍掉」的调用看后者。常驻线上服务用 py-spy，不改代码直接附身采样。C/C++/Rust 用 `perf record` 出火焰图：横向宽度就是耗时占比，最宽的那座塔就是你下一个工作对象。

```text
$ python -m cProfile -s tottime bench.py
         1200345 function calls in 1.842 seconds

   ncalls  tottime  percall  cumtime  filename:lineno(function)
   200000    0.913    0.000    1.203    bench.py:14(lookup)        ← 自身耗时第一
   200000    0.290    0.000    0.290    {built-in method sorted}   ← 循环里的 sorted
        1    0.121    0.121    1.842    bench.py:3(main)           ← cumtime 是总账
```

第 2 步的「翻倍实验」值得单独解释：给基准输入从 n 到 2n，看耗时怎么变。这是区分「算法问题」和「实现问题」最快的实验——量级问题去找新结构，常数问题才轮到缓存和分配。顺序反了，就是在用 5% 的常数收益掩盖 100 倍的量级损失。

> [!WARNING]
> 没有测量的优化是猜测。关于「瓶颈在哪」，程序员直觉猜错的次数远多于猜对的——profile 出来的第一名常常不是你怀疑的那个函数。先量，再改，改完再量（确认收益真的落在了基准上）。

把收益量级摆在一起看就明白顺序为什么不能乱：换对结构是量级收益（[第 09 篇](09-heap-priority-queue.md) 的实测：TopK 用堆 0.024 秒，全排序 0.561 秒，23 倍——这还只是 K = 100 的小案例）；抠常数是倍数收益（换个布局省一半，预留容量省 20%，已经是很好的战果）；并行是「把同一份工作摊给更多核」，它不降低复杂度，且被串行部分封顶。**先拿量级，再拿倍数，最后才摊核。**

## 8. 三个选型演练

### 8.1 演练一：十万用户的实时排行榜

**需求与约束**：10 万用户，分数更新频繁（峰值每秒 10⁴ 次）；查询前 100 名高频；查某个用户的排名中频；按 ID 查分数低频。单机内存几个 GB。

**走一遍四问**：主导操作是「增量更新 + 排名查询」——需要键值序，且数据动态增删，指向有序结构；键是「用户 ID」（可哈希）与「分数」（可比数值）的组合；n = 10⁵，内存无忧。

**排除错误答案**：每次查前 100 时排序？10⁵ 个元素排一次约 1.7×10⁶ 次比较，乘上每秒 10⁴ 次更新触发的失效——不可行。用堆？堆只认识堆顶，给不了「某人的排名」。缓存前 100 名快照？更新太频繁，缓存秒级失效。

**结论**：双索引（4.5 节）——哈希表 `id → score` 管按 ID 查分，有序索引按 `(-score, id)` 排列管前 K 与排名。Python 标准库用 `bisect` + list 实现：`rank` 与 `top` 是 O(log n) 与 O(k)，`update` 的搬移在 n = 10⁵ 时实测约 31 微秒一次——每秒 10⁴ 次更新只占 0.3 个核，完全可行。更新涨到 10⁶ QPS、或 n 上到 10⁷ 时，把有序索引换成跳表或平衡树（`update` 从 O(n) 降 O(log n)），或直接上 Redis 的 zset——它就是「哈希表 + 跳表」的产品化。**不用每次排序的理由**：排序是「为一次查询重排全量」，双索引是「把每次更新的增量摊进结构」，前者 O(n log n) 每查一次，后者维护成本只在写入时付一次 O(log n) 或小常数 O(n) 搬移。

### 8.2 演练二：日志系统统计「最近 5 分钟每个 IP 的请求数」并找 TOP 10

**需求与约束**：流量 10⁴ QPS，5 分钟窗口约 3×10⁶ 条请求，独立 IP 假设 10⁵ 量级；统计用于风控，精度要求高；单机内存几个 GB。

**推理**：每条请求要做三件事——该 IP 计数加一、把 5 分钟前的旧账过期、周期性产出 TOP 10。

- **精确计数**：哈希表 `ip → deque[时间戳]`。请求到达时 `append(now)`，顺手从队首 `popleft` 掉过期时间戳（队首永远最老，单调性保证正确——这正是队列语义，[第 05 篇](05-queue-deque.md)）；窗口计数就是 `len(deque)`。内存账：3×10⁶ 个时间戳 × 约 40 B（Python 的 int 对象 + 引用槽）≈ 120 MB，单机装得下；换成 C 或 Go 只要 24 MB 左右。
- **降内存**：把窗口切成 30 个 10 秒桶，`ip → 环形计数数组`——这是 4.4 节「哈希 + 环形缓冲」的直接应用，内存降到 10⁵ × 30 × 4 B = 12 MB，代价是时间粒度粗到 10 秒。
- **TOP 10 不要每条请求都维护**：每 5 秒重算一次——10⁵ 个 IP 排序约 1.7×10⁶ 次比较，Python 里几十毫秒，摊到 5 秒周期与 5 万条请求上可以忽略。流式堆只在「查询比数据更频繁」时才赢（[第 09 篇](09-heap-priority-queue.md) 第 6 节的选择标准）；真要流式，用容量 10 的小顶堆配惰性过期（同篇第 9 节）。

**精度与内存的取舍**：独立 IP 上到 10⁷\~10⁸（运营商级流量）时，精确计数的内存到 10 GB 级，装不下。这时引入 Count-Min Sketch（[第 16 篇](16-advanced-structures.md)）：固定几 MB 内存，点查询误差不超过 ε × 总请求数、置信 1 − δ，且只会高估不会低估。实战用法是两阶段：CMS 粗筛出可疑的高频 IP，再对候选白名单精确计数——**用近似结构缩小精确结构的规模**。

**结论**：10⁵ 级 IP：哈希表 + 时间窗口队列（或时间分桶）+ 周期重算 TOP 10；10⁷ 级以上：Count-Min Sketch 粗筛 + 精确复核。

### 8.3 演练三：10 亿条 URL 去重，单机内存 8 GB

**需求与约束**：10 亿条 URL 流式到达（平均 80 字节），输出去重后的集合；单机内存 8 GB，磁盘可用。

**先算精确去重的内存账**：

```text
10 亿条 URL，平均 80 字节，内存 8 GB：
  原样存字符串          ≈ 80 GB（10^9 × 80 B，光字符串本体就超 10 倍）
  C 哈希集合（存字符串） ≈ 100 GB 量级（字符串 + 节点指针 + 空槽开销）
  只存 64 位哈希指纹    10^9 × 8 B ÷ 负载 2/3 ≈ 12 GB        → 仍超 1.5 倍
  只存 32 位哈希指纹    ≈ 6 GB，能装下——但必错：
        生日问题：n 条数据、2^32 个哈希值，期望碰撞对数 ≈ n^2/2^33 ≈ 10^8
        （64 位指纹的碰撞概率约 2.7%，十亿分之一量级也不能接受时同样出局）
```

结论很硬：**在 8 GB 内存里做精确去重，数学上不成立**——即使把每条压缩到 8 字节指纹也装不下，压到 4 字节必撞。这不是换算法能解决的，是信息量对物理容量的约束。正确动作是把存储分层：

1. **布隆过滤器粗筛**（[第 16 篇](16-advanced-structures.md)）：1% 误报率下每元素约 9.6 bit，10⁹ × 9.6 bit ≈ 1.2 GB，装得下。关键性质是**无假阴性**——判「没见过」的一定真没见过，可以直接判新放行；判「见过」的可能是误报。它把需要落盘的流量从 10⁹ 条压到「真重复 + 约 1% 误报」。
2. **磁盘哈希分片精确去重**：对通过布隆的 URL，按 `hash(url) % 1000` 写 1000 个分片文件；每个分片约 10⁶ 条 × 80 B ≈ 100 MB，连同哈希集合开销不到 300 MB——单分片在内存里轻松精确去重，逐片处理后合并输出。这正是把第 06 篇的哈希思想搬到外存：**同一个哈希函数保证「相同的 URL 必然落进同一个分片」**，跨分片不需要比对。

**结论**：布隆过滤器（内存，粗筛，无假阴性）+ 磁盘哈希分片（外存，精确）。若不在乎磁盘 I/O，跳过布隆直接分片也能得到正确结果——布隆优化的是 I/O 量级，不是正确性。整套思路可以推广：**内存装不下时，先算清「精确」的硬下界，然后降级存储层（内存 → 磁盘 → 多机），并用概率结构把层间的流量砍掉一个量级**。

## 9. 小结

- 选型的起点是操作画像四问，不是结构清单：主导操作及占比、顺序需求的强度、规模与到达方式、键的形态。四问答完，候选结构通常只剩一两个。
- 顺序需求分强度：存在性（哈希）< 极值（堆）< 排名与范围（有序结构）。用能覆盖需求的最弱保证，别拿全序结构付极值需求的维护税。
- 单一结构不够用时的通用模式：**链式或有序结构管形状，哈希表管定位**。LRU（哈希 + 双向链表）、O(1) 随机删除（哈希 + 数组 swap-pop）、滑动窗口（哈希 + 环形缓冲）、双索引（哈希 + 有序结构）全是这个模式。
- 组合结构的心脏是不变式，且必须在测试里断言。「只更新一半」是组合结构的头号 bug：一个结构改了、另一个忘了，错误延迟爆发。
- 组合的代价在写入端：每多一个索引，每次写入多一次维护。这就是数据库二级索引的代价模型——读性能是买来的。
- 语言容器的接口相似但复杂度契约不同（`operator[]` 会插入、`setdefault` 急切求值、堆的默认方向不一）；记「画像 → 结构家族」的映射，关键路径在目标机器实测。
- 复杂度之外的账：缓存局部性、分配次数、真实内存开销、并发下的锁粒度——它们解释「同复杂度却差 10 倍」，也决定「装不装得下」。
- 性能工作的顺序不可交换：测量 → 定性（量级还是常数）→ 换结构（量级收益）→ 抠常数（倍数收益）→ 最后才并行。内存装不下时承认它装不下，先算账，再谈近似与分层。

## 10. 练习

**1.** 一个函数的画像：90% 是 `contains`（在不在），9% 是 `add`，1% 是「按插入序全量遍历」。选什么结构？给出每种操作的复杂度，并说明遍历频率低到什么程度时不值得为它加第二个结构。

> [!TIP]
> 思路主结构用哈希集合（`contains` 与 `add` 平均 O(1)）。「按插入序遍历」的频率只有 1% 时，遍历前临时排序：`sorted(s, key=插入时间)` 需要额外存时间戳，或直接维护一个并行的插入序列表 `order`（`add` 时同步 `append`，O(1)）。只要遍历不是热路径，O(n) 的临时遍历方案就赢过为它引入哈希 + 双向链表的维护成本——判据是「遍历频率 × O(n)」是否追上「每次 add 多付的双链维护」。

**2.** 把 4.1 节的 LRU 改成 LFU（淘汰**访问次数最少**的，次数相同淘汰最旧），需要哪些结构的组合？写出不变式。

> [!TIP]
> 思路 O(1) 版本：哈希表 `key → 节点`（节点含 key、value、freq）+ 哈希表 `freq → 双向链表桶`（同频次的节点按新旧排序）+ 一个 `min_freq` 指针。不变式：每个 key 恰在一个桶里；`min_freq` 桶非空。命中时 freq 加一并搬桶；淘汰时摘 `min_freq` 桶的尾节点，桶空则 `min_freq` 加一。若允许 O(log n)，可以退化成「哈希 + 堆 + 惰性删除」（ freq 改了不搬堆，弹出时检查是否过期），实现简单得多——这正是复杂度与实现成本的又一对交换。

**3.** 4.2 节的 `SwapPopSet` 顺序会被打乱。若还需要「按插入序遍历」且删除保持 O(1)，怎么改？Python 里有个现成的单结构答案，是什么？

> [!TIP]
> 思路换 4.1 节的组合：哈希表 + 双向链表（链表按插入序串起来，尾插即插入序），删除 O(1)、遍历 O(n) 且稳定。Python 3.7+ 的 `dict` 本身就是答案：它保插入序、`del d[k]` 平均 O(1)（紧凑布局里删除只留墓碑），`d.pop` 配合迭代即得；用 `OrderedDict` 语义更明确。原理在 [第 06 篇](06-hash-table.md) 第 6.1 节：紧凑条目数组天然就是那条「隐形链表」。

**4.** 滑动窗口中位数：数据流每个元素带时间戳，查询「最近 T 秒的中位数」。把 4.3 节的对顶堆和 [第 09 篇](09-heap-priority-queue.md) 第 9 节的延迟删除组合起来，过期元素怎么处理？堆会无限膨胀吗？

> [!TIP]
> 思路对顶堆的每个元素带时间戳；查询中位数前，循环检查两个堆顶，过期（时间戳早于 now − T）就弹出。注意堆只能看堆顶——堆中间的过期元素要等它浮到顶才被清走，所以堆的规模可能暂时超过窗口大小（膨胀上界 = 数据速率 × 元素在窗口外仍滞留的时间）。控制手段：定期把两个堆合并重建（丢弃过期元素），摊还成本 O(n)；或用「按时间分块 + 每块一个有序数组」的结构，整块过期整块丢弃。

**5.** 内存预算题：8 GB 内存分别用 Python dict、C++ `unordered_map`、C 开放寻址表存 int 到 int 的映射，各能存约多少条？用 5.3 节的每条字节数估算。

> [!TIP]
> 思路按 5.3 节的每条开销：Python 约 100 B/条 → 8×10⁹ / 100 ≈ 8×10⁷（8000 万条）；C++ `unordered_map` 约 40 B/条 → 约 2×10⁸（2 亿条）；C 开放寻址约 16 B/条 → 约 5×10⁸（5 亿条）。同一个「8 GB」下三种实现差 6 倍——容量规划必须绑定实现语言，不能只写「一个哈希表」。

**6.** 只用 1.5 节的决策树给下面四个需求选结构：①输入法的候选词自动补全；②线程池的任务等待队列；③账号体系里「这两个账号是否同属一人」（支持合并）；④电梯调度里「选出距离当前楼层最近的请求」。

> [!TIP]
> 思路①键带前缀语义 → Q3 分支 → Trie（[第 10 篇](10-trie.md)）。②位置序、先进先出 → Q1 分支 → 队列（[第 05 篇](05-queue-deque.md)）。③关系型问题「谁与谁同组」→ Q4 分支 → 并查集（[第 11 篇](11-union-find.md)）。④只要反复取最值 → Q2 分支 → 堆（按距离的最小堆；注意电梯请求的「最值」定义要先想清楚，距离最近不等于先服务）。

**7.** 用 `timeit` 实测 `list.pop(0)` 与 `deque.popleft()`：各把 10⁵ 个元素全部弹出。预测倍数，再解释为什么倍数没有达到 n = 10⁵ 的理论值。

> [!TIP]
> 思路实测约 200 倍（0.59 秒对 0.003 秒量级）。理论上是 O(n²) 对 O(n)，但 `pop(0)` 的「整体前移」是 C 级 `memmove`——每秒能搬数 GB，把 O(n²) 的常数压得极小；n 越小，这个常数优势越明显。把 n 加到 10⁶，耗时按平方增长（约 60 秒），倍数拉开到数千倍——**量级差会被 n 放大，小 n 时常数救得了，大 n 时救不了**。

**8.** 线上接口 p99 从 20 ms 涨到 400 ms，同事猜测「是新加的 JSON 序列化拖慢的」。按第 7 节的顺序，列出你接下来做的事，以及每一步要产出的证据。

> [!TIP]
> 思路①建立可复现基准（固定回放流量或压测脚本），记录当前 p99 作为基线；②测量：线上用 py-spy 采样或开火焰图，看耗时最宽的塔是谁——不预设是序列化；③翻倍实验或对比发布前后 profile，定性是量级变化（新代码引入了 O(n²) 路径）还是常数变化（多了几次分配）；④若确认是序列化：看它是热路径上的重复构造（可复用）还是量级问题（换流式解析）；⑤改完重新量，确认 p99 回到基线。每一步的证据依次是：基线数据、火焰图、对比 profile、修改后的基准结果——「猜测」在第二步就应该被证实或证伪。
