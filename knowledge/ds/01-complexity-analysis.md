判断一段代码快不快，最直接的办法是跑一遍计时。但这个办法几乎从不可靠：换台机器结论就变；数据量小的时候常数项主导，优雅的算法反而输给笨办法；输入分布一换（已排序的数据、全部落在同一个桶里的哈希键），最坏情况才浮出水面。复杂度分析要做的事，是把「这台机器上、这一次运行」抽象成「代价随规模增长的趋势」。它是唯一能跨机器、跨规模、跨输入分布比较算法的语言——也是后面十几篇所有取舍论证的共同基础。

这一篇不教你背诵复杂度表，而是把三件事说清楚：记号的确切含义、四种容易混淆的「复杂度语义」、以及复杂度分析本身失效的地方。

## 1. 渐进记号：从「跑得快」到「长得慢」

### 1.1 为什么必须忽略细节

一个操作的真实耗时取决于：CPU 主频、指令流水线、缓存命中率、编译器优化、操作系统调度。把这些都算进去，得到的结论换个环境就作废。渐进分析只保留**与输入规模 n 相关的增长部分**，把所有与 n 无关的机器细节打包成常数因子丢掉。

这个选择有代价（见第 3 节），但换来的是可移植的结论：两个算法在 n 趋于无穷时的相对关系，在任何机器上都是一样的。

### 1.2 五个记号

| 记号   | 读法      | 确切含义                                | 类比          |
| ---- | ------- | ----------------------------------- | ----------- |
| O(f) | 大 O     | 存在常数 c、n₀，使 n ≥ n₀ 时 T(n) ≤ c·f(n)  | 上界：「不超过」    |
| Ω(f) | 大 Omega | 存在 c、n₀，使 n ≥ n₀ 时 T(n) ≥ c·f(n)    | 下界：「不少于」    |
| Θ(f) | 大 Theta | 同时是 O(f) 和 Ω(f)                     | 紧确界：「量级就是」  |
| o(f) | 小 o     | n ≥ n₀ 时 T(n) < c·f(n) 对**任意** c 成立 | 严格小于：n 对 n² |
| ω(f) | 小 omega | 同理反向                                | 严格大于        |

两个最常见的误用：

- **大 O 是上界，不是等号**。「快速排序是 O(n²)」这句话完全正确——n² 确实是它的一个上界；只是它同时也满足 O(2ⁿ)、O(n³)，这些描述没用。日常说「快排是 O(n log n)」，严谨的表述是「期望 Θ(n log n)，最坏 Θ(n²)」。工程沟通里图省事可以省略，但脑子里要清楚这是**紧确界**的省略说法。
- **常数因子可以被吞掉**：O(2n) 就是 O(n)，O(n² + 100n + 5000) 就是 O(n²)。所以「这个算法比那个快一倍」在渐进分析里根本无法表达。

> [!NOTE]
> 小 o 与大 O 的区别常被忽略：T(n) = 2n 既满足 O(n) 也满足 O(n²)，但只满足 o(n²) 不满足 o(n)。写论文或严格推导时用得上，工程讨论里几乎只用大 O 和 Θ。

### 1.3 常见增长阶与现实的对应

下表按「一秒钟能处理多大规模的输入」给出直觉（假设每次基本操作约 1 纳秒，即 C/C++/Rust 量级；Python 要再差两到三个数量级）：

| 复杂度        | n = 10 时的操作数 | n = 1000 时 | n = 10⁶ 时      | 现实参照         |
| ---------- | ------------ | ---------- | -------------- | ------------ |
| O(1)       | 1            | 1          | 1              | 数组下标、哈希查找平均  |
| O(log n)   | \~3          | \~10       | \~20           | 二分查找、平衡树高度   |
| O(n)       | 10           | 10³        | 10⁶（约 1 毫秒）    | 一次遍历、前缀和     |
| O(n log n) | \~33         | 10⁴        | 2×10⁷（约 20 毫秒） | 排序、分治合并      |
| O(n²)      | 100          | 10⁶（1 毫秒）  | 10¹²（约 20 分钟）  | 双重循环、朴素字符串匹配 |
| O(n³)      | 1000         | 10⁹（约 1 秒） | 10¹⁸（约 30 年）   | 朴素矩阵乘法、Floyd |
| O(2ⁿ)      | 1024         | 10³⁰¹      | —              | 枚举所有子集       |
| O(n!)      | 3.6×10⁶      | 天文数字       | —              | 枚举所有排列       |

这张表最实用的推论是第 6 节要讲的「反推法」：看到数据范围，就该知道目标复杂度是多少。

## 2. 四种复杂度语义：别把摊还当成平均

「这个操作的复杂度是多少」这个问题，答案取决于你问的是哪种情况。四种语义经常被混为一谈，但它们的**适用条件和工程含义完全不同**。

| 语义   | 定义             | 何时该看它                  | 典型例子              |
| ---- | -------------- | ---------------------- | ----------------- |
| 最好情况 | 最有利输入下的代价      | 几乎从不关心（无决策价值）          | 顺序查找第一个就命中 O(1)   |
| 最坏情况 | 最不利输入下的代价      | 对延迟有承诺的场景：实时系统、接口超时    | 快排 O(n²)、哈希表 O(n) |
| 平均情况 | 按输入分布加权的期望代价   | 日常性能预期，**必须声明分布假设**    | 哈希表假设散列均匀         |
| 摊还   | 一串操作的总代价除以操作次数 | 单次可能很贵、但贵得「有规律、有预算」的结构 | 动态数组扩容、并查集路径压缩    |

四个容易踩的坑：

1. **平均情况是分布的产物，不是算法的性质**。「哈希表平均 O(1)」隐含了「哈希函数把键均匀撒开」的假设。如果键是被攻击者精心构造的（哈希碰撞攻击），平均就退化成最坏，这是安全问题而不只是性能问题（见 [第 06 篇](06-hash-table.md) 第 7 节）。
2. **摊还 ≠ 平均**。平均是对随机输入取期望；摊还是对**任意输入序列**给出的总代价保证——它不需要任何概率假设。动态数组的摊还 O(1) 在最坏输入下也成立（只要你只看总时间）。
3. **摊还不抹平单次延迟**。摊还 O(1) 允许某一次 push 花掉 O(n) 的时间。对延迟敏感的场景（音视频、实时控制、高频交易），那个长尾就是问题，做法是预估容量提前 `reserve`。这是"摊还分析的真实工程含义"。
4. **期望复杂度 ≠ 摊还复杂度**。随机化快排的 O(n log n) 是**期望**（对 pivot 的随机选择取期望）；动态数组是**摊还**（对操作序列取平均）。两者都可能出现坏运气，但坏运气的来源不同：前者是随机数，后者是操作顺序。

### 2.1 摊还分析三法

以动态数组的倍增扩容为例（容量满时申请 2 倍空间并整体拷贝），三种方法都能证明「n 次 push 总代价 O(n)，摊还每次 O(1)」。

**聚合法**：算总账。容量为 1、2、4、8……时各扩容一次，拷贝元素总数 1 + 2 + 4 + … + n/2 < n。加上每次 push 本身的 O(1)，n 次 push 总代价 O(n)，摊还 O(1)。

**记账法**：给每次操作预收「信用」存起来，用于支付将来的昂贵操作。每次 push 收 3 枚：1 枚支付本次写入，2 枚存在这个元素上；扩容时要搬的元素，每个身上恰好存着 2 枚，正好够支付「搬走 + 在新位置重新存入自己的 2 枚」。因为预收的信用总是非负，摊还上界成立。

**势能法**：定义势能函数 Φ 表示「已预付的未来工作」。令 Φ = 2·size − capacity（容量翻倍策略下 Φ ≥ 0 恒成立）。一次不触发扩容的 push：实际代价 1，Φ 增加 2（size +1，capacity 不变），摊还代价 = 1 + 2 = 3。一次触发扩容的 push（此时 size = capacity = c）：实际代价 = c 次拷贝 + 1 次写入 = c + 1，Φ 从 2c − c = c 变为 2(c+1) − 2c = 2，变化量 2 − c，摊还代价 = (c + 1) + (2 − c) = 3。两种情况都是 3，摊还 O(1)。

> [!TIP]
> 三种方法等价，选最顺手的一种即可：**聚合法**适合「周期性昂贵操作」的粗糙论证；**势能法**适合需要在论文里严格证明的场合；**记账法**最适合口头解释给别人听。势能函数怎么找？看那个「昂贵的操作」在还债之前积累了多少工作——动态数组里累积的是元素数，所以 Φ 取元素数的线性函数。

## 3. 忽略常数的代价：复杂度相同时，谁赢

渐进分析说两个 O(n log n) 的排序「一样快」。现实里它们可以差 3 倍，因为被丢掉的常数包含了：

- **访存模式**：顺序访问数组 vs 链表指针追逐。CPU 一次取一整条缓存行（通常 64 字节），数组的顺序访问能一次换来 15 次命中，链表每次都要等主存（约 100 纳秒，够 CPU 执行几百条指令）。
- **指令级并行**：连续内存上的简单循环能被流水线、甚至自动向量化（SIMD，一次算 4/8/16 个元素）；带数据依赖的指针跳转全部失效。
- **分支预测、函数调用开销、分配器行为**。

一个量级参考：遍历一个有 10⁶ 个 int 的数组和一个同样规模的链表，前者通常在毫秒级，后者可能慢 10 倍以上，尽管两者都是 O(n)。细节见 [第 02 篇](02-array-dynamic-array.md) 与 [第 03 篇](03-linked-list.md)。

所以正确的态度是：**用复杂度筛掉量级不对的方案（这一步通常能淘汰 90% 的候选），用实测在剩下的少数方案里选**。反过来做——先写最优雅的实现再测——往往在错误的方向上优化。

> [!WARNING]
> 复杂度分析最常见的实际误用，是拿它当「性能结论」用。O(n) 的哈希查找在 n = 8 的时候，几乎必然输给 O(log n) 但只用比较几次的有序数组二分。**n 很小时，简单结构 + 简单代码几乎总是赢**。复杂度是趋势语言，不是时间预言机。

## 4. 递归式：分治算法的复杂度怎么算

递归函数的时间 T(n) 通常写作递归式，例如归并排序 `T(n) = 2T(n/2) + Θ(n)`。三种解法，从实用到严格：

### 4.1 递归树：画出来看每一层

把递归展开成树，每层求和，再看层的数量。

以 `T(n) = 2T(n/2) + n` 为例：

```text
第 0 层:            n                  → 本层代价 n
第 1 层:        n/2 + n/2              → 本层代价 n
第 2 层:    n/4 + n/4 + n/4 + n/4      → 本层代价 n
…
第 k 层:  2^k 个节点，每个 n/2^k        → 本层代价 n
叶节点出现在 n/2^k = 1，即 k = log2(n) 层
总代价 = n × (log2(n) + 1) = Θ(n log n)
```

递归树的价值在于它能处理主定理覆盖不到的情形。比如 `T(n) = 2T(n/2) + n log n`：每层代价是 n log(n/2^k)，往下逐层递减，求和后是 Θ(n log² n)——比主定理第 2 条给出的 n log n 大，因为 f(n) 比 n 多了个 log 因子，不属于主定理的三种情况。

### 4.2 代入法：先猜后证

猜一个上界，然后用归纳法证明。以 `T(n) = 2T(n/2) + n` 猜 Θ(n log n)：

1. 假设对所有小于 n 的规模成立：`T(n/2) ≤ c·(n/2)·log(n/2)`
2. 代入：`T(n) ≤ 2·c·(n/2)·log(n/2) + n = c·n·(log n − 1) + n = c·n·log n − (c − 1)·n`
3. 只要 c ≥ 1，就有 `T(n) ≤ c·n·log n`，归纳成立（边界条件 n = 1 需单独处理）。

代入法的难点只在「猜」，猜错的典型是忽略低阶项导致归纳放不紧（比如把 c·n·log n − c·n 收缩成 c·n·log n 时要求 c ≥ 1，如果猜的是 c·n·log n − n 这种更紧的形式就会翻车）。工程里极少需要严格证明，知道这个套路能帮你判断「猜的结果是否自洽」。

### 4.3 主定理：分治递归的查表法

对形如 `T(n) = a·T(n/b) + f(n)`（a ≥ 1，b > 1）的递归式，比较 f(n) 与「叶子总数」`n^(log_b a)`：

| 情况 | 条件                                                    | 结论                             | 直觉               |
| -- | ----------------------------------------------------- | ------------------------------ | ---------------- |
| 1  | f(n) = O(n^(log\_b a − ε))                            | T(n) = Θ(n^(log\_b a))         | 叶子层的代价主导（分得太多）   |
| 2  | f(n) = Θ(n^(log\_b a))                                | T(n) = Θ(n^(log\_b a) · log n) | 每层代价相当，共 log n 层 |
| 3  | f(n) = Ω(n^(log\_b a + ε))，且 a·f(n/b) ≤ c·f(n)（c < 1） | T(n) = Θ(f(n))                 | 根节点代价主导（合并太贵）    |

常用递归式对照：

| 递归式                    | a | n^(log\_b a) | 情况 | 结果         | 出处            |
| ---------------------- | - | ------------ | -- | ---------- | ------------- |
| T(n) = T(n/2) + O(1)   | 1 | n⁰ = 1       | 2  | Θ(log n)   | 二分查找          |
| T(n) = 2T(n/2) + O(n)  | 2 | n            | 2  | Θ(n log n) | 归并排序、快排期望     |
| T(n) = 2T(n/2) + O(1)  | 2 | n            | 1  | Θ(n)       | 二叉树的递归遍历      |
| T(n) = 3T(n/2) + O(n)  | 3 | n^1.585      | 1  | Θ(n^1.585) | Karatsuba 乘法  |
| T(n) = 7T(n/2) + O(n²) | 7 | n^2.807      | 1  | Θ(n^2.807) | Strassen 矩阵乘法 |
| T(n) = 2T(n/2) + O(n²) | 2 | n            | 3  | Θ(n²)      | 分治但合并代价极高     |

主定理覆盖不到的常见形态：

- `T(n) = T(n − 1) + O(1)`：不是分治，递归树是一条链，Θ(n)。（递归求阶乘、线性递归遍历链表）
- `T(n) = T(n − 1) + O(n)`：Θ(n²)。（选择排序的递归写法）
- `T(n) = 2T(n − 1) + O(1)`：Θ(2ⁿ)。（汉诺塔、子集枚举）
- `f(n)` 落在两个情况之间的间隙（如 `2T(n/2) + n log n`）：主定理失效，用递归树或推广形式。

> [!TIP]
> 记不住主定理也没关系，记住这个更强的直觉：**分治的复杂度由「叶子层的总量」和「根层的工作量」谁更大决定**，相等时乘一个 log n（分治的层数）。所有分治算法都可以用这句话先估个八九不离十，再用递归树确认。

## 5. 空间复杂度：容易被忘掉的一半

时间不是唯一资源。空间复杂度里最常被忽略的是**递归栈深度**：

| 算法         | 辅助数组     | 递归栈深                | 总空间         |
| ---------- | -------- | ------------------- | ----------- |
| 归并排序       | O(n)     | O(log n)            | O(n)        |
| 快速排序（原地分区） | O(1)     | O(log n) 期望、O(n) 最坏 | O(log n) 期望 |
| 递归遍历二叉树    | O(1)     | O(h)，h 是树高          | 退化树 O(n)    |
| 迭代版 DFS    | O(n) 显式栈 | O(1)                | O(n)        |
| 递归求阶乘      | O(1)     | O(n)                | O(n)        |

几个具体的工程后果：

- **递归深度会爆栈**。Python 默认递归上限 1000 层，Linux 进程栈默认 8 MB，深递归（10 万节点的图）必须改成显式栈迭代（[第 12 篇](12-graph-representation-traversal.md) 的遍历模板会讲怎么改）。
- **「原地」通常指 O(1) 或 O(log n) 辅助空间**，但递归栈也是空间。说「快排是原地排序」时，严格讲是 O(log n) 额外空间。
- **输出不占总空间**。返回一个长度为 n 的结果，那是 Θ(n) 的输出，不叫「额外空间」。但要注意**输出敏感（output-sensitive）**的算法：枚举所有合法解，复杂度是解的数量乘以单个解的代价，跟输入规模无关——回溯类算法基本都是这类，别用输入 n 去估它的耗时。
- **Python 里一切都有隐性开销**。一个 int 对象 28 字节，一个指向它的 list 元素 8 字节；所以「n 个整数的数组」在 Python 实际占 36n 字节左右，比 C 的 4n 大一个数量级。做内存估算时必须以对象为单位，不是以「机器字」为单位。

## 6. 数据范围反推算法：实战中最常用的一步

刷题与性能设计里，比「算复杂度」更常用的是它的逆运算：**给定 n 的范围，反推可接受的复杂度**。经验对照如下（假设时间限制 1 秒，C/C++/Java 量级）：

| n 的量级     | 可接受的复杂度                   | 对应算法类型            |
| --------- | ------------------------- | ----------------- |
| n ≤ 20    | O(2ⁿ)、O(n!)               | 枚举子集、状压 DP、全排列回溯  |
| n ≤ 100   | O(n⁴)                     | 高维 DP、区间 DP 的朴素形式 |
| n ≤ 500   | O(n³)                     | Floyd、矩阵乘法、区间 DP  |
| n ≤ 5×10³ | O(n²)                     | 二维 DP、朴素配对        |
| n ≤ 10⁵   | O(n log n)                | 排序、堆、二分、树状数组      |
| n ≤ 10⁶   | O(n)、O(n log n) 常数要小      | 线性扫描、前缀和、哈希       |
| n ≥ 10⁷   | O(n) 且常数极小，或必须外存/O(1) 记忆化 | 流式处理、位运算、分块       |

理论上的操作次数与实际时间的换算（数量级参考，随机器与实现浮动）：

```text
1 秒能做的「简单操作」：
  C / C++ / Rust：约 10^8 ~ 10^9
  Java / C#：约 10^8
  Python：约 10^6 ~ 10^7（解释器开销，循环尤其慢，向量化可追平 C）

所以 n = 10^5 的 O(n²) 在 C++ 里约 10^10 次操作 → 几十秒，超时
     n = 10^5 的 O(n log n) 约 1.7×10^6 次 → 毫秒级，安全
```

> [!IMPORTANT]
> Python 的常数因子足以吃掉整个量级差异。以 n = 10⁵ 为例：纯 Python 的 O(n log n) 排序（内置 `sorted` 是 C 实现）和「手写的 O(n²) 冒泡」差距是 10¹⁰ : 10⁶，但「纯 Python 的 O(n) 循环」和「C 实现的 O(n log n)」之间可能只差几倍。**在 Python 里，先看能不能用内置/向量化的实现，再谈复杂度**。

## 7. 常见错误清单

这些是复杂度分析里最常出错的地方，每一条在生产代码里都见过真实案例。

### 7.1 嵌套循环不一定是 O(n²)

```python
total = 0
for i in range(n):        # 外层 n 次
    for j in range(i):    # 内层 i 次，与 n 无关地递减
        total += 1
# 总次数 = 0 + 1 + 2 + ... + (n-1) = n(n-1)/2 = Θ(n²)，量级没变但常数是一半
```

但如果内层的循环次数是常数，或者内层总次数被外层的某种单调性限制（如双指针），整体就是 O(n)：

```python
# 双指针：左右指针各自单调移动，总移动次数不超过 2n
i, j = 0, len(a) - 1
while i < j:              # 外层「循环」与内层加起来一共 O(n) 次
    if a[i] + a[j] < target:
        i += 1
    else:
        j -= 1
```

判断的标准是**总操作次数**，不是循环的嵌套层数。看到嵌套先问：内层平均跑多少次？

### 7.2 语言里那些「看起来 O(1)」的操作

| 操作                                  | 实际复杂度               | 说明                        |
| ----------------------------------- | ------------------- | ------------------------- |
| `x in list`                         | O(n)                | 线性扫描；放进循环就是 O(n²)         |
| `x in set` / `x in dict`            | O(1) 平均             | 哈希；最坏 O(n)                |
| `list.pop(0)` / `list.insert(0, x)` | O(n)                | 后面的元素整体前移/后移              |
| `list.append`                       | 摊还 O(1)             | 扩容时单次 O(n)                |
| `a + b`（两个列表拼接）                     | O(len(a) + len(b))  | 每次都新建                     |
| `a += [x]`                          | 摊还 O(1)             | 原地扩展，与 `a = a + [x]` 不同   |
| `s.find(t)` / `t in s`（字符串）         | O(len(s)·len(t)) 最坏 | Python 的实际实现更接近线性，但不是语言保证 |
| 字符串切片 `s[i:j]`                      | O(j−i)              | 拷贝，不是视图                   |
| `sorted(x)`                         | O(n log n)          | 循环里调用它是常见的隐藏杀手            |
| `dict` 的键比较                         | 键长度 L 的 O(L)        | 字符串键的哈希与相等比较都不是常数         |

> [!WARNING]
> 两个高频的真实 bug 模式。第一，在循环里用 `if item in lst` 去重（O(n²)），换成 `set` 立刻是 O(n)——这是最值得记住的一条。第二，在循环里 `total_str += piece` 拼大字符串：CPython 对引用计数为 1 的字符串会尝试原地扩容，所以实测常常接近 O(n)，但这是**实现细节不是语言保证**，换 PyPy 或字符串被别处引用时就退化成 O(n²)。规范做法永远是 `"".join(pieces)`。

### 7.3 把「访问」当成 O(1) 的错

比较两个长字符串是否相等是 O(L)（要逐字符比）。如果它出现在循环里，总复杂度里就藏着一个 L 因子。同理：大整数运算的每一位、dict 的字符串键、以及「哈希一个长字符串」本身都不便宜。分析时把 L 显式写出来，别默默当成 1。

### 7.4 忘了摊还分析的前提

摊还分析要求操作序列的**状态不被外部破坏**。典型反例：动态数组的摊还 O(1) 建立在「扩容因子 > 1 且恒定」之上。如果有人把扩容因子设成 1.1 并同时保留「每次缩容到刚好装下」的策略，在临界点反复 push/pop 就会把 O(1) 打回 O(n)（见 [第 02 篇](02-array-dynamic-array.md) 的抖动一节）。用结论时要想清楚前提。

## 8. 小结

- 渐进记号丢掉的是与 n 无关的常数，换来的是跨机器成立的结论；日常说的「是 O(…)」默认指紧确界 Θ。
- 四种语义各有适用场景：最坏用于承诺（超时、实时），平均用于预期（且必须声明分布），摊还用于「单次可能很贵但总量可控」的结构，最好情况几乎没有决策价值。
- 摊还不需要概率假设，也不承诺单次延迟；这是它和期望复杂度的分界。
- 摊还三法：聚合法（算总账）、记账法（预收信用）、势能法（定义 Φ，证明每次摊还代价一致）。
- 分治递归式的复杂度由「叶子层总量」与「根层工作量」的较大者决定，相等时乘以 log n；这就是主定理的直觉版本。
- 递归栈深是空间复杂度的一部分，也是「递归改迭代」的主要动机。
- 复杂度只能筛方案，不能定胜负：n 小的时候常数与缓存主导，此时简单实现几乎总是赢。
- 实战最常用的是反推法：先看数据范围，再定目标复杂度（n ≤ 20 想搜索/状压，n ≤ 10⁵ 想 O(n log n)，n ≥ 10⁷ 只能想 O(n) 或流式）。
- 警惕语言里的伪 O(1)：`in list`、`pop(0)`、字符串拼接、循环里的 `sorted`。

## 9. 练习

**1.** 分析下面代码的时间复杂度，说明每一步的依据。

```python
def f(nums):
    s = set()
    out = []
    for x in nums:
        if x not in s:
            s.add(x)
            out.append(x)
    return sorted(out)
```

> [!TIP]
> 思路前半个循环是 O(n)（集合查找平均 O(1)）；`sorted` 是 O(k log k)，k 是去重后的元素数，最坏 k = n。所以整体 O(n + k log k)，最坏 O(n log n)，平均 O(n)。注意结论要写成两项之和，边界情况（全部重复 → O(n)）才有正确解释。

**2.** 用记账法证明：容量翻倍策略下，n 次 push 的总代价是 O(n)，并指出每次操作预收多少枚信用。

> [!TIP]
> 思路每次 push 收 3 枚：1 枚付本次写入，2 枚存在新元素上。扩容时把 c 个旧元素搬到新数组，每个元素身上的 2 枚正好支付「搬运 + 自己重新存入的信用」。因为每次预收都覆盖了后续支出，任意前缀的信用余额非负，所以摊还代价上界为 3 = O(1)。

**3.** 用主定理求 `T(n) = 4T(n/2) + n²`。

> [!TIP]
> 思路a = 4，b = 2，n^(log₂4) = n²，与 f(n) = n² 同阶，落在第 2 种情况，故 T(n) = Θ(n² log n)。（直觉：每层代价都是 n²，共 log₂n 层）

**4.** 求 `T(n) = 2T(n/2) + n log n`，并说明为什么主定理不能直接用。

> [!TIP]
> 思路n^(log₂2) = n，而 f(n) = n log n 不是 Θ(n)（不是第 2 种），也不满足第 1、3 种要求的「多项式级别的差距」（log n 与 n^ε 之间没有多项式关系），所以主定理失效。用递归树：第 k 层代价 n log(n/2^k) = n(log n − k)，k 从 0 到 log₂n，求和 = n·((log n)² − (log n)(log n − 1)/2) = Θ(n log² n)。

**5.** 「哈希表的查找是 O(1)」这句话有哪些不严谨之处？给出一个严谨的表述。

> [!TIP]
> 思路三点：①它是**平均/期望**而非最坏（最坏 O(n)）；②「平均」隐含了散列均匀的假设，键被人为构造时可以打破；③忽略了对键做哈希的代价 O(L)（L 是键长度），以及扩容时的摊还代价。严谨表述：「在假设哈希函数对当前键集均匀分布的前提下，查找的期望代价为 O(1 + α)，其中 α 是负载因子；最坏情况 O(n)」。

**6.** 下面两个函数功能相同，估算 n = 10⁵ 时它们的耗时差多少量级，并说明原因。

```python
def f1(nums):
    seen = []
    for x in nums:
        if x not in seen:
            seen.append(x)
    return seen

def f2(nums):
    seen = set()
    for x in nums:
        seen.add(x)
    return seen
```

> [!TIP]
> 思路f1 的 `x not in seen` 是线性扫描，最坏 O(n²)：n = 10⁵ 时约 5×10⁹ 次比较，在 CPython 里可能要几十分钟；f2 平均 O(n)，约 10⁵ 次哈希操作，毫秒级。差距在 5 个数量级以上——这就是「用错结构」和「用对结构」的真实代价。

**7.** 一个递归函数处理 n = 10⁵ 个节点的链式结构，每次递归深度加一。为什么它可能崩，怎么改？

> [!TIP]
> 思路空间复杂度里递归栈深是 O(n)：Python 默认递归上限 1000 直接 `RecursionError`；C/C++ 里每帧几十字节到几百字节，8 MB 栈在 10⁵ 层时可能栈溢出。改法：显式栈（把待处理对象压进 list/deque），或用循环改写；如果确实要保留递归形式，可以加大栈（线程栈可配），但这只是延后问题。

**8.** 给定 n = 2×10⁵ 的数组，要求找出「数组中出现次数超过一半的元素」。至少给出两种解法并比较复杂度。

> [!TIP]
> 思路①哈希计数：O(n) 时间、O(n) 空间，一趟统计再一趟找最大。②Boyer-Moore 投票：O(n) 时间、O(1) 空间，维护候选与计数，相同加一、不同减一、归零换候选，最后验证候选是否真的过半。③排序后取中位数：O(n log n) 时间、O(1) 额外空间（原地排序）。数据范围 n = 2×10⁵ 时三者都能过，但空间约束（嵌入式、流式）会把答案逼向第二种——**同一份数据范围下，约束不止时间一项**。
