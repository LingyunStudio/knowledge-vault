哈希表把「按键找值」变成了一次计算，代价是键与键之间再没有任何关系：`car` 和 `cart` 在哈希表里是两个互不相干的条目，而它们的公共前缀明明可以只存一份。Trie（前缀树，读作「try」）走的是相反的路——不计算位置，而是把字符串按字符逐层摊开，让公共前缀共享同一条路径。这个改动换来了一整类哈希表做不了的操作：前缀存在性、自动补全、字典序遍历、最长前缀匹配。代价同样明确：每个字符都是一次指针跳转，常数比哈希大，内存估算也比哈希容易翻车——同一个词表，Trie 能吃掉哈希表十倍以上的内存。

这一篇要讲的是：前缀这件事为什么需要专门的结构、节点的三种实现如何取舍、删除时怎么回收无人共享的路径、空间从哪来又怎么省，以及由 Trie 演化出的 AC 自动机为什么是「一次扫描匹配上万个模式」的标准答案。

## 1. 前缀是一等公民

### 1.1 哈希表的结构性缺口

哈希表的定位由**整个键**决定，任何前缀都用不上。于是「有哪些词以 `ca` 开头」这个问题在哈希表上只有一个答案：遍历所有键，逐个做 `startswith`，代价 O(n·L)。这不是实现不够聪明，而是这种结构把前缀信息当作噪声丢掉了。

工程师通常会试三种补丁，各有各的代价：

| 补丁          | 做法                              | 代价                                  |
| ----------- | ------------------------------- | ----------------------------------- |
| 把所有前缀也存进哈希表 | 每个词的所有前缀都作为独立键插入，标记「只是前缀」       | 空间 O(总字符数) 个字符串对象，共享前缀被摊平成互不相干的键    |
| 排序 + 二分     | 词按字典序排序，前缀 `ca` 的候选词是排序数组里连续的一段 | 每次查询 O(L·log n)（每次比较要逐字符），插入维护 O(n) |
| Trie        | 让前缀成为结构本身                       | 需要新结构，节点有固定开销                       |

第一种补丁在真实代码里很常见，值得点名：中文分词器 jieba 的 `PrefixDict` 就是把每个词的所有前缀都以计数 0 的形式插进字典，用「前缀键存在性」代替前缀查询。它简单、够用，但当词表涨到百万级，那些前缀键会变成内存灾难——而 Trie 天生就是这件事的紧凑形式（见 6.1 节和练习 5）。

### 1.2 五个前缀任务

| 任务                      | 哈希表的做法与代价               | Trie 的做法与代价               |
| ----------------------- | ----------------------- | ------------------------- |
| 前缀存在性（是不是某个词的前缀）        | 遍历全表 O(n·L)             | 沿边走到节点 O(L)               |
| 自动补全（前缀 + 热度 TopK）      | 无便宜解法                   | 定位前缀 O(L)，再遍历子树           |
| 字典序遍历全部词                | 取出所有键排序 O(n log n·L)    | 先序遍历 O(总字符数)，天然有序         |
| 最长前缀匹配（IP 路由、URL 路由、区号） | 按前缀长度逐个试，32 位地址要 33 次查找 | 一次下行 O(位数)                |
| 多模式匹配（敏感词、规则集）          | 每个模式单独扫一遍               | Trie + 失败指针 = AC 自动机，一次扫描 |

### 1.3 心智模型：字符是边，路径是词

Trie 里**节点不存字符**，边才是字符。这一条是全部设计的地基，它带来一个不变式：

```text
不变式：从根到任一节点的路径拼接起来，就是该节点代表的字符串；
        于是该节点的所有后代，都代表以这个字符串为前缀的词。
```

前缀查询由此退化成「沿边走」，「枚举以 p 开头的词」退化成「遍历某节点的子树」，共享也由此发生——同一个前缀路径只存在一份。

```text
词表 {cat, car, cart, care, do, dog} 的 Trie：
(root)
 ├── c
 │   └── a                      ← "ca" 被 4 个词共享，只存一份
 │       ├── t  [cat]
 │       └── r  [car]           ← 路径是词，同时还有孩子（is_end 与 children 并存）
 │           ├── e  [care]
 │           └── t  [cart]
 └── d
     └── o  [do]
         └── g  [dog]

总字符数 19，非根节点只有 9 个；[词] 处 is_end = True。
先序遍历（子节点按字符排序）输出：car, care, cart, cat, do, dog —— 字典序，无需排序。
```

注意 `[car]` 那个节点：它既是一个完整词的结尾，又继续有孩子。这就是为什么节点必须同时有 `children` 和 `is_end` 两样东西——「路径存在」和「路径是词」是两件不同的事，`starts_with("car")` 和 `search("car")` 的差别就在这一个布尔值上。

## 2. 节点设计：三种子节点实现

### 2.1 定长数组：字符集小、分支稠密时的答案

每个节点开一个固定长度（26 或 256）的数组，下标就是字符编码。一次转移 = 一次下标计算 + 一次数组读：没有哈希、没有比较、没有指针追逐，而且一个节点的所有孩子在内存里是连续的。

代价藏在「分支数」这个词里：小写字母词的 Trie 中，绝大多数节点的孩子只有 1 到 3 个（1000 个随机 6 字符词建出的 4517 个节点只有 4516 条边，平均每个节点 1.0 个孩子），26 个槽里用掉 1 个——**96% 的槽是空的**。实测（Python 的 list 表示，3.2 节的代码可复现）：26 槽的行每个 264 字节，256 槽的行每个 2104 字节；那 4517 个节点光行数组就要 119 万字节，而同样 1000 个词放进一个 dict、连键字符串一起只要 7.3 万字节，相差 16 倍。

C 里用「节点池 + 下标」而不是指针，26 个 4 字节下标能把每节点压到 104 字节，但结论不变：**定长数组的开销与分支数无关**。字符集一旦变大（256 路的字节、汉字、Unicode 码点），这个固定开销会直接爆炸——10 万个节点的 256 路数组就是约 200 MB，而它可能只存了几千个字符。这是 10.3 节要重点说的翻车方式。

### 2.2 哈希子节点：通用实现的默认选择

把子节点集合放成一个哈希表（Python 的 `dict`、C++ 的 `unordered_map`），只在真的有孩子时占空间，分支数是几就存几条，字符集多大都无所谓。这是「字符集未知、正确性优先」时的默认选择。

代价有两条：

1. **每次转移都有哈希开销**。定长数组的转移是「乘 + 加 + 读」，哈希子节点的转移是「算哈希 + 探测槽位 + 比较键」。Python 里每走一步都要一次 `dict.get`（含一次 C 层调用），是 Trie 在小数据量下输给哈希表的主要原因之一。
2. **每个节点一个小容器对象**。父节点里的指针指向一个独立的堆对象，遍历时每一步都是随机访存；节点自身还有对象头。实测（4.4 节）平均每个节点约 194 字节。

### 2.3 有序数组 / 链表 / BST：省内存且天然有序

- **有序数组**：孩子按字符排序存进一个小数组，转移用二分 O(log d)。d 很小时（不超过 8）线性扫描比二分更快（分支预测 + 缓存），所以很多实现干脆按顺序扫。好处是按实际分支数占内存，且「取字符区间内的孩子」很容易。
- **链表**：每个孩子一个节点、一个指针，最省内存，转移 O(d)，只在分支数极小的时候有意义。
- **BST / 跳表**：把 d 个孩子组织成搜索树，O(log d)，但多一层指针。

三者共同的额外好处是**天然有序**：子节点按字符排序存放，先序遍历直接产出字典序。用它做自动补全时，「按字典序补齐」不需要任何额外的排序步骤；而用 `dict` 的实现必须在收集之后显式 `sorted`（`dict` 只保证插入序，不保证字典序）。

成熟实现常把两种合起来用：**孩子少时用有序小数组，孩子多了自动升级成哈希表或树**——和 Java 8 HashMap 的桶树化是同一个思路。这种升级确实需要：根附近节点的分支数可能到几十（ASCII 全集、汉字集合），此时线性扫描就贵了。

### 2.4 取舍对照

| 子节点实现      | 一次转移                  | 每节点开销                 | 内存随分支数         | 字典序遍历  | 适用场景         |
| ---------- | --------------------- | --------------------- | -------------- | ------ | ------------ |
| 定长数组 26 路  | O(1)，一次下标 + 一次读       | 26 个槽，C 里 104\~208 字节 | 恒定，与分支数无关      | 天然有序   | 字符集小且分支稠密    |
| 定长数组 256 路 | 同上                    | 256 个槽，约 2 KB         | 恒定             | 天然有序   | 按字节建树且分支真的稠密 |
| 哈希表        | O(1) 平均，含哈希开销         | 节点对象 + 容器对象           | 按实际分支数，小分支时不划算 | 需要显式排序 | 字符集任意，通用实现   |
| 有序数组       | O(log d)，d 小则 O(d) 更快 | d 个条目                 | 按实际分支数         | 天然有序   | 分支数中等，要范围能力  |
| 链表         | O(d)                  | 每孩子 1\~2 个指针          | 最省             | 有序     | 分支极少，极端省内存   |

## 3. 一份完整可跑的 Trie

### 3.1 dict 子节点版（含删除的回溯清理）

```python
class TrieNode:
    __slots__ = ("children", "is_end", "freq")

    def __init__(self):
        self.children = {}      # 字符 -> TrieNode
        self.is_end = False     # 根到本节点的路径是否构成一个完整的词
        self.freq = 0           # 词频，只给自动补全排序用


class Trie:
    def __init__(self):
        self.root = TrieNode()
        self.n_words = 0

    # ---------- 增与查 ----------
    def insert(self, word, freq=1):
        node = self.root
        for ch in word:
            nxt = node.children.get(ch)
            if nxt is None:
                nxt = TrieNode()
                node.children[ch] = nxt
            node = nxt
        if not node.is_end:
            self.n_words += 1
        node.is_end = True
        node.freq = freq

    def _walk(self, prefix):
        """沿 prefix 走到对应节点；中途缺边返回 None。"""
        node = self.root
        for ch in prefix:
            node = node.children.get(ch)
            if node is None:
                return None
        return node

    def search(self, word):
        """整词存在性：必须落在 is_end 的节点上。"""
        node = self._walk(word)
        return node is not None and node.is_end

    def starts_with(self, prefix):
        """前缀存在性：只要路径存在即可。"""
        return self._walk(prefix) is not None

    # ---------- 删除：回溯清理无用节点 ----------
    def delete(self, word):
        if not word:
            return False
        path = []                            # [(父节点, 字符), ...]
        node = self.root
        for ch in word:
            nxt = node.children.get(ch)
            if nxt is None:
                return False                 # 词不在树里
            path.append((node, ch))
            node = nxt
        if not node.is_end:
            return False                     # 路径存在，但这里不是词尾
        node.is_end = False                  # 先摘掉词尾标记
        node.freq = 0
        self.n_words -= 1
        for parent, ch in reversed(path):    # 自底向上回收
            child = parent.children[ch]
            if child.is_end or child.children:
                break                        # 还被别的词共享，停止回收
            del parent.children[ch]
        return True

    # ---------- 遍历 ----------
    def collect(self, node=None, prefix="", out=None):
        """收集子树里的全部词；子节点按键排序，输出即字典序。"""
        if node is None:
            node = self.root
        if out is None:
            out = []
        if node.is_end:
            out.append(prefix)
        for ch in sorted(node.children):
            self.collect(node.children[ch], prefix + ch, out)
        return out

    def autocomplete(self, prefix, k=3):
        """前缀补全：定位前缀节点，收集子树里的词，按词频取 TopK。"""
        node = self._walk(prefix)
        if node is None:
            return []
        hits = []
        stack = [(node, prefix)]
        while stack:
            cur, path = stack.pop()
            if cur.is_end:
                hits.append((cur.freq, path))
            for ch, child in cur.children.items():
                stack.append((child, path + ch))
        hits.sort(key=lambda t: (-t[0], t[1]))   # 词频降序，同频按字典序
        return [w for _, w in hits[:k]]

    def stats(self):
        """迭代统计节点数（不用递归，不担心深度）。"""
        nodes, stack = 0, [self.root]
        while stack:
            nodes += 1
            stack.extend(stack.pop().children.values())
        return nodes


if __name__ == "__main__":
    trie = Trie()
    for w, f in [("cat", 10), ("car", 5), ("cart", 3), ("care", 7), ("dog", 20), ("do", 4)]:
        trie.insert(w, f)

    # 整词查询与前缀查询是两件事
    assert trie.search("cat") and trie.search("care") and trie.search("do")
    assert not trie.search("ca")             # "ca" 只是前缀，从未作为词插入
    assert not trie.search("carts")
    assert trie.starts_with("ca") and trie.starts_with("")   # 空前缀是任何词的前缀
    assert not trie.starts_with("cav")       # 缺边，路径不存在
    assert trie.n_words == 6
    assert trie.collect() == ["car", "care", "cart", "cat", "do", "dog"]   # 字典序，无需排序

    # 自动补全：按词频 TopK
    assert trie.autocomplete("ca", k=2) == ["cat", "care"]
    assert trie.autocomplete("do", k=5) == ["dog", "do"]
    assert trie.autocomplete("z") == []

    # 删除：cart 末尾的 t 无人共享，回溯时被回收；car / ca 仍被别的词用到
    n = trie.stats()
    assert trie.delete("cart")
    assert not trie.search("cart") and not trie.starts_with("cart")   # 节点真的没了
    assert trie.search("car") and trie.starts_with("ca") and trie.stats() == n - 1
    assert not trie.delete("cart") and not trie.delete("za")   # 已不存在 / 路径不存在

    # 删光 ca 分支下的所有词后，整条链回溯回收
    assert trie.delete("cat") and trie.delete("car") and trie.delete("care")
    assert not trie.starts_with("ca")        # ca 分支整体消失
    assert trie.starts_with("do")            # 别处不受影响
    assert trie.collect() == ["do", "dog"]   # 只剩 d -> o -> g 这条链
    print("ok, 剩余词:", trie.collect(), " 节点数:", trie.stats())
```

删除是这里唯一需要动脑的操作，三个设计点：

- **先检查 `is_end`**：路径走得通不等于要删的词存在（`ca` 能走到，但它不是词）。删不存在的词必须原地返回 `False`，不能顺手把路径清了。
- **回收条件是「没有孩子且不是词尾」**：`child.is_end or child.children` 为真说明还有别的词依赖这个节点，立刻停止回溯——注意是 `break` 而不是 `continue`，因为一旦某个节点被共享，它上面的所有祖先必然也被共享（祖先的后代集合是超集）。
- **写成迭代而不是递归**：`path` 栈把「自底向上」的顺序显式记下来。递归版本读起来更短，但深度等于词长，遇到长 URL、DNA 序列、拼接出来的超长键时就是 `RecursionError`（第 10 节）。

### 3.2 26 路定长数组版：内存布局的另一极

```python
import sys


class ArrayTrie:
    """26 路定长数组版：节点池 + 每节点一行 26 个下标，-1 表示无此边。"""

    def __init__(self):
        self.nxt = [[-1] * 26]      # 节点 0 是根；一行就是「定长数组节点」
        self.is_end = [False]

    def insert(self, word):
        node = 0
        for ch in word:
            c = ord(ch) - 97
            child = self.nxt[node][c]
            if child == -1:
                child = len(self.is_end)        # 节点池的下一个空槽
                self.nxt.append([-1] * 26)
                self.is_end.append(False)
                self.nxt[node][c] = child
            node = child
        self.is_end[node] = True

    def _walk(self, prefix):
        node = 0
        for ch in prefix:
            node = self.nxt[node][ord(ch) - 97]
            if node == -1:
                return -1
        return node

    def search(self, word):
        node = self._walk(word)
        return node != -1 and self.is_end[node]

    def starts_with(self, prefix):
        return self._walk(prefix) != -1


if __name__ == "__main__":
    t = ArrayTrie()
    for w in ["cat", "car", "care", "dog"]:
        t.insert(w)
    assert t.search("car") and t.starts_with("ca") and not t.search("ca")
    assert not t.starts_with("cav")

    # 每个节点一行的固定成本（CPython 3.13，64 位）
    print("26 个指针的行 :", sys.getsizeof([-1] * 26), "字节")
    print("256 个指针的行:", sys.getsizeof([-1] * 256), "字节")
    import random
    random.seed(1)
    t2 = ArrayTrie()
    for w in {"".join(random.choices("abcdefghijklmnopqrstuvwxyz", k=6)) for _ in range(1000)}:
        t2.insert(w)
    print("1000 个随机 6 字符词的节点数:", len(t2.is_end), " 行数组总计:",
          sum(sys.getsizeof(r) for r in t2.nxt if r is not None), "字节")
```

两个版本的区别只在最后一行代码：`node.children[ch]` 是「沿指针找一个容器，再在里面找键」，`self.nxt[node][c]` 是「在一条连续的数组里按下标取值」——前者省内存、支持任意字符集，后者常数更小、内存与分支数无关（分支稀疏时纯属浪费）。删除的逻辑与 3.1 完全同构（同样自底向上回溯、同样遇到共享节点就停），差别是回收时把 `nxt[child]` 整行置 `None`、槽位不再复用——**池化布局让转移变快，也让内存回收变难**，实际工程里通常再用一个空闲链表把释放的行串起来复用。

## 4. 复杂度与空间

### 4.1 时间是 O(L)，与词库规模无关

| 操作               | 复杂度              | 说明                     |
| ---------------- | ---------------- | ---------------------- |
| `insert(word)`   | O(L)             | 最坏新建 L 个节点，每个 O(1)     |
| `search(word)`   | O(L)             | 与词库里有 100 个词还是 1 亿个词无关 |
| `starts_with(p)` | O(L)             | 与子树里挂着多少词无关            |
| `delete(word)`   | O(L)             | 回溯清理也是 O(L) 步          |
| 收集某前缀子树的全部词      | O(子树节点数 + 命中词数)  | 最坏 O(C)，C 是总字符数        |
| 全量字典序输出          | O(C)             | 不需要排序                  |
| 前缀计数（每节点存计数）     | O(L)             | 写入时维护，见练习 1            |
| 空间               | O(N)，且 N ≤ 1 + C | 见 4.3                  |

「与词库规模无关」是 Trie 最被低估的性质。哈希表的平均查找同样是 O(L)——哈希函数必须读完整键才能算，最后的相等比较也要读完——但哈希表给不出前缀；而 Trie 的前缀查询和整词查询是同一个代价。另外，Trie 的查找路径只由这个键自己决定，不受别的键影响，所以**最坏情况就是 O(L)，没有退化**，这对有硬延迟承诺的场景有价值（哈希表的最坏情况是 O(n)，见 [第 06 篇](06-hash-table.md) 第 7 节）。

### 4.2 「Trie 比哈希表快」是错的

等值查找上，哈希表通常更快，理由很具体：

- 哈希表：算一次哈希（顺序读 L 个字节，缓存友好）+ 一两次数组访问 + 一次 O(L) 的相等比较。
- Trie：L 次节点转移，每次一次指针解引用（大概率是缓存未命中）+ 一次容器查找（`dict.get` 或数组下标）。

键越短、表越小，哈希表的优势越明显。Trie 真正赢的地方有两处：一是**前缀类操作**（哈希表根本没有便宜解法）；二是**增量查询**——用户每敲一个字符，Trie 可以复用上一步停在的节点，本次只走一条边 O(1)；哈希表则每次都要把变长了的整个前缀重新哈希一遍 O(L)。搜索框的联想、路由表的转发都属于后一类场景。

### 4.3 空间：节点数、每节点开销、最坏情形

空间由两个因子相乘决定，两个因子都很容易估错。

**因子一：节点数。** 每次插入最多新增 L 个节点，所以

```text
节点总数 N ≤ 1 + C，C = 所有词的字符总量（包括重复字符）
等号当且仅当词与词之间没有任何公共前缀时成立
更紧的说法：N = 不同前缀的个数 + 1
```

共享前缀越少，N 越接近 C。**最差的情形是「短词多、前缀重叠少」**：一批互不相干的 8 字符短词，几乎只有前两三层能共享，N 是词数的 5 倍上下（4.4 节实测：10 万条词、50.8 万节点、80 万字符总量），已经和字符总量同一量级。反过来，前缀共享充分的词表（自然语言单词、URL、IP 前缀、日志字段）能让节点数明显低于字符总量——那是 Trie 唯一能赚回内存的场合。

**因子二：每节点开销。**

| 表示                      | 每节点固定开销                        | 备注                 |
| ----------------------- | ------------------------------ | ------------------ |
| C，26 路数组                | 104 字节（int32 下标）或 208 字节（指针）   | 与分支数无关             |
| C，256 路数组               | 约 1 KB 或 2 KB                  | 字符集大时的内存炸弹         |
| Python 一行 26 路数组（list）  | 264 字节                         | `sys.getsizeof` 实测 |
| Python 一行 256 路数组（list） | 2104 字节                        | 同上                 |
| Python 节点对象 + dict 子节点  | 空节点约 120 字节，有 1\~2 个孩子约 240 字节 | 对象头 + 容器对象 + 条目    |

于是估算公式是：

```text
Trie 内存 ≈ N × (节点自身开销 + 子节点容器开销) + E × (每条边的记录开销)
其中 E = N - 1（树），N 是节点数
```

### 4.4 估算内存的方法

先数节点，再乘开销。数节点不用递归，一次显式栈遍历即可（下面这段不依赖前面的类，节点就是 dict，`None` 键标记词尾）：

```python
import random
import string
import sys


def build(words):
    """最朴素的 Trie：节点就是 dict，None 键标记词尾。"""
    root = {}
    for w in words:
        node = root
        for ch in w:
            node = node.setdefault(ch, {})
        node[None] = True
    return root


def measure(root):
    """迭代遍历：节点数 + 所有节点 dict 的字节数。"""
    nodes = total = 0
    stack = [root]
    while stack:
        node = stack.pop()
        nodes += 1
        total += sys.getsizeof(node)                 # 每个节点的真实字节数
        stack.extend(c for k, c in node.items() if k is not None)
    return nodes, total


if __name__ == "__main__":
    random.seed(7)
    words = list({"".join(random.choices(string.ascii_lowercase, k=8)) for _ in range(100_000)})
    nodes, size = measure(build(words))
    d = dict.fromkeys(words)                        # 同样的词放进哈希表作对照
    dsize = sys.getsizeof(d) + sum(map(sys.getsizeof, words))
    print("词数 %d  节点数 %d  节点/词 %.1f" % (len(words), nodes, nodes / len(words)))
    print("Trie %.1f MB  平均每节点 %d 字节   同词量 dict + 键 %.1f MB" %
          (size / 2**20, size / nodes, dsize / 2**20))
    print("空 dict %d B  1 项 dict %d B  26 槽 list %d B" %
          (sys.getsizeof({}), sys.getsizeof({"a": 1}), sys.getsizeof([-1] * 26)))
```

本机（CPython 3.13，64 位）的输出：

```text
词数 100000  节点数 507727  节点/词 5.1
Trie 94.0 MB  平均每节点 194 字节   同词量 dict + 键 8.3 MB
空 dict 64 B  1 项 dict 184 B  26 槽 list 264 B
```

三行数字把 Trie 的空间性格说清楚了：**10 万个 8 字符短词，纯字符量只有 800 KB，Trie 却要 94 MB**（平均每节点 194 字节），而哈希表只要 8.3 MB。省掉的内存是前缀共享（节点数 50.8 万，小于 80 万字符总量），花掉的内存是每个节点的对象与容器开销。所以：

- 短词多、前缀重叠少 + Python 的 dict 子节点 = 内存最差组合。此时哈希表是更好的选择，或者必须上第 6 节的压缩表示。
- 前缀重叠充分（自然语言、URL、IP 前缀、日志字段）时，Trie 的空间代价才可能被共享赚回来。

> [!WARNING]
> 别用「字符总量 × 几个字节」估 Trie 的内存。真正要乘的是**节点数**，而节点数可以接近字符总量（互不相干短词），也可以远小于它（共享充分）；每节点的开销又取决于子节点表示（C 的 104 字节到 Python 的 264 字节，相差 2.5 倍）。按「字符数 × 1 字节」估出来的 800 KB，和实测的 94 MB 差了两个数量级。

## 5. 与哈希表的分工

| 维度     | 哈希表                      | Trie                          |
| ------ | ------------------------ | ----------------------------- |
| 等值查找   | 平均 O(L)，一次计算 + 一两次访存，常数小 | O(L)，L 次转移，常数明显更大             |
| 最坏情况   | 平均假设被打破时 O(n)（碰撞、攻击）     | O(L)，稳定不变                     |
| 前缀查询   | 只能遍历全表 O(n·L)            | O(L)                          |
| 字典序遍历  | 取出所有键排序 O(n log n)       | 先序遍历 O(C)，天然有序                |
| 最长前缀匹配 | 无实用解法                    | 一次下行，见 7.3                    |
| 内存     | 每键一份完整存储，无共享             | 共享前缀，但每节点有固定开销                |
| 缓存局部性  | 好（一次顺序读键 + 少量槽位）         | 差（L 次随机访存）                    |
| 删除     | O(L)，简单                  | O(L) + 回溯（或只清 `is_end`，不回收节点） |
| 键的类型   | 任意可哈希对象                  | 必须是「字符序列」，且要能定义逐位比较           |
| 额外能力   | 计数、任意映射、集合运算             | 前缀计数、TopK、按前缀分组、多模式匹配         |

结论很直接：

- **只做等值查找（键到值的映射、去重、计数）**：用哈希表。Trie 在这里没有任何优势，只有开销。
- **需要前缀能力（前缀存在性、补全、路由、敏感词、前缀统计、按前缀分组）**：用 Trie。哈希表没有便宜解法。
- **需要有序但不关心前缀**：平衡树或跳表（[第 08 篇](08-bst-balanced-trees.md)），比 Trie 更适合范围查询与前驱后继。
- **两样都要**：哈希表 + Trie 双结构（两倍内存，写入时维护两处），或者用 FST 这类既压缩又带前缀能力的结构（6.4 节）。
- **n 很小（几十以内）**：有序数组线性扫描或二分最快——没有哈希计算，也没有指针追逐，见 [第 01 篇](01-complexity-analysis.md) 第 3 节。

## 6. 空间优化

节点太多、每节点太胖，是 Trie 唯一的死穴。四类解法，从「改形状」到「改编码」。

### 6.1 压缩 Trie：把单链合并成一条边

**思路**：如果一个节点只有一个孩子且自己不是词尾，那它就没有分叉的信息量，把它和孩子的边合并成一条「多字符串边」（radix tree，也叫 Patricia trie）。

```text
词表 {cat, car, cart, dog}
普通 Trie（非根节点 8 个，每字符一个节点）:
(root)
 ├─ c ─ a ─┬─ t [cat]
 │         └─ r [car] ─ t [cart]
 └─ d ─ o ─ g [dog]

radix tree（非根节点 5 个，只有分叉处和词尾才是节点）:
(root)
 ├─ "ca" ─┬─ "t" [cat]
 │        └─ "r" [car] ─ "t" [cart]
 └─ "dog" [dog]          ← 单链 d-o-g 被合并成一条边
```

节点数从 8 降到 5，看上去不惊人，但增长性质变了：单链被压缩后，**节点数与词数成正比，而不是与字符总量成正比**（非叶节点不超过词数 − 1，总节点不超过 2n − 1，n 是词数）。极端的例子是一个 100 字符的单词：普通 Trie 要 100 个节点，radix tree 只要 1 个。

**代价**：一次转移不再只花 O(1)，而要比较边上那段子串（O(标签长)）；插入和删除要在边的中间做分裂与合并，实现复杂度显著上升。Patricia 变体进一步不存标签字符串，只存「引用底层字符串的起始位置 + 长度」，靠位索引比较来跳过分叉点，因此特别适合「字典是一大块只读字节」的场景。

**谁在用**：Linux 内核的 IPv4 转发表实现（`net/ipv4/fib_trie.c`）就是一棵 LC-trie（层级压缩前缀树），把每个包的路由查找压到个位数的内存访问；BSD 系的路由表用 Patricia trie；Go 的 `httprouter`（Gin 的路由底层）用压缩前缀树匹配 URL；Redis 的 `rax.c` 用它给 Streams 的消息 ID 建索引。Rust 生态里也有 `radix_trie`、`prefix-trie` 等 crate，但要注意 Rust 标准库并不提供 Trie（历史上 pre-1.0 有过一个整数键的 `std::trie`，因为与 `BTreeMap` 功能重叠被移除了），标准库只有 `HashMap` 和 `BTreeMap`，需要 Trie 得引 crate 或自己写。

### 6.2 双数组 Trie：两个整型数组表示整棵树

**思路**：把 Trie 的转移关系编码进两个整型数组，`base` 和 `check`。字符先映射成小整数 code：

```text
转移规则：  t = base[s] + code(c)     合法当且仅当 check[t] == s
```

`check` 数组的作用是消歧：`base[s] + code(c)` 算出来的槽位可能被别的节点占了，`check[t] == s` 才说明 t 真的是 s 的孩子。一个最小的例子（字符映射 a=1, b=2, c=3，词表 {ab, ac}）：

```text
下标    0     1     2     3     4
base    1     -     1     -     -
check   -     -     0     2     2
词尾    .     .     .     T     T

查找 "ab":  t = base[0]+1 = 2, check[2] == 0 ✓ → 到 "a"
            t = base[2]+2 = 3, check[3] == 2 ✓ → 到 "ab"，词尾命中
查找 "c":   t = base[0]+3 = 4, check[4] == 2 ≠ 0 ✗ → 没有这条边
```

整个自动机就是两个连续的整型数组：一次转移是两次数组读 + 一次比较，没有指针追逐、没有哈希计算、没有对象头。内存按槽位算（一个 int32 槽 4 字节，每个节点约占两个槽），通常比同规模的对象化 Trie 小一个数量级；Darts 这类实现还会按字频重排编码空间，把常用字映射到小区间，让 `base` 值不至于被稀疏的码点撑开。**代价**是构建：要为每个节点的所有孩子找一组空闲槽位（first-fit 分配），本质是一个装箱问题，构建成本高、删改困难，所以双数组 Trie 基本都是**离线编译成二进制、运行时只读**。日文分词器 MeCab 的词典就是 `mecab-dict-index` 用 darts 编译出来的双数组，Kuromoji（Java）同样基于双数组；它们把词典 mmap 进来直接查，这也是 6.1 与 6.4 之外最常用的词典结构。

### 6.3 Ternary Search Tree：每个节点只有三个指针

**思路**：把「字符集大小」从每个节点的开销里彻底拿掉。TST 的每个节点存一个字符、一个词尾标志、三个指针：

```text
        (c)             eq: 走同一个词的下一字符
       / │ \            lo: 当前字符比 c 小时走这边（BST 左）
     lo  eq  hi         hi: 当前字符比 c 大时走这边（BST 右）
```

于是每个节点的开销是固定的 4 个字段，与字符集是 26 还是 65536 无关——不像定长数组那样给不存在的字符留槽位，也不像每个节点挂一个哈希表那样要额外的容器对象。一个字符处的转移变成一次 BST 比较，期望 O(log σ)（σ 是字符集大小），成功查找平均 O(L + log n)。**代价**是常数比普通 Trie 大（每读一个字符要绕一次 BST），而且 BST 在插入顺序不巧时会退化。它适合「字符集大、词量中等、内存受限」的场面——最初就是为拼写检查器设计的。

### 6.4 位图与稀疏表示

**思路**：一个 σ 路的节点，用 σ 个比特标记「哪些孩子存在」，第 c 个孩子的编号 = 位图里第 c 位之前 1 的个数（`rank` 运算，现代 CPU 用 `popcount` 一条指令就能算）。于是节点里不再需要任何指针，整棵树可以按层序编码成一串位图（LOUDS 表示），节点开销降到**每个节点两三个比特**的量级，再配一份字符表和一份节点权值数组。

**代价**：`rank/select` 计算（常数很小但比数组下标贵）；结构一旦建好就不能改，只能重建；实现复杂度高，属于「工具库负责写、使用者只管查」的类别。收益是数量级的：把 100 万条词的 Trie 从几百 MB 压到几十 MB 以内（约每词几个字节），这正是手机输入法词库、离线词典、全文检索引擎能把词典常驻内存的原因。带压缩能力的 FST（把等价的子树合并成 DAG）是同一条路线上的另一种做法，Lucene/Elasticsearch 的词项字典用的就是它。

### 6.5 四种优化的对照

| 方案             | 节点表示                    | 一次转移          | 空间（相对普通 Trie） | 构建与更新    | 典型场景                 |
| -------------- | ----------------------- | ------------- | ------------- | -------- | -------------------- |
| 压缩 Trie（radix） | 边上存整段子串，只有分叉处是节点        | O(标签长)，要做子串比较 | 节点数降到 O(词数)   | 分裂/合并复杂  | 路由表、URL 路由、Redis rax |
| 双数组 Trie       | `base` / `check` 两个整型数组 | O(1)，两次数组读    | 很省，无指针无对象头    | 离线构建，只读  | 分词词典                 |
| TST            | 每节点 1 字符 + 3 指针         | 每字符一次 BST 比较  | 很省，与字符集无关     | 简单，有退化风险 | 嵌入式拼写检查              |
| 位图 + rank      | 位图 + 层序节点数组             | rank 计算 + 数组读 | 最省，每节点几比特     | 只读，压缩最狠  | 离线词典、输入法词库、FST       |

## 7. 应用

### 7.1 自动补全：瓶颈在「收集」这一步

流程分三段：走前缀定位节点 O(L) → 收集子树里的所有词 O(子树节点数) → 按热度取 TopK。

朴素实现（3.1 节的 `autocomplete`）在第二步上是无上限的：用户输入 `a` 的时候，`a` 子树里可能有几十万个词，收集完再排序，代价是 O(子树节点数 + m log m)。**「收集」的代价由子树大小决定，与最终要输出的 K 个词无关**，这是自动补全最容易被忽略的一点。

优化方向只有两条：

- **在每个节点上预存该子树的 TopK 候选**。查询代价降到 O(L + K)：定位前缀，直接读该节点的 TopK 列表。代价是写入放大：插入一个词或更新一次词频，要沿路径更新每个祖先节点的 TopK 列表（K 条记录）。只读或低频更新时这笔账非常划算，工业界的联想词就是这么做的：Trie（或 FST）+ 每节点候选缓存 + 离线重算。
- **不预存，但控制遍历**。用堆做流式 TopK 是 O(子树节点数 · log K)；更好的做法是给每个节点缓存一个「子树最大词频」，遍历时按最大值做分支限界（优先展开最有希望的子树），命中 K 个就停止。

> [!TIP]
> 判定该用哪种方案，看「读写的比例」和「K 与子树规模的比例」。K 远小于子树规模、且写入不频繁（词库、商品名、`/etc/hosts` 这类基本不变的数据）时，预存 TopK 是压倒性的。写入频繁（用户的实时输入历史）时预存反而会拖慢插入，应当退回流式限界，或者对热点前缀做 LRU 缓存。

### 7.2 拼写检查：在 Trie 上跑编辑距离

朴素拼写检查（枚举编辑距离 1 或 2 的所有变形再查词典）在距离 2 时候选数上万，而且生成出来的候选绝大多数不在词典里。Trie 上可以反过来做：**拿着查询词，去字典树里找距离不超过 d 的词**。

做法是在 DFS 时维护编辑距离 DP 的**一行**：`prev_row[j]` 表示「当前 Trie 前缀」与「查询词前 j 个字符」的编辑距离。走到一个孩子（多了一个字符 `ch`）时算出新的一行：

```text
cur[0]     = prev_row[0] + 1
cur[j+1]   = min(prev_row[j+1] + 1,      # 删掉前缀末尾的 ch
                 cur[j] + 1,             # 在查询词里插入一个字符
                 prev_row[j] + cost)     # 匹配或替换，cost 取 0 或 1
```

剪枝的合法性来自一个单调性：**给前缀追加字符，行里的最小值只增不减**（三个候选项都引用上一行或本行左边的值，逐项归纳可得 min 不下降）。所以一旦整行的最小值都大于 d，这棵子树里不可能有答案，直接剪掉——这就是「编辑距离自动机（Levenshtein automaton）与字典树求交」的全部直觉：DP 的一行就是自动机的一个状态，剪枝就是自动机的死状态。

```python
def fuzzy_search(trie, query, max_dist=1, limit=8):
    """在 Trie 上枚举与 query 编辑距离 <= max_dist 的词（DFS + 整行剪枝）。"""
    results = []

    def dfs(node, prefix, prev_row):
        """prev_row[j] = 编辑距离(prefix, query[:j])；对每个孩子算一行新的。"""
        for ch, child in node.children.items():
            cur = [prev_row[0] + 1]                  # prefix 多一个字符、query 为空
            for j, qch in enumerate(query):
                cost = 0 if ch == qch else 1
                cur.append(min(prev_row[j + 1] + 1,  # 删掉前缀末尾的 ch
                               cur[j] + 1,           # 在 query 里插入 qch
                               prev_row[j] + cost))  # 匹配或替换
            if min(cur) > max_dist:
                continue                             # 整行都超标：整棵子树不可能有解
            if child.is_end and cur[-1] <= max_dist:
                results.append((prefix + ch, cur[-1]))
            dfs(child, prefix + ch, cur)

    dfs(trie.root, "", list(range(len(query) + 1)))
    results.sort(key=lambda t: (t[1], t[0]))
    return results[:limit]


if __name__ == "__main__":
    trie = Trie()                                   # 用 3.1 节的实现
    for w in ["cat", "car", "cart", "care", "dog", "dot", "coat", "cut", "cartoon"]:
        trie.insert(w)
    assert fuzzy_search(trie, "cat", 1) == [("cat", 0), ("car", 1), ("cart", 1),
                                            ("coat", 1), ("cut", 1)]
    assert fuzzy_search(trie, "catt", 1) == [("cart", 1), ("cat", 1)]
    assert fuzzy_search(trie, "dog", 1) == [("dog", 0), ("dot", 1)]
    assert fuzzy_search(trie, "xyz", 1) == []
    print(fuzzy_search(trie, "cat", 1))
```

复杂度：每访问一个节点算一行 DP，所以是 O(访问节点数 × L)。访问节点数只取决于查询词和 d（被剪枝限制在 DP 值不超过 d 的「带」里），与词典规模无关——这正是它比「枚举变形再查表」强的地方。注意标准 Levenshtein 距离不把相邻换位算作一次编辑（`cta` 到 `cat` 的距离是 2 不是 1），需要换位就得上 Damerau 变体，状态和表都会变大。

### 7.3 IP 路由：二进制 Trie 与最长前缀匹配

路由表存的是**前缀**：`10.1.0.0/16` 表示「前 16 位等于 10.1 的所有地址」。一个包到达时要回答的问题不是「这个地址在不在表里」，而是「表里与它匹配的、最长的那个前缀是哪个」——因为最长前缀代表着最精确的路由，而 `0.0.0.0/0` 的默认路由是兜底。

把地址的每一位当一层，得到一棵每层两个分支的 Trie。从根出发沿着地址的比特往下走，**路上遇到的每一个被标记为路由的节点都是一个匹配**，越深前缀越长，所以最后记录的那个就是答案：

```text
把地址缩成 4 位来看，路由表:  00** -> A    10** -> B    101* -> C    1011 -> D
（* 表示这一位可以是 0 或 1，即前缀长度）

查找地址 1011：
  bit0 = 1  走右分支，匹配 "1*"（没有路由标记）
  bit1 = 0  走左分支，匹配 "10**"，命中 B，记下
  bit2 = 1  走右分支，匹配 "101*"，命中 C，记下
  bit3 = 1  走右分支，匹配 "1011"，命中 D，记下
  沿途最后记下的是 D → 最长前缀 1011，转发到 D（路径断掉也不用回溯：停在最近记下的路由上）
```

为什么这比线性扫描路由表快得多：全球 IPv4 的 BGP 表已接近 100 万条前缀，一次线性扫描就是每个包 100 万次比较；而 10 Gbps 线速下 64 字节小包满打时，每个包的预算只有几十纳秒（1500 字节大包约 1.2 微秒）。二进制 Trie 的查找是 32 次分支（IPv4），而且前十几层几乎总是热的、留在 CPU 缓存里。压缩之后就更快了：LC-trie 与 Patricia 把稀疏的单链合并，让平均深度降到个位数，这就是 Linux 内核转发表的做法（顺便说：硬件路由器用 TCAM 在硅片里一次并行比较完所有前缀，是目前最快的方案，但它耗电、容量小，软件路径仍然依赖压缩 Trie）。

反过来说，这个任务**不适合用哈希表**：哈希只能回答「这个完整键在不在」，而最长前缀匹配要求「匹配且最长」。用哈希硬做，得从 32 位前缀到 0 位前缀逐个构造键去查，最多 32 次哈希——既没有比 32 次分支快，还要为每种前缀长度准备一份表，更新代价更大。

### 7.4 敏感词与多模式过滤

过滤敏感词的要求是「一篇文本里，把命中的关键词全部标出来」。逐个词跑单模式匹配（KMP 之类，见 [第 15 篇](15-strings.md)）是 O(K·n)，K 是词表大小——一万个词就要把文本扫一万遍。正确做法是把词表建成 Trie，再给它加上「失败指针」，一次扫描同时跟踪所有词：这就是第 8 节的 AC 自动机。Trie 在这里的作用是把 K 个模式的前缀合并成一张共享的有向图，扫描文本时走的是一条路径而不是 K 条。

### 7.5 词典序输出、T9、单词接龙、按前缀分组

- **词典序输出**：子节点按字符有序存放时，先序遍历就是字典序（`collect` 里的 `sorted` 就是为了这点）。哈希表要输出有序结果必须先 O(n log n) 排序，Trie 的输出本身有序，「按字典序分页列出关键词」因此非常便宜。
- **T9 输入法**：数字键 2~~9 各对应 3~~4 个字母。把按键序列变成「在 Trie 上同时走多个分支」：维护当前可能的节点集合，每按一个键就按该键对应的字母集扩展一步，集合非空说明还有候选词。Trie 在这里被当成 NFA 用，代价 O(L × 活跃节点数)；子节点用有序表加位图，还能把「这个键有没有分支」算成位运算。
- **单词接龙（词梯）**：每步改一个字母、途中必须都是词典里的词。做法是枚举「位置 × 26 个字母」的候选，用 Trie 判断「改完后是否还是某个词的前缀」——不是前缀这条路就走不通，直接剪掉。Trie 把每个候选的检查压到 O(L)，还顺带给出「这条路还有没有前途」的剪枝信息；哈希表只能判断整词存在性，剪不了枝。
- **按前缀分组**：每个节点天然就是一个分组（该前缀下的全部词），「按 URL 前缀聚合日志」、「按 IP 段统计流量」、「按部门前缀划分工号」都是同一件事；在节点上维护计数与聚合值，插入时沿路径更新，查询 O(L)。

## 8. AC 自动机：给 Trie 装上网状的回退边

### 8.1 失败指针的定义

AC 自动机（Aho-Corasick automaton）在 Trie 的每个节点上多加一条 `fail` 指针：

```text
fail(v) = v 代表的前缀的「最长的真后缀」，且这个后缀必须同时是
          某个模式的前缀（也就是说，它在 Trie 里对应一个节点）
```

直觉：走到节点 v，说明「文本刚读过的最后 |v| 个字符恰好是 v」。如果下一个字符 c 在 v 这里没有边，我们不希望从头再扫，而是想知道——**文本当前的后缀里，最长的、可能继续往下匹配的那一段是什么**。那就是 `fail(v)`。它把 Trie 里所有「互为后缀」的前缀串成了一张网，这张网让一次扫描可以同时跟踪所有模式。

### 8.2 构建与匹配

构建用 BFS，逐层算（第 12 篇的图遍历模板正好用得上）：

```text
BFS 构建 fail（root 的孩子先入队，它们的 fail 都指向 root）：
  while 队列非空:
      u = 出队
      for (c, v) in u 的孩子:
          f = fail[u]
          while f != root 且 f 没有字符 c 的边:  f = fail[f]
          fail[v] = f 的 c 孩子（若存在）否则 root；v 入队
```

匹配阶段就是「走 Trie，走不动就沿 fail 回退」：

```text
状态 s = root
for ch in 文本:
    while s != root 且 s 没有 ch 这条边:  s = fail[s]
    s = s 的孩子[ch]（若不存在则回到 root）
    if s 是模式的结尾:  报告命中
    t = fail[s]                 # 后缀里可能还藏着更短的模式
    while t != root:
        if t 是模式的结尾:  报告命中
        t = fail[t]
```

一个具体的例子（模式 `{he, she, his, hers}`，实测的 fail 指针）：

```text
h → root      he → root     her → root
s → root      sh → h        she → he      hi → root
his → s       hers → s

含义：she → he 说明「匹配到 she 时，文本末尾的 he 也是一个完整模式」。
文本 "ushers" 一次扫描的命中：she（位置 1）、he（位置 2）、hers（位置 2）。
```

### 8.3 代价

- **构建**：每个节点最多沿 fail 链回退，但总回退量是摊还 O(总模式长)。若在字符集很大时想避开「沿 fail 找边」的查找开销，可以把每个节点的转移补全成完整的转移表（把缺失的边直接指向 fail 链上的对应转移），构建代价变成 O(总模式长 × 字符集大小)，换来匹配阶段严格 O(文本长)。
- **匹配**：每个文本字符最多让状态深度 +1，沿 fail 回退会降低深度，所以回退的总次数不超过前进的次数，摊还 O(文本长)；报告命中的部分可以预处理成「输出链（output link）」，代价 O(命中数)。合计 **O(文本长 + 命中数)**——和模式有多少个、多长都无关。
- 内存：Trie 的内存 + 每节点一个 fail 指针。若模式集很大，同样要上第 6 节的压缩表示（`aho-corasick` crate 就用「连续 NFA + 稀疏/稠密混合」的编码来压这块）。

**谁在用**：敏感词与内容审核（词表上万，必须一次扫描）、IDS/IPS 的规则集匹配（Snort 类系统的多模式匹配器）、杀毒引擎的特征码扫描、生物信息学里在 DNA 序列上找一组模式、GNU grep 的 `-F`（固定字符串多模式，用 Commentz-Walter，即 AC 结合 Boyer-Moore 类跳跃）、Rust 的 `aho-corasick` crate（正则引擎的字面量预筛也走这里）。单模式的对应物是 KMP，它本质上就是「一个模式的 fail 函数」，可对照 [第 15 篇](15-strings.md)。

## 9. 邻近结构

| 结构         | 一句话定位                                                                          |
| ---------- | ------------------------------------------------------------------------------ |
| 后缀树        | 把一个文本的所有后缀建成压缩 Trie，O(文本长) 空间里解决「任意子串」问题（最长重复子串、最长公共子串、在线模式匹配），能力极强但构建复杂、常数大   |
| 后缀数组 + LCP | 把后缀排序后存下标，配 LCP 数组能覆盖后缀树的大部分用途，空间和实现都更友好，是子串问题的现代主流（[第 15 篇](15-strings.md)）   |
| FM-index   | BWT 变换 + 少量索引，在压紧的文本上直接做子串计数与定位，比后缀数组小一个数量级，基因组比对的主力（BWA、bowtie）               |
| Burst Trie | 节点装不下就「炸」成一个桶（排序数组或哈希表），用少量深节点换掉大量浅节点，减少指针追逐，对缓存和磁盘都友好（Burstsort 的基础）          |
| FST / DAWG | 把 Trie 里同构的子树合并成有向无环图，等价于对 Trie 做最小化，能同时支持前缀查询与压缩存储，Lucene/Elasticsearch 的词项字典 |

## 10. 陷阱

**10.1 按字节建树会切坏多字节字符。** 如果按 UTF-8 字节序列建树，一个汉字占 3 个字节（`"中".encode("utf-8")` 是 `b'\xe4\xb8\xad'`），路径上就会出现「某个字符的字节尾巴 + 下一个字符的字节头」这种跨越字符边界的组合。这在 `starts_with` 上会给出**假阳性**：查询前缀的最后一个字符被砍成半个，仍可能匹配到某个节点的路径（很多汉字共享头两个字节）。Python 的 `str` 是码点序列，直接按 `str` 迭代再配合 `dict` 子节点即可，别自己编码成 `bytes` 再喂给 Trie。

**10.2 先规范化再建树。** Unicode 里「同一个字符」可以有多种码点序列：`é` 既可以是预组合的 U+00E9，也可以是 `e` + U+0301 两个码点；全角字母、韩文的组合字母同理。视觉上一样的两个词在 Trie 里会走成两条路径，查不到对方。工程做法是先做规范化（`unicodedata.normalize("NFC", s)`），更严格的话再做大小写折叠（`casefold`）与全半角统一，把键变成规范形式后入库。

**10.3 内存估算失误：字符集大时的定长数组。** 256 路数组每节点约 2 KB，10 万个节点就是约 200 MB，而 Trie 里最不缺的就是节点。这类事故的特征是「本地小数据集测试正常，上线后 OOM」——因为节点数随词表线性增长。定长数组只在字符集固定且小时才是省内存的表示（DNA 的 4 个碱基、二进制 2 路）。

**10.4 把 Trie 当哈希表用。** 只看等值查找的话，Trie 是「L 次指针跳转 + L 次容器查找」对哈希表的「一次哈希 + 一两次访存」，常数更大、内存更多。用 Trie 的理由必须是前缀（补全、路由、多模式、分组），而不是「分层查找听起来更优雅」。

**10.5 Python 里每个节点一个 dict 的开销。** 空 dict 64 字节、装 1\~2 项 184 字节，加上节点对象本身，平均每节点接近 200 字节（4.4 节实测 194 字节）。几百万节点的词表就是几百 MB 起。真要拿 Python 做大规模前缀结构，优先考虑：`__slots__`（已用）、把子节点存成 `array`/`bytes` 的紧凑编码、或者用 C 扩展/第三方库（MARISA-trie、datrie、pyahocorasick）。

**10.6 递归收集/删除的深度。** 递归遍历子树的深度等于最长词长，普通词典没问题，但 URL、文件路径、DNA 序列、或用户可控的键可能非常长。Python 默认递归上限 1000，超了就 `RecursionError`；C 里就是栈溢出。凡是要遍历深度不确定的结构，优先用显式栈（3.1 节的 `collect` 用了递归是因为它的深度可控，`stats` 与 `delete` 则刻意用迭代）。

> [!CAUTION]
> 删除时要区分「只摘词尾」和「回收节点」。如果同一棵树同时被并发读，回溯回收会删掉读者正在走的节点；更稳妥的做法是只把 `is_end` 置为 `False`（逻辑删除），节点留给后续的整体重建或压缩过程回收。另外，删除后节点的计数、子树 TopK 缓存这类派生的聚合值，必须在同一次回溯里一起更新，否则会留下「前缀计数正确但词已不在」的脏数据。

**10.7 其它容易踩的小坑。**

- `starts_with("")` 是 `True`：空前缀是任何词的前缀。API 设计上要明确这个语义，否则前端「搜索框为空时返回空列表」的逻辑会被它坑到。
- `dict` 子节点的迭代顺序是**插入序**，不是字典序。要字典序输出必须显式排序，或者改用有序数组子节点、或给每个节点维护有序的键列表。
- 词频/权重的更新必须走完整路径：只写叶子节点的 `freq` 而不管祖先，预存的 TopK 缓存就会失真（7.1 节）。
- 大小写：`Cat` 与 `cat` 是两条路径。要么在插入前统一（`casefold`），要么在查询时枚举大小写组合（代价 2^L，只适合很短的词）。

## 11. 小结

- Trie 的核心不变式是「字符是边、路径是词」：从根到节点的路径就是它代表的前缀，节点的全部后代都以它开头。共享前缀由此免费，前缀查询退化成沿边行走。
- 节点必须同时有 `children` 和 `is_end`，因为「路径存在」与「路径是词」是两件事，`search` 与 `starts_with` 的区别全在这一个布尔值。
- 子节点表示决定性格：定长数组转移常数最小、内存与分支数无关（字符集大就爆）；哈希子节点省内存、支持任意字符集，但每次转移有哈希开销、每节点一个容器对象；有序数组/链表省内存且天然有序。成熟实现按分支数在几种表示间切换。
- 所有单点操作都是 O(L)，与词库规模无关，最坏情况不退化；哈希表的等值查找也是 O(L)（读完整键才算得出哈希），所以 Trie 赢在**前缀**与**增量查询**，不是赢在等值查找。
- 空间 ≈ 节点数 × 每节点开销。节点数 N ≤ 1 + 总字符数，最差情形是「短词多、前缀重叠少」，此时普通 Trie 的内存可以是哈希表的十倍以上（实测 94 MB 对 8.3 MB，10 万个短词）。
- 删除的要点是三个判断：走不通直接 `False`、`is_end` 为假也返回 `False`、回溯到「有孩子或是词尾」的节点就 `break`（共享意味着祖先必然也被共享）。
- 空间优化四条路：压缩 Trie（合并单链，节点数与词数同阶，路由表在用）、双数组（两个整型数组，无指针无对象头，词典在用）、TST（每节点 3 指针，与字符集无关）、位图 + rank（每节点几比特，离线词典在用）。
- AC 自动机 = Trie + 失败指针，把「K 个模式各扫一遍」变成「一次扫描报告全部命中」，代价 O(文本长 + 命中数)，是敏感词过滤与多模式匹配的标准答案。

## 12. 练习

**1.** 给 Trie 加一个 `count_prefix(p)`：返回以 p 为前缀的词数。给出遍历版与维护版两种实现，比较复杂度。

> [!TIP]
> 思路遍历版：走 p 到节点，再 DFS 数 `is_end` 的个数，代价 O(子树节点数)，最坏 O(总字符数)。维护版：每个节点加一个 `cnt` 字段，`insert` 时沿路径对每个节点 `cnt += 1`，`delete` 时沿路径 `cnt -= 1`，查询只走 O(L)。维护版把代价从读侧移到写侧，且要注意「同一个词重复插入」必须不重复计数（先判断 `is_end`），删除不存在的词不能减计数。

**2.** 把 `{a, ab, abc}` 依次插入一棵空 Trie，画出节点与 `is_end`，然后删除 `ab`，说明哪些节点被回收、哪些必须留下。

> [!TIP]
> 思路节点链是 root-a-b-c，`is_end` 在 a、b、c 三个节点上（三个词都是词）。删除 `ab` 后：b 的 `is_end` 置 `False`，但 b 有孩子 c，所以 b 不能删；回溯到 a 时因为 a 本身是词尾（`a` 还在），也停止。结果节点一个不少，只是 b 不再是词尾。再删 `a` 时，a 的 `is_end` 为假、有孩子 b，同样不能删。只有当 `abc` 也被删掉后，c 才能被回收，继而 b、a 依次被回收——**回收的粒度是一条从叶子向上的连续单链，遇到任何共享点就停**。

**3.** 为什么「按 UTF-8 字节建 Trie」会让 `starts_with` 出现假阳性？举一个具体的字节序列说明。

> [!TIP]
> 思路多字节字符的编码前缀（首字节的高位模式）与后续字节（`10xxxxxx`）是不同集合，按码点查询时切分位置总在字符边界上，但按字节查询时前缀可以被切在字符中间：例如查询「中」的一半字节 `b'\xe4\xb8'` 在字节 Trie 里是一条合法路径，它匹配到的是所有以 `\xe4\xb8` 开头的字符（很多汉字共享头两个字节），于是一个不存在的、被截断的「前缀」被判为存在。修法是按码点建树（Python 的 `str` 天然如此），并在入库前做 `unicodedata.normalize("NFC", s)`。

**4.** 一个系统要支持「1 亿条短 URL 的精确查找」和「按路径前缀的 10 万次每秒的补全」，怎么设计结构？说明每一层为什么这么选。

> [!TIP]
> 思路精确查找用哈希表（1 亿条约几 GB，等值查找常数最小，Trie 在这个规模上内存会失控）；补全另建一棵**压缩树 + 每节点预存 TopK**，规模只有「不同前缀」的数量级，比全量 Trie 小得多。写入时两处同步（或由离线任务重建前缀索引，接受秒级延迟）。若前缀查询的 QPS 极高，再在压缩树前面加一层热点前缀的 LRU 缓存。思路是「按操作分家」：等值走哈希、前缀走 Trie/FST，而不是指望一个结构两样都强。

**5.** 用哈希表模拟前缀查询的老办法是「把每个词的所有前缀也插进字典」（jieba 的 `PrefixDict` 就是这么做的）。对比它和 Trie 的空间与时间。

> [!TIP]
> 思路空间：前缀字典要存 C 个独立的字符串键（C 是总字符数），Python 里一个 8 字符的 `str` 就要 49 字节（CPython 3.13 实测），10⁶ 个前缀就是几十 MB 的纯字符串对象，且**共享前缀被复制成了互不相干的键**；Trie 只存节点，公共前缀共享。时间：哈希查找是「算哈希 + 探测」，判定「p 是不是某个词的前缀」两者都是 O(L)，但哈希方案还要为每个前缀做一次插入与一次哈希计算，构建成本更高。结论：前缀字典的优点是复用现成的哈希表和零结构设计成本，缺点是空间随字符总量线性膨胀，规模一大就必须换成 Trie 家族的表示（6.2 的双数组词库是这条路的终点）。

**6.** 用 Trie 优化「词梯」问题（每次改一个字母，每步都必须是词典里的词，求最短变换序列）：说明 Trie 在 BFS 的每一步里提供了什么哈希表给不了的信息。

> [!TIP]
> 思路BFS 时对当前词的每个位置尝试 26 个字母得到候选词，需要判断「候选词是否存在」——哈希表能判断整词，但要走到目标词还得逐层展开，候选数量是 26×L×（已访问层数）。Trie 多给了一条信息：**前缀存在性**。判断「改到第 i 位之后的前缀是否还在树里」是 O(i)，不是前缀就可以立刻放弃这条分支；此外对「只允许前缀扩展」的变体（每次只能在末尾加字符）Trie 直接给出了 O(L) 的可扩展性判断。本质区别是：哈希表只能回答「这个完整键在不在」，Trie 能回答「继续往下还有没有可能」。

**7.** 给一个 4 位地址的迷你路由表：`00** -> A`、`10** -> B`、`101* -> C`、`1011 -> D`。分别写出 `1011`、`1000`、`0011`、`1111` 的最长前缀匹配结果，并说明为什么不能改用哈希表。

> [!TIP]
> 思路`1011` → 沿路命中 B、C、D，最深的是 D（前缀 1011）。`1000` → 命中 B（10\*\*），再往下 bit2 = 0 时树里没有 101\* 分支，停在 B。`0011` → 只命中 A。`1111` → 第一位是 1，而表里所有前缀都以 0 或 10 或 101 开头，「1\*」没有路由，只能落在默认路由（若表里有 `0.0.0.0/0` 就是它，否则无路由丢包）。哈希表不行，因为最长前缀匹配要求「匹配且最长」，哈希只能判等值；硬用哈希要从最长前缀长度往下逐个构造键去查，每个包最多 32 次（IPv6 是 128 次）哈希查找，比 32 次分支更慢，还要为每种前缀长度各维护一份表。

**8.** 要为 10⁶ 条平均长度 8 的短词做「精确查找 + 前缀补全」，实测普通 Trie 要几百 MB。给出三种把它压到 100 MB 以内的方案，并说明各自的代价。

> [!TIP]
> 思路①压缩 Trie（radix/FST）：节点数与词数同阶，能砍掉大量单链节点，代价是转移要做子串比较、插入删除要分裂合并。②位图 + rank（LOUDS/双数组）：每个节点压到几比特到几个字节，代价是只读、构建复杂，适合离线词库。③换语言/换容器：不用「每节点一个 dict」，改用定长数组（若字符集真的是 26 个小写字母，104\~208 字节/节点在 C 里可接受）或第三方库（MARISA-trie 号称每词几字节），代价是失去任意字符集/动态更新的灵活性。共同思路是：先算出「节点数 × 每节点开销」，再去压其中较大的那个因子。
