栈和队列都限制访问位置，但限制的方向相反：栈只允许在一端进出，于是它记住的是「最近的过去」；队列要求一端进、另一端出，于是它承诺的是「到达的先后」。这个承诺看起来比栈更弱，实现代价却更大——栈用数组实现天然完美（入栈出栈都在末尾），而队列的每次出队都发生在头部，正好是数组最不擅长的一端。队列实现史上的所有花样，都是围绕「如何在头部出队还能保持 O(1)」展开的。

一旦这个问题被解决，队列就成了计算机里最普遍的协调装置：BFS 靠它按层推进，操作系统靠它调度进程，消息中间件靠它解耦生产者与消费者，无锁并发里它几乎是唯一被普遍信任的共享结构。

## 1. FIFO 的语义价值

### 1.1 先来先服务：顺序本身就是承诺

栈的顺序由「最近」决定，队列的顺序由「最早」决定。这个差别在单线程算法里只是遍历顺序不同，在多方协作的场合却是**公平性契约**：打印任务按提交顺序输出、HTTP 请求按到达顺序处理、数据库的 WAL 日志按写入顺序落盘、消息按生产顺序投递。一旦顺序被打破，暴露出来的往往不是性能问题而是正确性问题——消费者会读到还没创建的对象，或者重放日志时状态机走到一个不存在的中间态。

队列之所以能承担这个契约，是因为它把「顺序」变成了结构上的必然：元素进入的顺序唯一决定离开的顺序，不需要额外的排序、时间戳或比较函数——这正是它和优先队列的根本区别（第 9.5 节）。

### 1.2 天然按层推进：BFS 为什么必须用队列

队列最有价值的性质不是「公平」，而是**按距离递增地推进**。想象水面上扩散的波纹：先被访问的节点一定不比后被访问的更远。用队列做 BFS 时，出队顺序天然是按层（到源点的距离）非递减的，这一点不需要任何额外判断：

```python
from collections import deque

def level_order(root):
    """层序遍历：出队顺序就是「按层、从左到右」"""
    out, q = [], deque([root] if root else [])
    while q:
        node = q.popleft()
        out.append(node.val)          # 队列保证：此刻出队的节点，层号不会变小
        for child in (node.left, node.right):
            if child:
                q.append(child)
    return out
```

把 `deque` 换成 `list` 当栈用，出队顺序立刻从按层变成深度优先——同一个遍历骨架，换个容器就换了一个算法。这正是队列在算法里的地位：**它是「按层推进」这个语义的载体**，而不只是一个先进先出的容器。细节见 [第 07 篇](07-binary-tree-traversal.md) 与 [第 12 篇](12-graph-representation-traversal.md)。

> [!NOTE]
> BFS 的「层序正确」建立在每一步的代价相同之上。如果边的权重不同（哪怕只是 0 和 1 两种），普通的 FIFO 队列就不够了——但 0-1 权重的特例会允许我们只把队列升级成双端队列（第 7.1 节），这是队列家族最漂亮的用法之一。

### 1.3 队列在系统里的四种化身

| 场景 | 队列里装什么 | 打破顺序的后果 |
| --- | --- | --- |
| 任务调度 | 待运行的进程/协程/线程 | 饥饿：早到的任务永远轮不上 |
| 缓冲区 | 尚未处理的字节/事件/请求 | 数据错乱（TCP 重排错、音频爆音） |
| 消息队列 | 待消费的消息 | 状态机乱序执行，重放失败 |
| 流水线 | 各级之间传递的中间结果 | 级间速率差被放大成抖动 |

这四类场景的共同点是**速率不匹配**：生产速度和处理速度不可能恒定相等，队列是把瞬间的差值存起来的那块空间。这也解释了为什么队列在工程里总与两个词同时出现——容量（存多少）与背压（存不下怎么办），第 8、9 节会分别展开。

## 2. 数组实现：从假溢出到循环队列

### 2.1 朴素数组队列与「假溢出」

最直接的想法：数组加一个尾下标，入队时 `tail++`，元素全部堆在数组左侧，出队端固定在 0 号位。问题立刻暴露：如果出队时把后面的元素整体前移，出队就是 O(n)，队列退化成 `list.pop(0)`；如果只是把 head 往后挪，那么数组的前半部分会永久废弃——head 和 tail 一路向右，总有一天 tail 撞到数组末尾。

```text
容量 8、已出队 3 个元素的朴素数组队列：
下标:   0      1      2      3      4      5      6      7
      +------+------+------+------+------+------+------+------+
      |  --  |  --  |  --  |  D   |  E   |  F   |  G   |  --  |
      +------+------+------+------+------+------+------+------+
                              ^                             ^
                           head=3                        tail=7
队列里只有 4 个元素，数组却已经「用到头」了：下一次入队写进 slot[7]，
再下一次 tail 就是 8 —— 越界。可下标 0、1、2 三格从头到尾没人用过。
```

这就是**假溢出（false overflow）**：判定「满了」的依据是下标到达边界，而不是元素真的占满了空间。它浪费的是空间，更糟的是**浪费量随运行时间增长**——一个长期运行的队列会把整个数组耗光，被迫扩容或搬迁，而搬迁正是我们想避免的 O(n) 操作。

### 2.2 循环队列：让下标回绕

治本办法是让下标到达末尾后绕回开头，把数组逻辑上接成一个环：

```text
   数组首尾在逻辑上相接（下标回绕）：
   +------+------+------+------+------+------+------+------+
   |  I   |  J   |  --  |  D   |  E   |  F   |  G   |  H   |
   +------+------+------+------+------+------+------+------+
   下标:   0      1      2      3      4      5      6      7
   head=3（队首是 D），tail=2（下一个可写槽，此刻正好空着）
逻辑顺序是 D E F G H I J：从 head 出发沿环走，绕过数组末尾回到 0、1。
槽位 2 空着 —— 它正是用来区分「空」和「满」的那一格（第 3 节）。
```

关键动作只有一行：`tail = (tail + 1) % n`（`head` 同理）。取模把「越界」变成了「绕回」，从此不存在被永久浪费的前缀。代价是每次访问都要一次取模运算，以及在容量固定时**不能使用「扩容」来缓解满**——循环队列的容量是它的规格，不是它的建议。

### 2.3 完整可编译的 C 实现

下面这份实现用「留一个空位」的约定区分空与满，`rq_new(3)` 表示最多能放 3 个元素（实际申请 4 个槽位）。

```c
/* 循环队列：数组 + head/tail 双下标，留一个空槽区分「空」与「满」
 * 编译运行：gcc -std=c11 -Wall -Wextra -o rq rq.c && ./rq */
#include <stdbool.h>
#include <stdio.h>
#include <stdlib.h>

typedef struct {
    int   *slots;    /* 槽位数组 */
    size_t n;        /* 槽位总数 = 可存元素数 + 1 */
    size_t head;     /* 队首下标：下一个出队的位置 */
    size_t tail;     /* 队尾下标：下一个入队的位置 */
} RingQueue;

RingQueue *rq_new(size_t want) {
    RingQueue *q = malloc(sizeof *q);
    if (!q) return NULL;
    q->n = want + 1;                     /* 多要一格，专门用来区分空与满 */
    q->slots = malloc(q->n * sizeof(int));
    if (!q->slots) { free(q); return NULL; }
    q->head = q->tail = 0;
    return q;
}

void rq_free(RingQueue *q) { if (q) { free(q->slots); free(q); } }

/* head/tail 都落在 [0, n) 内，先加 n 再取模，避免 size_t 下溢 */
size_t rq_size(const RingQueue *q) { return (q->tail - q->head + q->n) % q->n; }
bool rq_empty(const RingQueue *q) { return q->head == q->tail; }
bool rq_full(const RingQueue *q)  { return (q->tail + 1) % q->n == q->head; }

/* 返回 0 成功；-1 表示队满（调用方决定重试、阻塞还是覆盖最旧元素） */
int rq_push(RingQueue *q, int v) {
    if (rq_full(q)) return -1;
    q->slots[q->tail] = v;
    q->tail = (q->tail + 1) % q->n;      /* 到末尾就绕回 0 */
    return 0;
}

/* 返回 0 成功；-1 表示队空 */
int rq_pop(RingQueue *q, int *out) {
    if (rq_empty(q)) return -1;
    *out = q->slots[q->head];
    q->head = (q->head + 1) % q->n;
    return 0;
}

#define CHECK(cond, msg) do { if (!(cond)) { puts(msg); return 1; } } while (0)

int main(void) {
    int v;
    /* 1. 装满、判满、FIFO 顺序 */
    RingQueue *q = rq_new(3);                        /* 只能装 3 个元素 */
    CHECK(q, "分配失败");
    CHECK(rq_push(q, 1) == 0 && rq_push(q, 2) == 0 && rq_push(q, 3) == 0, "入队失败");
    CHECK(rq_push(q, 4) == -1, "第 4 个元素不该塞得进去");
    CHECK(rq_size(q) == 3 && rq_full(q), "判满错误");
    CHECK(rq_pop(q, &v) == 0 && v == 1, "FIFO 顺序错误（应为 1）");
    CHECK(rq_pop(q, &v) == 0 && v == 2, "FIFO 顺序错误（应为 2）");
    CHECK(rq_size(q) == 1, "出队后 size 错误");

    /* 2. 环绕：此刻存着 3（下标 2）、tail 停在 3
     * 朴素数组队列会在这里报「队满」（tail 到了数组末尾），而实际空闲两格 */
    CHECK(rq_push(q, 4) == 0 && rq_push(q, 5) == 0, "环绕后入队失败——朴素队列正是在这里假溢出");
    CHECK(rq_push(q, 6) == -1, "6 个元素塞进了 3 格队列");
    int expect[3] = {3, 4, 5};         /* 元素实际在 2、3、0 号槽，环序才是真的顺序 */
    for (int i = 0; i < 3; i++) {
        CHECK(rq_pop(q, &v) == 0 && v == expect[i], "环绕后 FIFO 顺序错误");
    }
    CHECK(rq_pop(q, &v) == -1 && rq_empty(q), "空队列不该出得了队");

    /* 3. 容量 1：槽位 2 个可存 1 个；容量 0：槽位 1 个，恒满但不越界 */
    RingQueue *one = rq_new(1), *zero = rq_new(0);
    CHECK(one && zero, "分配失败");
    CHECK(rq_push(one, 42) == 0 && rq_push(one, 43) == -1, "容量 1 的边界处理错误");
    CHECK(rq_pop(one, &v) == 0 && v == 42 && rq_empty(one), "容量 1 出队后状态错误");
    CHECK(rq_push(zero, 1) == -1 && rq_pop(zero, &v) == -1 && rq_size(zero) == 0,
          "容量 0 的边界处理错误");

    rq_free(zero); rq_free(one); rq_free(q);
    puts("all ring-queue tests passed");
    return 0;
}
```

四个必须理解的设计点：

- **`rq_size` 里的加法顺序**：先 `tail - head + n` 再取模。`size_t` 是无符号的，`tail - head` 在 head 追上 tail 时会下溢成一个巨大的数，加 `n` 再取模正好把它拉回正常范围；写成 `(tail - head) % n` 就错了（先下溢，取模救不回来）。
- **`rq_push` 不覆盖、不阻塞**，满了就返回 -1 把选择权交给调用方。库代码不该替你决定丢掉谁——日志场景想丢最旧的，任务场景想阻塞，两者不能共用一种策略。
- **两个下标都在 [0, n) 内**，所以 `rq_size` 恒落在 [0, n-1]，加上「留一格」的约定，`size == n-1` 就等于满；**容量为 0 不是崩溃而是恒满**（`n = 1` 时 `(0 + 1) % 1 == head` 恒成立，`rq_push` 永远返回 -1），边界值不特判也能安全退化。

### 2.4 容量取 2 的幂：用位与代替取模

取模是除法，在多数 CPU 上要 20~40 个周期，而环形队列的每次入队出队都要做两次。如果 n 是 2 的幂，`i % n` 等价于 `i & (n - 1)`，一条指令搞定：

```c
#define RING_CAP 1024                      /* 2 的幂 */
#define MASK(i)  ((i) & (RING_CAP - 1))    /* 等价于 (i) % RING_CAP，天然处理回绕 */
q->tail = MASK(q->tail + 1);               /* 连「+1」都不必显式取模 */
```

代价是容量被锁死为 2 的幂（初始化时把 `want` 向上取整），浪费通常在 30% 以内，换来的是热路径上一次除法——内存紧张的嵌入式场景要权衡，桌面与服务端几乎总是划算。

> [!WARNING]
> `MASK(i)` 只对**非负**的 i 成立。C 语言里 `-1 % 1024 == -1`（向零取整），`-1 & 1023 == 1023`，两者完全不同。如果代码里出现「回退一步」的下标运算（`head - 1`、`tail - k`），要么保证下标是 `size_t`／`unsigned`（回绕是有定义的），要么显式写成 `((i % n) + n) % n`。这是循环队列最常见的越界来源，尤其在下标类型从 `size_t` 改成 `int` 之后。

## 3. 判空与判满：三种约定

循环队列的核心难点不是回绕，而是**当 `head == tail` 时，队列到底是空还是满**。两种状态在数值上完全一样，必须靠额外的约定区分：

| 约定 | 判空 | 判满 | n 个槽位可存 | 代价 |
| --- | --- | --- | --- | --- |
| 留一个空位 | `head == tail` | `(tail + 1) % n == head` | n − 1 | 浪费一格；但状态完全由两个下标决定，没有冗余 |
| size 计数器 | `size == 0` | `size == n` | n | 多一个字段，每次进出都要维护，并发下成为第三个共享变量 |
| full 标志位 | `head == tail && !full` | `full` | n | 状态分散在两处，出队时必须记得清标志，否则空队列被判成满 |

**留一格成为最常见选择**，理由不是省一个字段，而是它把「队列状态」完全编码在 head 与 tail 的相对位置上——**状态没有第二份拷贝，也就不可能不同步**。约定三最典型的 bug 就是这个：出队到 `head == tail` 时忘了把 `full` 清掉，队列从此永远显示「满」，而这类 bug 只在「恰好出空」的时机出现，测试很容易漏过。

第二层理由是并发：无锁队列里 head 与 tail 各由一个线程独占写（生产者写 head、消费者写 tail），这是它能无锁的前提；而 size 计数器**两个线程都要写**，立刻需要原子自增或额外的同步，还会让同一个缓存行在两个核之间来回弹（伪共享）——约定一让每个共享变量只有一个写者，这是它在系统编程里胜出的决定性原因。第三层理由是容量本来就要取整。环形缓冲的容量通常按 2 的幂向上取整（第 2.4 节），多要一格的浪费往往在取整时就吸收掉了：想要 1000 个元素的容量，实际申请 1024 个槽位，可存 1023 个，浪费 2.4%。

代价也确实存在：**当 n 很小时，浪费比例会变得刺眼**。每块只放 8 个元素的分块队列若留一格，利用率就只有 87.5%，此时该选约定二。下面是用 size 计数器的 Python 版本，`RingQueue(3)` 真的能装 3 个元素：

```python
class RingQueue:
    """循环队列：head/tail 取模回绕，另加 size 计数器区分空与满。
    与「留一个空位」相比，n 个槽位可以装 n 个元素。"""

    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("容量必须为正")
        self._buf = [None] * capacity
        self._cap = capacity
        self._head = 0      # 出队位置
        self._tail = 0      # 入队位置
        self._size = 0

    def push(self, v):
        if self._size == self._cap:
            raise OverflowError("queue full")
        self._buf[self._tail] = v
        self._tail = (self._tail + 1) % self._cap
        self._size += 1

    def pop(self):
        if self._size == 0:
            raise IndexError("queue empty")
        v = self._buf[self._head]
        self._buf[self._head] = None        # 断开引用，避免对象被队列长期持有
        self._head = (self._head + 1) % self._cap
        self._size -= 1
        return v

    def __len__(self):
        return self._size


q = RingQueue(3)                 # 3 个槽位真的装 3 个元素（留一格的方案只能装 2 个）
q.push(1); q.push(2); q.push(3)
assert len(q) == 3 and q.pop() == 1 and len(q) == 2
```

> [!TIP]
> 不确定该选哪种约定时，问一句「这个队列的容量会不会小到 8 或更少」。答案是「不会」就用留一格（省心、天然适合无锁）；答案是「会」就用 size 计数器（省空间）。`full` 标志位这一派在教科书里常见，在工业代码里几乎见不到——它的唯一优势是省一个整数字段，而代价是一个必须人工维护的状态位。

## 4. 链式队列与双端队列

### 4.1 链式队列：head/tail 双指针

链表没有「假溢出」问题：每个节点独立分配，出队就是把 head 指向下一个节点。代价是每个元素一次堆分配、一次指针解引用，以及比数组差得多的缓存局部性（见 [第 03 篇](03-linked-list.md)）。

```python
class Node:
    def __init__(self, val):
        self.val = val
        self.next = None


class LinkedQueue:
    def __init__(self):
        self.head = None          # 出队端
        self.tail = None          # 入队端

    def push(self, v):
        node = Node(v)
        if self.tail is None:             # 空队列：两个指针同时指向新节点
            self.head = self.tail = node
        else:
            self.tail.next = node
            self.tail = node

    def pop(self):
        if self.head is None:
            raise IndexError("pop from empty queue")
        node = self.head
        self.head = node.next
        node.next = None                  # 断链，帮助 GC 回收
        if self.head is None:             # 最后一个元素出队后，tail 必须一起置空
            self.tail = None
        return node.val
```

链式队列的坑几乎全部集中在 tail 的维护上，规则只有三条，但每条都能写出真实 bug：

1. **空队列入队时，head 与 tail 必须同时指向新节点**。只更新 tail，队列就丢了头部，之后 `pop` 直接报空。
2. **出队到空时，tail 必须置空**。否则 tail 仍然指着那个已经被释放的节点；在 Python 里是延迟释放（对象被 tail 一直引用，内存泄漏），在 C 里就是 use-after-free——下一次入队会往一块已释放的内存里写 `next` 指针。
3. **只用 head 判断空、用 tail 判断入队位置**，不要让两者承担相同的职责。判断空必须用 head（tail 可能悬垂，见第 2 条）。

> [!CAUTION]
> 在 C 里实现链式队列时，「出队最后一个元素后把 tail 置 NULL」是必须的，而且它常常被写成 `if (q->head == NULL) q->tail = NULL;` 放在错误的位置（比如放在 `free(node)` 之后，此时读 head 是安全的，但若先 free 了 head 再读就完了）。安全顺序是：先读旧值 `old = q->head`，再 `q->head = old->next`，再判断 `q->head == NULL` 决定是否清 tail，最后 `free(old)`。

### 4.2 双端队列：两端都能进出的代价

双端队列（deque, double-ended queue）同时具备栈与队列的能力：两端都能 O(1) 推入和弹出。它不是「新结构」，而是**把两种受限访问合并**的产物——栈是只允许一端操作的双端队列，队列是只允许一端进、另一端出的双端队列：栈顶就是它的左端，队首队尾分别是它的两端。代价不在时间（两端仍是 O(1)），而在实现复杂度与访问模式：双端队列必须同时维护左右两个入口，任何「中间访问」都变成两头都不靠的慢路径。用数组实现时通常用环形缓冲；用链表实现时每个节点多一个反向指针（58 字节的 Python 对象、24 字节的 C 节点），而且双向指针意味着更新时要同步两处。

| 实现方式 | push/pop 两端 | 中间访问 | 空间开销 | 典型场景 |
| --- | --- | --- | --- | --- |
| 环形缓冲数组 | O(1) 摊还（无扩容时严格 O(1)） | O(1) 下标 | 无额外指针 | 定长缓冲、SPSC（第 8 节） |
| 分块双向链表 | O(1) | O(n/块大小) | 每块少量指针 | Python `deque`（第 5 节） |
| 双向链表 | O(1) | O(n) | 每元素两个指针 | 频繁中间增删（[第 03 篇](03-linked-list.md)） |

### 4.3 四种实现的选型

| 实现 | 何时选它 | 主要代价 |
| --- | --- | --- |
| 数组 + head 指针 | 几乎不要选（除非元素数极少、出队后会整体重建） | 假溢出，空间随运行时间泄漏 |
| 循环队列 | 容量可预估、要求零分配与稳定延迟 | 容量固定，满了必须由调用方决策 |
| 链式队列 | 元素大小差异大、数量无法预估、需要严格 O(1) 单次延迟 | 每次分配、缓存不友好 |
| 双端队列 | 两端都要进出（0-1 BFS、滑动窗口、工作窃取） | 实现复杂，中间访问慢 |

## 5. Python 的 collections.deque

### 5.1 分块双向链表：内部长什么样

CPython 的 `deque` 不是普通的链表，而是**双向链表 + 每节点一个定长数组**：每个块（block）容纳 64 个指针（`BLOCKLEN`），块之间用双向指针串起来。

```text
      leftblock                          rightblock
          |                                  |
          v                                  v
     +---------+      +---------+      +---------+
     |  块 0   | <--> |  块 1   | <--> |  块 2   |
     +---------+      +---------+      +---------+
       ^                                        ^
   appendleft / popleft 在这一端            append / pop 在这一端
   块内是连续内存（64 个指针），块与块之间才是指针跳转
```

这个设计同时解决了两个问题：

- **两端 O(1)**：`append`/`pop` 只动右端块的指针，`appendleft`/`popleft` 只动左端块。块满了就分配新块，块空了就释放——不需要搬移任何已有元素，也就没有动态数组那种「扩容时整体拷贝」的长尾延迟。
- **缓存友好**：在链表里移动 64 个元素是线性遍历连续内存，不是 64 次随机访存。相比每个元素一个节点的普通链表，访存次数降低到 1/64 量级。

### 5.2 为什么不能用 list 当队列

`list.pop(0)` 与 `list.insert(0, x)` 的代价来自数组的物理布局：头部腾出或填上一个位置，后面所有元素都必须整体移动。CPython 用 `memmove` 做这件事，每次约 30 字节一个元素（8 字节指针加上引用计数维护开销），所以单次代价是 O(n)，在被元素数除之前无法忽略。

```python
import time
from collections import deque

def drain(n, use_deque):
    d = deque(range(n)) if use_deque else list(range(n))
    while d:
        d.popleft() if use_deque else d.pop(0)   # 前者 O(1)，后者 O(n)

def best(n, use_deque):
    t0 = time.perf_counter()
    drain(n, use_deque)
    return time.perf_counter() - t0

for n in (10000, 20000, 40000):
    tl, td = best(n, False), best(n, True)
    print(f"n={n:6d}  list.pop(0): {tl * 1e3:7.1f} ms   "
          f"deque.popleft: {td * 1e3:5.2f} ms   比值 {tl / td:5.1f}x")
```

输出（Python 3.13，本机单次实测；绝对数字随机器与负载浮动，看趋势即可）：

```text
n= 10000  list.pop(0):     5.2 ms   deque.popleft:  0.44 ms   比值  11.7x
n= 20000  list.pop(0):    19.2 ms   deque.popleft:  1.12 ms   比值  17.2x
n= 40000  list.pop(0):    81.4 ms   deque.popleft:  2.21 ms   比值  36.8x
```

真正要看的是趋势：**n 翻倍时 list 的耗时翻两番**（5.2 → 19.2 → 81.4），这是 O(n²) 的签名；deque 只线性增长（0.44 → 1.12 → 2.21），因为每次 `popleft` 都是常数工作量。差距随规模无上限地拉大——用 list 当队列的代码在测试数据上跑得动，在生产数据上会把整个请求拖垮。

### 5.3 maxlen：环形缓冲语义

`deque(maxlen=N)` 直接提供第 2 节那种环形缓冲的语义：满了以后追加新元素会自动从另一端丢弃旧元素，永不扩容、永不阻塞。

```python
from collections import deque

# 最近 5 条日志：满了自动丢最旧的
recent = deque(maxlen=5)
for i in range(8):
    recent.append(i)
assert list(recent) == [3, 4, 5, 6, 7]

# 滑动窗口平均值：maxlen 自动丢弃 + 增量维护窗口和（避免每步重新 sum，O(nk) 变 O(n)）
def moving_average(stream, k):
    window, total = deque(maxlen=k), 0.0
    for x in stream:
        if len(window) == k:        # 这一格马上会被 append 挤掉
            total -= window[0]
        window.append(x)
        total += x
        if len(window) == k:
            yield total / k

assert [round(v, 6) for v in moving_average([1, 2, 3, 4, 5], 3)] == [2.0, 3.0, 4.0]
```

几个必须记住的细节：

- **自动丢弃的方向与操作端相反**：`append` 满时从左侧丢，`appendleft` 满时从右侧丢，`extend` 同 `append`，`extendleft` 同 `appendleft`。**`maxlen` 是只读属性**，创建后不能改；`deque(maxlen=0)` 是一个合法的「黑洞」，所有写入立即被丢弃。
- **`window[0]` 从近端取是 O(1)**，所以增量维护窗口和的版本是严格 O(n)；如果每步都写 `sum(window)`，复杂度会退化成 O(nk)——这是个很容易忽略的隐藏因子。

### 5.4 复杂度速查

| 操作 | 复杂度 | 说明 |
| --- | --- | --- |
| `append` / `pop` / `appendleft` / `popleft` | O(1) | 只动两端块的指针 |
| `d[0]` / `d[-1]` | O(1) | 两端的下标访问是特例 |
| `d[i]`（中间） | O(min(i, n−i)/64) | 从较近的一端逐块走，块大小 64：**不是严格 O(1)** |
| `d[i] = x` / `del d[i]` / `d.insert(i, x)` | O(n) | 中间写、删、插都要走块链 |
| `x in d` / `d.index(x)` / `d.remove(x)` | O(n) | 线性扫描 |
| `d.rotate(k)` / `len(d)` | O(k) / O(1) | 逐个搬移 / 单独维护计数 |

> [!WARNING]
> `deque` 的随机访问是**近似** O(1) 而不是 O(1)。`d[i]` 的代价是块链上的跳跃次数，约 `n/128` 次指针解引用；一百万个元素时是几千次跳转。**把 deque 当中序数组来用（二分查找、随机采样）是错误的方向**，那是有序数组与哈希表的地盘。deque 的主场始终是两端。

## 6. 单调队列：滑动窗口最大值

### 6.1 问题与直觉

给定数组与窗口大小 k，求每个窗口的最大值。暴力法每个窗口扫 k 个元素，O(nk)；用堆维护是 O(n log k)。单调队列给出 O(n)。

思路是维护一个「有潜力成为最大值」的候选集合。当新元素 `x` 在下标 `i` 到来时，把队尾所有**值不大于 x** 的元素全部丢掉，理由是：

> 设被丢掉的元素下标为 j（j < i）。只要 j 还在窗口内，i 也一定在窗口内——窗口是右端点固定在 i 的左闭区间 `[i−k+1, i]`，越靠右的下标越晚过期。而 `nums[i] >= nums[j]`，所以任何包含 j 的窗口里，i 都是不比 j 差的候选。j 从此再无机会成为答案。

这就是「压制」：**更靠后且不更小的元素，完全支配更靠前且更小的元素**。丢掉 j 不是近似，是逻辑等价——它对应的所有可能答案都被 i 覆盖了。

处理完压制，队列剩下的元素满足两条不变式：**下标严格递增**（新元素永远从尾部进）且**值严格递减**（不满足的都被压制弹出）。两条合起来给出关键结论：**队首 v1 就是当前窗口的最大值**（值最大），而队首也会最早过期（下标最小），所以从头部弹出过期元素正好合法。两端各管一件事——尾部管压制，头部管过期——这就是这里必须用双端队列而不是普通队列的原因。

```text
nums = [1, 3, -1, -3, 5], k = 3     （队列里实际存的是下标，这里画成值便于看）
0: x=1  → [1]                     窗口未满
1: x=3  → 1 被压制弹出 → [3]       窗口未满
2: x=-1 → [3, -1]                 窗口 [1,3,-1]，最大值 = 队首 3
3: x=-3 → [3, -1, -3]             3 对应的下标 1 仍在窗口内，最大值 = 3
4: x=5  → 弹出 -3、-1、3 → [5]     队首即 5，最大值 = 5
```

### 6.2 完整实现

```python
from collections import deque

def max_sliding_window(nums, k):
    """返回每个长度为 k 的窗口的最大值，共 n-k+1 个。O(n) 时间，O(k) 空间。"""
    if k <= 0:
        raise ValueError("k 必须为正")
    if k > len(nums):
        return []
    dq = deque()                 # 存下标，对应值严格递减；队首是当前窗口最大值
    out = []
    for i, x in enumerate(nums):
        while dq and nums[dq[-1]] <= x:
            dq.pop()             # 队尾被 x 压制：更靠后且更大，永远不再有机会
        dq.append(i)
        while dq[0] <= i - k:
            dq.popleft()         # 队首滑出窗口，过期失效
        if i >= k - 1:
            out.append(nums[dq[0]])
    return out
```

三处细节决定了正确性：

- **比较用 `<=` 而不是 `<`**：丢掉相等的旧值，队列里保留的是「值相同但下标更大」的那个。对「最大值」这个问题两者等价，但如果还要知道最大值的**首次出现位置**，就必须保留旧值（用 `<`）；如果要知道**最后一次出现位置**，就用 `<=`。写之前先明确要哪一个。
- **过期判断放在入队之后**：新元素入队时可能把队首一起压制掉（k = 1 时就是这样），此时再判断过期是正确的顺序；反过来会访问到空队列。
- **判断过期用 `<= i - k`**：下标 `i - k` 已经不在窗口 `[i−k+1, i]` 里了。写成 `< i - k` 会多留一个过期元素在队列里，输出错误。

### 6.3 摊还 O(n) 的论证

每个下标在执行过程中**恰好被入队一次**，而每次 `d.pop()` 或 `d.popleft()` 都会永久删掉一个曾经入队过的下标、不会再回来。所以 n 次入队之外，两种弹出加起来最多 n 次——总操作数不超过 2n，摊还到每次操作是 O(1)，总体 O(n)。没有任何概率假设，这是对**任意输入序列**都成立的上界。空间是 O(k)：队列里最多同时存在 k 个下标（更早的都被过期检查弹掉了）。

作为对照，堆版本是 O(n log k)：每次窗口滑动都要 push 一个元素、并把所有过期元素从堆里弹出（惰性删除），堆里最多同时存在 k 个元素。k 很大时两者差距明显，k = 1 时两者都很便宜——但单调队列的实现通常更快，因为它不需要比较与 sift。

### 6.4 与单调栈的分工

两者是同一思想的两种投影，容易混在一起：

| | 单调栈 | 单调队列 |
| --- | --- | --- |
| 回答的问题 | 下一个更大/更小元素、柱状图最大矩形 | 滑动窗口内的最大/最小值 |
| 弹出触发条件 | 只有一个：新元素更大（或更小） | 两个：尾部被压制 + 头部过期 |
| 数据进出端 | 同一端（栈顶） | 两端（尾部进新元素，头部出过期） |
| 弹出的那一刻 | 被弹出的元素在此刻确定了答案 | 被弹出的元素只是失去资格或过期，答案在队首 |

一句话记法：**栈解决「下一个更大」，队列解决「窗口内最大」**。前者问的是「谁在我右边且比我大」，后者的窗口有左右两个边界，所以需要两端——见 [第 04 篇](04-stack.md)。

## 7. 双端队列的应用

### 7.1 0-1 BFS：用双端队列替代优先队列

最短路的标准解法是 Dijkstra + 优先队列（[第 13 篇](13-graph-shortest-path-mst.md)）。但当所有边权只有 0 和 1 时，优先队列里键的取值范围退化到极小：**任何时刻堆里只有两种距离值——当前的 d，和 d+1**。既然只有一个「下一档」，堆的操作就完全可以由一个双端队列替代：

- 从距离为 d 的节点出发，走 0 边松弛出的节点距离仍是 d，插到**队首**（它和当前层同级，应该优先处理）；
- 走 1 边松弛出的节点距离是 d+1，插到**队尾**。

```python
from collections import deque

def zero_one_bfs(n, adj, src):
    """边权只有 0 和 1：双端队列即可当优先队列用，O(V + E)。"""
    INF = float("inf")
    dist = [INF] * n
    dist[src] = 0
    dq = deque([src])
    while dq:
        u = dq.popleft()
        for v, w in adj[u]:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                if w == 0:
                    dq.appendleft(v)      # 权 0：与 u 同层，插到队首
                else:
                    dq.append(v)          # 权 1：更远一层，插到队尾
    return dist
```

正确性来自一个不变式：**双端队列中的元素距离值单调不减，且最多取两个相邻的值**。因此「取队首」等价于「取最小键」，Dijkstra 的贪心选择依然成立。复杂度从堆版本的 O(E log V) 降到 O(V + E)——每个节点可能被多次松弛入队，但入队次数与边数同阶，每次入队只是 O(1) 的双端操作。

> [!NOTE]
> 边界条件很清楚：**所有权重相等 → 普通 BFS（FIFO 队列）**；**权重只有 0 和 1 → 0-1 BFS（双端队列）**；**权重是任意非负整数 → Dijkstra（优先队列）**。这三档的容器选择恰好是同一条思路的三级台阶：队列 → 双端队列 → 堆。不要用 0-1 BFS 处理「权重 0、1、2」的情况，那时队列里会出现三个距离档，不变式失效。

### 7.2 其他四种用法

- **滑动窗口**：单调队列的底座（第 6 节），也是「窗口内极值 + 两端进出」问题的通用骨架；配合 `maxlen` 还能零成本维持定长窗口。
- **回文检查**：把清洗后的字符依次 `append` 进 `deque`，然后循环 `popleft()` 与 `pop()` 比较——两端同时取字符、从外向内收敛，正好用满双端队列的两个出入口。
- **工作窃取（work stealing）**：每个工作线程持有一个双端队列，自己从尾部推入与取出，其他线程空闲时从**头部**偷——所有者与偷窃者分处两端，锁竞争降到最低，同时天然实现负载均衡（第 9.4 节）。
- **撤销/重做或双向历史**：一条路径两端增长（比如同时支持「回到上一版」和「跳到最新版」），双端队列比两个栈更省心。

## 8. 环形缓冲与生产者消费者

### 8.1 SPSC 无锁环形缓冲

当队列的两个角色恰好各有一个线程时（单生产者单消费者，SPSC），整个队列可以有**零锁**实现：生产者独占写 head，消费者独占写 tail，双方只读对方的那个索引。判断空满不再靠「留一格」，而是**比较 head 与 tail 的距离**——把两个下标当成单调递增的计数器（不取模），差值直接就是元素个数，于是容量 100% 可用。

```c
/* SPSC 无锁环形缓冲：单生产者单消费者，容量 100% 可用
 * 编译运行：gcc -std=c11 -O2 -Wall -Wextra -pthread -o spsc spsc.c && ./spsc
 */
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdio.h>

#define RING_CAP 1024                     /* 必须是 2 的幂 */
#define ITEMS    1000000

_Static_assert((RING_CAP & (RING_CAP - 1)) == 0, "RING_CAP 必须是 2 的幂");

typedef struct {
    /* head/tail 是「单调递增的计数器」，不是取模后的下标：距离 head - tail 直接给出
     * 元素个数，于是不必留空槽。size_t 回绕良定义，RING_CAP 整除 2^64，差值依然正确。 */
    _Alignas(64) _Atomic size_t head;     /* 生产者独占写，消费者只读 */
    _Alignas(64) _Atomic size_t tail;     /* 消费者独占写，生产者只读 */
    int slots[RING_CAP];
} SpscRing;

/* 生产者：先读 tail（acquire），再写数据，最后 release 发布新 head */
bool spsc_push(SpscRing *r, int v) {
    size_t head = atomic_load_explicit(&r->head, memory_order_relaxed); /* 只有自己写 */
    size_t tail = atomic_load_explicit(&r->tail, memory_order_acquire); /* 看消费者进度 */
    if (head - tail >= RING_CAP) return false;        /* 满：调用方决定阻塞/丢弃/覆盖 */
    r->slots[head & (RING_CAP - 1)] = v;              /* 数据写入先于索引发布 */
    atomic_store_explicit(&r->head, head + 1, memory_order_release);
    return true;
}

/* 消费者：先读 head（acquire），再读数据，最后 release 发布新 tail */
bool spsc_pop(SpscRing *r, int *out) {
    size_t tail = atomic_load_explicit(&r->tail, memory_order_relaxed);
    size_t head = atomic_load_explicit(&r->head, memory_order_acquire);
    if (head == tail) return false;                   /* 空 */
    *out = r->slots[tail & (RING_CAP - 1)];
    atomic_store_explicit(&r->tail, tail + 1, memory_order_release);
    return true;
}

static SpscRing g_ring;

static void *producer(void *arg) {
    (void)arg;
    for (int i = 0; i < ITEMS; i++) {
        while (!spsc_push(&g_ring, i)) sched_yield();  /* 背压：自旋让出 CPU */
    }
    return NULL;
}

static void *consumer(void *arg) {
    long long *sum = arg;
    int v, expect = 0;
    *sum = 0;
    while (expect < ITEMS) {
        if (!spsc_pop(&g_ring, &v)) { sched_yield(); continue; }
        if (v != expect) {                     /* FIFO 必须严格保序 */
            fprintf(stderr, "顺序错误：期望 %d，得到 %d\n", expect, v);
            return (void *)1;
        }
        *sum += v;
        expect++;
    }
    return NULL;
}

int main(void) {
    /* 容量 100% 可用：填满 RING_CAP 个，第 RING_CAP + 1 个必须失败 */
    SpscRing r = {0};
    for (size_t i = 0; i < RING_CAP; i++)
        if (!spsc_push(&r, (int)i)) { puts("未装满就报满"); return 1; }
    if (spsc_push(&r, -1)) { puts("超出容量却入队成功"); return 1; }

    /* 一生产一消费两个线程：校验 100 万条数据的顺序与总和 */
    pthread_t p, c;
    long long sum = 0;
    if (pthread_create(&p, NULL, producer, NULL)) return 1;
    if (pthread_create(&c, NULL, consumer, &sum)) return 1;
    pthread_join(p, NULL);
    void *ret = NULL;
    pthread_join(c, &ret);
    if (ret || sum != (long long)ITEMS * (ITEMS - 1) / 2) {
        puts("校验失败：顺序或总和错误");
        return 1;
    }
    puts("SPSC 无锁环形缓冲：100 万个元素顺序与总和校验通过");
    return 0;
}
```

### 8.2 为什么内存序这样写

无锁代码的正确性完全建立在这几行 `atomic_*_explicit` 上，改一个参数就可能时灵时不灵：

- **读自己写的那个索引用 `relaxed`**：生产者读 head、消费者读 tail，这些值只有本线程写过（独占所有权），不需要任何同步保证。用 `acquire` 只会白白插入屏障。
- **读对方的索引用 `acquire`、发布自己的索引用 `release`**：这是关键的一对。生产者先写 `slots[...]`，再以 release 存储 head；消费者以 acquire 加载 head，然后才读 `slots[...]`。release/acquire 配对保证**「数据写入」对「数据读取」可见**——不会出现消费者看到新 head 却读到旧数据的情况。这条链一旦断掉（比如把 store 改成 relaxed），编译器或 CPU 都可能把数据写入重排到索引发布之后。
- **`_Alignas(64)` 把两个计数器分到不同的缓存行**：否则 `head` 与 `tail` 常常落在同一行（结构体相邻字段），生产者写 head 会让消费者那一行的副本失效、反之亦然，两个核在缓存一致性协议下反复弹这一行——这就是伪共享（false sharing），压测里能造成数倍差距。
- **`head - tail >= RING_CAP` 天然正确**：容量取 2 的幂的好处在这里二次体现——`size_t` 的模 2⁶⁴ 回绕刚好被「距离取模 2⁶⁴」的语义吸收，索引用 `& (RING_CAP - 1)` 掩码，不必担心回绕。

> [!IMPORTANT]
> 这套写法只在**恰好一个生产者、一个消费者**时成立。多个生产者会同时写 head，必须换成 `atomic_fetch_add` 抢槽位（拿到独占的序号再写数据，还要处理「序号 5 写完了但序号 4 还没写完」的发布顺序问题）；多个消费者同理。MPMC 无锁队列的正确实现远比 SPSC 复杂（通常还要带序号标记来解决 ABA 与内存回收），**不要凭直觉把 SPSC 改成 MPMC**。多生产者多消费者的常规做法是「每个生产者一个 SPSC 环形缓冲」，这也是日志采集、金融行情、DPDK 里最常见的拓扑。

### 8.3 覆盖还是阻塞：两种策略

环形缓冲满了之后只有两种选择，选哪种取决于**丢一条数据的后果**：

| 策略 | 行为 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| 覆盖（overwrite） | 丢最旧的，永远接受新数据 | 日志、指标、监控快照、音频采集、画面帧 | 静默丢数据，必须记录丢失计数 |
| 阻塞（block） | 生产者等待，直到有空位 | 任务队列、消息队列、订单处理 | 反压传导，最坏情况死锁或延迟无上界 |
| 拒绝（reject） | 返回失败，交给调用方 | 限流、过载保护、有降级路径的接口 | 调用方必须写错误路径 |

工程上的判断标准很直接：**数据是「最新最有价值」还是「每条都必须处理」**。监控采样、传感器读数属于前者，丢一条旧的无所谓，用覆盖；订单、支付、任务派发属于后者，丢一条都是事故，用阻塞或拒绝。

一个具体例子：Python 里 `deque(maxlen=N)` 就是覆盖式（第 5.3 节），而 `queue.Queue(maxsize=N)` 是阻塞式。两者的接口看起来相似，语义却完全相反——`deque(maxlen=N)` 永远不会卡住生产者，`queue.Queue(maxsize=N)` 在满的时候会让 `put()` 挂起。把前者当成后者来写，程序不会报错，只会安静地丢数据。

### 8.4 用环形缓冲代替动态数组的价值

在日志、采集、音视频这类**长期运行、写入频繁、读方随时可能落后**的场景，环形缓冲相对动态数组的优势不只是「省一次搬移」：

- **零分配、无 GC 压力**：初始化时一次性申请固定内存，之后不再调用分配器——没有分配器锁竞争，没有内存碎片，也不制造垃圾对象。在 Python/Java/Go 里，一个持续 append 的列表会把 GC 拖进稳态压力，而环形缓冲的对象图是常数。
- **延迟可预测**：动态数组扩容那一次是 O(n) 的长尾（[第 02 篇](02-array-dynamic-array.md)），而环形缓冲的最坏单次操作就是常数。实时音频、机器人控制、高频交易里，这个长尾比平均性能重要得多。
- **内存有上限**：容量固定意味着「上游爆炸」最多影响 N 条数据，而不是把内存吃光后 OOM。这是过载保护的第一道闸门。

代价同样明确：容量固定，超出就丢（或阻塞）；随机访问要经过回绕计算；多线程必须自己处理并发（第 8.1 节）。**如果数据量本来就有界，或者需要的是「全量留存」，动态数组/在磁盘上的追加日志更合适**——环形缓冲不是「更好的数组」，它是「有界 + 覆盖」这个语义的实现。

## 9. 队列的变体与相邻结构

### 9.1 延迟队列与定时任务

延迟队列要求「到时间才出队」，纯粹按到达顺序的 FIFO 做不到。标准做法是**堆 + 时间戳**：堆按到期时间排序，调度循环取出堆顶，若未到期就计算还差多久并休眠（或挂到定时器上），到期则弹出执行。堆不是队列（第 9.5 节），但这里是「队列语义需要堆来支撑」的典型例子：

```python
import heapq

class DelayQueue:
    """按到期时间出队：堆顶永远是最近到期的任务。"""
    def __init__(self):
        self._heap = []          # (due, seq, task)
        self._seq = 0            # 同 due 时打破平局，避免比较 task 本身

    def push(self, due, task):
        heapq.heappush(self._heap, (due, self._seq, task))
        self._seq += 1

    def pop_due(self, now):
        out = []
        while self._heap and self._heap[0][0] <= now:
            out.append(heapq.heappop(self._heap)[2])
        return out
```

两个实现要点：**`(due, seq)` 的二元组**——直接存 `(due, task)` 会在到期时间相同时尝试比较 task，而任务对象往往不可比较（Python 里直接 `TypeError`）；加上自增序号，同到期时间的任务按提交顺序出队，恰好恢复了 FIFO 语义（这被称为稳定优先队列）。**惰性删除**——取消任务时不去堆里找它，而是打标记，等它浮到堆顶时丢弃，把取消的代价从 O(n) 降到 O(1)。

调度循环本身在工程上更费心：任务量大时单堆的精度与开销都成问题，工业实现常用分层时间轮（timing wheel）或「堆 + 少量时间轮桶」的混合结构，见 [第 09 篇](09-heap-priority-queue.md) 与 [第 16 篇](16-advanced-structures.md)。

### 9.2 阻塞队列与背压

有界阻塞队列 = 环形缓冲（或链表）+ 互斥锁 + 两个条件变量（`not_empty`、`not_full`）。生产者加锁后若发现队列满，就 `wait(not_full)` 挂起，写入后 `notify(not_empty)`；消费者对称地 `wait(not_empty)` / `notify(not_full)`。三个容易写错的地方：**判断条件要用 `while` 而不是 `if`**（条件变量允许虚假唤醒，被唤醒后条件可能又不成立了）；**通知要在修改状态之后、释放锁之前**（顺序反了会丢失唤醒）；**两个条件变量不能合并成一个**（否则唤醒的对象可能全部是同类线程，导致集体空转）。

阻塞带来的反压（backpressure）是它的核心价值而不是副作用。反过来，**无界队列是生产事故的常见形态**：提交速度长期高于处理速度时，队列长度无上界地增长，延迟与内存一起失控（Little 定律：队列长度 = 到达率 × 平均等待时间）。Python 的 `ThreadPoolExecutor` 用的就是无界队列（`queue.Queue()` 默认 `maxsize=0`），长期过载必须在业务侧限流。

> [!WARNING]
> 阻塞队列有个隐蔽的死锁形态：**同一个线程既生产又消费同一个有界队列**。它先 `put` 并在满时阻塞，而能腾出空间的那个消费者永远是它自己——线程卡死，队列永久满。单元测试里因为队列总是空的，这个 bug 不会出现；一旦在重负载下触发，表现为随机卡死。凡是「在任务里再提交任务」的逻辑，都要确认用的是无界队列，或者有独立的执行线程。

### 9.3 双缓冲

双缓冲（double buffering）把「生产」与「消费」的时间彻底错开：两块缓冲区，生产者写 A 时消费者读 B，切换时交换角色。相比在单个缓冲上加锁，它的好处是**消费者拿到的是一份完整、稳定的快照**，不会读到写了一半的中间状态——图形渲染的前后缓冲、音视频的播放缓冲、数据库刷盘与检查点都靠它。代价是内存翻倍，以及**最多一个周期的时间延迟**（数据要等下一次交换才能被看到）。所以双缓冲适合「周期性产出的完整批次」，不适合要求逐条低延迟的场景——那里该用环形缓冲。

### 9.4 任务队列与线程池的排队策略

同样是 FIFO 队列，在线程池里的排队策略对性能的影响远超直觉：

| 策略 | 行为 | 适用与代价 |
| --- | --- | --- |
| FIFO | 先提交先执行 | 公平、延迟方差小；但任务的数据可能早已被挤出缓存 |
| LIFO | 后提交先执行 | 刚提交的任务数据往往还在缓存里，吞吐更好；代价是长延迟任务可能被反复插队（饥饿） |
| 优先级 | 按 key 出队（堆） | 保障重要任务；必须配 aging（等待越久优先级越高）防饥饿 |
| 工作窃取 | 本地双端队列：自己从尾进出，别人从头部偷 | 竞争最低、负载自动均衡，现代运行时的默认选择 |

工作窃取值得单独说：它把「队列」的语义从「一条全局队列」改成「每线程一条双端队列」。所有者从**尾部**推入与取出（后进先出，缓存友好），窃取者从**头部**拿（最老的任务，也就是所有者最不可能马上要处理的），两端分离使得绝大多数操作不需要任何全局同步。Go 调度器、Java `ForkJoinPool`、Rust rayon、.NET TPL 都是这个结构——**双端队列的并发价值正在于此：单端队列无法让「自己」和「别人」操作不同的端点**。

### 9.5 优先队列为什么不属于队列家族

优先队列（priority queue）的出队顺序由键决定，与到达时间无关。这看起来只是「多了一个排序规则」，实际破坏的正是队列的定义性特征：

| | 队列 | 优先队列 |
| --- | --- | --- |
| 出队规则 | 由到达顺序唯一确定 | 由键的比较结果决定 |
| 顺序可预测性 | 完全可预测（第 k 个元素已知） | 只能预测最小值，其余未知 |
| 实现底座 | 环形缓冲 / 链表 | 堆（[第 09 篇](09-heap-priority-queue.md)） |
| 能否保序 | 顺序就是它的语义 | 相同键的顺序不保证（除非加序号） |

「队列」这个名字在计算机里已经被固定为 FIFO 的同义词（`queue.Queue`、消息队列、事件队列都是这个意思）。把优先队列归进来会让「队列 = 保序」这条推理失效——比如「按提交顺序重放任务日志」这种需求，用优先队列实现就会出错。更准确的分类是：**优先队列是有序结构，与平衡树、跳表同族，只是接口长得像队列**。它和队列唯一的共同点是「不支持随机访问、只在固定端操作」。

## 10. 陷阱清单

- **用 `list` 当队列**：`list.pop(0)`、`list.insert(0, x)` 都是 O(n)，循环里用就是 O(n²)（第 5.2 节的实测：n 翻倍，耗时翻两番）。改 `deque` 是一行改动、几个数量级的收益。
- **`head == tail` 不区分状态**：这是「留一格」约定的前提，不是普适真理。若代码用 size 计数器判满，就不能同时依赖 `head == tail` 判空；两套约定混用必然出现「空队列被当成满」或反之。
- **对负数取模**：C 里 `-1 % 8 == -1`，`-1 & 7 == 7`，Python 里 `-1 % 8 == 7`。跨语言移植循环队列时，凡是可能出现负下标的减法（`head - 1`、`i - k`）都要显式归一化：`((i % n) + n) % n`。
- **容量为 0 与 1**：`rq_new(0)` 应当退化成「恒满」而不是除零或越界；容量 1 时「留一格」意味着申请 2 个槽位，如果初始化代码写成 `malloc(want * sizeof(int))`，容量 1 会立刻越界写。
- **遍历中修改**：Python 的 `deque` 在迭代时增删元素会抛 `RuntimeError: deque mutated during iteration`；C/Java 里则是静默的未定义行为或 `ConcurrentModificationException`。要边遍历边改，先 `list(q)` 做快照（注意这是 O(n) 且是浅拷贝）。
- **`deque` 的随机访问是 O(n/k)**：块大小 64，中间下标要逐块走。把它当中序数组做二分、随机采样是错误方向（第 5.4 节）。
- **`deque` 不支持切片、也不与 `list` 比较相等**：`d[1:3]` 抛 `TypeError`，`deque([1, 2]) == [1, 2]` 是 `False`（只与 deque 比较）；`extendleft([1, 2, 3])` 的结果是 `[3, 2, 1]`（逐个 `appendleft`，顺序会反）。要切片或比较先转 `list`，代价 O(n)。
- **`qsize()` 之类的「探测式」接口不可靠**：多线程下读到的长度在返回时就可能过期。用阻塞队列的 `get`/`put` 的阻塞语义，而不是「先查长度再决定」，后者是典型的 TOCTOU（check-then-act）竞态。

## 11. 小结

- FIFO 的语义价值是**顺序承诺**与**按层推进**：前者支撑公平性与可重放性，后者让 BFS 不必额外判断就能按距离递增地访问。数组队列的障碍来自「出队在头部」（假溢出由此而来），循环队列用 `tail = (tail + 1) % n` 把越界变成绕回，容量取 2 的幂时用 `& (n - 1)` 免掉除法。
- 判空判满三种约定：**留一格**（状态由两个下标完全决定、无冗余、适合无锁，代价是浪费一格）、**size 计数器**（100% 利用率，代价是多一个双方都要维护的共享变量）、**full 标志位**（几乎只在教科书里）。容量会小到 8 左右时选 size 计数器。
- 链式队列的 bug 几乎都在 tail 上：空队列入队要同时设 head 与 tail；出队到空必须把 tail 置空，否则 C 里就是 use-after-free。
- Python `deque` 是「双向链表 + 每块 64 个指针」的分块结构：两端 O(1)、块内连续内存、无扩容长尾，代价是随机访问 O(n/64) 而非 O(1)。`list.pop(0)` 的 O(n) 来自整体搬移，循环里用它是 O(n²)；`deque(maxlen=N)` 则提供了覆盖式环形缓冲语义，且永不阻塞。
- 单调队列用「更靠后且不更小的元素支配前面的元素」这一条丢弃规则把滑动窗口最值降到 O(n)：每个下标入队一次、出队至多一次，总操作数不超过 2n，是**不需要概率假设的摊还上界**。与单调栈的分工是「窗口内最大」对「下一个更大」。
- 双端队列是 0-1 BFS 的底座（0 边推前端、1 边推后端），也是工作窃取的底座（自己从尾部进出、别人从头部偷）；SPSC 无锁环形缓冲的三条要点是 head/tail 各由一个线程独占写、用单调递增计数器比较距离判空满、release/acquire 配对保证「数据写入」先于「索引发布」被看见。
- 环形缓冲代替动态数组的价值是零分配、无 GC 压力、可预测的最坏延迟、内存有上界；它不适合需要全量留存的场景。优先队列不是队列：它破坏 FIFO，属于有序结构家族。

**1.** 「留一个空位」的约定下，容量为 n 的循环队列最多存多少元素？如果要求 n 个槽位全部可用，有哪些改法，各自代价是什么？

> [!TIP] 思路
> 最多 n − 1 个。改法两种：①加 size 计数器，判空 `size == 0`、判满 `size == n`，代价是多一个每次进出都要维护的字段，且并发下它是第三个双方共同读写的共享变量；②加 full 标志位，判空 `head == tail && !full`、判满 `full`，出队到 `head == tail` 时必须清标志，忘记清会让空队列永远报满。想要「无锁 + 满容量」时，用 SPSC 那种「单调递增计数器 + 比较距离」的方案（第 8.1 节）：不再用取模后的下标判空满，格子数就等于容量。

**2.** 解释什么是假溢出，并说明循环队列里 `tail = (tail + 1) % n` 解决了什么。为什么这个写法在 C 里可能出错？

> [!TIP] 思路
> 假溢出指「判满的依据是下标到达数组边界，而实际仍有空闲槽位」——朴素数组队列在出队后不搬移元素，head 一路右移，数组前缀被永久浪费，tail 撞到末尾时就报满，浪费量随运行时间增长。`% n` 让下标在越过末尾后绕回 0，环上不再有「永远用不到的前缀」。C 里出错的原因是负数取模向零取整（`-1 % 8 == -1`），只要出现 `head - 1`、`i - k` 这类可能为负的下标运算，就必须写成 `((i % n) + n) % n`，或者把下标统一声明为 `size_t`／`unsigned`（回绕有定义），或者干脆用容量为 2 的幂 + 掩码 `& (n - 1)`。

**3.** 把第 6.2 节的滑动窗口改写成「求窗口最小值」，需要改动哪几处？如果改为「求窗口最大值及其最后一次出现的下标」，比较运算符该用 `<=` 还是 `<`？

> [!TIP] 思路
> 求最小值把两处不等号反向：入队时弹出队尾所有 `>= x` 的元素（改为保留严格更小的），不变式变成「队列中值严格递增」，队首仍是最小值。求最大值及最后一次出现的下标：用 `<=`（弹出相等的旧值），这样队列里保留的是「值相同但下标最大」的那个，队首下标即最后一次出现的位置；若要用 `<` 保留旧值，则得到的是首次出现的下标。选哪个取决于你要「首次」还是「最后」。

**4.** 0-1 BFS 为什么能用双端队列替代优先队列？换成权重集合 {0, 1, 2} 还行吗？

> [!TIP] 思路
> 因为边权只有 0 和 1 时，当前的候选距离只有两种取值：d（当前层）和 d+1（下一层）。双端队列通过「0 边插队首、1 边插队尾」维持了「队列中距离值单调不减且最多两个相邻取值」的不变式，于是取队首等价于取最小键，Dijkstra 的贪心成立，复杂度从 O(E log V) 降到 O(V + E)。权重为 {0, 1, 2} 时队列里会同时存在 d、d+1、d+2 三档，单调性被破坏，取队首不再是最小键——此时要么用堆，要么用「多档桶」（Dial 算法，按距离分桶）。

**5.** SPSC 环形缓冲里，读自己写的索引为什么可以用 `memory_order_relaxed`？读对方的索引为什么必须用 `acquire`？如果生产者把发布 head 的 store 从 `release` 改成 `relaxed`，会出现什么后果？

> [!TIP] 思路
> 自己的索引只有本线程写过（独占所有权），不存在「别人改动而我不知道」的情况，所以不需要任何同步语义，`relaxed` 足够。读对方的索引前必须先确认对方发布的数据已经可见，所以用 `acquire` 与对方的 `release` 配对。若把发布 head 的 store 改成 `relaxed`，生产者对 `slots[]` 的写入与对 head 的写入之间不再有 happens-before 保证，编译器/CPU 可以把数据写入重排到索引发布之后：消费者看到「有新元素」却读到尚未写入或写了一半的旧值——这是最典型的无锁 bug，表现为压力测试下偶发的数据错乱，且几乎无法复现。

**6.** 有一个「按优先级取任务、同优先级按提交顺序」的需求，为什么不能直接用 `heapq` 存 `(priority, task)`？该怎么改？

> [!TIP] 思路
> `heapq` 在 priority 相同时会比较第二个元素，任务对象通常不可比较（Python 里抛 `TypeError`）。改法是在中间插入一个自增序号，存 `(priority, seq, task)`：seq 唯一且递增，比较永远能决出结果，同时同优先级的元素自然按提交顺序出队——这就是**稳定优先队列**（第 9.1 节的 DelayQueue 用的正是这个技巧）。补一句分类上的提醒：这个结构已经是优先队列而不是队列了，它破坏 FIFO，属于堆的地盘（[第 09 篇](09-heap-priority-queue.md)）。
