数组和链表是所有线性结构的两块基石，本质区别只有一个：**内存连续与否**。这一个差别派生出它们全部的性能特征——访问、插入、删除、缓存表现，全都由此而来。

## 数组：下标即地址

数组把元素放在一段连续内存里，所以 `a[i]` 的地址可以直接算出来：`base + i × 元素大小`——随机访问 O(1)，这是数组独有的能力。

代价是"连续"本身：

- **中间插入/删除要搬移**：在位置 i 插入，后面全部后移一位，O(n)
- **定长**：满了要扩容——申请更大的新块、整体拷贝过去

动态数组（vector / list / Vec）用**倍增扩容**把扩容代价摊薄成 O(1)，做法和上一章的摊还分析一致：每次空间翻倍，第 k 次扩容时之前总共才写过 k 次的量。

```python
# Python list 的 append 就是摊还 O(1)；预知大小时直接给足容量更好
buf = [0] * 1_000_000   # 一次性分配，避免反复扩容搬迁
```

## 链表：指针串起来的节点

链表每个节点自带数据和一个"下一个在哪"的指针，节点在内存里可以散落各处：

```c
typedef struct Node {
    int val;
    struct Node *next;
} Node;
```

- **已知位置的插入/删除是 O(1)**：改两个指针即可，不用搬移
- **但找到那个位置是 O(n)**：链表没有"下标即地址"的能力，只能顺着链走
- 每个节点都多一个指针的内存开销，且节点散落导致**缓存极不友好**——现代 CPU 顺访连续内存比随机跳转快一个数量级

三个工程上必会的变体：**双向链表**（多一个 prev 指针，可反向走、删除已知节点无需找前驱）、**循环链表**（尾接回头）、**哨兵节点**（虚构的头节点，让"插在头/删头"与"插在中间"逻辑统一，边界少一半）。

> [!TIP]
> 手写链表题先画图再动手，永远先处理空链表和头节点两个特例；用了哨兵节点，特例就消失了。

## 复杂度对照

| 操作         | 数组（动态）               | 链表         |
| ---------- | -------------------- | ---------- |
| 随机访问 a\[i] | O(1)                 | O(n)       |
| 头部插入/删除    | O(n)                 | O(1)       |
| 尾部插入       | 摊还 O(1)              | O(1)（带尾指针） |
| 已知节点后插入    | O(n)（要先搬移）           | O(1)       |
| 按值查找       | O(n)（有序可二分 O(log n)） | O(n)       |
| 缓存友好度      | 极好                   | 差          |

## 为什么实践里数组几乎总是赢

教科书说"频繁插删用链表"，但现代硬件上这个结论经常反过来：

- 就算要在数组中间插入，搬移一段连续内存是**高度优化的 memmove**，而链表逐节点跳转的缓存代价往往更贵
- CPU 预取器对连续访问模式极其友好；链表的指针追逐（pointer chasing）是缓存杀手
- 标准库在数组之上用各种技巧绕开搬移（如 C++ deque 分段存储、Python list 过采样）

真正适合链表的场景：需要 O(1) 的**节点级**拼接/摘除（如 LRU 缓存的双向链表 + 哈希表）、元素地址需要稳定不变（其他对象持有节点指针）、或者实现无界增长的自由结构（如哈希桶的冲突链）。

> [!WARNING]
> 面试里反转链表、找环这类题考的是指针操作功底，不代表工程里该用链表存数据。选型看整体操作 profile，不看单点复杂度。
