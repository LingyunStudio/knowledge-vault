模型只能算数字——文本进模型前必须翻译成 token 序列再映射成向量。这个「第一次翻译」的质量决定模型的边界：**模型看到的永远是 token，不是字符也不是词**。tokenizer 的设计直接影响成本（token 经济）、数字处理、多语言能力——理解它是理解 LLM 行为怪癖（为什么数不清 "strawberry" 里有几个 r）的钥匙。

## 1. BPE：从字符到词表的合并算法

```text
BPE（Byte Pair Encoding）训练过程：
1. 起点是字节/字符级（词表最小）
2. 统计语料中最常见的相邻对（如 "t"+"h"）
3. 合并成新 token "th"，加入词表
4. 重复数万次 → 词表长到 10 万级

编码 "unbelievable"：
  按 BPE 规则切：["un", "believ", "able"]   ← 高频词块整存
  低频/生造词：切成更多碎片
```

BPE 的权衡：**词表大 → 常见词一个 token（便宜）、生僻内容碎得厉害**。字节级 BPE（GPT 系）保证**任何文本都可编码**（没有「OOV 未登录词」）——代价是中文/代码/非英语内容常有更多碎片（中文常 1 字 1\~2 token，英文平均 1 词 \~1.3 token）。

工程后果——**token 经济学**：API 按 token 计费、上下文窗口按 token 计量。同一篇内容：英文 1000 token ≈ 中文 1500\~2000 token——中英混合系统的成本与窗口预算要按实测（tokenizer 的在线工具）核算。

## 2. Token 化的行为怪癖清单

| 现象                    | 根因                                     |
| --------------------- | -------------------------------------- |
| 数 "strawberry" 的 r 出错 | token 把词切块，模型看不到字母级                    |
| 大数字算术差                | "1234567" 可能切成 \["123","4567"]——位结构被破坏 |
| 倒序单词难                 | 逐 token 处理无法直接反转向量序                    |
| 中文「字」级任务不稳定           | 切分与人类「字/词」直觉不一致                        |
| 同义改写 token 数大变        | 成本与窗口预算的不可预测性                          |

对策是架构级而非 prompt 级：**精确算术交给工具**（[第 9 篇](09-agents-tools.md)）、**字符级任务交给代码执行**、**按 tokenizer 实测做预算**。「token 边界盲区」是所有 LLM 应用的背景噪音。

## 3. Embedding：token 映入语义空间

```text
词表 10 万 → embedding 矩阵 [10万 × 4096]（每个 token 一个可学习向量）
token "猫" → [0.21, -0.87, ..., 0.33]   （4096 维）

语义空间的结构（训练后涌现）：
  cat ≈ kitten（近）   cat ≈ spreadsheet（远）
  国王 - 男 + 女 ≈ 女王（线性关系——经典发现）
```

embedding 是「**语义的几何化**」：语义相近的向量距离近、语义关系体现为方向。注意两层 embedding 的区分：

- **token embedding**：模型内部的输入表示（逐 token，[第 3 篇](03-transformer-llm.md)的注意力在它们之上工作）。
- **句子/文档 embedding**（RAG 用的）：专门训练的模型把**整段文本**压成一个向量——「语义相似度检索」的地基（[第 8 篇](08-rag.md)）。

### 3.1 从静态词向量到上下文向量

```text
word2vec 时代（静态）："bank" 只有
 一个向量 → 河岸与银行语义混在一起
BERT/LLM 时代（上下文）：同一词的向量随上下文变
  → "河岸的 bank" 与 "银行的 bank" 向量不同
```

上下文依赖是 [Transformer 注意力](03-transformer-llm.md)的产物：每个 token 的表示是「与全部上下文交互后」的结果——歧义消解、指代理解都发生在向量层面。RAG 检索用的句向量模型（embedding model）是**单独训练**的双塔/交叉编码器——与 LLM 的内部 embedding 是两回事。

## 4. 陷阱清单

- 按「词/字符」直觉估算 token（成本/窗口预算）：用 tokenizer 实测；中英文差异显著。
- 字符级任务的幻觉（数字母/倒序/押韵）：token 边界盲区；交给工具。
- 大数字/长数字串直接算：位结构被切碎；代码执行。
- 把 RAG 的 embedding 模型与 LLM 混为一谈（「模型的 embedding 我拿不到」）：句向量用独立 embedding 模型。
- 不同模型 tokenizer 不可互换（token 数/成本不可移植）：换模型重算预算。
- 忽视 embedding 模型的语言/领域匹配（英文模型测中文）：评测先行。

## 5. 小结

- BPE 把文本切进有限词表：字节级保证万能编码、高频块省钱、碎片化造成行为怪癖；token 经济按实测。
- token 化的怪癖清单（数字/字母/中文）是「token 边界盲区」的推论——对策是工具调用与预算实测。
- embedding 是语义的几何化：token embedding（模型内部）与句向量（RAG 检索）是两种东西。
- 静态词向量 → 上下文向量的演化让歧义消解发生在向量层——注意力（[第 3 篇](03-transformer-llm.md)）的产物。

## 6. 练习

**1.** 用在线 tokenizer（或 tiktoken）实测：同一段中文/英文/代码/JSON 各多少 token——建立你项目的「token 预算表」，找出国语与代码的碎片化倍率。

> [!TIP]
> 思路典型发现：中文 ≈ 英文的 1.5\~2 倍 token、JSON 的结构符号吃 token、Base64/长哈希碎成灾难。预算表是成本与窗口规划的依据。

**2.** 数字实验：让模型数 "7777777" 有几个 7、比较 9999 与 10000 的大小（都是单 token 或多 token 的差异）——收集 5 个「token 边界盲区」案例并给出工具化解法。

> [!TIP]
> 思路每个案例的根因都写在 tokenizer 切分结果里——「模型行为怪 → 先看 token 化」是排查链的第一环（在 prompt 工程之前）。

**3.** 语义空间探索：用句向量模型（如 bge/m3e）算一组词与句子的向量，计算「国王-男+女」「北京-中国+日本」的最近邻——验证（或证伪）线性关系的成立范围。

> [!TIP]
> 思路线性关系在「高频典型语义」上成立、细粒度或领域语义上不稳定——embedding 的「语义近似性」要与「精确检索」的需求区分（RAG 的评测，[第 8 篇](08-rag.md)）。

**4.** 上下文向量实验：用 BERT 提取 "bank" 在「河岸」与「银行」两句中的向量，算余弦相似度——对比与同句内其他词的相似度，验证上下文化的效果。

> [!TIP]
> 思路同一词跨语境的相似度低于同语境相关词——上下文向量确实编码了语义消歧。这就是「预训练表示可迁移」的向量层证据。

**5.** 估算 token 化对你业务的影响：你的系统 prompt + RAG 上下文 + 历史对话的 token 构成，计算「对话轮次 × 单价」的成本曲线——找出裁剪点（历史摘要/压缩上下文）。

> [!TIP]
> 思路成本构成的典型分布：系统 prompt 固定占比高、RAG 上下文次之、历史线性增长。三段的治理手段不同（缓存/压缩/裁剪，[第 6 篇](06-inference-decoding.md)与[第 9 篇](09-agents-tools.md)）。

**6.** 讨论：为什么字节级 BPE「保证万能」但「碎片化不均」的设计最终胜出（对比 word-level 的 OOV 问题与 character-level 的序列过长）？从「编码完备性、序列长度、语义单元质量」三角分析，并讨论「中文 token 效率」对模型选择的影响——tokenizer 是「模型的方言」。

> [!TIP]
> 思路三角约束：word-level 语义好但 OOV 致命、char-level 万能但序列爆炸（注意力 O(n²)）、BPE 在两者间取工程最优。「模型的方言」：tokenizer 决定了模型对语言的原生舒适区——中文场景的模型选型先看 tokenizer 效率。
