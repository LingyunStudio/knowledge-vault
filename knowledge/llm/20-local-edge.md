「在本地跑大模型」的三个动机：**数据不出门**（隐私/合规）、**无网可用**（离线场景）、**成本可控**（无按 token 计费）。但端侧的世界被三个硬约束统治：**显存/内存容量**、**内存带宽**（解码速度的瓶颈，[第 3 篇](03-transformer-llm.md)）、**功耗**。本地部署的工程 = 在这三个约束下把「够用的模型」放进去。

## 1. 硬约束的心账本（端侧版）

```text
显存/内存预算 = 模型权重 + KV 缓存 + 运行时开销

权重（量化后）：
  7B @ Q4_K_M ≈ 4.4 GB       7B @ Q8_0 ≈ 7.5 GB
  13B @ Q4_K_M ≈ 8 GB        70B @ Q4_K_M ≈ 40 GB
KV 缓存：随上下文线性（[第 3 篇](03-transformer-llm.md)）—— 8K 上下文再吃 1~2GB
解码速度 ≈ 内存带宽 ÷ 模型大小
  手机（~50GB/s）跑 4GB 模型 ≈ 10 token/s；桌面 DDR5（~80GB/s）≈ 20 token/s
  Apple Silicon 统一内存（~400-800GB/s）—— 端侧的速度冠军
```

这张心账本直接推导选型：**16GB 内存的笔记本 → 7B Q4 是上限**（留系统空间）；**8GB 手机 → 3B 以下量化模型**；**Mac 64GB 统一内存 → 70B Q4 可跑（独占）**。「带宽决定解码速度」解释了为什么 Mac 跑本地模型比同价位 PC 快——统一内存的带宽优势。

## 2. llama.cpp 与 GGUF：量化格式族的机制

```text
llama.cpp：纯 C/C++ 的推理引擎 —— 无 Python、无 GPU 依赖也能跑
GGUF 格式：单文件打包「权重（量化）+ 词表 + 元数据」

量化格式族（Q 后缀的语义）：
  Q8_0    8 比特：几乎无损、体积减半
  Q6_K    6 比特混合：重要层更高精度
  Q5_K_M  5 比特混合
  Q4_K_M  4 比特混合 —— ★ 社区的默认甜点（大小/质量的平衡点）
  Q3/Q2   3/2 比特：明显质量下降（应急/极端约束）

_K_M 的含义：K = 基于 K-quant 的分层量化方案（重要层给更多比特）
             M = medium（还有 S/L 变体）—— 「混合量化」：不是均匀压缩，
             而是按「每层对误差的敏感度」分配精度
```

混合量化的设计思想值得体会：**不同层对量化的敏感度不同**（注意力层 vs FFN 层、首末层）——把比特预算花在敏感处。这是「均匀量化」到「结构感知量化」的进化（[量化的原理](../ai/09-deployment.md)的深入）。

```bash
# llama.cpp 的最小工作流
llama-cli -m model.Q4_K_M.gguf -p "你好" -n 256      # 命令行推理
llama-server -m model.Q4_K_M.gguf --port 8080        # OpenAI 兼容 API 服务
```

## 3. ollama 与 LM Studio：体验层

```bash
ollama run qwen2.5:7b          # 一条命令：拉模型+跑起来（自动量化选择）
ollama serve                   # 本地 API（OpenAI 兼容）—— 应用代码无缝切换
```

ollama/LM Studio 的定位是**「本地模型的包管理器 + 运行时」**：模型库（含量化变体）、自动资源检测（按内存选量化档）、OpenAI 兼容 API（应用零改造切换）。它们把「本地部署」从「编译 llama.cpp + 手动下权重」降到「一条命令」——端侧 LLM 普及的基础设施。

## 4. Apple Silicon：统一内存的红利

```text
传统 PC 架构：CPU 内存与 GPU 显存分离 → 模型要拷进显存（显存小是瓶颈）
Apple Silicon：统一内存（CPU/GPU 共享）→ 模型多大就能「放多大」
  64GB Mac → 70B Q4（40GB）真的能跑 —— 同价位独显方案做不到

MLX：Apple 的 ML 框架（为统一内存设计）—— 本地推理/微调的 Mac 原生路线
```

「统一内存」是端侧推理的架构级红利：**没有 PCIe 拷贝的瓶颈、内存即显存**。代价是 GPU 算力绝对值仍弱于独立显卡（生成速度受内存带宽限制、预填充较慢）——「能装下」与「跑得快」是两个维度。

## 5. 全离线 RAG 栈

```text
数据不出门的完整 RAG（[第 8 篇](08-rag.md)的本地版）：
  文档 → 分块 → [本地 embedding 模型（bge-m3 / nomic-embed）] → 本地向量库（Qdrant/sqlite-vec）
  查询 → 本地 embedding → 检索 → [本地 LLM] → 回答

全本地组件的选型：
  embedding：bge-m3（多语言、开源）/ nomic-embed-text
  LLM：Qwen2.5-7B / Llama-3.1-8B 的 Q4 量化
  向量库：Qdrant（自托管）/ sqlite-vec（嵌入式）
  重排：bge-reranker（本地重排，[RAG 第 4 节](08-rag.md)）
```

全离线栈的能力边界要诚实：**本地 7B 的推理与指令遵循弱于云端旗舰**——复杂任务的质量下降是「数据不出门」的价格。缓解：任务拆分（简单任务本地、复杂任务人工）、领域微调补足、RAG 上下文给足（本地模型更依赖上下文）。

## 6. 混合架构：本地与云的路由

```text
混合路由（[第 10 篇](10-deploy-engineering.md)分层路由的本地版）：
  用户输入 → [本地小模型分类/敏感检测]
    ├── 含敏感数据 → 本地模型处理（或脱敏后上云）
    ├── 简单任务 → 本地小模型
    └── 复杂任务且无敏感 → 云端旗舰
  断网时：全部本地降级（能力下降但可用）
```

混合架构的关键件：**敏感检测**（分类器/规则识别 PII 与机密——决定路由）、**能力分级**（什么任务本地够用——评估数据说话）、**离线降级**（断网时功能子集的预定义）。这是「隐私与能力」的动态平衡器。

## 7. 许可证：开源权重 ≠ 开源

```text
许可证的光谱：
  Apache/MIT（Qwen 部分/Mistral 部分）：商用自由、可再分发
  Llama 社区许可：商用可但有条款（月活 7 亿以上需另行授权、命名规范）
  非商业许可（部分研究模型）：商用禁止
  「开放权重」：你拿到的是权重文件，不是训练代码/数据

部署前的许可证核对：商用允许？再分发允许？衍生模型（微调）的许可继承？
```

「开源权重」的措辞陷阱：**权重可下载 ≠ OSI 开源**——许可证的附加条款（使用政策、命名要求、规模门槛）对商业部署有真实约束。企业选型的 checklist：许可类型、商用条款、输出内容的责任归属、微调产物的许可。

## 8. 陷阱清单

- 显存心账只算权重：KV 缓存与运行时开销（[第 3 篇](03-transformer-llm.md)）在长上下文反超。
- 量化档位贪小（Q2 当默认）：质量损失在推理任务上显著；Q4\_K\_M 起步。
- 本地模型的「能力幻觉」（拿云端旗舰的 prompt 直接用）：本地 7B 需要更简单的任务拆解与更明确的 prompt；评估先行。
- 端侧内存带宽的忽略：「能装下」≠「速度可用」；解码速度 ≈ 带宽÷模型大小。
- 混合架构的路由误判（敏感数据上云）：敏感检测的召回率要审计。
- 许可证误读（「在 GitHub 上就是开源」）：商用条款逐条核对。
- 离线场景没测试断网形态：「断网时功能降级」要在开发期演练。
- GGUF 量化无回归测试（[第 6 篇](06-inference-decoding.md)的量化回归）：黄金任务集对比。

## 9. 小结

- 端侧三约束（内存/带宽/功耗）的心账本：权重+KV 的容量账、带宽÷模型大小的速度账——选型先算账。
- GGUF 量化族（Q4\_K\_M 甜点）是「结构感知混合量化」——按层敏感度分配比特预算。
- ollama/LM Studio 把本地部署降到一条命令；OpenAI 兼容 API 让应用零改造切换。
- Apple 统一内存是端侧架构红利（能装下 70B Q4）；「能装下」与「跑得快」分离。
- 全离线 RAG（本地 embedding+向量库+LLM）与混合路由（敏感检测+能力分级）是隐私与能力的平衡架构；许可证是部署前的法律核对。

## 10. 练习

**1.** 心账本实测校准：在同一台机器上跑 7B 的 Q4\_K\_M 与 Q8\_0，记录模型文件大小、加载后内存占用、解码速度（token/s）——验证「速度 ≈ 带宽÷大小」的估算，校准你的心算系数。

> [!TIP]
> 思路实测的解码速度通常低于理论带宽值（运行时开销）——记录实测系数后，你的心算就带上了「本机的修正因子」。换设备重测。

**2.** 量化回归测试：7B 模型的 Q4\_K\_M 与 FP16 在三个任务（摘要/代码/推理）各跑 20 例对比——量化「质量损失」的任务分布（[第 6 篇](06-inference-decoding.md)练习 3 的本地版），确定哪些任务可以放心用 Q4。

> [!TIP]
> 思路任务敏感度分布的典型：摘要几乎无感、代码格式正确但细节错、多步推理掉分最多。量化部署的任务白名单由此建立。

**3.** 全离线 RAG 搭建：用 bge-m3 + Qdrant（或 sqlite-vec）+ Qwen 7B（ollama）搭建全离线的文档问答——拔网线验证全功能可用；对比云端旗舰版的回答质量，记录差距清单。

> [!TIP]
> 思路差距清单的分析维度：事实准确性（RAG 缓解部分）、指令遵循（本地弱项）、推理深度（复杂问题差距大）。差距清单决定「哪些查询必须路由上云」。

**4.** 混合路由实现：实现「敏感检测（正则+分类器）→ 路由（本地/云）」的混合架构，构造三类查询（含 PII/普通/复杂推理）验证路由的正确性；再断网测试「本地降级」的完整性。

> [!TIP]
> 思路敏感检测的召回率审计（[第 17 篇](17-llm-security.md)）：漏检的 PII 上云 = 合规事故。检测器的误报（正常数据被本地处理）是体验代价——阈值按业务定。

**5.** 许可证审计：选三个开源模型（如 Qwen/Llama/Mistral 各一），逐条阅读其许可证，回答「商用是否允许、月活限制、微调产物许可、再分发要求」——输出一张许可证对照表。

> [!TIP]
> 思路许可证审查的易漏点：使用政策（acceptable use policy）的附加约束、微调产物是否继承限制、商标与命名要求。法务确认前不上生产——许可证是部署的技术前提。

**6.** 讨论：「端侧小模型」与「云端大模型」的长期演化关系——端侧模型会追上云端吗？从「硬件带宽与功耗的物理约束」「模型的蒸馏与小模型效率进步」「混合架构的分工固化」三个角度分析，并对照「手机 NPU 跑 CNN（图像）的成熟路径」——推理模型（[第 13 篇](13-reasoning-models.md)）在端侧的可能性如何改变这个格局？

> [!TIP]
> 思路物理约束（功耗墙）决定端侧模型的「容量上限」——但「任务所需的容量」可以通过蒸馏与特化下降。图像 CNN 的路径（专用化后端侧成熟）可能复制到 LLM：「端侧跑特化小模型 + 云端跑通用大模型」的分工固化。推理模型在端侧的价值：思维 token 的质量收益让小模型也能处理复杂任务——但 token 成本在端侧是「时间」不是「钱」。
