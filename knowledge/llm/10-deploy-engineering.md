模型能跑通 demo 距离能上生产还差三座山：**资源**（显存装得下、成本算得过）、**吞吐**（并发下不崩）、**质量**（有评估、有护栏）。本篇按自部署的视角梳理，用 API 服务的话大部分压力转移给了云厂商，但评估与护栏部分依然全部适用。

## 显存账：先算再买卡

自部署 7B/70B 模型，显存两笔账：

```text
权重：参数量 × 每参数字节        FP16=2B；INT8=1B；INT4=0.5B
      7B FP16 ≈ 14GB   70B FP16 ≈ 140GB（需多卡）
KV Cache：随 序列长度 × 并发数 线性涨（见第 06 篇），长上下文的真正大头
```

经验公式：**部署显存 ≈ 权重 × 1.2 + KV Cache 预算**。剩余空间就是并发能力。

## 量化：几比特的权衡

量化把 FP16 权重压到更低比特，几乎必做：

| 精度 | 7B 权重 | 质量 | 适用 |
| --- | --- | --- | --- |
| FP16/BF16 | ~14GB | 基准 | 训练/资源充足 |
| INT8 (W8A8) | ~7GB | 几乎无损 | 通用推理 |
| INT4 (GPTQ/AWQ) | ~3.5GB | 轻微损失 | 单卡部署大模型 |
| GGUF Q4_K_M | ~4GB | 轻微损失 | 端侧/笔记本（llama.cpp） |

> [!TIP]
> INT4 量化已成熟到"默认可上线"的程度，损失通常在 1% 以内；激活量化（A8）比权重量化更敏感。**量化后再测评估集**，别只看别人博客的结论。

## 推理引擎：吞吐的来源

裸跑 transformers 只适合调试。生产用推理引擎，收益 5~10 倍：

- **vLLM**：PagedAttention（KV Cache 按页管理，碎片率从 60~80% 降到近零）+ Continuous Batching（新请求随时插批），事实标准首选
- **SGLang / TensorRT-LLM**：结构化生成加速、NVIDIA 深度优化，各有强项
- **llama.cpp / Ollama**：CPU/端侧/开发体验

另有两项通用加速值得一知：**FlashAttention**（分块算注意力，省显存提速，不改数学）与**投机采样**（小模型草稿、大模型验证，一次验证多个 token）。

## 评估：没有 eval，就没有迭代

"感觉变好了"不是工程结论。评估体系三层：

1. **自动指标**：格式合规率、字段抽取准确率、单测通过率（代码任务）——可脚本化、必做
2. **LLM-as-Judge**：用强模型按 rubric 给回答打分/对比，覆盖开放性任务；注意位置偏差（交换顺序重测）与自偏好
3. **人评**：抽样本双人标注 + 一致性检查，校准前两层

两个工程关键：**评测集来自真实流量**（含难例与脏例）；每次改提示词/换模型/升版本都全量回归——把 LLM 应用当传统软件做 CI，只是测试用例跑的是模型。

## 护栏与成本

- **输入侧**：注入检测、越狱模式拦截、敏感词与合规过滤
- **输出侧**：schema 校验、敏感信息脱敏、高危动作（发邮件/转账类工具）人工确认或限流
- **降本三板斧**：小模型路由（简单请求不进大模型）、prompt/语义缓存、流式 + 限量（max_tokens）

> [!NOTE]
> 生产大模型系统没有"一次配置终身免维护"：模型版本升级（哪怕 API 后端静默升级）都可能改变行为分布。**评估集 + 回归测试 + 灰度开关**，是这类系统唯一的稳定性来源。
