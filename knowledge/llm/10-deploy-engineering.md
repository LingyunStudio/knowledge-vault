LLM 应用的工程要点集中在四件事：**选型**（云 API 还是自托管）、**可靠性**（流式/重试/降级）、**成本**（token 账本与缓存）、**质量保障**（评估与安全护栏）。与[传统部署](../ai/09-deployment.md)的最大差异是「非确定性输出」——测试、监控、回滚的思路都要适配。

## 1. 选型：云 API vs 自托管

| 维度        | 云 API（GPT/Claude/国产大模型）      | 自托管（开源模型 + vLLM）              |
| ----------- | ------------------------------------ | --------------------------------------- |
| 起步成本    | 极低（一个 key 即用）                 | 高（GPU/运维/推理工程）                 |
| 规模经济    | 按 token 付费（量大成本线性涨）        | 固定成本（高 QPS 后单次更便宜）          |
| 数据合规    | 数据出域（需评估/私有化条款）          | 数据不出域（合规刚需场景）               |
| 模型能力    | 通常是最新最强                        | 开源与旗舰有差距（快速缩小中）           |
| 定制自由    | 受限（微调接口/有限参数）              | 完全（微调/改架构/量化自由）             |

决策的两大锚点：**数据合规**（数据能否出域——金融/医疗/政务常常一票定夺）与**成本曲线**（低 QPS 用 API、高 QPS 且任务简单用小模型自托管）。现实的形态常是混合：**API 用旗舰模型、自托管跑小模型**（简单任务路由到便宜模型——模型分层路由是成本优化的第一杠杆）。

## 2. API 应用的工程要件

```python
# 生产级 LLM 调用的骨架
async def ask(prompt: str) -> str:
    for attempt in range(3):                       # 指数退避重试（429/5xx）
        try:
            res = await client.chat(...)            # 超时设置必配
            return validate(res)                     # 输出校验（结构/内容）
        except RateLimitError:
            await sleep(2 ** attempt); continue
    return fallback_answer()                        # ★ 降级：模型不可用时业务还能跑
```

工程要件清单：**流式输出**（SSE——感知延迟，[第 6 篇](06-inference-decoding.md)）、**重试与退避**（429 限流是常态）、**超时与取消**（[AbortController](../frontend/07-async.md)）、**降级路径**（模型挂了 → 缓存/小模型/兜底话术）、**结构化输出**（schema，[第 5 篇](05-prompting.md)）、**多模型抽象**（统一的模型接口层——切换/降级/路由的自由）、**成本与延迟日志**（每调用记录 token 数与耗时）。

**多模型抽象层**（LiteLLM/自研网关）的定位：模型名只是配置——换模型/降级路由/A-B 测试都在网关层完成——「模型供应商锁定」的解药。

## 3. 自托管的技术栈

```text
模型获取：开源权重（Llama/Qwen/Mistral）+ 量化版本（[第 3 篇](03-transformer-llm.md)心账本选尺寸）
推理引擎：vLLM（服务高吞吐）/ llama.cpp（端侧）
服务层：API 网关 + 批处理配置 + 监控（[第 6 篇](06-inference-decoding.md)）
硬件：显存心算（权重 + KV）→ 选卡（24G/48G/80G）
```

自托管的隐性成本清单：**GPU 资源的运维**（利用率/扩容）、**推理优化的持续投入**（新模型适配/内核更新）、**模型升级的回归测试**（换版本 = 换行为）。工程判断：**自托管是「获得控制权」的持续成本**——QPS 与合规两条线决定值不值。

## 4. 成本核算：token 账本

```text
单次调用成本 = (输入 token × 输入单价) + (输出 token × 输出单价)
典型比例：输入便宜、输出贵（2~5 倍）——控制输出长度是省钱第一杠杆

成本优化的杠杆排序：
① 模型分层路由：简单任务（分类/抽取）→ 小模型；复杂任务 → 旗舰（差价 10~50 倍）
② 前缀缓存：固定 system prompt/RAG 前缀的缓存折扣（[第 6 篇](06-inference-decoding.md)）
③ 上下文治理：RAG 材料精选、历史摘要压缩（[第 8 篇](08-rag.md)、[第 9 篇](09-agents-tools.md)）
④ 输出约束：max_tokens + 结构化输出（防失控生成）
⑤ 批处理接口（离线任务）：半价常伴
```

成本的架构意识：**每层的 token 预算**（system/RAG/历史/输出）要在设计期核算——「上下文膨胀」是成本失控的渐进过程（Agent 的多轮累积尤甚，[第 9 篇](09-agents-tools.md)）。

## 5. 评估体系：没有评估就没有迭代

```text
三层评估（[第 4 篇](../ai/04-evaluation.md)的 LLM 版）：
① 黄金测试集：几十到几百个代表性输入 + 期望行为（回归测试的地基）
② 自动评分：规则（格式/关键词）+ LLM 评分（用强模型判分——先人工校准）
③ 在线评估：用户反馈（点赞/编辑距离）+ A/B 测试

评估的工程化：进 CI（prompt/模型改动跑回归）、版本化、与实验管理打通（[第 8 篇](../ai/08-training-practice.md)）
```

LLM 评估的特殊性：**输出没有唯一正确答案**——评估从「断言相等」变成「分布与质量的判断」：LLM 评分（LLM-as-judge）要校准（人工标注对齐评分尺度）、位置偏差/自偏好要意识。**评估集的持续扩充**（线上坏例回流测试集）是质量飞轮的燃料。

## 6. 安全护栏：提示注入与内容安全

```text
攻击面（[第 9 篇](09-agents-tools.md)的展开）：
提示注入：数据中的恶意指令（网页/邮件/文件）——Agent 场景的头号威胁
越狱：诱导模型违反安全策略（角色扮演/编码绕过）
数据外泄：prompt 中敏感信息的出域（云 API 场景）

护栏体系：
输入侧：注入检测（分类器/规则）、敏感信息过滤（脱敏再进模型）
输出侧：内容分类器（有害内容拦截）、结构校验、敏感动作人工确认
系统侧：权限最小化（[第 9 篇](09-agents-tools.md)）、CSP/沙箱（[frontend](../frontend/10-http-storage.md)、[docker](../docker/01-why-containers.md)）
```

## 7. 陷阱清单

- 无评估裸奔迭代 prompt/模型：回归测试是 LLM 工程的底线（[第 5 篇](05-prompting.md)）。
- 单模型供应商锁定：抽象层 + 多模型配置；切换/降级的自由。
- 忽视 429/超时的重试设计：限流是常态；指数退避 + 降级。
- 成本无核算：token 账本 + 模型分层路由；上下文膨胀的渐进失控。
- LLM 评分不校准：先人工对齐评分尺度再自动；位置偏差意识。
- 数据出域无合规评估：私有数据进云 API 前的合规审查；敏感字段脱敏。
- 流式/取消缺失：长回答的感知延迟与「用户跑了请求还在烧」。
- 安全护栏只靠 prompt：输出分类器 + 权限系统是工程护栏；prompt 声明会被注入绕过。

## 8. 小结

- 选型双锚点：数据合规与成本曲线；混合形态（API 旗舰 + 自托管小模型 + 分层路由）是常态。
- API 应用七要件：流式、重试退避、超时取消、降级路径、结构化输出、多模型抽象、成本日志——「模型不可用」是设计前提。
- 自托管的隐性成本（GPU 运维/优化投入/版本回归）与显性收益（合规/控制/高 QPS 成本）要算总账。
- 成本五杠杆：分层路由 > 前缀缓存 > 上下文治理 > 输出约束 > 批处理；token 预算在设计期核算。
- 评估三层（golden/自动评分/在线）+ 安全纵深（注入检测/输出分类/权限最小化）——「非确定性系统」的质量保障是 MLOps 的 LLM 特化。

## 9. 练习

**1.** 选型账本练习：为一个「日均 5 万次、每次平均 2K 输入 500 输出」的客服场景，分别算「云 API 旗舰」「云 API 小模型」「自托管 7B」三方案的月成本（按当前价格），画出「QPS-月成本」交叉点——得出你的选型结论与边界条件。

> [!TIP]
> 思路自托管的「回本 QPS」受 GPU 利用率制约（60% 利用率 vs 100% 的账差一倍）——工程现实要打折扣。分层路由（80% 简单请求走小模型）常把总成本砍半。

**2.** 多模型抽象层实现：用 LiteLLM（或自研）封装三家模型的统一接口，实现「主模型超时自动降级到备用模型」与「按任务类型路由」——注入故障验证降级路径真的能走通。

> [!TIP]
> 思路降级链的验证用「故障注入」（mock 主模型 500）——降级路径没演练过的系统等于没有降级路径（[事故响应](../git/11-pitfalls.md)的哲学）。

**3.** 评估体系搭建：为「客服总结」功能建 golden 测试集（30 例），实现三层评分（格式规则/关键词/LLM 评分并人工校准 20 例）——然后故意换一个弱模型，验证评估体系能发现退化。

> [!TIP]
> 思路LLM 评分校准的实操：先让 LLM 给 20 例打分、人工也打、对比分歧点、修正评分 prompt——循环到一致率满意。「评分器本身要被评估」是元评估。

**4.** 成本仪表盘：给你的应用接入 token 用量日志（每调用记录输入/输出/模型/延迟），做一张「按功能模块的日成本」看板——找出成本 Top1 模块并给出优化方案（缓存/路由/压缩）。

> [!TIP]
> 思路成本看板的第一洞察常是「某个.debug 循环在烧钱」或「system prompt 占 70%」——不可见才不可治。缓存（[第 6 篇](06-inference-decoding.md)）与压缩的 ROI 用数据说话。

**5.** 安全护栏联调：构造三类攻击（提示注入的文档、越狱式提问、超长输入 DoS），验证你的输入过滤、输出分类器与长度限制的拦截效果——记录绕过尝试，体会「护栏是概率性防御」。

> [!TIP]
> 思路护栏的评估也是「分布性的」（拦截率 95% 而非 100%）——与[ML 评估](../ai/04-evaluation.md)的概率性一致。红队测试的持续化（新攻击手法的回归集）是安全护栏的维护方式。

**6.** 讨论：LLM 应用的「质量保证」与[传统软件](../python/12-quality.md)的区别——为什么「测试金字塔」在 LLM 应用中要倒置（端到端评估为主、单元测试为辅）？从「输出的开放性（无数正确答案）」「行为的上下文依赖性」「评估即业务判断」三个角度分析，并思考「人审的位置」应该放在开发流程的哪几个点上。

> [!TIP]
> 思路LLM 输出的「正确」是模糊集合（好/可用/不可用而非对/错）——单测的断言相等失效，端到端评估（黄金集+LLM 评分）成为主战场；单元测试只守「确定性部分」（预处理/工具逻辑/解析）。人审的位置：评分校准、坏例回流、灰度期抽检——人从「执行者」变为「校准者」。
