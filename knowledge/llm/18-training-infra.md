[第 4 篇](04-pretrain-sft-rlhf.md)讲了训练什么；本篇讲「怎么把训练跑起来」——当模型与数据大到单卡装不下，**并行策略**成为训练的第一设计决策。核心问题只有一个：**显存装不下、单卡算不动——把什么切给谁**。

## 1. 显存解剖：四重账

```text
训练时每参数的显存占用（FP16 混合精度 + Adam）：
  权重（FP16）        2 字节
  梯度（FP16）        2 字节
  Adam 一阶动量（FP32）4 字节
  Adam 二阶动量（FP32）4 字节
  FP32 主权重         4 字节
  ────────────────────────
  合计 ≈ 16 字节/参数 → 7B 模型仅状态就要 ~112GB！

再加：激活值（随 batch 与序列长度暴涨——checkpoint 可省）
```

对照推理（[第 3 篇](03-transformer-llm.md)只有权重+KV ≈ 2+ 字节/参数）：**训练的显存是推理的 8 倍量级**——这就是「7B 推理单卡可跑、7B 训练单卡不可能」的数学。降账本的三条路：**LoRA**（[第 7 篇](07-fine-tuning-peft.md)：不训全参就没有梯度与优化器状态）、**量化训练**（QLoRA）、**并行切分**（本篇主角）。

## 2. 并行策略光谱：各自切什么

```text
切分的四个维度：
① 数据并行（DP/DDP）：切「数据」——每卡一份完整模型、吃不同数据
   梯度 all-reduce 同步。模型必须单卡装得下。
② ZeRO（1/2/3，DeepSpeed）/ FSDP：切「状态」
   ZeRO-1：切优化器状态
   ZeRO-2：+ 切梯度
   ZeRO-3 / FSDP：+ 切权重（参数在用时临时聚合——模型太大也能训）
③ 张量并行（TP）：切「单层的矩阵乘」——一层内的权重竖切/横切到多卡
   通信频繁（每层两次 all-reduce）——限单机内 NVLink
④ 流水线并行（PP）：切「层」——前几层在卡1、后几层在卡2（流水线微批）
   有 bubble（空转）——需要微批填充
⑤ 专家并行（EP）：MoE 的专家分布到不同卡（[第 3 篇](03-transformer-llm.md)）
```

| 策略          | 切什么    | 通信量           | 适用           |
| ----------- | ------ | ------------- | ------------ |
| DDP         | 数据     | 梯度 all-reduce | 模型单卡装得下      |
| ZeRO-2      | 优化器+梯度 | 分片通信          | 7B\~30B 常规选择 |
| ZeRO-3/FSDP | + 权重   | 参数聚合通信        | 30B+ / 单卡装不下 |
| TP          | 层内矩阵   | 高频 all-reduce | 单机 NVLink 内  |
| PP          | 层间     | 点对点（少）        | 跨机、超深模型      |
| EP          | MoE 专家 | all-to-all    | MoE 模型       |

真实的大模型训练是**组合拳**：TP（机内）+ PP（机间）+ ZeRO/FSDP（数据维度）+ EP（MoE）——「3D 并行」的配置是训练基础设施工程师的核心手艺。**中小规模（7B\~70B 微调/继续预训练）的组合通常很简单：FSDP 或 ZeRO-3 + 梯度累积**。

## 3. FSDP / DeepSpeed 的实操形态

```python
# PyTorch FSDP 的最小形态（ZeRO-3 的原生实现）
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

model = FSDP(model, auto_wrap_policy=transformer_wrap)   # 按层自动分片
# 训练循环与单卡完全一致：FSDP 在前向时临时聚合参数、反向后重新分片

# DeepSpeed 的形态：ZeRO 配置文件
# ds_config.json: { "zero_optimization": { "stage": 3, "offload_optimizer": {...} } }
# offload_optimizer：优化器状态卸载到 CPU/NVMe——再省显存换速度
```

训练代码「与单卡几乎一致」是现代框架的成就——**并行的复杂度被框架吸收**，工程师的决策收缩为「选策略 + 定分片粒度 + 调 batch」。

## 4. 效率账：MFU 与通信

```text
MFU（Model FLOPs Utilization）：实际有效计算 ÷ 理论峰值算力
  好的训练：MFU 40%~60%；低于 30% → 排查瓶颈（通信/数据/序）

通信是并行的税：卡间的 all-reduce 受「卡间带宽」限制
  单机 NVLink（~900GB/s）≫ 跨机 IB（~400Gb/s）≫ 跨区域
  → 策略：TP 放机内（通信重）、PP 跨机（通信轻）、梯度累积减少同步频率
```

「训练慢」的诊断顺序（[第 8 篇](../ai/08-training-practice.md)调试的规模化版）：**MFU 低 → 看瓶颈在哪**——数据加载跟不上（管道阻塞）、通信占比高（并行配置）、kernel 效率低（算子/精度）、频繁同步（检查点太密）。

## 5. 容错：训练是长跑

```text
千卡训练的现实的故障率：硬件故障每天都会发生
checkpoint：全量状态（[第 8 篇](../ai/08-training-practice.md)）+ 分布式保存（每卡存自己的分片）
  频率权衡：太密拖慢训练、太疏丢失进度（分钟级 checkpoint 是主流）
弹性训练：节点掉线 → 缩容继续（torch elasticity）→ 修复后加回
```

「checkpoint 的完整性」在并行下更复杂：ZeRO-3 时每个 rank 只有权重分片——恢复需要全 rank 协同。**「训练到 90% 崩了且没有可用 checkpoint」是基础设施工程师的噩梦**——容错演练与恢复验证是上线前的必修（[备份纪律](../database/11-ops-pitfalls.md)的训练版）。

## 6. 数据管线：被低估的另一半

```text
预训练数据管线的形态（[第 19 篇](19-data-engineering.md)的内容，基础设施视角）：
  万亿 token 存储分片（Parquet/Arrow）→ 流式读取（不装进内存！）
  → 在线 shuffle（分片级混洗 + 缓冲区）→ token 打包（拼满上下文长度）
  → 预取重叠（GPU 算第 N 批时 CPU 读第 N+1 批）

管道阻塞的检测：GPU 利用率锯齿状（算一下停一下 = 数据喂不上）
```

「数据管道是训练的隐形瓶颈」：GPU 太快，CPU/磁盘跟不上——**预取、并行读取、高效格式（Arrow）、打包策略**是数据工程的四个旋钮。

## 7. 训练监控：全局的体检

```text
loss 曲线（[第 8 篇](../ai/08-training-practice.md)）+ 大规模特有：
  loss spike（突刺）：数据坏批次/超参/硬件——处理：跳过批次/回退 checkpoint
  梯度范数：突增=不稳定前兆（裁剪梯度）
  吞吐（tokens/s）与 MFU：持续跟踪（下降=硬件退化/管道阻塞）
  硬件健康：ECC 错误/温度/NVLink 错误率
```

loss spike 的处理是「预训练运维」的经典场景：**先回退到 spike 前的 checkpoint、隔离可疑数据分片、再继续**——而不是「硬着头皮跑过去」（spike 常破坏后续收敛）。

## 8. 陷阱清单

- 只算权重显存（忘 Adam 状态与激活）：规划严重失准；16 字节/参数起步。
- 并行策略一刀切（全 ZeRO-3 或全 TP）：通信浪费与效率损失；按拓扑组合。
- FSDP 分片粒度不当（整模型一片 or 每层一片过细）：重构通信开销；按 transformer 块包裹。
- 忘 gradient checkpointing：激活显存爆炸；换显存的算力交易要算账。
- 数据管道无预取：GPU 空转等数据；MFU 与利用率监控暴露。
- checkpoint 太疏或不可恢复验证：长跑训练的生死线；恢复演练。
- loss spike 硬闯：污染后续收敛；回退+隔离数据的标准流程。
- 忽略 MFU：算力白买的最大单一来源；40% 以下必查。

## 9. 小结

- 训练显存的四重账（权重/梯度/优化器/激活）≈ 16 字节/参数起——「训练比推理贵 8 倍」的数学；LoRA 与并行是降账两路。
- 并行光谱按「切什么」记忆：数据（DDP）→ 状态（ZeRO/FSDP）→ 层内矩阵（TP）→ 层间（PP）→ 专家（EP）；真实训练是组合拳。
- 框架吸收复杂度：FSDP/DeepSpeed 让训练代码与单卡几乎一致——决策收缩为「策略+粒度+batch」。
- 效率与容错：MFU 是健康度指标（通信/数据/算子三类瓶颈）；checkpoint 恢复演练是长跑的生命线。
- 数据管道是被低估的另一半：预取/流式/打包——GPU 空转的锯齿曲线是它的指纹。

## 10. 练习

**1.** 显存账本验证：对 7B 模型分别用「普通 Adam FP32」「混合精度」「混合精度+ZeRO-2」「LoRA」估算训练显存，再用框架实际运行（或查文档）对照——四重账的实测校准。

> [!TIP]
> 思路估算与实测的偏差来源：激活值（随 batch/序列变）、框架开销、碎片。账本准了，「这张卡能训多大模型」的规划才有依据。

**2.** ZeRO 阶梯实验：同一 7B 训练任务分别用 ZeRO-1/2/3，记录显存占用与吞吐——验证「切得越细显存越省、通信越多」的权衡曲线。

> [!TIP]
> 思路ZeRO-3 的吞吐损失来自参数聚合通信——「模型越大 ZeRO-3 越必要、模型能装下就别开」。阶梯实验给出「你的模型该停在哪一档」。

**3.** MFU 诊断：写一个「数据加载故意变慢」的训练（加 sleep），观察 GPU 利用率与 MFU 的锯齿——再用预取与并行加载修复——数据瓶颈的检测与治理体验。

> [!TIP]
> 思路GPU 利用率的「锯齿」（算一下停一下）与「平滑高占用」的对比——数据管道健康度的肉眼判据。nvidia-smi 的利用率 ≠ MFU（前者含无效等待）。

**4.** 恢复演练：跑一个数小时训练（带分钟级 checkpoint），中途 kill -9 全部进程——从 checkpoint 恢复并验证 loss 曲线无缝衔接——列出你第一次尝试时漏恢复的状态（[第 8 篇练习 5](../ai/08-training-practice.md)的分布式版）。

> [!TIP]
> 思路分布式恢复的额外状态：各 rank 的数据加载位置、动态 loss scale、优化器分片——漏一个就「恢复了个寂寞」。演练发现的遗漏是基础设施的真实债务。

**5.** PP 与 TP 的组合理解：用 8 卡分别配置「纯 DDP」「TP=2×DP=4」「PP=2×TP=2×DP=2」，画通信拓扑图并解释每种组合的通信模式与适用硬件——「组合拳」的纸上推演。

> [!TIP]
> 思路推演的锚点：TP 的通信重→放 NVLink 机内；PP 的通信轻→跨机；DP 的通信中等→并行维度。拓扑（NVLink 域/IB 域）决定组合——没有通用最优解。

**6.** 讨论：为什么「训练基础设施工程师」成为独立的高价值岗位（而「会调 PyTorch」不等于会建训练系统）？从「硬件与软件的联合设计（拓扑/散热/故障率）」「失败的代价（一次预训练数百万美元）」「效率的复利（MFU 提升 10% = 省下百万级算力）」三个角度分析，并对照 [Web 工程的 SRE](../linux/11-ops-pitfalls.md)——「训练基础设施」是不是「SRE 的 GPU 极端版」？

> [!TIP]
> 思路共性：可靠性与效率的系统工程、故障演练、监控。差异：GPU 的故障率与耦合度（一个 NVLink 故障拖慢千卡）、失败的不可逆代价（预训练中断的经济损失）、优化对象从「延迟」变为「吞吐与 MFU」。基础设施的「乘法效应」：MFU 从 40% 到 50% 在千卡 × 数月尺度上是数百万美元——这就是岗位价值。
