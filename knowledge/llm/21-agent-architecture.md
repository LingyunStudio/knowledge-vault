[第 9 篇](09-agents-tools.md)讲的是 Agent 的「单循环」（模型 → 工具 → 观察 → 继续）——它解决了「能不能动」。当任务变复杂（多阶段、长时程、需要并行与质量把关），单循环不够：需要**架构模式**——把任务分解、把子任务编排、把质量闭环。本篇是 Agent 的「系统设计篇」：模式谱系、多智能体的克制使用、框架地图与评估形态。

## 1. 模式谱系：五种由简到繁的编排

```text
① 提示链（prompt chaining）：任务分解为固定子步骤，顺序调用
   写文案 → 检查事实 → 翻译 —— 每步可加验证闸门
② 路由（routing）：先分类输入，再分流到专门的下游处理
   客服：账单类 → 账单流程；技术类 → 技术流程
③ 并行化（parallelization）：同时跑多个独立子任务，聚合结果
   多路检索（[RAG](08-rag.md)）/ 多角度分析 / 投票
④ 编排者-工人（orchestrator-workers）：中央 LLM 动态分解任务、
   分派给工人 LLM、汇总 —— 「动态版的多路」
⑤ 评估者-优化者（evaluator-optimizer）：一个生成、一个评估，
   循环到通过 —— 带质量闭环的迭代
```

选型原则（Anthropic 的「Building Effective Agents」核心结论）：**从最简单的模式开始，只在测量到需求时升级**。绝大多数「需要 Agent」的场景，一条 prompt 链或路由就够——Agent 循环（[第 9 篇](09-agents-tools.md)）是「任务需要动态决策工具调用」时才上的形态，多智能体更是最后手段。

## 2. Plan-and-Execute：先规划后执行

```text
ReAct（[第 9 篇](09-agents-tools.md)）：走一步看一步——适合短任务，
  但长任务中「忘了最初目标」「走偏不回头」
Plan-and-Execute：先生成完整计划 → 逐步执行 → 按需重规划

计划（LLM）：1. 查航班  2. 查酒店  3. 算预算  4. 生成行程
执行：逐步跑，每步的结果回填
重规划触发：某步失败 / 结果与计划假设冲突
```

两种范式的取舍：

| 维度    | ReAct（边走边想） | Plan-and-Execute（先计划） |
| ----- | ----------- | --------------------- |
| 适应性   | 强（每步可改方向）   | 弱（依赖重规划触发）            |
| 可控性   | 弱（轨迹不可预测）   | 强（计划可审、步数可预算）         |
| 上下文效率 | 历史越来越长      | 计划作为骨架、上下文紧凑          |
| 适用    | 探索性任务、步数少   | 结构化长任务、可预见的流程         |

工程形态常是**混合**：plan 阶段生成任务清单 → 每个子任务内部用 ReAct → 完成后核对计划（plan 的「剩余步骤」是上下文的定海神针，[第 12 篇](12-context-engineering.md)）。

## 3. 反思循环：质量闭环

```text
Reflexion 模式：
生成初稿 → 自我批评（找出问题清单）→ 重新生成 → 循环 N 次

评估者-优化者（[第 1 节模式⑤]）的特化：
worker 生成 → evaluator 按 rubric 打分并给修改意见 → 不合格继续迭代
```

反思的收益集中在**有明确质量标准**的任务（代码可测试、翻译可对照、文案有 rubric）；失效场景：**没有外部验证器的自我反思会「空转」**——模型对「自己看起来对」的东西难以自我纠错。工程对策：**反思的评估者尽量用外部信号**（测试结果/编译器/检索比对）而不是模型自评（[评估体系](15-evaluation-systems.md)）。

## 4. 多智能体：拓扑与克制

```text
拓扑形态：
① 监督者（supervisor）：一个编排 Agent 分派任务给专家 Agent，汇总结果
② 网络/swarm：Agent 之间直接互相移交（handoff）—— 去中心
③ 层级：监督者的监督者 —— 大任务的树形分解

每个 Agent = 独立的 prompt + 工具集 + 上下文
```

多智能体的**正当理由**只有两个（[第 9 篇](09-agents-tools.md)的克制原则展开）：

1. **上下文隔离**：不同子任务需要的上下文互斥且巨大（研究者 Agent 不需要看到客服记录）——分 Agent 让各自的窗口干净。
2. **权限隔离**：不同 Agent 的工具权限不同（只读研究 Agent vs 有写权限的执行 Agent）——爆炸半径的切分。

反模式：**「更像团队」的人海战术**——三个 Agent 互相聊天完成一个本可直接回答的问题。多智能体的成本：通信开销、错误级联（上游 Agent 的错误被下游放大）、调试复杂度（N 个轨迹的交缠）。**默认单 Agent + 好工具，测量到瓶颈再拆**。

## 5. 记忆架构：Agent 的三账本

```text
[第 12 篇](12-context-engineering.md)的记忆三层在 Agent 语境的特化：
① 工作记忆：当前循环的上下文（计划 + 最近轨迹）—— 每步重组
② 情景记忆：任务的完整轨迹（结构化存储）—— 失败复盘与断点恢复
③ 语义记忆：跨任务的领域知识与用户事实（向量库/知识图谱）

长时程 Agent 的记忆治理：
  轨迹超出窗口 → 摘要旧步骤（保留：决定/发现/未完成项）
  跨任务知识 → 抽取到语义记忆（「这个 API 需要 POST」「用户偏好表格输出」）
```

MemGPT 类系统的思想：**把 LLM 当「CPU」、把上下文当「RAM」、把外部存储当「磁盘」**——由 Agent 自己管理「什么进窗口」（分页）。这套机制是长时程 Agent（数小时/数天的任务）的基础设施。

## 6. 框架地图：编排层的生态

| 框架                | 抽象                       | 适合                         |
| ----------------- | ------------------------ | -------------------------- |
| LangGraph         | 图状态机（节点+边+状态）            | 复杂控制流、需要 checkpoint 与人工介入点 |
| OpenAI Agents SDK | 轻量 handoffs + guardrails | OpenAI 生态的简单多 Agent        |
| AutoGen           | 对话式多智能体                  | 多 Agent 对话协作的研究与原型         |
| CrewAI            | 角色化团队                    | 快速搭建「角色分工」原型               |
| 自研循环              | 完全控制                     | 需求清晰、控制力要求高的产品             |

选型的判断框架：**控制流的表达需求**——固定流程用代码硬编排（[第 10 篇](10-deploy-engineering.md)）；动态流程用图框架（LangGraph 的状态机 + 中断恢复 + human-in-the-loop 节点）；研究探索用轻框架。**框架锁定**的代价要评估：Agent 逻辑长在框架的抽象上，迁移成本随复杂度增长——核心业务逻辑尽量写成「与框架无关的函数」，框架只做编排。

## 7. Agent 的评估：轨迹级测试

```text
Agent 的评估比单轮生成难一层——评估的对象是「轨迹」：
① 结果正确性：最终交付物对不对（端到端）
② 轨迹质量：步骤是否合理（走了弯路吗？多余调用吗？）
③ 效率：步数/token 成本/时间
④ 安全：有没有越权工具调用（[第 17 篇](17-llm-security.md)）

评估形态（[第 15 篇](15-evaluation-systems.md)的 Agent 版）：
  固定场景集（初始状态 + 环境模拟）→ 跑 Agent → 轨迹与结果对照评分
  tau-bench 类：模拟用户与工具环境的双重交互测试
```

轨迹评估的分层断言：**最终状态断言**（数据库里订单创建了吗）、**关键动作断言**（调用了退款工具吗）、**路径断言**（没走危险路径吗）——「只看最终答案」会漏掉危险的中间行为。

## 8. 陷阱清单

- 从多智能体起步：先单 Agent + 好工具；拆分的理由只有上下文与权限隔离。
- 无限循环的 Agent：预算/步数/终止判定（[第 9 篇](09-agents-tools.md)三闸）。
- 计划与执行脱节（计划成了摆设）：每步执行后核对计划、重规划有触发条件。
- 反思自评无外部验证：空转；评估者用外部信号（测试/编译/检索比对）。
- 框架长进业务逻辑：核心逻辑与框架解耦；换框架的可行性保留。
- 轨迹不可观测：thought/action/observation 全日志（[第 9 篇](09-agents-tools.md)）——多 Agent 下每层都要。
- Agent 记忆无治理：长时程的上下文堆积（[第 12 篇](12-context-engineering.md)）。
- 评估只看最终结果：中间的越权/浪费行为漏网（轨迹断言）。

## 9. 小结

- 模式谱系从简到繁：提示链 → 路由 → 并行 → 编排者-工人 → 评估者-优化者——「从最简开始，测量到需求再升级」。
- Plan-and-Execute 与 ReAct 的混合是长任务形态：计划是骨架、ReAct 是关节、重规划有触发条件。
- 多智能体的正当理由是隔离（上下文/权限），不是「更像团队」；默认单 Agent。
- 记忆三账本（工作/情景/语义）支撑长时程；框架吸收编排复杂度但业务逻辑保持解耦。
- Agent 评估是轨迹级测试：结果 + 关键动作 + 路径安全三层断言，tau-bench 类环境模拟是前沿。

## 10. 练习

**1.** 模式升级实操：把一个「客服问答」先实现为单循环 Agent，遇到「需要查三个系统再对比」的复杂请求时升级为编排者-工人（三个工人分别查、编排者汇总）——记录两种架构在同一批任务上的成功率与成本。

> [!TIP]
> 思路升级的触发信号：单循环的上下文在多系统检索后膨胀、模型遗漏对比维度——「测量到瓶颈再升级」的实例。

**2.** Plan-and-Execute 实战：实现「组织一次技术分享会」的 Agent（订会议室/准备材料/通知参与者），观察无重规划版本在「会议室被占」时的失败，加入重规划触发对比。

> [!TIP]
> 思路重规划触发的判定：步骤失败 / 结果与计划假设冲突 / 外部状态变化。计划是「可修正的假设」而非「圣旨」——这个心态是 plan-and-execute 的关键。

**3.** 反思消融实验：给一个代码生成 Agent 加/不加「测试驱动反思」（生成 → 跑测试 → 按失败修复），对比通过率与迭代次数——验证「外部验证器是反思有效性的前提」。

> [!TIP]
> 思路没有测试的反思是「自我感觉良好」——有测试的反思是「客观反馈循环」。反思设计的核心投资应该在「验证器」上。

**4.** 多 Agent 拓扑对比：同一研究任务用「单 Agent」与「监督者+三个研究员」分别实现，统计成功率、token 成本、调试时间——用数据检验「多智能体的收益与代价」在你任务上的表现。

> [!TIP]
> 思路预期：多 Agent 在「可并行子任务 + 独立上下文」时收益，在「强串行依赖」时纯开销。你的任务结构决定拓扑——不是流行度。

**5.** LangGraph 状态机实现：把[第 9 篇练习 4](09-agents-tools.md)的保险丝 Agent 用 LangGraph 重写（节点=步骤、边=流转、interrupt=人工确认）——对比自研循环与图框架在「人工介入点」上的表达力。

> [!TIP]
> 思路LangGraph 的 interrupt/checkpoint 让「人工确认点」成为一等公民（可暂停恢复）——自研版要自己实现状态持久化。框架的价值在「这些难点已被解决」。

**6.** 讨论：「Agent 的可靠性天花板」由什么决定——模型智力、架构模式、还是环境设计？从「误差累积的乘法结构」「环境的可验证性」「工具与反馈的质量」三个角度分析，并评估「让环境更可验证」（工具返回结构化结果、操作幂等、沙箱化）比「让模型更聪明」性价比更高的论断——对照 [RLVR 的洞察](13-reasoning-models.md)：可验证性不仅训练推理，也支撑 Agent 的质量闭环。

> [!TIP]
> 思路乘法结构：10 步任务每步 95% 成功率 = 60% 总成功率——提升「每步成功率」（环境反馈 + 小步验证）比「增加模型智力」杠杆更大。环境设计（可验证、可回滚、结构化反馈）是 Agent 可靠性的隐藏半场——模型是引擎，环境是赛道。
