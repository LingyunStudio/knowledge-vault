LLM 应用的陷阱有一个统一根因：**把概率性系统当确定性系统来建**（期待确定输出、用确定性测试、无监控无回滚）。本篇按十类汇编全部 20 篇的审查清单，附「输出质量不稳定」的诊断路线与反模式速查。

## 1. 十类审查清单

### 1.1 LLM 认知与推理（第 1、13 篇）

- [ ] 团队对幻觉/无状态/知识截止的认知一致（培训与文档）
- [ ] 关键输出的验证机制存在（人不审就有校验器）
- [ ] 算术/精确任务走工具（不靠模型）
- [ ] base/chat 模型形态区分（不拿 base 当助手）
- [ ] 推理模型的使用判据明确（按任务路由，非全局开关）
- [ ] 思维预算与任务难度匹配（截断导致的质量崩塌排查）
- [ ] 思维内容不当「真相」展示（它是生成的合理化文本）

### 1.2 上下文与 Prompt 工程（第 3、5、12 篇）

- [ ] prompt 是任务规范（角色/约束/格式/分隔符/边界五件套）
- [ ] 输出用结构化 schema（解码层强制，非祈祷）
- [ ] system prompt 版本化 + 评估驱动修改
- [ ] 上下文预算核算（system/RAG/历史/输出四段构成日志）
- [ ] 历史治理策略明确（滑动/摘要/结构化——70% 预算触发压缩）
- [ ] 记忆抽取质量审计（防幻觉写入）与隐私可删除
- [ ] 关键指令在注意力高密度区（头尾；needle 测试验证过）
- [ ] 复杂流程用状态机骨架（非隐式历史驱动）

### 1.3 检索（RAG，第 8 篇）

- [ ] 检索质量有评测（golden 对 + Recall\@K）
- [ ] 混合检索（向量 + BM25）覆盖关键词场景
- [ ] 重排存在（召回宽 + 精排准）
- [ ] 分块策略经过实验（父子分块/结构感知优先）
- [ ] 引用与拒答机制（材料外问题显式说「不知道」）
- [ ] 索引与文档同步（增量更新管道）

### 1.4 结构化输出（第 14 篇）

- [ ] 解码层约束存在（strict schema/文法——非 prompt 祈祷）
- [ ] schema 扁平化设计（适配约束系统的限制）
- [ ] 语义校验层（schema 合规 ≠ 值正确——业务规则校验）
- [ ] 重试携带错误信息（ValidationError 喂回）
- [ ] 可解析率与字段准确率的评估齐备

### 1.5 Agent 行为（第 9 篇）

- [ ] 工具 description 是「选择器」级质量
- [ ] 最大步数/成本上限/高危确认三保险丝
- [ ] 轨迹全日志（thought/action/observation）
- [ ] 工具返回整形（大 JSON 不直塞上下文）
- [ ] 失败路径设计（工具失败的重试/换路/汇报）

### 1.6 评估与成本（第 10、15 篇）

- [ ] golden 测试集存在且进 CI（prompt/模型改动的回归）
- [ ] 分层评估（提示层秒级/系统层发布/模型层换版）
- [ ] LLM 评分经过人工校准（位置/长度/自偏好偏差意识）
- [ ] 确定性断言先行（能下沉的检查不下沉给 LLM 裁判）
- [ ] 线上坏例回流测试集的机制
- [ ] token 成本看板与告警；模型分层路由
- [ ] 多模型抽象（降级/切换/路由的自由）

### 1.7 安全与合规（第 10、17 篇）

- [ ] 数据出域合规评估（云 API 的敏感数据审查）
- [ ] 提示注入的纵深防线（逐层绕过率已测量）
- [ ] 越狱的红队回归集（按家族统计 ASR）
- [ ] 护栏分级（规则先行→分类器→人工确认——延迟预算内）
- [ ] 数据外泄面检查（prompt/记忆/日志的敏感信息）
- [ ] 安全事件的响应预案

### 1.8 多模态（第 16 篇）

- [ ] 图像分辨率按任务选（token 成本平方敏感）
- [ ] 计数/测量任务走检测模型（VLM 不擅长）
- [ ] 视觉幻觉防线（位置引用 + 诱导测试）
- [ ] 文档理解的版式保留（截图方案 vs OCR 的选型依据）
- [ ] 语音链路的延迟预算拆解（ASR/LLM/TTS 各段）

### 1.9 训练与数据（第 4、7、18、19 篇）

- [ ] 微调的决策树走过（prompt/RAG 先行；行为定制才微调）
- [ ] 训练显存的心账本准（四重账；LoRA/QLoRA 按需）
- [ ] 数据质量审计（蒸馏风格污染/输入分布匹配）
- [ ] 灾难性遗忘的回归测试（新旧双评测）
- [ ] 合成数据的比例控制与血统记录（模型崩塌防线）
- [ ] 数据版本与 lineage（可复现可归因）
- [ ] 分布式训练的恢复演练（checkpoint 完整性）

### 1.10 本地部署（第 20 篇）

- [ ] 显存心账本准（权重 + KV + 开销）；量化档位按任务回归
- [ ] 解码速度满足场景（带宽约束的实测）
- [ ] 许可证审计（商用/再分发/微调产物）
- [ ] 混合路由的敏感检测召回率审计
- [ ] 离线降级形态演练过（断网功能子集）

## 2. 「输出质量不稳定」的诊断路线

```text
症状：同一个功能时好时坏 / 换模型就崩 / 改 prompt 牵一发动全身

按层诊断：
① 输入层：输入真的相同吗？（RAG 检索结果变了？上游数据变了？）
   → 记录完整输入对比（token 级 diff）
② prompt 层：prompt 的版本一致吗？（有人的临时改动上线了？）
   → prompt 版本化 + diff
③ 模型层：模型/版本/后端变了吗？（供应商静默更新！）
   → 钉版本 + 定期基准回归
④ 采样层：温度/参数/思维预算变了吗？（t=0 也有实现级噪声）
   → 参数随请求记录
⑤ 上下文层：上下文的构成漂移了吗？（记忆/RAG/历史治理改了？）
   → 装配日志对比（[第 12 篇](12-context-engineering.md)）
⑥ 评估层：你的「好」标准稳定吗？（LLM 评分的漂移）
   → 评分器校准 + 人工抽检
⑦ 任务层：任务本身在边界上（本来就难）？
   → 错误分析：坏例的分类与共性
```

诊断的元原则：**先固化输入与配置，再谈「模型不稳」**——大部分「LLM 不稳定」是「系统各层在静默变化」的叠加（上游数据、RAG 索引、prompt、模型版本四层都可能动过）。

## 3. 反模式速查

| 反模式                   | 一句话修复                                            |
| --------------------- | ------------------------------------------------ |
| 「接个 GPT 就上线」（无评估无监控）  | golden 集 + 回归 + 看板先行                             |
| prompt 硬编码散落代码        | 集中管理 + 版本化 + 模板                                  |
| 把 LLM 当数据库/搜索引擎       | RAG/工具的架构定位（[第 1 篇](01-what-is-llm.md)）          |
| 上下文无限堆积（历史/文档全塞）      | 预算核算 + 摘要裁剪（[第 12 篇](12-context-engineering.md)） |
| 微调当知识灌注               | 知识走 RAG（[第 7 篇](07-fine-tuning-peft.md)）         |
| 全自动 Agent 无保险丝        | 步数/成本/确认三闸（[第 9 篇](09-agents-tools.md)）          |
| 一次性 prompt 调优（无回归验证）  | 评估驱动迭代                                           |
| 单模型单供应商裸奔             | 抽象层 + 降级 + 多模型                                   |
| 工具返回原始数据直塞上下文         | 摘要化 + 按需详情                                       |
| 「AI 输出不用 review」的流程设计 | 校验器 + 抽检 + 关键点人审                                 |
| JSON 靠 prompt 祈祷      | 约束解码 + 校验重试（[第 14 篇](14-structured-output.md)）   |
| 简单任务用推理模型             | 任务路由（[第 13 篇](13-reasoning-models.md)）           |
| 高分辨率图片直塞              | ROI 裁剪 + 分辨率预算（[第 16 篇](16-multimodal.md)）       |
| prompt 声明当安全防线        | 分类器 + 权限 + 沙箱（[第 17 篇](17-llm-security.md)）      |
| 训练显存只算权重              | 四重账（[第 18 篇](18-training-infra.md)）              |
| 合成数据无比例控制             | 真实数据锚点（[第 19 篇](19-data-engineering.md)）         |
| 「能装下就能跑快」的端侧幻觉        | 带宽心算（[第 20 篇](20-local-edge.md)）                 |

## 4. LLM 应用的问题追问清单

```text
□ 这个功能的「失败」定义是什么？失败率多少可接受？
□ 幻觉的业务后果？（可容忍的幻觉率与场景隔离）
□ 模型的知识截止与任务的时效要求匹配吗？
□ 用户数据进模型链路的合规结论是什么？
□ prompt/模型/检索的变更流程是什么？（谁审、怎么测）
□ 上线后的质量监控信号是什么？（用户反馈/漂移/抽检）
□ 模型不可用时业务的降级形态？
□ 成本上限与告警线？
□ 恶意用户的攻击面（注入/滥用）评估了吗？
□ 多模态输入的预算与失败模式评估了吗？（若有）
□ 推理模型的路由判据与成本曲线测过吗？（若有）
□ 六个月后的维护者能理解这套 prompt/RAG 的设计吗？
```

与 [AI 工程清单](../ai/11-pitfalls.md)的对照：LLM 追加的维度是「非确定性」「上下文工程」「供应商生态」——三者的制度化同样是「把看不见的风险变成流程约束」。

## 5. 小结

- 十类清单的分布：认知类（幻觉/无状态）是设计错误的源头、评估类（回归/校准）是迭代的地基、安全类（注入/合规）是上线的闸门、数据类（血统/配比）是能力的上限。
- 「输出不稳定」的七层诊断（输入/prompt/模型/采样/上下文/评估/任务）——先固化再谈不稳；大部分「不稳」是静默变化的叠加。
- 反模式的总根：「demo 心态」（接个 API 就上线）——评估、成本、安全三支柱的缺席。
- 追问清单的核心三问：失败定义、幻觉后果、回滚路径——答不出即技术债。
- 与 [AI 工程清单](../ai/11-pitfalls.md)的连续性：LLM 是「非确定性系统」的极端形态——概率化验收、监控即测试、护栏即流程的思想一脉相承。

## 6. 练习

**1.** 用十类清单审查一个真实 LLM 应用（公司的或开源的），统计命中分布——验证「评估类与安全类最常缺席」的预期，并补充领域特定项。

> [!TIP]
> 思路领域补充的例子：客服（拒答话术/情绪处理）、代码生成（执行沙箱/测试闭环）、医疗（合规层级）——通用清单 + 领域增量。

**2.** 「不稳定」诊断实战：构造一个三层静默变化的场景（RAG 索引更新 + prompt 微调 + 模型换小版本），只看输出现象诊断——用第 2 节路线逐层排除，体会「固化输入」的排查价值。

> [!TIP]
> 思路诊断的实操难点：三层同时变时「单变量归因」不可能——所以「每次只动一层」的发布纪律是诊断能力的前提（[变更纪律](../git/02-daily-workflow.md)）。

**3.** 追问清单演练：对一个上线 LLM 功能逐问打分，把「答不上」的题目转化为 action item（每题指定负责人与期限）——体验「问题清单 → 技术债清单」的转化。

> [!TIP]
> 思路action item 的优先级排序：数据合规与回滚类（红线）> 评估监控（地基）> 成本优化（效率）。红线类不解决不上量——上量前的时间窗口是修复期。

**4.** 为你的 LLM 应用设计「发布检查单」：从十类清单中提炼 15 条上线前必查项（含验证方式），模拟一次「带新 prompt 上线」的流程走查。

> [!TIP]
> 思路检查单的可执行性标准：每条附验证方式（回归通过/告警配置截图/评审记录）——「检查过」要有证据形态。与 [docker 上线检查单](../docker/11-pitfalls.md)的合并使用。

**5.** 反模式案例写作：挑三个你踩过（或观察到的）LLM 应用反模式，按「现象→排查→根因→修复→预防」写成案例条目——沉淀为团队的知识库。

> [!TIP]
> 思路案例的稀缺信息在「排查弯路」——直奔答案的故事没有教学价值。弯路记录帮助新人建立「正确的第一反应」。

**6.** 讨论：LLM 应用工程的「终局形态」是什么？当前的自建管线（prompt/RAG/Agent 手搓）会像 [Web 工程的演化](../frontend/08-modules-tooling.md)（原生→框架→平台）一样收敛到平台化吗？从「哪些层会标准化（检索/评估/护栏/上下文管理）」「哪些层保持差异化（任务规范/领域数据/评估集）」「锁定效应」三个角度，给出你对「应用层价值将沉淀在哪里」的判断。

> [!TIP]
> 思路收敛预测：基础设施层（推理/缓存/评估工具/护栏框架/上下文管理）快速标准化（供应商化）；差异化沉淀在「领域数据 + 任务规范 + 业务闭环」——prompt 与 RAG 的「怎么搭」会标准化，「搭什么内容」永远是 yours。与 [npm 生态](../python/08-modules-packages.md)的历史对照：工具层商品化，应用层的价值反而因工具普惠而放大。
