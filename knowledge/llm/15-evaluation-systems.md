[第 10 篇](10-deploy-engineering.md)说过「没有评估的 prompt 修改是赌博」——本篇把评估体系讲成一个可构建的工程系统：**测什么（对象分层）、用什么测（断言与裁判）、在哪测（CI 与线上）**。评估体系是 LLM 应用的「仪表盘 + 回归测试 + 质量门禁」三合一，是所有迭代（prompt/RAG/模型/微调）的安全网。

## 1. 评估的对象分层

```text
三层对象，各自需要不同的评估：
① 模型层：换模型/升级版本的「能力对比」—— 基准 + 任务集
② 系统层：RAG/Agent/整条链路的「端到端效果」—— 端到端评估集
③ 提示层：prompt/参数改动的「回归检查」—— golden 快速回归

三层的测试频率与成本不同：
  模型层：换模型时跑（贵、全量）
  系统层：每次发布跑（中）
  提示层：每次改动跑（便宜、秒级）
```

「评估缺失」的典型形态：团队只在 demo 阶段人工看过效果，上线后「感觉变差了」但说不出哪次改动导致——**没有分层评估，就没有归因能力**。

## 2. 基准地图与数据污染

```text
公开基准的能力面：
  MMLU/MMLU-Pro        知识广度（多学科问答）
  GPQA                 专家级科学推理
  HumanEval/LiveCodeBench 代码生成
  SWE-bench            真实软件工程任务（修 bug）
  MATH/AIME            数学推理
  LMArena（Chatbot Arena）人类盲测偏好排名

数据污染（contamination）：基准题目混进了训练数据
  → 分数虚高，不反映真实能力 → 「 benchmark 分数与实际体验脱节」的根源
```

基准的正确用法：**粗粒度的能力对比与趋势参考**——绝不作为「选型决策」的唯一依据（你的任务 ≠ 基准任务）。选型的真正依据是**你自己任务的评估集**（下一节）：用 50~200 条真实业务样本测试候选模型，比任何榜单都准。

## 3. 构建黄金测试集：评估的地基

```text
黄金集（golden set）的构成工艺：
① 来源：真实流量的分层抽样（高频场景 + 边界案例 + 历史坏例回流）
② 规模：20 条即可起步 → 100 条覆盖主要模式 → 300+ 生产级
③ 标注：每条 = 输入 + 期望行为（关键词/结构/要点清单/参考答案）
④ 维护：线上坏例持续回流（[第 10 篇](10-deploy-engineering.md)的质量飞轮）

分类覆盖检查表（构造时的清单）：
□ 每个主要功能路径 ≥ 3 条
□ 每类已知的历史 bug 一条回归
□ 边界：空输入/超长输入/多语言/格式怪异
□ 对抗：注入尝试/越界请求（安全回归）
```

黄金集的反模式：**只收集「正常流量」**——评估集没有边界与对抗样本 = 「晴天测试」。**测试集的标注成本**是真实的（每条几分钟）——优先覆盖「出错代价高」与「高频」的场景。

## 4. LLM-as-judge：设计、偏差与校准

```python
JUDGE_PROMPT = """你是一个严格的评估员。根据标准评估以下回答。

任务：{task_description}
评分标准：
- 5 分：完全满足所有要求，信息准确
- 3 分：满足主要要求，有小遗漏
- 1 分：未满足任务

回答：{answer}
参考要点：{rubric}

只输出 JSON：{{"score": n, "reason": "一句话理由"}}"""

# ★ 校准：先人工评 20~50 条 → 对比 LLM 评分与人工评分的一致性
#   一致率（±1 分内）> 90% 才可信；分歧样本用于修正评分 prompt
```

LLM-as-judge 的已知偏差与对策：

| 偏差               | 表现                                       | 对策                              |
| ------------------ | ------------------------------------------ | --------------------------------- |
| 位置偏差           | 成对比较时偏向「先出现的」                   | 交换顺序各评一次取一致结果        |
| 自偏好             | 偏好自己（同家族模型）的输出                 | 用不同家族的模型当裁判            |
| 长度偏差           | 偏好更长更详细的回答                         | 评分标准里显式惩罚冗长            |
| 宽松/严苛漂移      | 不同批次评分尺度漂移                         | 固定锚点样本随批评估              |

裁判的工程纪律：**裁判模型 ≠ 被评模型**（自评偏好的规避）；**裁判结论人工校准**（首批 20~50 例对齐尺度，之后抽检）；**裁判的输出要结构化**（分数+理由——理由用于诊断而非直接采信）。

## 5. 断言库：确定性先于概率性

```python
def evaluate(output: str, case: GoldenCase) -> EvalResult:
    checks = []
    # ① 确定性断言（免费、稳定、必配）
    checks.append(("格式", is_valid_json(output)))
    checks.append(("必含字段", all(k in output_json for k in case.required_fields)))
    checks.append(("禁词", not any(w in output for w in case.forbidden)))
    checks.append(("长度", min_len <= len(output) <= max_len))
    # ② 相似度断言（半确定）
    checks.append(("要点覆盖", coverage(output, case.key_points) >= 0.8))
    # ③ LLM 断言（贵、用于语义判断）
    checks.append(("语义符合", judge_score(output, case.rubric) >= 4))
    return combine(checks, weights=...)
```

断言的分层原则：**能确定性的不相似度、能相似度的不 LLM 评分**——确定性断言免费且 100% 稳定，LLM 评分留给「语义质量」这种只能判断的部分。混合加权后的总分是「回归门禁」的依据。

## 6. 在线评估：真实世界才是终审

```text
在线信号的三层：
① 显式反馈：点赞/点踩（稀疏但有价值——坏例回流评估集）
② 隐式反馈：用户编辑量（AI 草稿被改多少字=质量代理）、采纳率、复述率
③ 业务指标：任务完成率/升级人工率/留存（[第 4 篇](../ai/04-evaluation.md)的离线-在线差异）

抽检制度：每日随机 N 条线上输出人工评分 —— 监控「静默劣化」
（模型供应商静默更新/上游数据变化——[第 21 篇](28-pitfalls.md)的漂移诊断）
```

在线与离线的闭环：**线上坏例 → 回流黄金集 → 回归测试覆盖 → 同类错误不再复发**——这个飞轮是 LLM 应用质量随时间「上升而非衰减」的唯一机制。

## 7. CI 回归：评估进流水线

```yaml
# prompt/模型/RAG 改动 → 自动跑评估 → 门槛门禁
steps:
  - run: pytest tests/ --timeout 300          # 单元/集成
  - run: python evals/run.py --suite golden --threshold 0.85
  - run: python evals/run.py --suite safety --threshold 1.0   # 安全是硬门禁
  - run: python evals/run.py --suite regression --baseline main
```

CI 的设计要点：**分级套件**（快速回归 30 例秒级 → 全量 golden 夜间跑 → 全量评估发布前）、**门槛与基线对比**（不只绝对阈值，还与 main 分支的基线对比防「慢性劣化」）、**失败的可诊断性**（评估报告输出每个失败案例的输入/输出/评分理由）。与[传统 CI](../python/12-quality.md) 的差异：评估结果是**分布性**的——门槛要考虑波动（多次运行或温度 0）。

## 8. 陷阱清单

- 无评估直接上线迭代：所有改动都是赌博。
- 评估集只有「好案例」：无边界与对抗样本 = 晴天测试；坏例回流机制。
- LLM 裁判不校准直接采信：位置/长度/自偏好偏差；人工对齐 20~50 例起步。
- 只评「语义质量」不做确定性断言：格式/必含字段这类免费检查缺失。
- 测试集污染进 prompt 迭代（对着测试集优化到过拟合）：留真正的 hold-out。
- 评估跑一次就归档：模型/上游/需求的漂移使旧评估失效；定期重跑与更新。
- 单指标门禁：多维度（质量/延迟/成本/安全）的组合门槛。
- 忽略评估本身的成本（LLM 评分也是钱）：分层套件控制预算。

## 9. 小结

- 评估的三层对象（模型/系统/提示）频率与成本各异——「分层」才有归因能力。
- 公开基准是参考不是决策依据；自建黄金集（真实流量分层 + 坏例回流）才是选型与回归的地基。
- LLM-as-judge 要校准：位置/长度/自偏好三大偏差 + 人工对齐 + 固定锚点。
- 断言分层：确定性免费优先、相似度居中、LLM 评分留给语义——混合加权成门禁。
- 在线信号与 CI 回归构成质量飞轮：坏例回流 → 测试覆盖 → 不再复发——评估是「持续系统」的仪表盘。

## 10. 练习

**1.** 黄金集构建实战：为「会议纪要总结」功能构建 30 例评估集——从真实/模拟会议记录分层采样（常规/超长/多人冲突发言/无明确结论），每条标注要点清单——写下你的分层策略与标注规范。

> [!TIP]
> 思路标注规范的要点：「要点」的粒度（一条=一个可验证的陈述）、边界案例的期望行为定义（无结论的会 → 应输出「无明确结论项」）。规范先于标注，否则标注员各自理解。

**2.** LLM 裁判校准实验：人工评 30 条（1~5 分），同批让 LLM 评——计算一致率与分歧分布；针对分歧最大的 5 条修正评分 prompt 再评——体验「裁判校准」的迭代循环。

> [!TIP]
> 思路常见分歧根因：人工考虑了「上下文/用户身份」而裁判不知道（把上下文喂给裁判）、评分档位定义模糊（给出每档的具体例子）。

**3.** 断言分层改造：把一个「纯 LLM 评分」的评估改造成「确定性断言 + 相似度 + LLM 评分」三层——对比改造前后的评估成本与稳定性（同输入重复跑，看分数方差）。

> [!TIP]
> 思路稳定性对比：LLM 评分在温度>0 或不同批次下有波动、确定性断言恒定——「能下沉的断言尽量下沉」让总评估又稳又省。

**4.** CI 门禁演练：搭一个评估流水线（golden 套件 + 阈值），然后做两次演练——「改坏 prompt」必须被拦、「无害重构」必须通过——校准门槛的松紧。

> [!TIP]
> 思路门槛的调参：太松放过退化、太紧阻断迭代——用「历史好版本的分数分布」定门槛（如 ≥ 基线均值 − 1 个标准差）。

**5.** 坏例回流机制：实现「线上用户点踩 → 自动进入待审队列 → 人工确认后回流评估集」的最小管道——一个月后统计评估集中「来自线上坏例」的占比，验证飞轮转动。

> [!TIP]
> 思路回流的关键设计：去重（同类坏例合并）、脱敏（用户数据）、确认（不是所有点踩都是模型错）。飞轮的转速 = 坏例捕获率 × 确认吞吐。

**6.** 讨论：为什么 LLM 评估无法像传统软件一样「写完测试就一劳永逸」？从「正确答案的开放性」「输入与模型的共同漂移」「评估集自身会过拟合」三个角度分析「评估的持续维护成本」，并思考「自动化的评估集进化」（用模型挖掘评估盲区）的风险与价值——评估系统的「元问题」。

> [!TIP]
> 思路评估集是「对任务空间的有限采样」——模型/需求/数据的漂移会让采样盲区暴露为新事故。自动进化（模型生成边界案例）有价值但要人工确认（[数据合成](19-data-engineering.md)的同款纪律）——「评估系统本身也需要评估」是元问题的元问题。
