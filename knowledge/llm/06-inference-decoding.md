调用 API 时只看到流出的文字，背后是一次自回归循环：**每次前向计算只生成一个 token，然后把它拼回输入继续**。理解这个循环，temperature、上下文长度计费、显存估算就全都有了物理解释。

## 两阶段：Prefill 算力密集，Decode 显存密集

```text
Prompt: "今天天气"  ──Prefill(并行算完整个输入)──▶  首个 token "很"
        "今天天气很" ──Decode(一次一个)──▶ "好" ──▶ "，" ──▶ …
```

- **Prefill（预填充）**：把整个 prompt 并行过一遍模型，填好 KV Cache。计算密集，决定**首 token 延迟（TTFT）**
- **Decode（解码）**：之后每生成一个 token，只做一次"单 token 前向"。瓶颈是显存带宽——每生成一个字都要把全部参数和缓存读一遍

所以长 prompt 的应用（RAG、长文档）首字慢、逐字快；这是服务端做 prompt caching（缓存已算好的前缀 KV）的原因——系统提示和公共前缀不必每次重算。

## KV Cache：用显存换速度

Decode 阶段每生成一个 token，都要拿新 token 的 Q 去和**之前所有 token 的 K、V** 做注意力。重算历史 K/V 太浪费，于是缓存起来——KV Cache：

```text
显存 ≈ 2(缓 K 和 V) × 层数 × KV头数 × 头维度 × 序列长度 × 精度字节 × 并发数
```

以 7B 模型、FP16、8K 序列为例，缓存可达 GB 级——**长上下文的显存大头是缓存而非权重**。这也解释了两件事：批处理并发越高、上下文越长，显存越爆；以及 MQA/GQA（多查询/分组查询注意力）为什么成了标配——它们砍 KV 头数，直接压缩缓存。

## 采样参数：从概率分布里怎么挑下一个词

模型每步输出的是词表上的概率分布，怎么选下一个 token 由参数决定：

| 参数 | 作用 | 建议起点 |
| --- | --- | --- |
| temperature | 分布的"温度"：→0 几乎总取最优，→∞ 趋向均匀 | 事实/代码 0~0.3，创作 0.7~1.0 |
| top_p（核采样） | 只从累计概率达 p 的最小集合里采样 | 0.9~0.95，一般只调 temp 或 top_p 之一 |
| top_k | 只保留概率前 k 个候选 | 常用 20~50 |
| max_tokens | 生成上限 | 防跑飞，按任务给足 |
| repetition_penalty | 惩罚已出现的 token，抑制复读 | 1.0~1.2，过高伤语法 |

> [!TIP]
> 要"稳定、可复现"：temperature=0（贪心解码）+ 固定 seed。要"发散、多方案"：temperature 0.8+。**工程默认值不是越低越好**——过低的温度会让长文本生成陷入重复循环。

## 流式与吞吐

- **流式输出（stream）**：逐 token 推给客户端，体感延迟大幅降低——首 token 时间不变，但用户不用干等全文
- **吞吐优化在服务端**：Continuous batching（新请求随时插入批）、投机采样（小模型起草、大模型并行验证）等，是 vLLM 这类推理引擎（第 10 篇）的核心竞争力

> [!NOTE]
> 采样有随机性，同一提示两次输出不同是**设计使然**。评测和回归测试要控制温度与 seed，或改为"断言结构/要点"而非全文比对——把随机性当 bug 治，是评测框架常见的第一坑。
