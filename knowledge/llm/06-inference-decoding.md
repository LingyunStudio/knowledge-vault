LLM 的「回答」不是一次成型——**逐 token 的采样循环**：每一步从概率分布中挑一个 token。解码策略（怎么挑）与推理工程（怎么算得快）决定输出质量与成本。本篇把「采样的语义」与「推理的吞吐」讲成一套账本。

## 1. 采样机制：从 logits 到 token

```text
每步：logits（词表上的原始分数）→ 温度缩放 → softmax 概率 → 采样规则选 token

温度（temperature）：分布的「尖锐度」旋钮
  T→0：贪心（永远选最高分——确定性最强、多样性最低）
  T=1：原始分布
  T>1：更平坦（更随机、更有创意、更易胡说）

top-k：只保留概率最高的 k 个候选（砍掉长尾）
top-p（核采样）：保留累计概率达 p 的最小候选集（动态候选数）
```

参数选型的语义（不是玄学是工程）：

| 场景                     | 推荐参数                              |
| ------------------------ | ------------------------------------- |
| 结构化输出/代码/分类     | **T=0 或低温**（稳定性优先）          |
| 创意写作/头脑风暴        | T=0.8~1.2 + top-p 0.9~1（多样性优先） |
| 客服/事实问答            | 低温 + top-p 0.9（稳定但不过死板）    |
| 采样多样性策略（self-consistency） | 高温采样多条 + 投票（[第 5 篇](05-prompting.md)）|

repetition penalty/frequency penalty：抑制重复——对话与长文本生成常用；副作用是「必要的重复」也被惩罚（代码的关键词）——按任务调。

## 2. 推理的两阶段与 memory-bound

```text
prefill（预填充）：处理整段 prompt —— 一次大矩阵乘（GPU 并行满载，快）
decode（解码）：逐 token 生成 —— 每步只算一个 token 的 Q（算不满，受限于显存带宽）
```

解码阶段的本质是 **memory-bound**：每生成一个 token 要把全部权重与 KV 从显存读一遍——**瓶颈是带宽不是算力**。三个推论：

1. **批处理几乎免费**：多个请求共享同一次权重读取——吞吐随 batch 近线性涨（GPU 算力本来就没用满）。
2. **量化降带宽**：INT4 权重 = 读取量 ÷4 → 解码提速 ~2-4x（量化的速度收益不止是显存）。
3. **小模型投机解码**：小模型快速草拟多个 token → 大模型一次并行验证——把「逐 token」变成「逐段验证」。

## 3. 吞吐工程：continuous batching 与 vLLM

```text
静态 batching（传统）：一批请求一起生成，等最长的完成——短请求陪跑（GPU 空转）
continuous batching（vLLM）：某请求完成立刻补新请求进来——GPU 永远满载
+ PagedAttention：KV 显存的分页管理（[第 3 篇](03-transformer-llm.md)）——碎片 80%→4%
```

vLLM 的两项创新让 LLM 服务的吞吐提升数倍到十数倍——「LLM 推理服务的技术门槛」从「能不能跑」变成「KV 管理与调度」。吞吐与延迟的权衡（batch 越大吞吐越高、单请求延迟越高）是服务容量规划的主轴。

```bash
# 自托管的主流选择
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 32768
ollama run qwen2.5:7b          # 本地/桌面（llama.cpp 内核，GGUF 量化）
```

| 框架        | 定位                             | 特点                                |
| ----------- | -------------------------------- | ----------------------------------- |
| vLLM       | 生产服务（高吞吐）               | continuous batching + PagedAttention |
| llama.cpp   | 端侧/本地（GGUF 量化）           | CPU/低资源可跑；生态 ollama          |
| SGLang      | 高吞吐 + 结构化生成              | RadixAttention 前缀缓存              |
| TensorRT-LLM| NVIDIA 极致性能                  | 编译优化；配置复杂                    |

前缀缓存（prefix caching）：**相同 system prompt/RAG 前缀的 KV 复用**——多轮对话与固定 prompt 场景的成本杀手（ TTFT 显著下降）。

## 4. 量化推理与端侧

```text
量化谱系（[第 3 篇](03-transformer-llm.md)的显存账本落地）：
FP16（14GB/7B）→ INT8（7GB）→ INT4（3.5GB）→ 混合精度（关键层保精度）

GGUF/llama.cpp 系：Q4_K_M 等「混合块量化」——大小与质量的工程平衡点
端侧约束：手机 NPU/内存带宽——小模型 + 量化是唯一组合（[第 3 篇](03-transformer-llm.md)的心账本）
```

量化的精度代价不均匀：**小模型量化伤更大**（容量冗余少）、 perplexity 的变化要配合下游任务的回归测试（[第 10 篇](10-deploy-engineering.md)）。「质量-速度-显存」三角的每个点都是决策。

## 5. 陷阱清单

- 创意任务用 T=0（输出死板同质）/ 事实任务用高温（幻觉放大）：参数按任务语义配。
- 「temperature=0 = 确定」的误解：实现级非确定仍在；严格复现要钉后端与版本。
- 长输出不考虑生成长度上限与停止序列：失控生成烧钱；max_tokens + stop 序列标配。
- 不用前缀缓存：固定 system prompt 反复付费；结构化 prompt 顺序（稳定前缀在前，[第 5 篇](05-prompting.md)）。
- 吞吐与延迟不分：「QPS 高」与「响应快」是两个指标（batch 权衡）。
- 量化后不做任务回归：perplexity 正常但下游任务退化；黄金集回归测试。
- 流式输出（SSE/stream）忘掉：长回答的感知延迟（TTFT/TBT）是体验核心——用户等的是「开始看到字」。

## 6. 小结

- 采样的语义：温度是尖锐度、top-k/p 砍长尾、惩罚控重复——参数按「稳定性 vs 多样性」的任务语义配。
- 推理两阶段：prefill 算力满载、decode 带宽受限——「memory-bound」推出批处理免费、量化提速、投机解码三结论。
- vLLM 的 continuous batching + PagedAttention 是吞吐革命；前缀缓存是固定 prompt 的成本杀手。
- 量化谱系（FP16→INT8→INT4/GGUF）的「质量-速度-显存」三角：按部署约束选点，回归测试兜底。
- 「确定性」的工程定义精确到解码参数与后端；流式输出的 TTFT/TBT 是感知延迟的核心。

## 7. 练习

**1.** 采样参数语义测绘：同一创作 prompt 在 T∈{0, 0.7, 1.0, 1.3} 各生成 10 次，人工评估质量与多样性——为「客服」「写作」「代码」三个场景各定一套参数并写理由。

> [!TIP]
> 思路评估维度分开：流畅性/多样性/事实性。T>1.2 的「创意」常是「胡言」——多样性的正确来源是 prompt（[第 5 篇](05-prompting.md)）而不是高温的失控。

**2.** 吞吐压测：用 vLLM（或任意框架）测「batch=1/8/32/64」的吞吐（token/s 总和）与单请求延迟——画出吞吐-延迟曲线，找到你服务的容量拐点。

> [!TIP]
> 思路曲线的两个读数：吞吐随 batch 上升（斜率放缓）、单请求延迟随 batch 上升——SLO（P99 延迟上限）反推最大 batch。容量规划（[第 10 篇](10-deploy-engineering.md)）的数据源。

**3.** 量化回归实验：同一模型 FP16 vs Q4 在三个任务（摘要/代码/数学）的对比——验证「量化损失不均匀」（数学/长推理更敏感），建立「量化必须任务回归」的流程。

> [!TIP]
> 思路perplexity「看起来没差多少」但多步推理任务掉分明显——困惑度与下游能力不同构。黄金任务集（[第 10 篇](10-deploy-engineering.md)）是量化验收的标准。

**4.** 前缀缓存收益测量：多轮对话场景（固定 system prompt + 递增历史），对比开/关前缀缓存的 TTFT 与成本——推导「prompt 结构（稳定前缀在前）」对缓存的利用。

> [!TIP]
> 思路缓存的命中前提是「前缀完全一致」——prompt 里把动态内容放后、静态放前（[第 5 篇](05-prompting.md)）直接决定缓存命中。多轮对话的「历史 append 而非重排」同样是缓存友好的结构。

**5.** 流式体验改造：把一个长回答接口从「等待完整响应」改为流式（SSE），用秒表测「首字时间」与「总完成时间」的感知差异——定义你的 TTFT 目标。

> [!TIP]
> 思路感知延迟的组成：TTFT（首字）比总时长更影响体验。流式 + 前缀缓存 + 解码速度（[第 3 篇](03-transformer-llm.md)）三层共同决定 TTFT。

**6.** 讨论：为什么 LLM 推理的优化史（KV 缓存→continuous batching→PagedAttention→投机解码→前缀缓存）几乎全是「显存与带宽」的故事，而不是「算力」的故事？从「自回归解码的计算结构」（每 token 一读全模型）推演 memory-bound 的必然性，并预测「长上下文时代」下一个瓶颈（长注意力的计算回升？KV 压缩？）。

> [!TIP]
> 思路自回归 = 每 token 触发一次「全权重遍历」——算术强度（计算/访存比）极低，天然 memory-bound。长上下文把注意力计算拉回 O(n²)（prefill 端），计算与带宽的瓶颈在轮换——推理优化的历史就是「找到当前瓶颈→消灭它→暴露下一个」的循环。
