「Prompt 工程」这个词正在被「**上下文工程（context engineering）**」取代——因为 LLM 应用的真正难点不再是「怎么措辞指令」，而是**每次调用时，往有限的窗口里放什么**：system 规范、工具定义、检索材料、对话历史、中间推理——每一块都在争夺同一个预算，且互相稀释注意力（[第 3 篇](03-transformer-llm.md)的 lost in the middle）。上下文工程 = **在窗口约束下，为当前这步推理组装最优信息集**。

## 1. 上下文的经济学：三重稀缺

```text
窗口预算的三重约束：
① 容量：窗口有上限（32K~1M+）——超限即截断或报错
② 注意力：内容越多，每个 token 获得的「注意力密度」越低
   （模型对中间内容的 recall 显著低于头尾——[第 3 篇](03-transformer-llm.md)）
③ 成本：每次调用的输入 token 都计费——上下文膨胀 = 成本线性放大

推论：往上下文里放任何东西都要回答——
「它对「这一步」的推理有多大贡献？能否用更少的 token 表达同等信息？」
```

上下文膨胀是渐进的杀手：**demo 时 2K 上下文效果很好 → 上线后 RAG 材料 + 十轮对话 + 工具结果堆到 50K → 关键指令淹没在中间 → 质量悄然劣化**。治理必须在架构里，不能靠「事后精简」。

### 1.1 构成解剖：预算分配表

```text
一次典型 Agent 调用的上下文构成（总预算 32K 的例子）：
├─ system prompt（规范/角色/安全边界）      1~3K    ← 固定，缓存友好（[第 6 篇](06-inference-decoding.md)）
├─ 工具定义（10 个工具的 schema）           2~5K    ← 固定
├─ RAG 检索材料（5~10 块）                  4~10K   ← 按查询变化
├─ 对话历史（多轮）                         增长…   ← 必须治理
├─ 工具调用结果（本轮）                     1~10K   ← 可能巨大（大 JSON！）
└─ 输出空间（预留）                         1~4K    ← 必须预留

经验配比：指令与规范 ≤ 10%、检索材料 ≤ 30%、历史 ≤ 30%、
         预留输出 ≥ 10%、其余给工具结果
```

「工具结果」是最容易失控的一项：一次 API 调用返回 50KB 的 JSON，两个工具就把窗口吃满——**工具返回必须整形**（[第 9 篇](09-agents-tools.md)：返回相关字段 + 摘要 + 取详情的工具）。

## 2. 对话历史的四种治理策略

```python
# 策略①：滑动窗口——只保留最近 N 轮
history = history[-MAX_TURNS:]          # 简单粗暴：丢失早期关键信息

# 策略②：滚动摘要——旧对话压成一段摘要，新对话原样保留
def maybe_compress(history, tokenizer, budget_tokens):
    if token_len(history) <= budget_tokens * 0.7:
        return history                       # 未超预算：不动
    old, recent = history[:-KEEP_RECENT], history[-KEEP_RECENT:]
    summary = llm_summarize(old)             # 把旧对话压成一段
    return [system_msg, {"role": "user", "content": f"<此前对话摘要>\n{summary}"}] + recent

# 策略③：结构化记忆——把对话中的「事实」抽取到结构化存储，历史可丢弃
#   用户: 我叫张三，对花生过敏       → 记忆写入 {name: 张三, allergy: 花生}
#   之后每轮组装上下文时注入记忆而非原始对话

# 策略④：混合——摘要（情节）+ 结构化抽取（事实）+ 原始窗口（近期细节）
```

| 策略         | 优点                   | 丢失什么               | 适用                       |
| ------------ | ---------------------- | ---------------------- | -------------------------- |
| 滑动窗口     | 零成本                  | 早期全部上下文          | 短会话、上下文无关的任务    |
| 滚动摘要     | 保留情节脉络            | 细节、精确措辞          | 长对话助手                  |
| 结构化记忆   | 事实精确可查            | 未抽取的隐含信息        | 个人助理/长期客户           |
| 混合         | 兼顾                    | 复杂度最高              | 高价值长期产品              |

摘要压缩的注意事项：**摘要本身也是 LLM 生成——会丢信息、会幻觉**；摘要的 prompt 要明确「保留：决定/承诺/事实/偏好；丢弃：寒暄/过程」；压缩时机在「接近预算的 70%」时触发（留缓冲），不要等到爆。

## 3. 记忆的三层架构

```text
┌─ 工作记忆：当前窗口内的内容 —— 每次调用重新组装
├─ 短期记忆：本次会话的结构化状态（购物车/表单半成品/任务清单）
│            —— 会话结束即弃（Redis/内存）
└─ 长期记忆：跨会话的用户事实与偏好（向量库 + 结构化存储）
             —— 写入策略：显式（用户说「记住」）/ 隐式（抽取器自动识别）
```

```python
# 长期记忆的写入与检索（伪代码）
def on_message(user_id, text):
    facts = extract_facts(text, existing=load_facts(user_id))   # LLM 抽取
    for f in facts:
        upsert_fact(user_id, f)              # 去重/覆盖旧的

def assemble_context(user_id, query):
    return {
        "profile": load_facts(user_id),      # 结构化记忆：精确
        "related": vector_search(query, user_id),   # 语义记忆：相关历史片段
        "history": recent_turns(user_id, 5),
    }
```

记忆的三个工程难点：**抽取质量**（LLM 抽取要防幻觉——「用户说他喜欢 X」必须真的在对话里）、**冲突处理**（新事实与旧事实矛盾——时间戳 + 覆盖策略）、**隐私**（记忆里的敏感信息要加密/可删除——合规刚需）。

## 4. 上下文腐烂：注意力的实证

「lost in the middle」（[第 3 篇](03-transformer-llm.md)）的工程推论不止于 RAG：

1. **关键指令放头尾**：system 的核心约束在开头、输出格式要求放在紧邻生成的位置——中间的指令遵循率显著更低。
2. **上下文越长，「忠实度」越低**：长材料中的事实被「平均稀释」——引用与核对（[RAG](08-rag.md)）比「塞更多」有效。
3. **重复强调不如重新组织**：同一指令出现 5 次不如把它移到注意力高密度区。
4. **陈旧内容主动清除**：已完成任务的工具结果、已解决的错误信息——留在上下文里只会干扰（「干净上下文」原则：每步只保留对当前推理有用的内容）。

## 5. 结构化装配：上下文组装管道

```python
# 把「拼字符串」升级为「声明式装配」——上下文是构建产物，可测试可审计
def build_context(task: Task, state: SessionState, budget: int) -> list[Message]:
    sections = []
    sections.append(Fixed("system", SYSTEM_PROMPT))                    # 固定层
    sections.append(Fixed("tools", tool_schemas(task.allowed_tools)))
    sections.append(Dynamic("memory", render_facts(load_facts(task.user_id)),
                            priority=3))                                # 记忆层
    sections.append(Dynamic("rag", retrieve(task.query, top_k=8),
                            priority=2, dedup=True))                    # 检索层
    sections.append(Dynamic("history", state.recent_turns(),
                            priority=1, compressible=True))             # 历史层
    return assemble(sections, budget)      # 按优先级装填，超预算先降级低优先级段
```

装配管道的三个收益：**预算可控**（超限时有明确的降级顺序）、**可测试**（对固定输入断言组装结果）、**可观测**（记录每次实际发送的构成——「上下文组成」应该像请求日志一样被记录）。

## 6. 压缩技术：少 token 表达同等信息

| 技术                 | 原理                                     | 保存率/损失风险       |
| -------------------- | ---------------------------------------- | --------------------- |
| LLM 摘要             | 强模型压缩对话/文档                       | 中——细节丢失          |
| Prompt 压缩（LLMLingua 类）| 删除低信息量 token（小模型判别）     | 高保真——2~20 倍压缩    |
| 结构化重表达         | JSON/表格替代自然语言描述                  | 高——字段化无损        |
| KV 缓存复用          | 固定前缀的缓存复用（[第 6 篇](06-inference-decoding.md)）| 零损失——省钱不省窗口 |
| 工具结果整形         | 返回字段白名单 + 截断长文本                | 高                    |

结构化重表达常被低估：**「用户说：他下周三想去北京，希望靠窗，可能带行李」→ `{dest:"北京", date:"下周三", seat:"靠窗", bags:1}`**——同样的信息 token 减半且无歧义。**能结构化的上下文不要用自然语言**。

## 7. GraphRAG 与结构化知识

向量检索（[RAG](08-rag.md)）的盲区：**多跳关系问题**（「A 公司 CEO 的母校在哪」需要 A→CEO→母校两跳）。GraphRAG 的思路：**从文档抽取实体与关系构建知识图谱，检索时沿图遍历**：

```text
文档 → 实体/关系抽取 → 知识图谱（节点=实体，边=关系）
查询 → 识别查询中的实体 → 图上多跳遍历 → 收集相关子图 → 喂给 LLM 生成

适用：关系密集的语料（企业知识库/情报分析/生物医学）
代价：抽取与建图的离线成本高；图质量决定上限
```

工程判断：**简单 RAG 覆盖 80% 需求**——GraphRAG 只在「关系查询占比高、向量检索明显失败」时引入；实体抽取的质量是它的天花板。

## 8. 状态机式会话：显式状态优于隐式历史

```python
# ❌ 隐式状态：整个对话历史就是状态——多轮后模型「忘记」流程走到哪
# ✅ 显式状态：流程状态是结构化的，LLM 只做「当前状态的决策」
state = {"step": "collect_items", "items": [...], "address": None}

def route(state, user_msg):
    intent = llm_classify(user_msg, allowed=TRANSITIONS[state["step"]])
    return TRANSITIONS[state["step"]][intent]      # 状态机驱动流转

# LLM 的角色：理解这一句话的意图 + 抽取参数 —— 不是「记住整个流程」
```

显式状态机的收益：**流程可控可测试**（非法流转在代码层被拒）、**上下文极简**（每轮只注入当前状态 + 有限历史）、**可恢复**（状态可持久化）。LLM 在其中的角色收窄为「意图理解 + 参数抽取 + 话术生成」——**复杂流程用状态机骨架 + LLM 关节**，而不是让 LLM 自由发挥。

## 9. 陷阱清单

- 上下文「多多益善」：注意力稀释 + 成本；每一项都要有存在理由。
- 工具结果直塞上下文：50KB JSON 两轮吃满窗口；整形 + 摘要 + 按需详情。
- 摘要压缩的幻觉：摘要也可能编造；关键事实走结构化记忆而非摘要。
- 记忆抽取的幻觉与隐私：抽取要有据可查、敏感信息加密可删。
- 历史无限堆积不治理：渐进劣化；70% 预算触发压缩。
- 关键指令埋在中间：头尾放关键；用「needle 测试」验证自己的上下文布局。
- 无装配管道的字符串拼接：不可测试不可观测；声明式装配 + 构成日志。
- GraphRAG 过早引入：先测量向量检索的失败模式再上图谱。

## 10. 小结

- 上下文工程 = 「窗口预算内的信息装配」：三重稀缺（容量/注意力/成本）决定每一项的去留。
- 历史治理四策略（窗口/摘要/结构化/混合）按会话长度与信息类型选；压缩时机在 70% 预算、摘要 prompt 要明确保留清单。
- 记忆三层（工作/短期/长期）：抽取质量、冲突处理、隐私是三大工程难点。
- 上下文腐烂的对策：关键放头尾、陈旧内容清除、结构化替代自然语言、构成日志可观测。
- 复杂流程用「状态机骨架 + LLM 关节」；GraphRAG 只在关系查询密集时引入。

## 11. 练习

**1.** 上下文构成审计：记录一个真实 Agent 应用的 20 次调用上下文构成（各段 token 数），画出堆叠面积图——找出增长最快的段并给出治理方案。

> [!TIP]
> 思路典型的发现：工具结果占比远超预期（某 API 返回全量对象）。治理优先级 = 「增长最快 × 对推理贡献最低」的段。

**2.** 历史治理对比实验：构造 30 轮的长对话（含早期关键约束「预算不超过 500 元」），分别用滑动窗口/摘要/结构化记忆组装——测试「第 30 轮还能否遵守早期约束」。

> [!TIP]
> 思路滑动窗口大概率丢约束；摘要可能保留但措辞模糊；结构化记忆精确。这个实验决定你的长对话产品选哪种策略。

**3.** 摘要器设计：写一个对话压缩 prompt——保留决定/承诺/事实/数字，丢弃寒暄；用「压缩后再问早期细节」的方式测量信息保留率，迭代 prompt。

> [!TIP]
> 思路信息保留率的测法：从旧对话抽 10 个「应保留事实」，问压缩后的摘要（或压缩后的下游对话）能否回忆——压缩器的回归测试。

**4.** 上下文装配管道实现：实现本篇第 5 节的装配器（优先级 + 预算 + 降级），写 3 个单测（预算内全装/超预算降级历史/超预算降级 RAG）。

> [!TIP]
> 思路装配器的「优先级顺序」是产品决策：RAG 材料通常优先于历史（相关性高于时效）——顺序写错的效果差异用「needle 测试」验证。

**5.** needle 测试工具化：写一个脚本——把「暗号是 X」插入长上下文的不同位置（头/1/4/中/3/4/尾），问「暗号是什么」——画出位置-正确率曲线，验证你自己上下文的 lost-in-the-middle 程度。

> [!TIP]
> 思路这条曲线是你模型的「注意力地形图」——关键内容布局（头尾）的依据。不同模型/上下文长度下曲线不同，换模型要重测。

**6.** 讨论：「上下文工程」与「软件工程的内存管理」的相似度有多高？从「预算分配/泄漏（该清的不清）/碎片（无关内容挤占）/GC（压缩回收）」的类比逐项映射，并指出类比失效的地方（LLM 的「注意力稀释」没有传统内存对应物）——类比的力量与边界。

> [!TIP]
> 思路映射成立的部分：预算=内存上限、泄漏=历史堆积、GC=摘要压缩、工作集=当前需要的内容。失效的部分：内存是「确定性存取」而注意力是「稀释性存取」——放进去不等于用得上。类比的正确用法：借「管理稀缺资源」的纪律，警惕「存取语义」的差异。
