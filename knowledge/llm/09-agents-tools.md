模型只会输出文字，世界却要求行动：查数据库、调 API、发邮件、跑代码。**Agent = LLM + 工具 + 循环**——让模型在循环里自主决定"调用什么工具、传什么参数、要不要继续"，直到完成任务。这是当前 LLM 应用的主战场。

## Function Calling：结构化的"动手意图"

给模型一份工具清单（名称、功能描述、JSON Schema 参数定义），模型在需要时输出一个结构化调用意图，**由你的代码执行**后把结果回填对话：

```json
{
  "name": "get_weather",
  "arguments": {"city": "北京", "date": "明天"}
}
```

三件必须想清楚的事：

1. **执行权在你**：模型只生成"调用意图"，真正按下按钮的是你的代码——权限校验、金额上限、危险操作确认，全部在这一层把关
2. **工具描述是提示词**：描述写得越清楚（什么时候用、什么时候别用、参数含义），调用越准——工具接口质量直接等于 Agent 能力上限
3. **结果回填要完整**：工具失败也回填错误信息，让模型自己调整策略，而不是让循环静默中断

## ReAct：思考-行动-观察的循环

Agent 的经典骨架：模型交替输出**思考（Reason）→ 行动（Act）→ 观察（Observe）**，直到得出最终答案：

```text
用户: 上海到北京的最快高铁，到站后打车去机场要多久？
思考: 需要查车次和用时 → 调 train_search
观察: G22 4小时18分，19:00 抵达北京南
思考: 再估打车时间 → 调 route_estimate
观察: 北京南→首都机场 约 45 分钟
回答: G22（19:00 到）+ 打车约 45 分钟，全程预计 6 小时以内……
```

每一轮都是一次普通的 LLM 调用（对话历史 + 工具结果不断累加）。工程要点：**循环上限**（防失控烧钱）、**每步校验**（参数合法性、输出 schema）、**全程留痕**（trace 每步的输入输出，出错可回放）。

## MCP：工具生态的 USB 接口

每个应用都手写一遍"Google 搜索、读文件、查数据库"的连接器，重复且碎片化。**MCP（Model Context Protocol）**把它标准化：工具方跑一个 MCP Server，声明自己的能力（tools/resources/prompts）；任何支持 MCP 的客户端（Claude、IDE、Agent 框架）即插即用——**一次实现，处处可用**，像 USB 之于外设。

> [!NOTE]
> 工具设计是 Agent 工程里最像"API 设计"的部分：粒度太粗模型无法组合，太细模型要在泥潭里挣扎；错误信息要"可读"（告诉模型怎么改），而不是裸抛异常。**先优化工具，再考虑换更强的模型。**

## 多智能体：浪漫与真相

多 Agent 协作（规划者/执行者/审查者分工）很诱人，但现实的账要算清：

- 每次转手都是一次 LLM 调用，成本和延迟乘倍；上下文在 Agent 间传递会失真
- 错误会**级联放大**：上游一个误解，下游全体跑偏
- 单 Agent + 好工具 + 强循环，往往跑赢"五个 Agent 开会"

升级到多 Agent 的正当理由：**并行**（同时调研十个方向）、**上下文隔离**（子任务各自有独立干净的记忆窗）、**对抗校验**（写代码的和审代码的分开，利益不一致才有真审查）。

> [!WARNING]
> 安全是 Agent 的第一优先级：提示注入（prompt injection）可以让网页内容、检索到的文档"指挥"你的 Agent 泄密或误操作。防线：工具最小权限、读写分离、高危操作人工确认、把外部内容永远当"数据"而非"指令"对待。
