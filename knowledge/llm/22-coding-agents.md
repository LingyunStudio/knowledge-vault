编程是 LLM 最成功的应用领域，没有之一——原因可以拆解：**代码可执行验证**（跑测试就知道对不对，[第 13 篇](13-reasoning-models.md)的 RLVR 天然适用）、**训练数据充足且高质量**（GitHub 语料 + 严格的语法结构）、**工具生态丰富**（编译器/linter/测试框架给 Agent 反馈）。理解编程智能体的架构，等于理解「LLM + 可验证环境」这个组合的天花板在哪。

## 1. 三种产品形态：交互契约的演化

| 形态       | 交互契约                          | 人类角色      | 例                              |
| -------- | ----------------------------- | --------- | ------------------------------ |
| 补全式      | 光标处续写（FIM：fill-in-the-middle） | 实时审阅每个建议  | Copilot 补全、Tabby               |
| 对话式      | 描述需求 → 生成代码片段                 | 复制粘贴与整合   | Chat 模式                        |
| 自主 Agent | 给任务 → 自主读写文件/跑命令/提交           | 审查最终 diff | Claude Code/Cursor Agent/Devin |

三种形态的**信任与验证模型**完全不同：补全式的错误被「人工逐行审阅」天然拦截；自主 Agent 的错误需要**测试与评审兜底**——「Agent 化」的每一步都在把验证责任从「人的眼睛」移到「自动化验证」上。

## 2. 仓库级上下文：编程 Agent 的第一难题

```text
改一个函数需要知道什么？
  函数本体 + 它的调用方 + 它调用的依赖 + 类型定义 + 相邻约定（命名/错误处理风格）

仓库的规模现实：数百万行 —— 远超上下文窗口（[第 3 篇](03-transformer-llm.md)）
上下文策略的光谱：
  grep/正则检索（[符号级精准]）
  embedding 检索（语义相近代码，[第 24 篇](24-embeddings-search.md)）
  依赖图分析（imports/调用图的结构化遍历）
  agentic 探索（让 Agent 自己 grep/read——[第 21 篇](21-agent-architecture.md)的工具循环）
```

现代编程 Agent 的主流答案是 **agentic 探索**：不预先构建「完美的仓库索引」，而是给 Agent grep/read/glob 工具让它**自己按需探索**——「Agent 花几个回合找到相关文件」比「预先算错的 embedding 检索」更可靠。代价是回合数与延迟——混合方案（embedding 预筛 + agentic 精查）是工程甜点。

## 3. Agentic Loop：编辑-测试-修复

```text
编程 Agent 的核心循环：
① 探索：读相关文件，理解现状
② 计划：列出修改方案（改哪些文件/怎么改）
③ 编辑：用编辑工具改文件（精确 diff 或整文件重写）
④ 验证：跑编译/linter/测试——失败信息回灌
⑤ 循环：根据失败修正，直到绿
⑥ 交付：生成 diff 供人审

「④ 验证回灌」是这个循环的灵魂——
失败信息是「免费的、精确的、客观的反馈」（[RLVR](13-reasoning-models.md)），
Agent 的自我纠错能力大部分来自它
```

编辑工具的设计是 Agent 质量的隐形变量：**整文件重写**（简单但易破坏无关内容）、**精确 diff/字符串替换**（可控但对上下文敏感）、**搜索替换块**——每种都有失败模式，工具的错误反馈（「找不到要替换的串」）要能被模型自纠。

## 4. FIM 与补全式生成的细节

```text
Fill-in-the-middle（FIM）的训练与推理：
输入 = <前缀> + <中缀空洞> + <后缀>   模型补中缀
  —— 让「光标后已有的代码」也参与预测（不只是从左到右）

工程细节：
  上下文窗口的「预算分配」：前缀放多少（光标前的代码）+ 后缀放多少（光标后的代码）
  相邻文件的选择（打开的 tab/导入的模块/同名符号）
  去重与截断策略（[第 12 篇](12-context-engineering.md)的上下文工程在补全场景的特化）
```

补全式产品的体验红线：**延迟（<100ms 级）与建议的「接受率」**——接受率是这类产品的核心指标（每次弹建议打断注意力，低接受率 = 负体验）。这就是为什么补全模型通常是小模型（速度）+ FIM 训练（上下文利用）——与 Agent 的旗舰大模型分工。

## 5. 评测：从 HumanEval 到 SWE-bench

```text
评测的演化 = 任务真实度的演化：
HumanEval：独立函数生成（签名+docstring → 实现）—— 太玩具
LiveCodeBench：竞赛题 + 防污染（持续新题）
SWE-bench：真实 GitHub issue → 修好仓库中的 bug
  ★ 评测 = 「仓库快照 + issue 描述」→ Agent 自主工作 → 跑仓库测试验证
  —— 最接近真实软件工程的公开基准；Agentic 版（SWE-bench Verified 人工校验）
```

SWE-bench 的启示：**「能写函数」与「能修仓库」之间隔着整个软件工程**——定位代码、理解隐含约定、多文件协调、跑测试自纠。编程 Agent 的进步就是这条鸿沟的收窄史；你的内部评估也应按「真实任务形态」设计（[第 15 篇](15-evaluation-systems.md)）。

## 6. 沙箱与安全：Agent 能跑命令的世界

```text
编程 Agent 的安全面：
① 代码执行：Agent 跑的命令可能 rm -rf / curl 恶意脚本
   → 沙箱（容器/VM/权限最小化，[docker](../docker/01-why-containers.md)）
② 包幻觉（package hallucination）：模型编造不存在的包名 → 攻击者抢注投毒
   → 依赖白名单/锁定文件（[第 8 篇](../python/08-modules-packages.md)）
③ 数据外泄：Agent 读到的 .env/密钥随 diff/日志外流
   → 敏感文件屏蔽（.gitignore 同款逻辑 + 抓包审计）
④ 提示注入：仓库里的文件内容（README/issue）藏指令（[第 17 篇](17-llm-security.md)）
```

沙箱的工程形态：**容器 + 文件系统快照**（改动可回滚）+ **网络限制**（白名单域名）+ **资源限额**（CPU/内存/时长）——「Agent 的每一次执行都被假设可能出错」（[最小权限](../linux/04-permissions.md)）。

## 7. 陷阱清单

- Agent 改文件无版本控制兜底：一切编辑要在 git 之下（[可回滚](../git/07-undo.md)）。
- 验证只有「编译通过」：测试/linter/类型检查的全链验证才是质量闸。
- 上下文塞满整个仓库：agentic 探索 + 按需读取；embedding 预筛做辅助。
- 生成代码不审直接合（「能跑就行」）：测试覆盖 + 人工审 diff 是 Agent 时代的代码评审。
- 包幻觉依赖直接安装：锁定文件 + 私源白名单。
- 补全产品的打断成本忽视：接受率监控优先于功能堆叠。
- FIM 的预算分配失衡（只放前缀）：后缀上下文对「改而非写」任务至关重要。
- Agent 的修改越界（改了无关文件）：diff 审查 + 工具层的范围限制。

## 8. 小结

- 编程是 LLM 的最优应用：可执行验证（RLVR 燃料）+ 高质数据 + 工具生态——三种形态（补全/对话/Agent）的验证责任逐级自动化。
- 仓库级上下文的答案偏向 agentic 探索：grep/read 工具循环优于静态索引；embedding 预筛混合。
- agentic loop 的灵魂是「验证回灌」：失败信息免费精确客观；编辑工具的错误反馈要能自纠。
- SWE-bench 定义了「真实软件工程」的评测形态；内部评估按真实任务设计。
- 安全面三件：沙箱执行、包幻觉防投毒、敏感数据屏蔽——「Agent 会犯错」的假设贯穿架构。

## 9. 练习

**1.** FIM 的上下文分配实验：固定 8K 窗口，把预算分配为「全前缀」「前缀 70%+后缀 30%」「前 25%+后 75%」三种策略做补全任务，统计接受率——验证后缀上下文对「修改类补全」的价值。

> [!TIP]
> 思路修改类任务（改现有函数）的后缀信息（函数的剩余部分/调用处）直接影响补全的正确性——「纯生成」任务则前缀主导。任务类型决定预算分配。

**2.** agentic 探索 vs embedding 检索：在一个开源仓库中给「修复某个 issue」任务，分别用「纯 embedding 检索上下文」与「grep/read agentic 探索」跑修复，对比成功率与回合数。

> [!TIP]
> 思路agentic 探索的优势：发现「检索想不到的相关文件」（命名不一致/隐式约定）；劣势：回合数与延迟。混合（embedding 初筛 + agentic 确认）是甜点。

**3.** SWE-bench Lite 体验：跑一个开源编程 Agent（或手搓最小 agentic loop：read/edit/bash 工具）解 5 个 SWE-bench Lite 任务——记录每任务的成功/失败与失败原因分类（定位错/修错/测试理解错）。

> [!TIP]
> 思路失败原因的分类统计是「Agent 改进方向」的地图：定位类失败 → 上下文策略；修复类失败 → 模型能力；测试理解失败 → prompt/任务规范。

**4.** 沙箱设计实现：为编程 Agent 实现一个「容器沙箱执行器」：文件系统快照（可回滚）、网络白名单、资源限额——故意让 Agent 跑危险命令验证拦截，再实现「快照回滚」。

> [!TIP]
> 思路沙箱的三层（文件/网络/资源）对应三种事故（删文件/外泄/资源耗尽）。快照回滚的实现（overlayfs 或复制目录）让「Agent 的破坏」变成「一次回滚」。

**5.** 包幻觉实验：让多个模型生成「安装依赖的命令」100 次，收集出现的包名，对照 PyPI 注册表统计「不存在的包」比例——量化包幻觉的规模，理解「为什么锁定文件与私源白名单是必须的」。

> [!TIP]
> 思路包幻觉的攻击模型（slopsquatting）：攻击者抢注模型常编造的包名 → 用户安装即中招。「模型输出中的包名永远要过注册表校验」是 CI 的硬规则。

**6.** 讨论：编程 Agent 的「信任建立」过程——为什么团队普遍经历「从不信任到选择性信任」的曲线？从「验证成本的不对称」（审查 diff 比写代码便宜但比点接受贵）「任务风险的分层」（改文案 vs 改核心逻辑）「反馈循环的质量（有无测试）」三个角度，给出「按任务风险分级的 Agent 授权策略」——对照 [第 17 篇](17-llm-security.md)的权限最小化。

> [!TIP]
> 思路分级授权的形态：只读任务全自动、低风险写任务自动+CI 兜底、核心逻辑人工审 diff、生产变更全流程。信任随「验证基础设施的成熟」而增长——授权策略是动态的，绑定在验证能力上而非信任上。
