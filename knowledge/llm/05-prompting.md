提示工程的本质：**prompt 是 LLM 的编程接口**——ICL（[第 1 篇](01-what-is-llm.md)）让上下文临时「编程」模型行为。好的 prompt 不是咒语，是**明确的任务规范**：任务定义、输入说明、输出格式、边界与示例。而 prompt 的脆弱性（换模型/改一个词可能失效）决定了它的工程定位：**必须评估驱动迭代，必须版本化管理**。

## 1. 基础技法：把任务说清楚

```text
❌ 模糊：帮我写个总结
✅ 明确：
  你是技术编辑。把下面的会议记录总结成 5 条以内的要点，
  每条 ≤ 30 字，按重要性排序，使用名词短语结尾。
  只输出要点列表，不要其他内容。

  <会议记录>
  {{transcript}}
  </会议记录>
```

基础五件套：**任务与角色**（你是谁、做什么）、**约束**（长度/数量/格式）、**输出格式**（JSON schema/模板）、**分隔符**（`<></>`/``` 隔开数据与指令——防注入混淆）、**边界说明**（信息不足时怎么办：说「不知道」而不是编）。

```text
结构化输出的现代正解：JSON mode / 结构化输出（function calling 的 schema）
  —— 比「请输出 JSON」的祈祷可靠一个量级（解码层强制 schema，[第 6 篇](06-inference-decoding.md)）
```

## 2. few-shot：示例是最强的规范

```text
任务：把客户问题归类为 [账单|技术|投诉|其他]

示例1：输入"我的账单多扣了钱" → 账单
示例2：输入"APP 打不开了" → 技术
示例3：输入"你们服务太差了我要举报" → 投诉

现在分类：输入"{{query}}" →
```

few-shot 的机制是 ICL（[第 1 篇](01-what-is-llm.md)）：**示例定义了任务的输入-输出映射**。示例选择的三个维度：**覆盖**（每类至少一个，边界案例覆盖）、**典型与边界并存**（典型示例教模式、边界示例教判据）、**顺序**（最新示例的影响最大——把最重要的放最后）。示例的「多样性 > 数量」：3~5 个精选通常优于 20 个相似。

## 3. CoT：让模型「多想一步」

```text
❌ 直接：Q: 小明有 3 个苹果，买了 5 个又吃掉 2 个，还有几个？
✅ CoT：请一步一步推理后再给出最终答案（格式：先写推理步骤，最后以"答案: N"结尾）
```

CoT 的机制：**把「内部计算」外化成 token**——生成的中间步骤成为后续预测的上下文（相当于给模型更多的「草稿纸」，[第 1 篇](01-what-is-llm.md)的推理能力需要中间 token 承载）。适用判据：**多步推理/组合计算/约束满足**的问题收益大；简单检索/改写任务收益小甚至啰嗦。

进阶形态：**自洽性（self-consistency）**——采样多条推理链投票取多数（[第 6 篇](06-inference-decoding.md)的采样温度配合）；**分解（decomposition）**——把复杂任务拆成子任务分别问（每步可验证）；**ReAct**（推理 + 行动交替——[agent 的前身](09-agents-tools.md)）。

## 4. 系统 prompt 的设计：产品人格的宪法

```text
系统 prompt 的分层结构（长系统 prompt 的组织）：
1. 身份与角色：你是什么产品、面向什么用户
2. 能力与边界：能做什么、不能做什么（超出范围的引导话术）
3. 行为规范：语气、语言、安全边界（拒答策略）
4. 工具说明：可用工具与调用时机（[第 9 篇](09-agents-tools.md)）
5. 输出规范：格式、引用要求

维护纪律：system prompt 是「产品的宪法」——版本化、评审、评估驱动修改（[第 10 篇](10-deploy-engineering.md)）
```

系统 prompt 的长度权衡：越长越「受控」但吃上下文预算且可能稀释任务注意力——**把不变的规范放 system、把变化的任务放 user**、RAG 材料单独分区（[第 8 篇](08-rag.md)）。

## 5. Prompt 的脆弱性与评估驱动

```text
prompt 的脆弱性真相：
- 换模型（GPT→Claude→开源）→ 风格敏感，可能失效
- 改一个措辞 → 边界案例行为漂移
- 上下文内容变化 → 干扰响应

应对不是「找完美咒语」而是「评估驱动的迭代」：
① 建 golden 测试集（20~100 个代表性输入 + 期望行为）
② 每次 prompt 修改跑一遍测试（自动评分：包含关键词/JSON 可解析/LLM 评分）
③ 版本化（prompt 与代码同库，[第 10 篇](10-deploy-engineering.md)）
④ A/B 验证线上效果
```

「prompt 工程没有银弹，只有评测」——**没有评估集的 prompt 修改就是赌博**。评估驱动让 prompt 迭代像代码一样有回归测试（[测试纪律](../python/12-quality.md)的 LLM 版）。

## 6. 陷阱清单

- 追求「神奇咒语」不做任务规范：prompt 的本质是规范不是咒语。
- 输出格式靠「请输出 JSON」祈祷：结构化输出/函数调用 schema。
- 分隔符缺失（用户输入与指令混流）：prompt 注入的温床（[第 10 篇](10-deploy-engineering.md)）。
- few-shot 示例互相矛盾或覆盖不全：示例即规范——质量与覆盖度决定行为。
- CoT 滥用（简单任务也强制长推理）：成本与延迟翻倍收益为零；按任务结构选。
- system prompt 无版本无评估：产品「宪法」的裸奔；prompt 变更要过回归测试。
- prompt 过长挤占上下文：规范精简 + 动态内容分区（[第 8 篇](08-rag.md)）。
- 依赖「这句话很重要请认真」的情绪化措辞：明确约束优于情感恳求。

## 7. 小结

- prompt 是「用上下文编程」：任务规范五件套（角色/约束/格式/分隔符/边界）——明确性优于咒语。
- few-shot 的示例即规范：覆盖、典型与边界并存、顺序敏感；结构化输出用解码层 schema 而非祈祷。
- CoT 外化推理（中间 token 当草稿纸）：多步任务收益大；自洽性/分解/ReAct 是进阶形态。
- system prompt 是产品宪法：分层组织、版本化、评估驱动修改。
- 脆弱性的正解是评估驱动：golden 测试集 + 自动评分 + 版本化——prompt 迭代必须有回归测试。

## 8. 练习

**1.** 重构一个烂 prompt：拿一段「帮我总结一下」式的模糊需求，按五件套重写，用 20 个测试输入对比两者的输出稳定性——量化「明确性」的收益。

> [!TIP]
> 思路稳定性的度量：输出格式合规率、关键信息覆盖率、长度方差。模糊 prompt 的输出方差在测试集上一目了然——「明确性」从感觉变成数字。

**2.** few-shot 数量实验：同一分类任务，0-shot / 3-shot / 10-shot / 20-shot 的准确率曲线——找到你任务的「示例边际收益拐点」与「上下文成本」的平衡。

> [!TIP]
> 思路典型曲线：0→3 快速提升、3→10 平缓、10+ 收益趋平但成本线性增。示例的「覆盖边界案例」比堆数量有效——用错误分析选下一批示例。

**3.** CoT 收益测绘：把任务分成「单步检索/两步推理/多步计算」三组，分别测「直接答 vs CoT」——画出「任务步数 × CoT 收益」的关系，形成你自己的 CoT 使用判据。

> [!TIP]
> 思路CoT 收益随任务步数递增、对纯检索近零——「推理预算分配」的判据化。延迟与成本敏感的场景（[第 6 篇](06-inference-decoding.md)）更需要这张地图。

**4.** 结构化输出实验：三种方式生成 JSON——「请输出 JSON」/「给出 JSON schema 示例」/「解码层结构化输出（json mode/函数调用 schema）」——统计 50 次生成的可解析率。

> [!TIP]
> 思路预期：祈祷版偶发解析失败（尤其长输出/嵌套）、schema 版接近 100%。解析失败的重试逻辑（[第 9 篇](09-agents-tools.md)）是第三层保险。

**5.** prompt 回归测试搭建：把你的最佳 prompt 版本化（git），建 30 条 golden 测试集，写一个评分脚本（格式合规+关键内容+LLM 评分）——然后故意改坏 prompt 验证测试能抓住。

> [!TIP]
> 思路LLM 评分（用模型给输出打分）的校准：先人工标 20 条对齐评分尺度。这套「prompt CI」是 prompt 工程从手艺变成工程的分水岭（[第 10 篇](10-deploy-engineering.md)）。

**6.** 讨论：为什么「prompt 工程师」作为独立岗位正在消失（融入应用工程师的职责）？从「prompt 脆弱性倒逼评估与代码化」「模型能力增强降低 prompt 技巧需求」「工程化（评估/版本/自动化）比措辞更重要」三个角度分析——「prompt 工程」的终局形态是什么？

> [!TIP]
> 思路prompt 技巧的半衰期短（模型升级后咒语失效），评估基础设施的半衰期长（测试集与流程跨模型存活）。终局：prompt 是「软件的一个配置层」——工程的价值在评估与迭代体系，不在措辞的炼金术。
