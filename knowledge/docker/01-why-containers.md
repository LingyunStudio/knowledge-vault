Docker 的流行不是因为它发明了容器，而是因为它把容器变成了**标准化交付物**。理解 Docker 要先理解它解决的两个真实工程问题：「在我机器上能跑」与「部署形态不统一」——容器用两个机制回答它们：**进程级隔离**（每个容器看到自己的世界）与**镜像打包**（应用连同环境一起运输）。

## 1. 两个问题：环境一致性与交付

**问题一：环境不一致。** 同一个应用在开发机（Python 3.12 + 某版本的依赖）、测试机（旧一点的库）、生产服务器（系统 Python）上行为各异——依赖版本、系统库、配置的差异让「测试过」变得没有意义。容器的答案：**把应用与它的整个用户态环境（依赖、运行时、系统库）一起打包**，在任何能跑容器的机器上行为一致。

**问题二：交付形态不统一。** 每个应用的部署方式不同（pip install、npm、apt、手动拷贝）——部署脚本与文档各自为政。容器的答案：**统一的交付标准**——任何应用都交付为「一个镜像」，用同一条命令（`docker run`）运行，无论内部是 Python 还是 Go 还是 Nginx。

这两点的深层价值是**不可变基础设施**的雏形：部署物不再「在服务器上改」，而是「构建镜像 → 替换旧镜像」——环境变更进入版本控制（[git 篇](../git/01-object-model.md)的思想延伸到基础设施）。

## 2. 容器 vs 虚拟机：隔离的两种层次

```text
虚拟机：                            容器：
┌──────┐ ┌──────┐                 ┌──────┐ ┌──────┐
│ App A │ │ App B │                 │ App A │ │ App B │
│ Guest OS│ │ Guest OS│                 ├──────┤ ├──────┤
├──────┴─┴──────┴─┤                │ 库+运行时│ │库+运行时│
│   Hypervisor     │                ├──────┴─┴──────┴─┤
├──────────────────┤                │  宿主 OS 内核     │
│    宿主 OS        │                ├──────────────────┤
├──────────────────┤                │    硬件           │
│    硬件           │                └──────────────────┘
└──────────────────┘
（每个 VM 带完整操作系统：GB 级、启动分钟级）  （共享内核、隔离用户态：MB 级、启动秒级）
```

容器不是「轻量虚拟机」——它是**不同的隔离层次**：

- **虚拟机**在硬件层隔离：Hypervisor 虚拟出整套硬件，每个 VM 跑完整操作系统。隔离强（内核都不同），代价是重量。
- **容器**在操作系统层隔离：所有容器**共享宿主内核**，通过两个内核机制实现「各过各的」：
  - **Namespace**：让进程「看不见」别的进程/网络/挂载——每个容器有独立的 PID 空间、网络栈、文件系统视图。
  - **cgroups**：限制每个容器能用的资源（CPU/内存/IO）——防止互相吞噬。

工程推论：容器启动是**毫秒级**（本质是「启动一个进程 + 配好隔离视图」），镜像以 **MB** 计，单机轻松跑上百容器。代价是隔离弱于 VM（共享内核 → 内核漏洞可能穿透）——「多租户不可信环境用 VM，同信任域内微服务用容器」是安全边界的基本分工。

## 3. 镜像与容器：类与实例的关系

```bash
docker pull nginx:1.27           # 镜像（image）：静态模板
docker run -d -p 8080:80 nginx:1.27    # 容器（container）：模板的一次运行实例

docker ps                        # 运行中的容器
docker images                    # 本地镜像清单
```

核心心智模型：**镜像是只读模板（类），容器是镜像的运行实例（对象）**——同一个镜像可以起 N 个容器，各自独立。容器的可写层在镜像之上叠加（写时复制）：容器里改文件不改镜像；容器删除，写层消失——「容器内的数据是临时的」这一特性直接推出 Volume 的必要性（[第 5 篇](05-volumes.md)）。

镜像的内容寻址与分层（[第 3 篇](03-images.md)细讲）与 git 的对象模型惊人相似：内容寻址、层复用、轻量分支（tag）——理解过 git 的人对镜像的分层与共享会有既视感。

## 4. Docker 的架构与 CLI 全景

```text
┌─────────┐   REST API   ┌──────────────┐
│ docker   │ ───────────→ │ dockerd 守护  │──→ containerd ──→ 容器进程
│ (客户端)  │              │ (守护进程)    │
└─────────┘              └──────────────┘
```

- **docker CLI** 是客户端，真正干活的是 **dockerd 守护进程**——build/run/pull 都是 API 调用。这个架构解释了「Docker Desktop 的 VM」（Windows/macOS 上 dockerd 跑在轻量 Linux VM 里——因为容器需要 Linux 内核）与权限问题（docker 用户组 ≈ root，[第 11 篇](11-pitfalls.md)的安全条目）。

CLI 的动词分组（全程复用的地图）：

| 组       | 命令                                    | 对象   |
| -------- | --------------------------------------- | ------ |
| 运行     | `run`、`start/stop/restart`、`exec`、`logs` | 容器   |
| 观察     | `ps`、`inspect`、`stats`、`top`          | 容器   |
| 构建     | `build`、`tag`、`push/pull`              | 镜像   |
| 数据     | `volume ls/inspect`                      | 卷     |
| 网络     | `network ls/create`                      | 网络   |
| 编排     | `compose up/down`                        | 多容器 |

## 5. Docker 在部署版图中的位置

```text
裸机/脚本部署 → 配置管理(Chef/Ansible) → 容器(Docker) → 编排(Kubernetes) → PaaS/Serverless
```

- 容器是「单机/小集群部署」的甜区：`docker run`/`docker compose`（[第 7 篇](07-compose.md)）覆盖绝大多数中小项目。
- Kubernetes 是容器的「集群调度层」——容器是它的交付单位。学容器的命令与模型是 K8s 的前置（K8s 里没有 docker build，但镜像/容器的概念原样复用）。
- 反过来，「只有一台服务器、几个服务」的项目上 K8s 是过度工程——compose 足够。

## 6. 陷阱清单

- 把容器当 VM 用（SSH 进去改配置、装调试包）：容器是**不可变**的运行实例，改了不持久且偏离镜像；改 Dockerfile 重建。
- 期待容器内数据常存：写层随容器删除消失；持久数据走 Volume（[第 5 篇](05-volumes.md)）。
- 在 Windows/macOS 上对路径与性能的直接假设：dockerd 在 VM 里，bind mount 跨 VM 有性能与换行符问题。
- 生产环境用 latest 标签：镜像不可追溯；tag 精确版本（[第 8 篇](08-registry.md)）。
- 把 docker 用户组当普通权限：它等价 root（挂载宿主文件系统的能力）；按需授予。
- 混淆「镜像瘦身」与「容器瘦身」：镜像构建时的选择决定一切（[第 9 篇](09-dockerfile-best.md)）。

## 7. 小结

- 容器回答「环境一致性」（应用+环境一起打包）与「交付标准化」（一切皆镜像）——不可变基础设施的入口。
- 容器 ≠ 轻量 VM：共享内核 + Namespace（视图隔离）+ cgroups（资源隔离）；启动秒级、MB 级、隔离弱于 VM。
- 镜像=类、容器=实例：只读模板 + 可写层（写时复制）——数据临时性推出 Volume。
- CLI 架构：客户端 → dockerd → containerd；动词分组（运行/观察/构建/数据/网络/编排）是命令的地图。
- 部署版图：容器是单机与 K8s 之间的甜区——「先容器化，再谈编排」是演进正道。

## 8. 练习

**1.** 在容器里执行 `ps aux`、`ls /`、`cat /etc/os-release`，对比宿主机——找出三个「容器看到的世界与宿主不同」的证据，并对应到 Namespace 的哪一种。

> [!TIP]
> 思路PID 1 是你的应用（PID namespace）、/etc/os-release 是镜像的发行版（mount namespace）、网络接口只有 lo/eth0（net namespace）。三个观察 = 三种 Namespace 的现场教学。

**2.** 用同一个镜像（如 nginx）启动两个容器并修改各自的文件，验证互不影响、删除容器后修改消失——把「镜像=类、容器=实例、写层=临时」三个概念做成实验。

> [!TIP]
> 思路`docker exec` 各改一个 HTML 文件 → 两个容器内容不同（写层独立）→ `docker rm` 后重起新容器改动消失。这一套实验做完，Volume 的必要性不言自明。

**3.** 对比一台虚拟机与一个容器从启动到可用的时间与磁盘占用（手动计时/查镜像大小），用数字回答「为什么微服务生态选择容器」。

> [!TIP]
> 思路VM 分钟级+GB 级 vs 容器秒级+MB 级——弹性伸缩与密度（单机容器数）的差距是数量级。同时想清楚反面：什么样的负载必须 VM（不同内核、强隔离多租户）。

**4.** 用 `docker inspect` 查看一个运行容器的详细信息，找出：Namespace 类型、cgroup 路径、网络 IP、挂载列表——把「容器 = 进程 + 隔离配置」的模型落到 JSON 字段上。

> [!TIP]
> 思路inspect 是容器的「身份证」：HostConfig（资源限制与挂载）、NetworkSettings（IP/端口）、Config（启动命令/环境变量）。读 inspect 是排障的基本功（[第 10 篇](10-debug-ops.md)）。

**5.** 画一张你所在项目（或设想的项目）的部署演进图：从「裸机 + 手动部署」到「容器 + compose」到「K8s」，标注每个阶段的收益与引入成本——论证你选择的「当前甜区」。

> [!TIP]
> 思路成本维度的清单：学习曲线、运维复杂度、团队规模匹配。K8s 的引入成本在「集群本身的运维」——单机项目跳过它是理性选择而非能力不足。

**6.** 讨论：「不可变基础设施」为什么优于「登录服务器修修补补」？从「可追溯、可回滚、漂移消除」三个维度分析，并说明它与 [git 的历史观](../git/02-daily-workflow.md)（提交不可改、前进式修复）的相似性。

> [!TIP]
> 思路修补式部署 = 分支上的隐式提交（服务器状态没人记得全）；镜像化部署 = 每次变更有 hash、可 revert。基础设施与代码共享同一套工程纪律——「DevOps 的本质是 git 思想覆盖运维」。
