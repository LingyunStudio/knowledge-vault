容器的陷阱有清晰的分布规律：**误解抽象**（把容器当 VM、把写层当存储、把 tag 当不可变）与**默认值依赖**（root 运行、无轮转日志、latest 标签）。本篇按五类汇编全书陷阱成审查清单，附事故路线与「容器化准入」的检查表。

## 1. 五类审查清单

### 1.1 镜像构建（第 3、4、9 篇）

- [ ] .dockerignore 存在且挡住 .git/依赖目录/秘密文件
- [ ] 指令按变化频率排序（依赖声明 → 源码）；依赖层缓存命中
- [ ] apt/pip 安装与清理同层（或 BuildKit cache mount）
- [ ] 多阶段构建：编译环境不进运行镜像
- [ ] 基础镜像钉版本（不用 latest）；alpine 的 musl 兼容性核查过
- [ ] CMD/ENTRYPOINT exec 形式；entrypoint 脚本以 exec "$@" 收尾
- [ ] hadolint 通过；镜像体积与层数合理（对照历史分析）

### 1.2 运行配置（第 2、4 篇）

- [ ] 容器命名规范（项目-服务-环境）；不用随机名
- [ ] 端口映射方向核对；内部服务绑 127.0.0.1 或不映射
- [ ] 配置走环境变量/env_file；秘密零镜像零仓库
- [ ] --restart 策略明确；资源限额（memory/cpus）基于观测设定
- [ ] TZ/时区语义统一（UTC 存储或显式 TZ）
- [ ] stop 优雅关闭验证过（信号可达、清理执行）

### 1.3 数据与网络（第 5、6 篇）

- [ ] 持久数据全部走命名卷（写层无状态假设成立）
- [ ] bind mount 的用途限定在开发/配置注入；权限对齐核查
- [ ] 数据库等有状态服务有备份配方（逻辑备份优先）
- [ ] 服务互访用自定义 bridge + 容器名 DNS；无 IP 直连
- [ ] 双网络隔离（前端/后端）；数据库不暴露公网
- [ ] volume prune 前有盘点流程；-v 不在生产随手用

### 1.4 安全（第 1、9 篇）

- [ ] USER 非 root；文件属主对齐（--chown）
- [ ] 运行时加固：read_only/cap_drop/no-new-privileges（视场景）
- [ ] 镜像扫描（trivy）进 CI 且高危阻断
- [ ] registry 凭据走平台 secret；生产镜像走私有 registry
- [ ] docker 用户组成员最小化（它等价 root）
- [ ] 基础镜像更新有跟踪机制（Dependabot/定期重建）

### 1.5 运维（第 7、10 篇）

- [ ] compose.yml 是应用架构的真实描述（网络/卷/健康检查齐全）
- [ ] healthcheck 存在且分级合理；depends_on 用 condition
- [ ] 日志驱动带轮转（max-size/max-file）；应用写 stdout
- [ ] 定期清理有节奏（prune 分级、构建缓存）
- [ ] 退出码与重启循环有监控（RestartCount/事件告警）
- [ ] 回滚路径验证过（旧 tag 可拉、引用切换可执行）

## 2. 高频事故的「处理路线」

| 事故                          | 路线（按序执行）                                            |
| ----------------------------- | ----------------------------------------------------------- |
| 容器反复重启                   | inspect(ExitCode/OOMKilled/RestartCount) → logs 尾部 → events → 修根因 |
| 磁盘满                        | system df → 日志文件大小 → builder prune → image prune → （卷单独决策） |
| 数据「丢了」                   | 先确认容器是否重建过（inspect 的 Created 时间）→ docker volume ls 找匿名卷 → 挂回去 |
| 端口冲突                      | ss -tlnp 找占用 → docker port 看映射 → 改宿主端口或停占用者   |
| 服务外部访问不到               | -p 配置核对 → 绑定地址（0.0.0.0?）→ 容器内监听地址 → 防火墙三层 |
| 镜像拉取慢/失败               | 镜像加速器配置 → 网络代理 → 私有 mirror 预拉                  |
| 时钟/时区错乱                 | 宿主 chrony 核对 → 容器 TZ/UTC 策略统一 → 日志时间轴重放核对   |

事故路线的共同起点永远是**inspect + logs + events**（[第 10 篇](10-debug-ops.md)的五步）——先固化现场再动手，与 [git 事故的三问](../git/11-pitfalls.md)方法论同源。

## 3. 容器化改造的准入检查

把一个既有应用容器化时的决策顺序：

```text
1. 依赖清单化了吗？（语言版本/系统库/系统工具——Dockerfile 的原材料）
2. 配置外部化了吗？（环境变量注入——12-factor 检查）
3. 状态识别了吗？（无状态部分容器化，持久状态走卷/数据库）
4. 日志走 stdout 了吗？（驱动收集的前提）
5. 信号处理过吗？（SIGTERM 优雅关闭——数据完整性）
6. 健康语义能表达吗？（/health 探针的存在）
7. 构建可复现吗？（依赖锁定文件 + 钉住的镜像 tag）
```

七问全绿才有「容器化收益」（可复制、可迁移、可编排）；跳过前五问的容器化只是「把问题搬进容器」。

## 4. 反模式速查

| 反模式                                      | 一句话修复                              |
| ------------------------------------------- | --------------------------------------- |
| SSH 进容器当服务器用                          | exec 只调试；变更走镜像重建              |
| 镜像里塞数据集/模型再 volume 挂出来           | 数据与镜像分离；下载放启动脚本/挂载      |
| `docker run` 长命令没有 compose 化           | 一切多容器场景 compose 声明化           |
| 一个容器塞多进程（supervisor 全家桶）          | 一容器一进程；编排管组合                 |
| root 跑应用 + 777 权限解决报错                | USER 非 root + 显式权限                 |
| 秘密打在 docker run 命令行/日志里              | env_file/secret 机制                    |
| 用 latest 部署生产                            | 精确版本/digest                         |
| 容器里跑 cron 管定时任务                      | 外部调度（compose 外的 cron/K8s CronJob）|
| restart: always 掩盖崩溃循环                  | 监控重启次数 + 修根因                   |
| 数据库容器不开卷                              | 命名卷 + 备份                           |

「一容器一进程」值得展开一句：容器的主进程语义（PID 1 收到信号即容器生命周期）决定了「容器 = 单一职责单元」——多进程容器在信号、日志、伸缩、自愈四个维度全部劣化。要组合就上 compose/K8s（编排管组合，容器管进程）。

## 5. 小结

- 五类清单覆盖全书：构建（缓存/多阶段/钉版本）、运行配置（命名/端口/秘密/限额）、数据网络（卷/备份/DNS/隔离）、安全（非 root/扫描/凭据）、运维（compose 真相/健康检查/日志轮转/回滚）。
- 事故路线的起点是 inspect+logs+events 的现场固化；六条高频事故各有标准序列——先诊断后动手与 [git 事故手册](../git/11-pitfalls.md)同源。
- 容器化准入七问（依赖/配置/状态/日志/信号/健康/复现）是「收益兑现」的前提——跳过它们等于把旧问题搬进新抽象。
- 反模式的共同根源是「容器当 VM 用」与「依赖默认值」：一容器一进程、数据外置、秘密外置、版本钉住是四条总纲。

## 6. 练习

**1.** 用五类清单审查一个真实项目（或你练习中的 compose 栈），统计各类命中数与分布——为最密集的类别回到对应篇目补课。

> [!TIP]
> 思路自查的典型分布：1.3 数据与 1.4 安全类最弱（便利优先的惯性）。审查记录与 [C 篇/MATLAB 篇](../c/14-pitfalls.md)的审查练习一样，是个人风险地图。

**2.** 对一个未容器化的简单应用执行七问准入检查：逐问打分，把「缺的」补齐（配置外部化/信号处理/健康端点）后再写 Dockerfile——体会「先改应用再容器化」的顺序价值。

> [!TIP]
> 思路最典型的补课：应用把日志写进文件、配置写死在代码里——先改这两处，Dockerfile 只需要 15 行。「容器化是应用改造的下游」是这条练习的元结论。

**3.** 演练「数据丢失事故」的完整处理：故意 rm 掉带匿名卷的数据库容器 → 从 volume ls 找回匿名卷 → 挂回新容器验证数据 → 把「匿名卷盘点」写成预防脚本。

> [!TIP]
> 思路匿名卷的 hash 名难辨认——用 `docker volume inspect` 看挂载点内容反查归属。预防脚本：列出孤儿卷 + 提示（不自动删）。

**4.** 为团队写「容器服务上线检查单」：从五类清单中提炼 10 条上线前必查项（含验证命令），并设计一次「检查单演练」（找一个 staging 服务实测全过）。

> [!TIP]
> 思路检查单的每条要带验证命令（不是口号）：如「日志轮转」→ `docker inspect web --format '{{.HostConfig.LogConfig}}'`。可执行的检查单才能防走样。

**5.** 演练一次「镜像供应链事件响应」：假设你的基础镜像被通报 CVE——按「扫描确认 → 升级基础镜像重建 → 全量重推 → 通知部署端拉新」的流程走一遍（模拟），记录各环节耗时与信息流。

> [!TIP]
> 思路响应链的顺畅度取决于前置投资：扫描有没有常态化、重建是否一条命令、部署端引用是否好改。事件响应能力是平时流程的投影——与[git 事故手册](../git/11-pitfalls.md)的练习同构。

**6.** 讨论：容器的「不可变」与运维的「变更」如何共存？从「镜像重建 vs 运行时修改」的边界出发，分析哪些变更应该走「重建」（代码/依赖/配置默认值）、哪些走「运行时」（数据/临时调参），以及这个边界被打破后会发生什么（配置漂移 → 雪崩）。

> [!TIP]
> 思路边界判据：「变更是否需要在新环境复现」——需要就进镜像（可追溯可复现），不需要才是运行时。打破边界的代价：容器间配置不一致（漂移）、重启丢修改、无法回溯——与「登录服务器改配置」的旧世界殊途同归。不可变不是教条，是把变更纳入版本控制的手段。
