Python 与 C 的世界观正好相反。C 问「这块内存里是什么字节」；Python 问「这个**名字**指向哪个**对象**」。`x = 42` 在 C 里是「往 x 的格子写进 42」，在 Python 里是「造一个 int 对象 42，把名字 x **绑定**到它」。这个「名字→对象」的间接层是 Python 一切行为的总开关：赋值从不拷贝、函数传参从不复制、`is` 与 `==` 的区别、默认参数的经典陷阱——全部由它派生。

本篇建立 Python 的三张底图：**对象模型**（对象是什么、类型与值的关系）、**绑定模型**（名字与对象的关系）、**内存模型**（谁在什么时候回收对象）。后面十一篇全部铺在这三张图上。

## 1. 对象模型：一切皆对象

Python 里没有一个「裸值」——数字、字符串、函数、类、模块、代码块，全是对象。每个对象携带三样东西：

| 组成       | 说明              | 例子                                                            |
| -------- | --------------- | ------------------------------------------------------------- |
| 类型（type） | 决定行为：有哪些操作、怎么打印 | `type(42)` → `int`；`type(len)` → `builtin_function_or_method` |
| 值        | 对象携带的数据         | `42` 的值是整数 42                                                 |
| 身份（id）   | 对象在内存中的唯一标识     | `id(x)` 返回地址级数字；`is` 比较的就是它                                   |

```python
x = 42
type(x)        # <class 'int'>        —— 类型
id(x)          # 140...816            —— 身份（CPython 里是地址）
isinstance(x, int)   # True          —— 类型检查的标准姿势

# 函数也是对象：可以赋值、传递、放进容器
say = print
say("hello")   # hello —— print 的别名

# 类也是对象，能运行时修改
class Dog:
    pass
Dog.name = "旺财"     # 动态加属性：类本身就是可操作的对象
```

「类型也是对象」带来 Python 的终极灵活性：**类型检查发生在运行时**。`x + y` 能不能加，Python 不看声明（没有声明），看 x、y 的**实际类型**——这正是「动态类型」的含义。

## 2. 绑定模型：变量是名字，不是盒子

### 2.1 赋值 = 绑定

```python
a = [1, 2, 3]
b = a                  # 不是拷贝！b 与 a 绑定到同一个列表对象
b.append(4)
print(a)               # [1, 2, 3, 4] —— a「也变了」，因为只有一个列表
```

心智模型画出来是这样：

```text
C 的世界（盒子模型）：          Python 的世界（标签模型）：
a ┌─────┐                      a ──┐
  │ 1 2 3 │                      ├──→ [列表对象 1,2,3] ←──┐
b └─────┘                      b ──┘                      └── b
（b 是新盒子，拷贝）              （a、b 是同一个对象的两张标签）
```

由绑定模型直接推出的四条规则：

1. **赋值永不拷贝**：`b = a` 只是多贴一张标签。要拷贝必须显式（`list(a)`、`copy.copy`、`copy.deepcopy`）。
2. **函数传参不拷贝**：传的是对象引用（详见[第 4 篇](04-functions.md)）——「Python 全部按引用传参」的通俗说法，精确说是「按对象引用传递」（pass by object reference）。
3. **删除的是名字不是对象**：`del a` 摘掉标签；对象在标签数为 0 时才被回收。
4. **`is` 比较身份，`==` 比较值**：`a is b` 问「同一对象吗」，`a == b` 问「值相等吗」——日常代码 99% 该用 `==`（详见[第 2 篇](02-data-model.md)）。

### 2.2 可变与不可变：绑定模型的分界线

对象分两族，行为差异贯穿整门语言：

| 族   | 例子                                  | 「变」意味着什么                 |
| --- | ----------------------------------- | ------------------------ |
| 不可变 | int、float、str、tuple、frozenset、bytes | 对象内容永不变；「修改」实际是造新对象、重绑名字 |
| 可变  | list、dict、set、自定义类实例                | 原地修改，所有绑定到它的名字同时「看到」变化   |

```python
s = "hello"
s.upper()          # 返回新字符串，s 原封不动 —— 不可变对象的方法都是「返回新对象」
s = s.upper()      # 必须重绑才有变化

lst = [1, 2]
lst += [3]         # list 的 += 是原地扩展（等价 extend）：其他绑定者也能看到
t = (1, 2)
t += (3,)          # tuple 的 += 是造新元组重绑：其他绑定者看不到
```

「可变性」与「共享」的组合是 Python bug 的一半来源（另一半是作用域）：共享的**可变**对象被意外修改、共享的**不可变**对象被当成「轻量安全」滥用。识别每行代码操作的是哪一族，是 Python 基本功（[第 2 篇](02-data-model.md)展开）。

## 3. 内存模型：引用计数 + 分代回收

### 3.1 引用计数：主要回收机制

CPython 给每个对象记一个**引用计数**（有多少名字/容器指向它）：绑定时 +1，解绑/离开作用域/从容器移除时 −1，**减到 0 立即释放**。

```python
import sys
a = [1, 2, 3]
sys.getrefcount(a)     # 2：a 本身 + getrefcount 的临时参数

b = a                  # 计数 3
del a                  # 计数 2（只摘标签，列表还活着）
```

「减到 0 立即释放」是确定性行为——这解释了 Python 为什么不需要 with 之外的析构语义：对象不可达的**那一刻**资源就释放了。但它有一个盲区：**循环引用**。

### 3.2 分代 GC：处理循环引用

```python
a = []
a.append(a)      # a 引用列表，列表引用 a —— 互相引用，计数永远 ≥ 1
del a            # 名字没了，但对象组计数都是 1 —— 引用计数永远清不了零
```

循环引用的对象组永远到不了计数 0。CPython 的对策是**分代垃圾回收器**：周期性扫描「不可达但计数非零」的对象组并整组释放（`gc` 模块可控：`gc.collect()`、`gc.set_threshold`）。

工程结论：循环引用在纯 Python 里已被 GC 兜住，真正要小心的是**循环引用 + `__del__` 终结器**（历史上曾导致不可回收，CPython 3.4+ 已处理）与**C 扩展对象参与的循环**。日常代码的正确姿势仍是[第 10 篇](10-files-context.md)的 `with`——显式管理文件、锁、连接，不赌 GC 时机。

### 3.3 小整数缓存与驻留：身份的特例

```python
a = 256; b = 256
a is b           # True：CPython 缓存 [-5, 256] 的 int 对象
a = 257; b = 257
a is b           # 交互式里 False（两个对象）；同一行里 True（编译器常量折叠）
s1 = "hello"; s2 = "hello"
s1 is s2         # True：字符串驻留（字面量自动 intern）
```

这些「特例」只是实现优化，**不是语言承诺**——再次证明 `is` 只该用于单例比较（None、True、False）与身份语义需求，值比较永远 `==`。

## 4. 动态类型的代价与偿还

### 4.1 为什么 Python 慢

`x = a + b` 一行在 CPython 里的真实工作量：

```text
1. 字节码 LOAD a：从名字字典里找到对象，查引用
2. LOAD b：同上
3. 判断 a、b 的类型 → 查 int 的加法方法表 → 调用 PyNumber_Add
4. 分配一个新 int 对象装结果
5. STORE x：把名字 x 绑到新对象
```

对比 C 的 `x = a + b`：一条 `add` 指令。差距的来源是**每个操作都要运行时查类型 + 每个值都是堆上的对象**（连续算术还有巨大的指针追逐与缓存开销）。这不可救药也无法救——它是动态类型的本质成本。

### 4.2 偿还之道：让热路径离开解释器

Python 的性能哲学不是「把解释器调快」，而是**把热路径挪出纯 Python 层**：

| 手段                     | 原理                | 典型                         |
| ---------------------- | ----------------- | -------------------------- |
| 内置函数与标准库               | C 实现              | `sum`、`sorted`、`re`、`json` |
| NumPy 等向量化             | 整段循环下沉到 C         | 数值计算                       |
| 推导式/生成器                | 比手写循环省方法查找与函数调用开销 | 数据变换                       |
| multiprocessing/并发     | 绕过 GIL（见下）        | CPU 密集并行                   |
| JIT（PyPy、3.13 实验性 JIT） | 运行时把字节码编译成机器码     | 长时运行                       |

> [!NOTE]
> **GIL（全局解释器锁）**：CPython 里一把全局锁，保证同一时刻只有一个线程执行 Python 字节码。后果：多**线程**无法加速 CPU 密集代码（但 IO 等待时会释放 GIL，所以 IO 密集多线程仍然有效）；CPU 并行要用 `multiprocessing`（多进程）。Python 3.12 起实验性 free-threaded 构建开始移除 GIL，3.13/3.14 逐步成熟——但生态与性能仍在演进中，当前写代码仍按「有 GIL」的规则来。

### 4.3 知道慢在哪里：cProfile 入门

```python
import cProfile
cProfile.run("main()", sort="cumulative")
# 按累计时间排序：一眼看到 80% 时间在哪个函数
```

性能纪律与 C 篇同源：**先测量再优化**；测出来的热点通常是循环里的重复方法查找、频繁小对象分配、字符串拼接——对策全是「下沉到内置/批量操作」。

## 5. 执行模型：从源码到结果

```text
.py 源文件
   │ 编译（自动、按需）
   ▼
字节码（.pyc 缓存：__pycache__/）
   │ CPython 虚拟机逐条执行
   ▼
结果
```

- **按需编译**：import 时编译成字节码并缓存到 `__pycache__`（源码变了自动重编）。这就是「第一次 import 慢、之后快」的原因。
- **没有独立链接期**：模块在 import 时执行顶层代码（[第 8 篇](08-modules-packages.md)），这决定了 Python 的导入语义与循环导入问题。
- **REPL 与脚本的差别**：交互式里每行单独编译，脚本整体编译——小整数缓存那类「同一行 True、分两行 False」的差异源于此。
- 3.11+ 的 **specializing interpreter** 给热点字节码做特化（adaptive specialization），3.13 的实验性 JIT 更进一步——解释器在变快，但「热路径下沉」的法则不变。

## 6. 陷阱清单

- 把 `=` 当拷贝：b = a 后改 b，a「莫名」变了；可变对象显式 `list(a)`/`copy.deepcopy`。
- 可变对象当函数默认参数：`def f(x, acc=[])` 所有调用共享一个列表（[第 4 篇](04-functions.md)）。
- 用 `is` 比较值：`is` 是身份比较，只该用于 None/True/False 单例。
- 以为 del 释放对象：del 摘名字；对象回收看引用计数（与循环引用）。
- 循环引用 + 依赖立即释放：靠 GC 兜底但不赌时机；资源用 with 显式管理。
- 多线程加速 CPU 密集代码：GIL 挡路；用 multiprocessing 或让热路径下沉 C。
- 循环里反复调用可提出去的方法：`len(x)` 在循环不变时提出去；批量操作优先。
- 在性能敏感处手写字符串拼接循环：`"".join(parts)` 或 io.StringIO。

## 7. 小结

- 一切皆对象：类型决定行为、身份唯一标识、值承载数据；类型检查发生在运行时——这就是动态类型。
- 变量是名字不是盒子：赋值 = 绑定、传参 = 传对象引用、del = 摘标签；可变/不可变的分界决定「修改」是原地还是重绑。
- 内存由引用计数（确定性立即回收）+ 分代 GC（兜住循环引用）共同管理；资源管理仍应显式（with）。
- 动态类型的本质成本是「每操作查类型 + 每值一对象」；偿还之道是热路径下沉（内置、NumPy、扩展）而非调解释器。
- GIL 使多线程只对 IO 密集有效，CPU 并行走多进程；先 cProfile 测量再谈优化。

## 8. 练习

**1.** 用 `id()` 验证绑定模型：`a = [1,2]; b = a; b.append(3)` 后打印 `id(a) == id(b)`；再对 `a = [1,2]; b = list(a)` 重复。写出你的心智模型修正。

> [!TIP]
> 思路前者同一 id（同一对象），后者不同 id（新列表）。注意 `b = list(a)` 只做**浅**拷贝——嵌套的内层对象仍共享（`copy.deepcopy` 才完全独立），用嵌套列表实验验证。

**2.** 解释为什么 `x = 1000; y = 1000`（两行）在函数内 `x is y` 为 False，而 `x, y = 1000, 1000`（同一行）为 True。

> [!TIP]
> 思路同一行属于同一个编译单元，1000 被常量折叠成同一个 code object 内的常量对象；两行在交互式 REPL 是两次独立编译。这证明了「小整数缓存是 CPython 实现细节」，别在业务代码依赖任何 `is` 值比较。

**3.** 写一个循环引用并验证引用计数的盲区：创建互相引用的两个对象，删除外部名字，用 `gc.get_referrers`/`gc.collect()` 观察回收时机。

> [!TIP]
> 思路`a.b = b_obj; b_obj.a = a; del a, b_obj` 后计数仍为 1；`gc.collect()` 返回值包含这批不可达对象。对照无循环引用的对象在 del 时立即回收（可在 `__del__` 打印验证）。

**4.** 用 `sys.getsizeof` 对比 `int`、`list`（空与 100 万元素）、`dict`、`str` 的对象开销，解释「每值一对象」的内存含义与 NumPy 数组省在哪。

> [!TIP]
> 思路Python int 对象约 28 字节（还有引用它的名字占 8 字节指针），百万 int 列表 ≈ 8MB 指针 + 28MB 对象；NumPy int64 数组 = 8MB 连续裸字节（无对象头）。这就是数值计算下沉 C 的内存收益。

**5.** 测量三段等价代码的耗时：手写循环求和、`sum(range(n))`、`math.fsum`/NumPy。用 `timeit` 写基准，解释差距来源。

> [!TIP]
> 思路手写循环最慢（每轮方法查找 + 解释器调度）；sum 是 C 循环遍历 Python 对象（仍逐对象加）；NumPy 是纯 C 连续内存（快几十倍）。规律：每下沉一层，省掉的是「逐对象解释」的成本。

**6.** 讨论：`def process(items): result = []; for i in items: result.append(i * 2); return result` 有哪些「Python 层浪费」？改写成最快纯 Python 版本，再说明什么时候连它也该换 NumPy。

> [!TIP]
> 思路浪费：append 的属性查找（每轮）、函数调用开销、列表动态扩容。改进：`[i * 2 for i in items]`（推导式专用字节码，无方法查找）。再往下：`np.array(items) * 2`——但仅当数据量大且已是/可成数组时值得；转换成本可能吃掉收益。性能决策永远是「测量，而不是信仰」。
